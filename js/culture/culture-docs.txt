## 1. Ownership Contract

The culture subsystem is split into eight modules, each with a single
layer of responsibility. The rule is simple: **every module owns exactly
one thing, and everything else is out of scope.**

| Module | Owns | Does NOT own |
|---|---|---|
| `CultureConstants` | Frozen vocabulary (appearance categories, default templates, `CULTURE_DEFAULT_APPEARANCE`) | Policy, defaults-for-missing-data, runtime state |
| `CultureValidation` | Structural and value validation rules (`validateCreate`, `validateUpdate`, `validateDelete`) | Orchestration, mutation, persistence, defaults |
| `CultureState` | Indexes, subscriptions, mutation primitives (`_addCulture`, `_updateCulture`, `_removeCulture`) | Canonical data, persistence, mutation policy, queries |
| `CultureQueries` | Semantic reads, analytics, projections, cross-domain composition | Mutation, rendering, persistence, presentation defaults |
| `CultureCommands` | Write boundary, validation orchestration, commit tail (`hydrate → markDirty → publish → dispatch`), `persist()` | Canonical data ownership, cross-domain side effects, presentation |
| `CultureGeneration` | Weighted appearance generation from a culture (pure core + query-integrated wrappers) | Mutation, rendering, persistence, policy |
| `CultureViewModels` | Presentation-ready projections (labels, icons, summaries) | DOM, event handlers, canonical reads |
| `CultureUI` | DOM rendering for lists, cards, dropdowns | Domain logic, field resolution, icon policy for chrome icons (delegates to `_getIcon`) |
| `CultureModals` | Modal form orchestration, persist batching | Validation, defaults, field resolution, mutation |
| `CultureBootstrap` | Load-time verification, index hydration, `window.Culture` namespace | Mutation, persistence, UI wiring |

### The cross-cutting rules

**Commands own mutation.** Nothing outside `CultureCommands` may call
`CultureState._addCulture`, `_updateCulture`, or `_removeCulture`. If
another subsystem needs to write culture data, it must go through a
command.

**Commands own persistence.** `CultureCommands.persist()` is the only
call site for `window.saveMasterData` in the culture subsystem. Nothing
else saves. The UI calls `persist()` once per successful command batch.

**Queries own reads.** Every read goes through `CultureQueries`. No
module reads `masterData.data.cultures` directly except `CultureState`
(for indexing) and `CultureQueries` (for enumeration).

**Live records are for commands only.** `CultureState._getCultureCanonical(id)`
returns the live object. Only `CultureCommands` may call it. Everything
else calls `CultureQueries.getCultureById(id)`, which returns a clone.

**Generation is a distinct layer.** It is not rules, not queries, not
view-models. It is a read-side consumer of queries that produces domain
objects (a character's appearance). It sits alongside queries, not above
it. Do not fold it into any other layer.

**Validation is pure.** `CultureValidation` has no dependencies, no
side effects, no randomness. Given the same candidate and context it
returns the same `{valid, errors}` result.

## 2. Load Order

Every HTML file that loads culture modules must include them in this
order. Load order is verified by `CultureBootstrap.init()` at page load;
a broken order throws before anything tries to use the culture subsystem.

```
1.  js/core/storage.js
2.  js/core/ids.js
3.  js/core/accessors.js
4.  js/ui/modals-core.js
5.  js/core/location/location-queries.js
6.  js/core/religion/religion-queries.js
7.  js/core/character/character-queries.js

8.  js/culture/culture-constants.js
9.  js/culture/culture-validation.js
10. js/culture/culture-state.js
11. js/culture/culture-commands.js
12. js/culture/culture-queries.js
13. js/culture/culture-generation.js
14. js/culture/culture-view-models.js
15. js/culture/culture-ui-list.js
16. js/culture/culture-modals.js
17. js/culture/culture-bootstrap.js   ← loads last, verifies everything
```

**Files that need the bootstrap script tag:**

- `DataManager.html`
- `GENERIC.html`
- `GENERIC_sidebar.html`
- `GovernmentManager.html`
- `HouseholdManager.html`
- `ReligionManager.html`
- `RoleManager.html`
- `SettlementManager.html`

If a page loads any culture module, it must load `culture-bootstrap.js`
after the last culture script and before any script that reads
`window.Culture`.

### Initialization

`CultureBootstrap.init()` is idempotent. The first call verifies
dependencies, hydrates indexes, runs integrity checks, and creates
`window.Culture`. Subsequent calls re-hydrate indexes only.

The bootstrap auto-initializes if `masterData.data` is already available
at script load. If a page requires explicit initialization (e.g. after
an asynchronous data fetch), the loader calls `window.CultureBootstrap.init()`
directly.

**A failed auto-init logs to console but does not throw.** A top-level
throw aborts subsequent `<script>` loading, which would mask the real
problem (a missing dependency) behind secondary failures. If a caller
needs to gate other initialization on culture availability, it calls
`init()` explicitly and catches the throw.

## 3. File-by-File API Reference

### 3.1 `culture-constants.js`

Frozen exports. No inline numbers elsewhere in the subsystem.

| Export | Type | Description |
|---|---|---|
| `CULTURE_APPEARANCE_CATEGORIES` | Object | Canonical category names |
| `CULTURE_DEFAULT_APPEARANCE` | Object | Fallback appearance options |
| `CULTURE_TEMPLATES` | Object | Pre-defined culture templates |
| `getCultureTemplate(name)` | Function | Lookup by template key |
| `getCultureTemplateNames()` | Function | List template keys |
| `getAllCultureTemplates()` | Function | List templates with metadata |

### 3.2 `culture-validation.js`

Pure rules. Returns `{valid: boolean, errors: [{field, message}]}`.

| Export | Description |
|---|---|
| `validateCreate(candidate, {cultures})` | Validates a new culture candidate |
| `validateUpdate(candidate, {cultures, index})` | Validates a fully-patched candidate |
| `validateDelete(id, {cultures})` | Validates that a culture exists |

**Note:** `validateUpdate` rejects an id mismatch against the original
record. Commands pass `index` so validation can detect identity changes.

### 3.3 `culture-state.js`

Indexes, subscriptions, and mutation primitives.

| Export | Description |
|---|---|
| `hydrateFromMasterData()` | Rebuild indexes from canonical data. Throws on duplicate ids. |
| `refreshFromMasterData()` | Deprecated alias for `hydrateFromMasterData()`. |
| `getById(id)` | Clone. Null if not found. |
| `getByName(name)` | Clones. Case-insensitive. |
| `getByDisplayName(name)` | Clones. Case-insensitive. |
| `getByAssociatedLocation(locationId)` | Clones. Descriptive association only. |
| `getByReligion(religionId)` | Clones. |
| `_getCultureCanonical(id)` | Live record. **Commands only.** |
| `_addCulture(culture)` | Mutation primitive. **Commands only.** |
| `_updateCulture(id, culture)` | Mutation primitive. **Commands only.** |
| `_removeCulture(id)` | Mutation primitive. **Commands only.** |
| `subscribe(callback)` | Subscribe to change events. Returns unsubscribe. |
| `publish(eventName, data)` | Publish to subscribers. |
| `validateIntegrity()` | Warn-only integrity check. Returns findings array. |
| `getIndexStats()` | Diagnostic index sizes. |

**Note:** There is no `byPrimaryCultureLocation` index. The primary
culture relationship lives on `Place.cultureId`, not on the culture
record. `CultureQueries.getPrimaryCultureForLocation` walks the place
hierarchy.

### 3.4 `culture-queries.js`

Semantic reads. Cross-domain composition.

| Export | Description |
|---|---|
| `getCultureById(id)` | Clone. Primary lookup. |
| `getAllCultures()` | Array of clones. |
| `getCulturesByName(name)` | Clones matching name. |
| `getCulturesByDisplayName(name)` | Clones matching display name. |
| `getCultureCount()` | Number. |
| `cultureExists(id)` | Boolean. |
| `_getCultureCanonical(id)` | Live record. **Commands/hierarchy only.** |
| `searchCultures(query, {limit, sortBy})` | Full-text search. |
| `getPrimaryCultureForLocation(locationId)` | Walks hierarchy. Null if none. |
| `getAssociatedCulturesForLocation(locationId)` | Direct descriptive associations. |
| `getCulturesForLocation(locationId)` | Combined: primary + direct + ancestor. |
| `getCultureForCharacter(characterId)` | Resolves character's culture. |
| `getCharactersForCulture(cultureId)` | Characters with explicit culture. |
| `getCulturesForReligion(religionId)` | Cultures associated with a religion. |
| `getCultureSummary(id)` | Data projection (not presentation). |
| `getCultureStatistics()` | Aggregate stats. |
| `getCulturesWithMythology()` | Filtered clones. |
| `getCulturesWithAppearance()` | Filtered clones. |

### 3.5 `culture-commands.js`

Write boundary. Single save site.

| Export | Description |
|---|---|
| `createCulture(data)` | Validates, creates. Returns `{success, data, reason?, errors?}`. |
| `updateCulture(id, updates)` | Validates, updates. Unknown fields rejected. |
| `deleteCulture(id)` | Validates, deletes. |
| `addLocationToCulture(cultureId, locationId)` | Association helper. |
| `removeLocationFromCulture(cultureId, locationId)` | Association helper. |
| `addReligionToCulture(cultureId, religionId)` | Association helper. |
| `removeReligionFromCulture(cultureId, religionId)` | Association helper. |
| `addAppearanceOption(cultureId, category, option)` | Appearance helper. |
| `removeAppearanceOption(cultureId, category, value)` | Appearance helper. |
| `updateAppearanceWeight(cultureId, category, value, weight)` | Appearance helper. |
| `updateMythology(cultureId, mythology)` | Full replacement. |
| `persist()` | **The only save call site.** Returns `{success, reason?}`. |

**The commit tail:** Every successful command runs `hydrateFromMasterData`
→ `markDataDirty` → `publish` (in-process) → `dispatchEvent` (cross-domain
`CustomEvent`). Commands do **not** save.

**Field allowlist on `updateCulture`:** Only these top-level fields are
updatable: `name`, `displayName`, `description`, `icon`, `appearance`,
`mythology`, `locations`, `religions`, `notes`. Any other field is
rejected with a specific message.

### 3.6 `culture-generation.js`

Weighted appearance generation.

**Pure core** (no `window.*` lookups, no queries, deterministic under RNG):

| Export | Description |
|---|---|
| `rollWeightedValue(options, rng)` | Single weighted value. |
| `rollWeightedValues(options, count, rng)` | N distinct weighted values. |
| `rollHeight(heightConfig, gender, rng, fallback?)` | Range-rolled height. |
| `generateAppearanceFromCulture(culture, gender, opts, rng)` | Full appearance. Null culture → all-undefined fields. |

**Query-integrated wrappers** (resolve via `CultureQueries`, then delegate):

| Export | Throws when |
|---|---|
| `generateAppearance(cultureId, gender, opts, rng)` | Culture not found. |
| `generateAppearanceForLocation(locationId, gender, opts, rng)` | No primary culture applies. |
| `generateAppearanceWithRandomCulture(gender, opts, rng)` | No cultures exist. |

**RNG contract:** A provider with `pickWeighted`, `randomInt`, `pickRandom`
is required. Callers pass `window.randomness` explicitly, or the module
falls back to `window.randomness` if present. There is no `Math.random`
fallback.

### 3.7 `culture-view-models.js`

Presentation projections.

| Export | Description |
|---|---|
| `labelFor(culture)` | displayName or name, always a string. **Public helper.** |
| `iconFor(culture, {iconPlaceholder?})` | Culture icon or null. **Public helper.** |
| `buildListRow(culture, options)` | Single list row. |
| `buildListRows(cultures, options)` | Array of list rows. Skips nulls. |
| `buildCard(culture)` | Card projection. |
| `buildDetails(cultureId)` | Details projection. |
| `buildDropdownOptions(cultures, {selectedId})` | Sorted dropdown items. |

**Policy:** `labelFor` is authoritative across domains. Location, Character,
and any future subsystem that needs a culture's label must call
`CultureViewModels.labelFor(culture)`. Do not re-implement the
`displayName || name` fallback.

### 3.8 `culture-ui-list.js`

DOM rendering.

| Export | Description |
|---|---|
| `renderCultureList(containerId, options)` | Renders a list. One delegated click listener per container. |
| `renderCultureCard(containerId, cultureOrId)` | Renders a card. |
| `renderCultureDropdown(containerId, options)` | Renders a `<select>`. |

**Icon policy:** `row.icon` (culture icon) is data and is rendered verbatim.
Any chrome icon (chevrons, markers, close buttons) must route through
`window._getIcon(name)`. This file currently uses no chrome icons.

**Event delegation:** One click listener per container, attached once.
The current `onSelect` is read from `container.__cultureOnSelect` at
click time, so re-rendering with a new callback takes effect without
re-binding.

### 3.9 `culture-modals.js`

Modal UI.

| Export | Description |
|---|---|
| `openCreateCultureModal(onSuccess)` | Create form. |
| `openEditCultureModal(cultureId, onSuccess)` | Edit form. |
| `confirmDeleteCulture(cultureId, onSuccess)` | Delete confirmation. |
| `openCultureDetailsModal(cultureId)` | Read-only details. |

**Persistence:** Every successful command path calls
`CultureCommands.persist()` exactly once. A failed persist is a second
toast, not a thrown error — the canonical data is already updated.

**Modal contract:** `openModal` closes the modal when `onConfirm` returns
`true`, keeps it open when `onConfirm` returns `false`. `onConfirm`
callbacks return boolean; they do not call `closeTopModal` themselves.

**Legacy aliases** (retained for one release): `window.openCreateCultureModal`,
`window.openEditCultureModal`, `window.openDeleteCultureModal`,
`window.openCultureDetailsModal`.

### 3.10 `culture-bootstrap.js`

Load-time verification and initialization.

| Export | Description |
|---|---|
| `init()` | Idempotent. Verifies dependencies, hydrates indexes, runs integrity, creates `window.Culture`. |

**What `init()` verifies:**

- Modules: all eight (`CultureState`, `CultureQueries`, `CultureCommands`,
  `CultureValidation`, `CultureViewModels`, `CultureGeneration`, `CultureUI`,
  `CultureModals`).
- Globals: `generateId`, `markDataDirty`, `saveMasterData`, `escapeHtml`,
  `showToast`, `openModal`, `closeTopModal`.
- Cross-domain namespaces and methods: `PlaceQueries.getPlaceById`,
  `PlaceQueries.getAllPlaces`, `ReligionQueries.getReligionById`,
  `ReligionQueries.getAllReligions`, `CharacterQueries.getCharacterById`,
  `CharacterQueries.getAllCharacters`.
- Canonical shape: `masterData.data.cultures` is array or absent
  (absent → `[]`).

**What `init()` does not verify** (deliberate, lazy-checked at call sites):
`confirmDialog`, `getIconOptions`, `PlaceQueries`/`ReligionQueries` inside
the modal edit path.

**What `window.Culture` exposes:**

```js
window.Culture = {
    state:     window.CultureState,
    queries:   window.CultureQueries,
    commands:  window.CultureCommands,
    validation: window.CultureValidation,
    generation: window.CultureGeneration,
    viewModels: window.CultureViewModels,
    ui:        window.CultureUI,
    modals:    window.CultureModals
};
```

External callers should prefer `window.Culture.queries.getCultureById(id)`
over `window.CultureQueries.getCultureById(id)`, but both work.

## 4. Data Schemas

### 4.1 Culture Record

```javascript
{
    id: string,                    // 'culture_1234567890_abc123'
    name: string,                  // 'Nordic'
    displayName: string,           // 'Nordic Peoples' (or null)
    description: string,           // '' or flavor text
    icon: string | null,           // null = explicitly no icon
    appearance: {                  // weighted-option map
        skinTones:      [{value, weight}],
        eyeColors:      [{value, weight}],
        hairColors:     [{value, weight}],
        hairTypes:      [{value, weight}],
        buildTypes:     [{value, weight}],
        height: {
            male:   {min, max},
            female: {min, max}
        },
        commonFeatures: [{value, weight}]
    },
    mythology: {
        creation:   string,
        afterlife:  string,
        keyDeities: [string],
        keyEvents:  [string],
        cosmology:  string,
        symbols:    [string],
        themes:     [string]
    },
    locations: [string],           // descriptive association list (place ids)
    religions: [string],           // descriptive association list (religion ids)
    notes:     string,
    createdAt: number,             // Date.now() at creation
    updatedAt: number              // Date.now() at last update
}
```

**Note:** The `locations` and `religions` arrays are the culture's own
association lists, not fields owned by Location or Religion. Cross-domain
relationships (a place pointing at a culture via `place.cultureId`) live
on the other domain's record.

### 4.2 Appearance Roll Result

```javascript
{
    skinTone:       string | undefined,
    eyeColor:       string | undefined,
    hairColor:      string | undefined,
    hairType:       string | undefined,
    build:          string | undefined,
    height:         number | null,      // null if no range
    commonFeatures: [string]
}
```

**Note:** `undefined` here means "the culture has no options for this
category" (not "roll failed"). `null` height means no height range was
available. `generateAppearanceFromCulture(null, ...)` returns a fully
undefined appearance (except `commonFeatures: []`).

### 4.3 Weighted Option

```javascript
{
    value:  string,       // 'Pale'
    weight: number        // non-negative
}
```

### 4.4 Height Range

```javascript
{
    min: number,
    max: number           // must be >= min
}
```

## 5. Known Deferrals

The following are known gaps or deliberate deferrals in the current
implementation.

### 5.1 No `CultureCascade` module

When a culture is deleted, records in other domains that reference it
(e.g. `character.cultureId`, `place.cultureId`) are **not** automatically
cleared. The `cultureDeleted` `CustomEvent` fires, but no listener cleans
up references.

**Impact:** Deleting a culture can leave dangling references. Queries
return `null` for the missing culture, but the reference stays.

**Deferral:** A `CultureCascade` module belongs in the codebase but is
out of scope for this refactor. It must listen to `cultureDeleted` and
clear references through the owning domains' commands. Do not add this
to `CultureCommands` — the plan explicitly excludes cross-domain side
effects from the command module.

### 5.2 `getCultureSummary` / `getCultureStatistics` silently skip missing records

When a culture's `locations` array references a place that no longer
exists, `getCultureSummary` silently skips it (the place is not added to
the summary's `locations` array). Same for religions.

**Rationale:** A partial summary is more useful than no summary. The
caller cannot distinguish "no locations" from "locations that all got
deleted."

**Deferral:** If the UI needs to surface dangling references, add a
`danglingReferences` field to the summary. This is a data projection
choice, not a fallback, and it's deliberate.

### 5.3 `generateAppearanceForLocation` throws when no culture applies

The query-integrated wrapper throws. Character creation (see integration
notes) must either:

- pre-check `CultureQueries.getPrimaryCultureForLocation(locationId)`
  and handle `null`; or
- `try/catch` around `generateAppearanceForLocation` and fall back to
  `generateAppearanceFromCulture(null, gender, opts, rng)`.

**Deferral:** A `tryGenerateAppearanceForLocation` convenience wrapper
that returns `null` instead of throwing is a possible future addition.
Not added now because it would invite callers to ignore missing cultures
when they should decide explicitly.

### 5.4 `generateAppearanceFromCulture(null, ...)` produces all-undefined appearance

This is intentional. It is the caller's hook for best-effort generation.

**Deferral:** No indication of "best effort" is carried in the result.
Callers who care must check for `skinTone === undefined`.

### 5.5 No keyboard activation for list rows

`culture-ui-list.js` renders rows with `tabindex="0"` so they're
screen-reader-announced and focusable, but there is no keydown handler.
Click (or screen-reader "activate") triggers `onSelect`; Enter/Space on
a focused row does not.

**Deferral:** Deferred until the design confirms it's wanted. If added,
must not double-fire (Enter on a focusable element synthesizes a click
in most browsers).

### 5.6 Bootstrap does not verify modal lazy dependencies

`confirmDialog`, `getIconOptions`, and the modal edit path's use of
`PlaceQueries` / `ReligionQueries` are checked at call time, not load
time. A page that only uses create/edit/details modals does not need
`confirmDialog` to exist.

**Deferral:** If a page requires the delete flow to work, it should
verify `confirmDialog` before calling `confirmDeleteCulture`. This is a
page-level concern, not a subsystem concern.

### 5.7 No culture icon in dropdown options

Native `<option>` elements do not render arbitrary HTML, so dropdown
options omit icons. `CultureViewModels.buildDropdownOptions` returns
`{id, label, icon, selected}` per item; renderers that want icons must
build a custom control on top of that projection.

**Deferral:** A custom dropdown control is a future addition, out of
scope here.

### 5.8 `refreshFromMasterData` is a deprecated alias

Kept as `CultureState.refreshFromMasterData()` for any un-migrated caller.
Will be removed in a future release. New code uses `hydrateFromMasterData()`.

## 6. Anti-Patterns

Things that will cause pain if you do them.

### 6.1 Don't save directly

```javascript
// WRONG
window.saveMasterData();

// RIGHT
window.CultureCommands.persist();
```

`CultureCommands.persist()` is the single save call site. It returns
`{success, reason}` instead of throwing. Call it once per successful
command batch, from the UI layer.

### 6.2 Don't mutate canonical data directly

```javascript
// WRONG
window.masterData.data.cultures.push(newCulture);

// RIGHT
window.CultureCommands.createCulture(data);
```

Commands own the mutation transaction. Direct pushes skip validation,
index rebuilds, `markDataDirty`, `publish`, and `dispatchEvent` — every
subscriber and every cross-domain listener will silently miss the change.

### 6.3 Don't call mutation primitives from outside commands

```javascript
// WRONG (from, say, character-commands.js)
window.CultureState._updateCulture(id, culture);

// RIGHT
window.CultureCommands.updateCulture(id, updates);
```

`_addCulture` / `_updateCulture` / `_removeCulture` are the mechanism,
not the decision. Commands decide; State executes. Nothing outside
`CultureCommands` may call these.

### 6.4 Don't use `_getCultureCanonical` from UI

```javascript
// WRONG (from a renderer)
var c = window.CultureQueries._getCultureCanonical(id);
c.notes = 'edited in place';  // mutates canonical, skips everything

// RIGHT
var c = window.CultureQueries.getCultureById(id);  // clone
```

`_getCultureCanonical` returns the live object. Any mutation to it
skips the commit tail. Use it only when you're inside a transaction
that will re-hydrate afterward.

### 6.5 Don't re-implement the display-name fallback

```javascript
// WRONG
var label = culture.displayName || culture.name || 'Unknown';

// RIGHT
var label = window.CultureViewModels.labelFor(culture);
```

`labelFor` returns a string, always. It handles displayName, name, and
the malformed-culture case. Every domain that needs a culture's label
should call this helper.

### 6.6 Don't route culture icons through `_getIcon`

```javascript
// WRONG
var icon = window._getIcon(culture.icon);

// RIGHT
var icon = culture.icon;  // rendered verbatim
```

Culture icons are data. `_getIcon` is for chrome (chevrons, markers,
badges) — not for user-supplied icon strings from a culture record. If
you add a chrome icon to `culture-ui-list.js`, route it through `_getIcon`.

### 6.7 Don't throw from a UI entry point

```javascript
// WRONG (in a click handler)
if (!window.confirmDialog) throw new Error('...');

// RIGHT
if (!window.confirmDialog) {
    window.showToast('Confirmation unavailable', 'error');
    return;
}
```

A throw in a click handler shows the user nothing and logs nothing
useful unless a global error reporter is installed. Toast the user,
return, and let them know why the action didn't happen.

### 6.8 Don't assume `window.Culture` exists before `init()`

```javascript
// WRONG (before bootstrap runs)
window.Culture.queries.getCultureById(id);

// RIGHT
window.CultureQueries.getCultureById(id);  // always available once loaded
```

`window.Culture` is created by `CultureBootstrap.init()`. The individual
namespace objects (`CultureQueries`, etc.) are created when their scripts
load. If you must call culture functions before bootstrap runs, use the
individual namespaces.

### 6.9 Don't add to `CultureCommands` for cross-domain concerns

```javascript
// WRONG (adding cascade cleanup to the delete command)
function deleteCulture(id) {
    // ... delete ...
    // clear character.cultureId — NO, this is cross-domain
    // clear place.cultureId — NO
}
```

Cross-domain side effects belong in a cascade layer, not in `CultureCommands`.
The command dispatches `cultureDeleted`; a cascade module listens and
coordinates. When that module exists, add it — do not grow `CultureCommands`.

## 7. Version History

### 2.0 (2026-07-14) — Post-refactor

Converged to the rank/role/relationship/education reference pattern.

**Structural changes:**

- `CultureState.rebuildIndexes(cultures)` → `hydrateFromMasterData()`
- Removed `byPrimaryCultureLocation` index and `getByPrimaryCultureLocation`
  (the relationship lives on `Place.cultureId`)
- Public reads now return clones; added `_getCultureCanonical(id)` for
  commands
- Added mutation primitives `_addCulture`, `_updateCulture`, `_removeCulture`
- `CultureState.notify(event)` → `publish(eventName, data)`
- Duplicate-id detection on hydrate (throws on corrupted canonical)
- Added `CultureState.validateIntegrity()` (warn-only)
- `CultureCommands` no longer calls `saveMasterData` in `_commit`; added
  public `persist()` as the single save site
- Commands route mutation through State primitives
- `updateCulture` rejects unknown fields (previously silently ignored)
- `deleteCulture` now calls `validateDelete`
- Commands dispatch `CustomEvent` for cross-domain listeners
- Added `CultureBootstrap` module (new file)
- Added load-time dependency verification to every module

**Documentation:**

- This document (`culture-doc.md`) replaces `culture-docs.txt`
- Header contracts added to every module
- Anti-patterns section added

**Behavioural changes:**

## Appendix B: Cross-Domain Integration

### Character → Culture

- `character.cultureId` field
- `character.appearance` object (rolled from culture)
- Resolved via `CultureQueries.getCultureForCharacter(characterId)`
- Generated via `CultureGeneration.generateAppearance(cultureId, gender)`

**Caution:** `generateAppearanceForLocation` throws when no culture applies.
Character creation must pre-check `getPrimaryCultureForLocation` or
`try/catch`.

### Location → Culture

- `place.cultureId` field (authoritative primary culture)
- Set via `LocationCommands.updatePlaceCulture` (or equivalent)
- Resolved via `CultureQueries.getPrimaryCultureForLocation(locationId)`

**Note:** The primary-culture relationship lives on the place. Culture
records do not index it.

### Culture → Location (descriptive)

- `culture.locations` array
- Descriptive association only; does not participate in primary-culture
  resolution
- Queried via `CultureQueries.getAssociatedCulturesForLocation(locationId)`

### Culture → Religion

- `culture.religions` array
- Set via `CultureCommands.addReligionToCulture` / `removeReligionFromCulture`
- Queried via `CultureQueries.getCulturesForReligion(religionId)`

### Cross-domain events

`CultureCommands` dispatches three `CustomEvent`s on `window`:

| Event | `detail` |
|---|---|
| `cultureCreated` | `{culture: <record>}` |
| `cultureUpdated` | `{culture: <record>}` |
| `cultureDeleted` | `{culture: <record snapshot>}` |

Other domains may listen. **No domain currently listens.** When the
`CultureCascade` module is added, it will listen for `cultureDeleted` and
clear references through the owning domains' commands.

### In-process subscriptions

`CultureState.subscribe(callback)` receives `{type, data}` for every
command commit. UI modules that need to re-render on culture change
should subscribe here rather than listen for `CustomEvent`s.
