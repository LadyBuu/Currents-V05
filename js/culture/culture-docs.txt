================================================================================
PART 1 — FILE INVENTORY AND LAYERS
================================================================================

The culture subsystem follows the same layer chain as the reference
subsystems (rank / role / relationship / education / location /
settlement / government / religion):

  CONSTANTS (no deps; pure vocabulary + defaults)
    js/culture/culture-constants.js

  VALIDATION (pure rules; no deps)
    js/culture/culture-validation.js

  STATE (owns indexes; reads masterData)
    js/culture/culture-state.js

  COMMANDS (writes via State primitives; the only saveMasterData
            site)
    js/culture/culture-commands.js

  QUERIES (read-only; composes State + PlaceQueries +
           ReligionQueries + CharacterQueries + LocationQueries)
    js/culture/culture-queries.js

  GENERATION (pure core + query-integrated wrappers; consumes
              Queries and randomness)
    js/culture/culture-generation.js

  VIEW MODELS (presentation shaping; consumes Queries +
               PlaceQueries + ReligionQueries + CharacterQueries)
    js/culture/culture-view-models.js

  UI LIST (DOM rendering; consumes ViewModels + Queries)
    js/culture/culture-ui-list.js

  MODALS (DOM + commands; batch persist per successful action)
    js/culture/culture-modals.js

  BOOTSTRAP (load-time verification + hydration + namespace)
    js/culture/culture-bootstrap.js

      window.CultureValidation          [culture] — via
                                        _requireCultureValidation
                                        (redundant with load guard)
      window.CultureState               [culture] — via
                                        _requireCultureState
      window.markDataDirty              [core] via storage.js — via

                                        (non-fatal)
      window.dispatchEvent /
      window.CustomEvent                browser — via _dispatch;
                                        wrapped in try/catch
                                        (non-fatal)
    Consumed by:
      [load] culture-modals.js          (all command methods;
                                        persist — the modals are
                                        the save owner;
                                        culture-modals.js's
                                        load-time guard requires
                                        CultureCommands AND
                                        CultureCommands.persist)
      [load] culture-bootstrap.js       (persist, etc. — verified in
                                        _REQUIRED_MODULES via the
                                        module presence check)
    Notes:
      - PERSIST CONTRACT (Pattern A shape, but shape varies from
        rank/religion): persist() calls saveMasterData() and inspects
        the boolean return. On false it reports
        { success: false, reason: 'saveMasterData returned false' }
        — it does NOT read getLastSaveError(). This is a divergence
        from rank-commands.js and religion-commands.js; see
        HAZARDS §9.
      - Every command runs the same shape:
        validate → clone → mutate via State primitives →
        hydrate → markDirty → publish → dispatchEvent.
        Persistence is NOT in that shape.
      - updateCulture field allowlist (_ALLOWED_UPDATE_FIELDS):
        name, displayName, description, icon, appearance,
        mythology, locations, religions, notes. Any other field is
        rejected with `Field "X" is not updatable via updateCulture.`
      - Cross-domain side effects are OUT OF SCOPE. The
        cultureDeleted CustomEvent fires, but no command clears
        character.cultureId, place.cultureId, etc. A future
        CultureCascade listens for the event.
      - _commit calls hydrateFromMasterData, markDataDirty,
        state.publish, then _dispatch (CustomEvent). If
        markDataDirty or dispatch fails, the failure is caught and
        swallowed — the commit still completes.
      - Appearance and mythology are whole-object replacements on
        updateCulture. Sub-field mutation goes through the
        dedicated helpers (addAppearanceOption, etc.), which
        delegate to updateCulture.
      - Association helpers (addLocationToCulture, etc.) are
        wrappers over updateCulture. They read the canonical
        record to get the current list, slice it, mutate the
        slice, and hand the new list to updateCulture.

2.10 BOOTSTRAP — culture-bootstrap.js
--------------------------------------------------------------------------------

  js/culture/culture-bootstrap.js
    Owns: window.CultureBootstrap ({ init }) and
      window.Culture (namespace, installed by init()).
    Load-time dependencies: NONE at parse. Verification is
      performed inside init(). Auto-init runs at load if
      masterData.data exists.
    init() REQUIRED_MODULES (throw if missing):
      CultureState, CultureQueries, CultureCommands,
      CultureValidation, CultureViewModels, CultureGeneration,
      CultureUI, CultureModals
    init() REQUIRED_GLOBALS (throw if wrong type):
      generateId, markDataDirty, saveMasterData, escapeHtml
      (or _escapeHtml), showToast (or _showToast), openModal,
      closeTopModal
    init() CROSS_DOMAIN (throw if namespace or method missing):
      PlaceQueries.getPlaceById
      PlaceQueries.getAllPlaces
      ReligionQueries.getReligionById
      ReligionQueries.getAllReligions
      CharacterQueries.getCharacterById
      CharacterQueries.getAllCharacters
    init() CANONICAL:
      masterData.data.cultures must be Array or absent
      (absent -> coerced to []); non-array throws
    Consumed by: application bootstrap; any caller that needs
      window.Culture.
    Notes:
      - init() is idempotent. A second call re-hydrates indexes but
        does not re-run verification.
      - Auto-init at load is best-effort: a throw is caught and
        logged (not rethrown) so a top-level throw does not abort
        subsequent script loading.
      - After init() succeeds, window.Culture = { state, queries,
        commands, validation, generation, viewModels, ui, modals }.
      - Integrity check is warn-only. Findings are logged via
        console.warn.
      - CultureBootstrap does NOT verify confirmDialog,
        getIconOptions, PlaceQueries / ReligionQueries inside the
        edit modal path, or LocationQueries.getCurrentLocationId.
        These are lazy-checked at their call sites. See
        HAZARDS §11.

PART 6 — LOAD-ORDER INVARIANTS
================================================================================

Each invariant names the failure mode it prevents.

 1.  culture-constants.js before culture-commands.js.
     Failure without it: culture-commands.js throws at load
     ("CULTURE_DEFAULT_APPEARANCE is missing").

 2.  culture-validation.js before culture-commands.js.
     Failure without it: culture-commands.js throws at load
     ("window.CultureValidation is missing").

 3.  culture-state.js before culture-commands.js and
     culture-queries.js.
     Failure without it: both throw at load.

 4.  culture-queries.js before culture-generation.js,
     culture-view-models.js, culture-ui-list.js,
     culture-modals.js, culture-bootstrap.js.
     Failure without it: each throws at load.

 5.  culture-view-models.js before culture-ui-list.js and
     culture-modals.js.
     Failure without it: both throw at load.

 6.  culture-commands.js before culture-modals.js.
     Failure without it: culture-modals.js throws at load
     ("window.CultureCommands is missing" or
     "CultureCommands.persist is missing").

 7.  js/core/formatting.js before culture-ui-list.js and
     culture-modals.js.
     Failure without it: both throw at load ("escapeHtml missing").

 8.  js/core/modals-core.js before culture-modals.js.
     Failure without it: culture-modals.js throws at load
     ("openModal / closeTopModal missing").

 9.  js/core/ui.js before culture-modals.js.
     Failure without it: culture-modals.js throws at load
     ("showToast / _showToast missing").

 10. js/core/ids.js before culture-commands.js.
     Failure without it: culture-commands.js throws at load
     ("generateId is missing").

 11. js/core/storage.js AND initializeStorage() before
     culture-state.js's first hydrate.
     Failure without it: _readCanonicalCultures throws at hydrate
     time ("window.masterData is missing" / "masterData.data is
     missing"). Under the documented order,
     culture-bootstrap.js::init() is the first hydrate caller,
     and it runs after the storage block.

 12. window.PlaceQueries before culture-queries.js,
     culture-view-models.js, and culture-modals.js.
     Failure without it: culture-queries.js throws at load;
     culture-view-models.js throws at load; culture-modals.js
     throws at call time (first openEditCultureModal).
     [UNVERIFIED]: the exact module that installs PlaceQueries
     is not in the supplied batch.

 13. window.ReligionQueries before culture-queries.js,
     culture-view-models.js, and culture-modals.js.
     Failure without it: culture-queries.js throws at load;
     culture-view-models.js throws at load; culture-modals.js
     throws at call time.

 14. window.CharacterQueries before culture-queries.js and
     culture-view-models.js.
     Failure without it: both throw at load.

 15. js/location/location-queries.js before culture-queries.js
     is used to resolve a character's current location.
     Failure without it: no load-time throw — LocationQueries is
     a call-time dependency of _resolveCurrentLocationId —
     but resolution falls back to CharacterQueries.
     getCurrentLocationId (raw field), which under-counts
     characters placed only via move records.

 16. js/character/character-queries.js before
     culture-queries.js's first call to
     window.CharacterQueries.getCurrentLocationId (fallback
     resolver).
     Failure without it: no load-time throw if
     LocationQueries is present; a call-time throw if neither
     resolver exists.

 17. js/core/randomness.js (window.randomness) before the first
     call to CultureGeneration.* that does not supply an
     explicit rng.
     Failure without it: _resolveRng throws. No Math.random
     fallback.

 18. culture-bootstrap.js loads LAST in the culture group.
     Failure without it: verify() throws listing the missing
     modules. Under the documented order every module is present.

 19. initializeStorage() before CultureBootstrap.init() runs.
     Failure without it: init() throws at _verifyCanonical if
     masterData is missing; the auto-init path catches the throw
     and logs, but window.Culture is not created.

 20. No dependencies flow FROM core INTO the culture subsystem.
     state.js does not read CultureState. core/state.js's facade
     reads LocationUIState, not CultureState.


================================================================================
PART 7 — KNOWN HAZARDS
================================================================================

 1.  culture-docs.txt is out of sync with the code.
     Its own §7.1 says it should be replaced by culture-doc.md.
     Its §2 load order uses paths that do not match the tree
     (js/ui/modals-core.js, js/core/location/..., js/core/religion/...,
     js/core/character/...). Its §3 API list names files the tree
     does not contain at those paths (culture-modals.js is
     described but its own file is at js/culture/culture-modals.js;
     the docs.txt file references modals-culture.js in this batch
     — the actual file is culture-modals.js). Do not cite
     culture-docs.txt as authoritative; this document plus the
     files themselves are the source of truth.

 2.  window.PlaceQueries provider is [UNVERIFIED].
     culture-queries.js, culture-view-models.js,
     culture-modals.js, and culture-bootstrap.js all read
     window.PlaceQueries. The supplied location subsystem installs
     window.LocationQueries, not window.PlaceQueries. Confirm the
     provider before deploying culture. The natural assumption
     (matching settlement's parallel situation) is a facade over
     location-queries.js; if none exists, culture cannot load.

 3.  window.Culture is created by CultureBootstrap.init(), not at
     script load.
     The individual namespace objects (CultureQueries, etc.)
     exist as soon as their scripts load. window.Culture does not
     exist until init() runs. Callers that reach window.Culture
     before init() get undefined. Use the individual namespaces
     for pre-init calls.

 4.  CultureBootstrap auto-init does NOT throw on failure.
     A failure is caught and logged via console.warn. If the
     caller wants to gate other initialization on culture
     availability, it must call window.CultureBootstrap.init()
     explicitly and catch the throw. Do not assume the auto-init
     guarantees window.Culture exists.

 5.  getCultureSummary silently skips dangling references.
     If culture.locations references a deleted place, or
     culture.religions references a deleted religion, the summary
     silently omits the reference (does not add it to the summary
     arrays). This is deliberate: a partial summary is more
     useful than no summary. A caller cannot distinguish "no
     locations" from "all locations got deleted" through the
     summary shape. See culture-docs.txt §5.2.

 6.  generateAppearanceForLocation throws when no primary culture
     applies.
     This is deliberate. Callers who want "best effort" behaviour
     should:
       - pre-check CultureQueries.getPrimaryCultureForLocation
         and handle null; or
       - call generateAppearanceFromCulture(culture, ...) with
         the culture object directly (this never throws for a null
         culture).
     Character creation must do one of these. See culture-docs.txt
     §5.3.

 7.  buildDetails double-derives presentation from
     getCultureSummary.
     getCultureSummary is a data projection (what exists).
     buildDetails is a presentation projection (how to arrange
     it). The summary may grow to carry more data without
     buildDetails changing. This is deliberate, not an oversight.

 8.  culture-ui-list.js list rows lack keyboard activation.
     Rows have tabindex="0" so they are focusable and
     screen-reader-announced, but Enter/Space does not trigger
     onSelect. Click is the only activation. If keyboard
     activation is added, it must be coordinated with the design
     to avoid double-firing (Enter on a focusable element
     synthesizes a click in most browsers). See culture-docs.txt
     §5.5.

 9.  CultureCommands.persist does NOT read getLastSaveError.
     persist() reports `saveMasterData returned false` on
     failure. rank-commands.js and religion-commands.js surface
     `getLastSaveError().message`. The culture version is
     Pattern A shape but discards the failure message. This is a
     divergence across domains. Callers that need the underlying
     failure reason (quota exceeded, serialization failure,
     storage disabled) do not get it. Fix by adopting the same
     _requireGetLastSaveError pattern rank and religion use.

 10. culture-modals.js modal callbacks ignore the DOM root
     parameter.
     Every onConfirm callback in the supplied file uses
     document.getElementById to read form inputs. This collides
     when two culture modals are open simultaneously — the second
     modal's onConfirm reads the first modal's inputs. rank's
     modals-rank.js Phase 8.1 fixed this by scoping reads to
     root.querySelector. culture-modals.js has not adopted the
     fix. This is a live bug for stacked modals (e.g. create modal
     open, then details modal open on top). Confirm whether
     stacked culture modals are reachable in your application;
     if they are, migrate every _readText / _readRawText /
     _readMultiSelect to take a root parameter.

 11. CultureBootstrap does not verify lazy dependencies.
     confirmDialog, getIconOptions, PlaceQueries /
     ReligionQueries inside openEditCultureModal, and
     LocationQueries.getCurrentLocationId are checked at call
     time, not load time. A page that opens the delete flow
     without confirmDialog loaded sees a toast "Confirmation
     dialog unavailable" — a real, working state — but does not
     throw. Do not assume a page that passes bootstrap is fully
     functional. This is deliberate; see culture-docs.txt §5.6.

 12. CULTURE_DEFAULT_MYTHOLOGY does not exist.
     culture-commands.js reads
     window.CULTURE_DEFAULT_MYTHOLOGY || _emptyMythology().
     culture-constants.js does not define
     CULTURE_DEFAULT_MYTHOLOGY. The local _emptyMythology in
     culture-commands.js is the active default. If a future
     culture-constants.js adds CULTURE_DEFAULT_MYTHOLOGY, commands
     will use it; until then, the fallback is local. Do not
     assume the constants file provides this value.

 13. CULTURE_APPEARANCE_CATEGORIES is not read.
     The constants file defines it; no supplied culture module
     reads it. Consumers (generation, view models) iterate the
     culture.appearance object keys directly. The constant is
     documentation-as-data, not a required lookup table.

 14. generateAppearanceWithRandomCulture returns
     { culture, appearance }, not the appearance alone.
     Callers who only need the appearance must destructure. This
     is a different return shape than generateAppearance (which
     returns the appearance alone). Do not assume uniform return
     shapes across the generation wrappers.

 15. Appearance and mythology are whole-object replacements on
     updateCulture.
     The command allowlist includes `appearance: true` and
     `mythology: true`, and updateCulture replaces them
     whole-object. Sub-field mutation must go through the
     dedicated helpers (addAppearanceOption,
     removeAppearanceOption, updateAppearanceWeight,
     updateMythology). Do not pass a partial appearance object
     expecting a merge; it will replace.

 16. Association helpers (addLocationToCulture, etc.) delegate to
     updateCulture.
     A failure inside updateCulture (validation failure,
     unknown field rejection) surfaces as a failure from the
     helper. Callers who swallow a helper's result but call
     persist() anyway will save nothing new — no warning fires
     because persist succeeded. This is expected behaviour; do
     not assume a successful helper without inspecting the
     result.success field.

 17. Cross-domain cascade is absent.
     Deleting a culture fires a cultureDeleted CustomEvent but
     does not clear character.cultureId, place.cultureId, or any
     other domain's reference. A future CultureCascade must listen
     for the event and clear references through the owning
     domains' commands. Until then, dangling references are
     expected. See culture-docs.txt §5.1.

 18. window.getCharacterById in culture code resolves to the
     projection override.
     CultureQueries.getCultureForCharacter reads the character
     projection via CharacterQueries.getCharacterById (not the
     bare window.getCharacterById). Under the documented full-app
     order, character-system.js overrides window.getCharacterById
     with the projection version. Both paths return a projection.
     Do not mutate the returned character object.
