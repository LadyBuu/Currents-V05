# Still Waters — Relationship System Documentation

**Version 4.0** | Clean-slate architecture

---

## 1. Overview

The relationship system manages every interpersonal connection between characters. It is organised as a strict layered architecture with one canonical source of truth, pure policy functions, semantic reads, and transactional writes.

### Principles

| Principle | Rule |
|-----------|------|
| **Single source of truth** | `RelationshipState` owns every relationship entity. No other module stores relationship data. |
| **Layer separation** | Constants → State → Rules → Queries → Commands → UI. Each layer only depends downward. |
| **Fail loud** | No fallback values. A missing dependency throws. Nothing invents `1250`, `[]`, `null`, or `Math.random()`. |
| **Defensive reads** | Queries return projections, never live canonical objects. UI cannot mutate state by accident. |
| **One commit boundary** | One logical operation = one command = one `saveMasterData()`. |
| **Randomness is injected** | Rules are deterministic. Random values are passed in or come from `window.Random`. |
| **Derived, not stored** | Kinship, affair classification, marriage status are computed. Nothing is duplicated into storage. |

## 2. Layer Architecture

```
┌───────────────────────────────────────────────────────────────┐
│                          UI LAYER                             │
│  modals-relationship.js   modals-family.js                    │
│  modals-friendship.js     relationship-finder.js              │
│  relationship-ui-metadata.js (icons, labels, colors)          │
└──────────────────────────┬────────────────────────────────────┘
                           │ dispatch + render
┌──────────────────────────▼────────────────────────────────────┐
│                       COMMANDS LAYER                          │
│  RelationshipCommands  RomanceCommands  FriendshipCommands    │
│  FamilyCommands  ProfessionalCommands  JealousyCommands       │
│  AffairCommands                                               │
└──────────────────────────┬────────────────────────────────────┘
                           │ orchestrate
┌──────────────────────────▼────────────────────────────────────┐
│                        QUERIES LAYER                          │
│  RelationshipQueries  RomanceQueries  FriendshipQueries       │
│  FamilyQueries  ProfessionalQueries  JealousyQueries          │
│  AffairQueries  RelationshipFinderQueries                     │
└──────────────────────────┬────────────────────────────────────┘
                           │ read
┌──────────────────────────▼────────────────────────────────────┐
│                         RULES LAYER                           │
│  RelationshipRules  RomanceRules  FriendshipRules             │
│  FamilyRules  ProfessionalRules  JealousyRules  AffairRules   │
└──────────────────────────┬────────────────────────────────────┘
                           │ reference
┌──────────────────────────▼────────────────────────────────────┐
│                        STATE LAYER                            │
│  RelationshipState (entities, indexes)                        │
└──────────────────────────┬────────────────────────────────────┘
                           │ reference
┌──────────────────────────▼────────────────────────────────────┐
│                       VOCABULARY LAYER                        │
│  relationship-types.js (archetypes, attributes, statuses)     │
└───────────────────────────────────────────────────────────────┘
```

**Rules never call State. Rules never call Queries. Rules are pure.**

## 4. Relationship Identity Contract

```
relationshipId     uniquely identifies ONE entity (global)
participantPair    identifies the two participants (index only)
archetype          exactly one per entity, immutable
attributes[]       descriptors on committed relationships
status             lifecycle state
startYear          required
endYear            required if status ∈ {ended, widowed}
```

**Invariant:** `(A, B)` may have N relationship entities. N ≥ 0.

**Index invariant:** `byParticipantPair: Map<pairKey, Set<relationshipId>>` — never a single id.

## 10. Data Shapes

### Relationship entity (canonical, in State)

```js
{
    id: string,
    type: string,              // archetype
    status: string,
    participantA: string,
    participantB: string,
    startYear: number,
    endYear: number | null,
    attributes: string[],      // committed only
    metadata: {}               // domain-specific
}
```

### Relationship projection (from Queries)

```js
{
    id, type, status,
    startYear, endYear,
    participantA, participantB,
    attributes: [...],         // fresh copy
    metadata: {...}            // fresh copy
}
```

### Domain-specific metadata

| Archetype | metadata keys |
|-----------|---------------|
| `friendship` | `strength: number`, `events: [{ type, year, impact, description }]`, `notes` |
| `parent_child` | `parentType`, `parentRole`, `notes` |
| `sibling` | `autoDerived: true` |
| `apprenticeship` | `roleId`, `roleName`, `skillLevel`, `stage`, `specializationsTaught`, `notes` |
| `employment` | `role`, `wages`, `notes` |
| `guild_membership` | `rank`, `notes` |
| `committed` | `notes`, plus affair-only: `affairType`, `discovered`, `discoveryYear`, `discoveryCircumstances`, `discovererId`, `consequences`, `consequencesTriggered`, `legitimizedFromAffair`, `legitimizationYear` |

### Character projections

All Queries that reference characters return either:
- a character **id** (string), or
- a **summary** the caller builds — never a live character object.

The UI is responsible for resolving ids to full character records if it needs names for display, via `getCharacterById()`.

## 11. Ownership Contract

| Domain | Owns |
|--------|------|
| `RelationshipState` | Every relationship entity and its indexes |
| `CharacterState` | Character records (name, gender, birth, death, location, traits, rank assignment) |
| `SkillQueries` / `SkillCommands` | Skill levels per character per role |
| `Jealousy` | `character.jealousyHistory` (temporary; may move to `JealousyState` later) |
| `Family` | Parent relationships are the source of truth for kinship. Sibling entities are derived convenience and may be recomputed. |
| `Romance` | Nothing stored. Marriage status, affair classification, polyamory are derived from `committed` + attributes. |
| `Affair` | Metadata on the committed entity only. Discovery/consequence state lives on that entity. |
| `Groups` | (future) Not part of the relationship system. Groups belong in their own domain. |
| Households | (future) Not part of the relationship system. Household membership is its own domain. |

## 12. Rules of Use

### Do

- Use Queries for anything read-only.
- Use Commands for every mutation.
- Pass randomness into Rules as explicit values, or read it from `window.Random`.
- Compare statuses against `RELATIONSHIP_STATUS` constants.
- Compare archetypes against `RELATIONSHIP_ARCHETYPES` constants.
- Return `{ success: false, code, message }` for domain errors.

### Don't

- Don't read `character.relationships` — the state owns relationships.
- Don't mutate the object a Query returned.
- Don't call `saveMasterData()` outside a Command.
- Don't use `||` for numeric values — use `!== undefined` or `??`.
- Don't invent fallback values when a dependency is missing — throw.
- Don't classify an affair by any field other than the `secret` attribute.
- Don't store derived facts. Compute them.

## 14. Bootstrap

`relationships-bootstrap.js` runs on load and verifies that every required module and global exists. It throws if any are missing.

```js
window.Relationships.init()              // re-verifies and returns status
window.Relationships.State               // → RelationshipState
window.Relationships.Rules               // → RelationshipRules
window.Relationships.Queries             // → RelationshipQueries
window.Relationships.Commands            // → RelationshipCommands
window.Relationships.UI                  // → RelationshipUI
window.Relationships.Romance             // → { Rules, Queries, Commands }
window.Relationships.Friendship          // → { Rules, Queries, Commands }
window.Relationships.Family              // → { Rules, Queries, Commands }
window.Relationships.Professional        // → { Rules, Queries, Commands }
window.Relationships.Jealousy            // → { Rules, Queries, Commands }
window.Relationships.Affair              // → { Rules, Queries, Commands }
window.Relationships.Finder              // → { Queries, render }
```

**The `window.Relationships.*` namespace is the recommended public entry point.** Global names on `window` also exist for backward compatibility with external subsystems, but new code should use the namespace.

| Global | Used for |
|--------|----------|
| `Icons` | SVG icons in UI |
| `escapeHtml` | HTML escaping |
| `showToast` | toast notifications |
| `logEvent` | event log |
| `Random` | deterministic randomness for jealousy / affairs |
| `SkillQueries` | professional queries depend on this |
| `getCurrentLocation` | finder, affairs (same-location) |
| `getActiveRankDisplay` | finder previews |
| `getRankById` | rank priority lookups |

If `SkillQueries` is absent, professional modules throw. If `Random` is absent, jealousy/affair commands throw when they need to roll.

## 16. Adding a New Archetype

1. Add the id to `RELATIONSHIP_ARCHETYPES` and category/direction tables in `relationship-types.js`.
2. Add presentation metadata in `relationship-ui-metadata.js`.
3. Add any validation rules in `relationship-rules.js` (`validateAttributes`, `canCreate`, etc.).
4. Add domain-specific queries/commands if the archetype needs its own semantic layer.
5. Add a dispatch case in `modals-relationship.js`'s `_dispatchCreate()`.

If the archetype is a straightforward symmetric relation with no domain policy beyond validation, `relationship-types.js` + `relationship-rules.js` are enough.

## 17. Adding a New Attribute

1. Add the id to `RELATIONSHIP_ATTRIBUTES` and a group in `relationship-types.js`.
2. Add presentation metadata in `relationship-ui-metadata.js`.
3. Add any mutual-exclusion or requires rules in `RomanceRules.EXCLUSIVE_GROUPS` / `REQUIRES`.
4. Add the checkbox in `modals-relationship.js`'s `_attributeCheckboxesHtml()` if it should be user-selectable.

## 18. Anti-Patterns (Previously Present, Now Forbidden)

- ❌ `if (typeof window.foo === 'function')` dependency fallbacks
- ❌ Default values fabricated when dependencies are missing (`1250`, `[]`, `null`, `0`)
- ❌ Using `||` for numeric values where `0` is valid
- ❌ Returning live canonical entities from Queries
- ❌ Direct mutation of `character.relationships`
- ❌ Calling `saveMasterData()` outside Commands
- ❌ Storing derived facts (marriage status, affair classification, kinship)
- ❌ Using `Math.random()` directly in Rules or Commands
- ❌ Duplicating facts across `metadata` and top-level entity fields
- ❌ Reading character records from UI or domain modules instead of Queries

## 19. Version History

**v4.0** — Clean-slate rewrite.
- Introduced strict layer separation (State / Rules / Queries / Commands).
- Cardinality contract: pair may have N relationship entities.
- Removed all dependency fallbacks.
- Removed affair entity duplication (SECRET attribute is authoritative).
- Removed direct character mutation from UI.
- Centralised commit boundary in Commands.
- Randomness injected via `window.Random`.
- Sibling entities derived, not stored as truth.
- Groups removed from friendship system (pending their own domain).
