# 1. SYSTEM OVERVIEW

## Purpose

The Relationship System manages all interpersonal connections in the Still Waters simulation. It provides a unified framework for romantic, familial, social, and professional relationships with a clean separation between data storage, business logic, and user interface.

## Key Principles

| Principle | Description |
|-----------|-------------|
| **Three Relationship Types** | Relationships are either `one_night_stand`, `casual_dating`, or `committed` |
| **Attributes are Flavor Text** | `MARRIED`, `ENGAGED`, `COHABITING`, etc. have NO gameplay effect |
| **No Special Marriage Type** | Marriage is just the `MARRIED` attribute on a committed relationship |
| **No Divorce Function** | Use `breakUp()` for all relationship endings |
| **Database Layer** | `relationship-registry.js` is the pure data layer |
| **Separation of Concerns** | Registry, logic, queries, and UI are all separate files |
| **Bidirectional Consistency** | All relationships are stored on both participants |
| **Type Registry** | All relationship types, statuses, and attributes are centrally defined |
| **No Business Logic in Registry** | The registry only manages entities, not rules |
| **Graph Queries** | Pure query functions for social distance, path finding, and network analysis |

## Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| No special marriage type | Marriage is just an attribute; simplifies the system |
| No divorce function | `breakUp()` handles all relationship endings |
| Attributes are flavor text | No gameplay effect; purely descriptive |
| One night stands auto-end | End in the same year they start |
| Widowed status | `deathEndsRelationship()` sets status to WIDOWED |
| Smart creation | Auto-detects when a relationship should be an affair |
| Conflict detection | Validates relationships before creation |

## Relationship Types (The Three)

| Type | ID | Description |
|------|-----|-------------|
| **One Night Stand** | `one_night_stand` | Ephemeral encounter, auto-ends same year |
| **Casual Dating** | `casual_dating` | Non-committed romantic relationship |
| **Committed** | `committed` | Serious relationship with optional attributes |

## Relationship Attributes (Flavor Text Only)

| Attribute | ID | Description |
|-----------|-----|-------------|
| `MARRIED` | `married` | Legally and religiously married |
| `HANDFASTED` | `handfasted` | Common-law marriage |
| `ENGAGED` | `engaged` | Betrothed, promised to marry |
| `COHABITING` | `cohabiting` | Living together without formal marriage |
| `CIVIL_UNION` | `civil_union` | Legal recognition without religious ceremony |
| `POLYAMOROUS` | `polyamorous` | Open to multiple committed relationships |
| `MONOGAMOUS` | `monogamous` | Exclusive to one partner |
| `ARRANGED` | `arranged` | Family-arranged match |
| `LOVE_MATCH` | `love_match` | Based on romantic love |
| `DUTY_MATCH` | `duty_match` | Based on obligation or duty |
| `SECRET` | `secret` | Hidden from society |
| `PUBLIC` | `public` | Openly acknowledged |
| `SCANDALOUS` | `scandalous` | Known and disapproved of |
| `MORGANATIC` | `morganatic` | Spouse retains lower rank, children don't inherit |
| `LEVITIC` | `levitic` | Marriage to brother's widow |
| `POSTHUMOUS` | `posthumous` | Marriage after one partner's death |

# 6. ROMANCE-LOGIC.JS

## Purpose

Romance-specific business logic built on top of the relationship registry.

## Key Principles

- Relationships are: `one_night_stand`, `casual_dating`, or `committed`
- Everything else is an **ATTRIBUTE** on committed relationships (flavor text only)
- **No special "marriage" type** - it's just `MARRIED` attribute
- One night stands start and end in the same year automatically
- `breakUp()` ends any relationship (same for committed and casual)
- `widowed` status for death of partner
- Smart creation with auto-affair detection
- Validation with conflict detection
