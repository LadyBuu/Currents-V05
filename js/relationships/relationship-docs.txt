## 1. Overview

The relationship domain manages every non-family interpersonal connection between characters: romance, friendship, rivalry, enmity, professional relationships, affairs, jealousy, and matchmaking.

Family relationships — parentage, siblingship, kinship — do **not** live here. Parentage lives in `FamilyState`. Kinship is derived by `FamilyRules.classifyKinship`. The relationship domain never stores or duplicates parentage.

The domain is organised as a strict layered architecture:

```
Vocabulary → Utils → State → Queries → Commands → Domain (Rules/Queries/Commands) → UI
```

Each layer only depends downward. Rules are pure. Queries return projections. Commands are the only mutation path. Randomness is injected.

---

## 2. Principles

| Principle | Rule |
|---|---|
| **Single source of truth** | `RelationshipState` owns every non-family relationship record. No other module stores relationship data. |
| **Layer separation** | Vocabulary → Utils → State → Queries → Commands → Domain modules → UI. |
| **Fail loud** | Missing dependency throws. Nothing fabricates `0`, `[]`, `null`, or `1250`. |
| **Defensive reads** | Queries return fresh projections. Live records never leave the layer that owns them. |
| **One commit per logical operation** | One command = one batch State write = one `markDataDirty`. |
| **Randomness is injected** | Rules are deterministic. Rolls come from the caller or `window.Random`. |
| **Derived, not stored** | Affair classification, kinship, marriage-as-institution projection — all derived. |
| **State treats status as opaque** | Per-domain transition tables live in each domain's `-rules.js`. |
| **Domain commands never bypass domain rules** | `XCommands` → `XRules` → `RelationshipCommands` → `RelationshipState`. |
| **Historical edges, not current truth** | A pair may have any number of records. `committed #1 ended`, `committed #2 ended`, `committed #3 ongoing` is legitimate. |
| **No `RelationshipRules`** | Domain rules live in each `*-rules.js`. Structural helpers live in `relationship-utils.js`. |
| **Cultural gating is explicit** | Cultural attributes require `CultureRules.supportsRelationshipAttribute` for both participants. |
| **Attribute interpretation is domain-scoped** | No module outside the owning domain's `-queries.js` reads relationship attributes by name. |

## 5. Vocabulary

### Archetypes

| ID | Category | Direction |
|---|---|---|
| `casual_dating` | romantic | symmetric |
| `one_night_stand` | romantic | symmetric |
| `committed` | romantic | symmetric |
| `friendship` | social | symmetric |
| `rivalry` | social | symmetric |
| `enmity` | social | symmetric |
| `apprenticeship` | professional | directional (A=master, B=apprentice) |
| `mastership` | professional | directional (A=master, B=expert) |
| `employment` | professional | directional (A=employer, B=employee) |
| `guild_membership` | professional | directional (A=guild, B=member) |

**Family archetypes are deliberately absent.** Parentage lives in `FamilyState`. Kinship (sibling, grandparent, aunt/uncle, cousin) is derived.

### Attributes

Attributes only attach to committed relationships in v1.

**Universal** (may be applied without consulting `CultureRules`):

`cohabiting`, `polyamorous`, `monogamous`, `secret`, `public`, `scandalous`, `posthumous`

**Cultural** (must be validated against both participants' cultures by `RomanceRules.validateAttributesForCulture` before persisting):

`married`, `engaged`, `handfasted`, `civil_union`, `arranged`, `love_match`, `duty_match`, `morganatic`, `levitic`

### Statuses

Global vocabulary (union across domains):

`ongoing`, `ended`, `widowed`, `pending`, `proposed`, `declined`

Per-domain subsets (declared in `relationship-types.js`):

- Romance: all six.
- Friendship: `ongoing`, `ended`.
- Rivalry/enmity: `ongoing`, `ended`.
- Professional: `ongoing`, `ended`.

Transitions are per-domain and live in each domain's `-rules.js`.

### Direction and roles

Symmetric archetypes have interchangeable participants. Directional archetypes declare role names:

| Archetype | A role | B role |
|---|---|---|
| `apprenticeship` | master | apprentice |
| `mastership` | master | expert |
| `employment` | employer | employee |
| `guild_membership` | guild | member |

### Load-time consistency

`relationship-types.js` asserts at load time:

- Every archetype has a category and a direction.
- Every directional archetype has roles; every symmetric archetype has no roles.
- Every attribute has a scope (`universal` or `cultural`) and an owner (`romance`).
- Every per-domain status exists in the global vocabulary.

Any missing entry throws.

## 6. Record Schema

### Canonical record (in `RelationshipState`)

```
{
    id:            string           unique
    type:          string           archetype id
    status:        string           opaque to State; interpreted per domain
    participantA:  string           character id
    participantB:  string           character id
    startYear:     number | null
    endYear:       number | null
    attributes:    string[]
    metadata:      object           domain-specific; documented per domain
    createdAt:     number           epoch ms
    updatedAt:     number           epoch ms
}
```

### Projection (from `RelationshipQueries`)

Fresh object. Same fields, arrays and metadata copied.

### Pair invariant

`(A, B)` may have N records. The `byPair` index is `Map<pairKey, Set<relationshipId>>`. A pair index is never a single id.

State does not enforce multiplicity. Each domain command decides whether to refuse a duplicate active edge (friendship does, one-night-stand does not, committed does, rivalry does, etc.).

### Metadata schemas

Metadata is not validated by State. Each domain's `-rules.js` file is the authoritative place for its metadata schema, and the domain's `-queries.js` is the only module that reads it.

| Archetype | metadata keys |
|---|---|
| `friendship` | `strength: number (0–100)`, `events: Array`, `notes: string` |
| `parent_child` | (owned by `FamilyState`, not this domain) |
| `committed` | `notes: string`, `classification: string`, `classificationReason: string`, `affairType?: string`, `discovered: boolean`, `discoveryYear: number \| null`, `discoveryCircumstances: string \| null`, `discovererId: string \| null`, `consequencesTriggered: boolean`, `consequences: string[]`, `legitimizedFromAffair?: boolean`, `legitimizationYear?: number` |
| `apprenticeship` | `roleId: string \| null`, `roleName: string \| null`, `skillLevel: number`, `stage: string`, `specializationsTaught: string[]`, `notes: string` |
| `mastership` | `roleId: string \| null`, `notes: string` |
| `employment` | `role: string \| null`, `wages: number`, `notes: string` |
| `guild_membership` | `rank: string \| null`, `notes: string` |
| `rivalry` / `enmity` | `{}` |

**File:** `relationship-state.js`

Storage only. No validation beyond structural integrity. No policy. No queries beyond the raw index reads.

| `idsForPair(a, b)` | Id array |

### Batch mutation (reserved for `RelationshipCommands`)

| Function | Returns |
|---|---|
| `applyInserts(records)` | `{ success, inserted }` or `{ success: false, reason }` |
| `applyUpdates(updates)` | `{ success, updated }` or `{ success: false, reason }` |

### Persistence

State never calls `saveMasterData`. It calls `markDataDirty` and reloads on `masterDataUpdated`. Storage decides when to flush.

## 9. Commands

**File:** `relationship-commands.js`

Structural mutation. Refuses structurally malformed records. Does not enforce domain policy.

### API

| Function | Purpose |
|---|---|
| `create(input)` | Insert a new record. Input: `{ participantA, participantB, type, status, startYear?, endYear?, attributes?, metadata? }` |
| `update(id, patch)` | Patch status, startYear, endYear, attributes, or metadata (shallow merge) |
| `end(id, endYear, reason?)` | Ongoing → ended |
| `setWidowed(id, endYear)` | Ongoing → widowed |
| `remove(id)` | Hard delete from State |
| `addAttribute(id, attribute)` | Idempotent add |
| `removeAttribute(id, attribute)` | Idempotent remove |
| `endAllActiveForCharacter(id, options)` | Batch. Options: `{ endYear, reason?, type?, role? }` |
| `removeAllReferencesTo(id)` | Batch hard remove |

### Contract

- Every command returns `{ success: true, ... }` or `{ success: false, code, message }`.
- Never throws for domain errors.
- One command call performs one State batch, one `markDataDirty`, one subscriber event.
- The generic command is not a back door: domain commands call it, and it does not call any domain.

### Institution projections

Romance answers "what institutional marker does this relationship carry" via `getInstitution`. It does **not** answer "is this character legally married" — that is a culture-aware question and the caller consults `CultureRules` if legal weight is needed. Legal consequences (succession, inheritance, custody) must **not** read `attributes` by name; they read a semantic projection and a culture rule.

## 23. Rules of Use

### Do

- Use Queries for anything read-only.
- Use Commands for every mutation.
- Pass randomness into Rules as explicit values, or read it from `window.Random` at the command layer.
- Compare statuses against `RELATIONSHIP_STATUS` constants.
- Compare archetypes against `RELATIONSHIP_ARCHETYPES` constants.
- Return `{ success: false, code, message }` for domain errors.
- Call `RelationshipCommands` from domain commands, never `RelationshipState` directly.
- Route cross-domain effects through `RelationshipIntegrations`.
- Consult `CultureRules` via `RomanceRules.validateAttributesForCulture` before persisting cultural attributes.

### Don't

- Don't read `character.relationships` — the state owns relationships.
- Don't mutate an object a Query returned.
- Don't call `saveMasterData` outside a Command; commands call `markDataDirty`.
- Don't use `||` for numeric values where `0` is valid.
- Don't invent fallback values when a dependency is missing — throw.
- Don't classify an affair by any field other than the `secret` attribute.
- Don't store derived facts.
- Don't interpret relationship attributes outside the owning domain's `-queries.js`.
- Don't call `RelationshipState` directly from a domain command; go through `RelationshipCommands`.
- Don't persist legal consequences by reading `attributes.includes('married')`; read a culture-aware projection.
- Don't reintroduce `RelationshipRules` as a base module.

## 24. Semantic Contracts

### Return values

- Singular lookups: `T | null`
- Collections: `T[]`
- Commands: `{ success: boolean, code?: string, message?: string, ... }`
- Rules: `{ valid: boolean, errors?: string[], reason?: string, ... }`

### Missing data

- Missing character: `null`
- Missing collection: `[]`
- Invalid explicit input: `throw`
- Year `0` is preserved.
- Empty strings and `0` are legitimate values.

### Randomness

Every rules module is deterministic. Randomness is drawn at the command layer, either from the caller-supplied roll or from `window.Random`. `Math.random()` is never called.

### Persistence

State calls `window.markDataDirty()` after a batch write. It does not call `saveMasterData`. Storage decides when to flush.

### Events

- `RelationshipState.subscribe(callback)` — receives `{ action, relationshipIds }` after each batch.
- `masterDataUpdated` — triggers reload from `masterData.data.relationships`.

### Family boundaries

Parentage is not stored here. Sibling, grandparent, aunt/uncle, cousin archetypes do not exist in this domain. Kinship is derived by `FamilyRules.classifyKinship`. Any relationship edge that would duplicate parentage is a bug.

## 25. What Is Not Implemented

The following are deliberately outside the relationship domain in v1:

- **Succession and inheritance.** Separate domain. Reads a culture-aware partnership projection from this domain, but does not live here.
- **Justice.** Auto-execution of murderers, judicial records. `AffairCommands.applyConsequences` calls `ExecutionCommands` if present; the justice domain owns the records.
- **Legitimacy.** `FamilyRules` deliberately omits `canLegitimize`. Legitimization of a child, if reintroduced, is a family-domain decision.
- **Education.** Literacy, enrollment, graduation. Separate domain.
- **Groups and households.** Separate domains. The relationship domain stores edges between characters; a group is a distinct entity with its own state.
- **Persisted jealousy history.** The domain does not store past confrontations. If historical escalation later requires this, a dedicated state module is the correct home.
- **Event-sourced friendship history beyond the bounded array.** Friendship events live in the record's `metadata.events`, capped at 50. If independent querying over friendship events becomes necessary, it graduates to its own event collection.
- **Friendship recommendations.** Composable from `FriendshipQueries` output. Not delivered as a separate module.
- **Master/progress/teachable queries.** Belong in the role/skill domain. `ProfessionalQueries` provides the raw projections; discovery and recommendation over them is a role-domain concern.
- **Annual processing orchestrator.** `RelationshipIntegrations.processAnnualLifecycle` covers jealousy and affairs. A top-level simulation orchestrator that also advances mortality and aging is outside this domain.
- **`relationship-finder.js` UI panel.** Queries are ready; the UI panel that renders them is not part of this domain build.
- **`relationship-system.js` compatibility shim.** `window.Relationships` in bootstrap covers the new entry point.

## 26. Deletion and Lifecycle

### Hard delete of a character

`CharacterDeletionCommands.deleteCharacter(id)` must call `RelationshipIntegrations.removeAllReferencesTo(id)`. This removes every relationship record referencing the character in one State batch.

### Soft delete

Soft delete does not affect relationship records. Soft-deleted characters are hidden from normal queries; relationship records continue to exist and continue to reference them.

### Death of a character

`CharacterLifecycle.killCharacter(id, deathData)` must call `RelationshipIntegrations.handleCharacterDeath(id, { deathYear })`.

- Romance: committed relationships become `widowed`. Non-committed romantic relationships become `ended`.
- Friendship: `ended` with reason `death_of_participant`.
- Rivalry and enmity: `ended` with reason `death_of_participant`.
- Professional: `ended` with reason `death_of_participant`.

Relationship records remain in the graph. State stores history.

### Lifecycle hooks

If `window.registerLifecycleHook` exists, `RelationshipIntegrations` registers `death` and `delete` handlers on load. Callers may also invoke `handleCharacterDeath` and `removeAllReferencesTo` directly.

## 27. Anti-Patterns

The following are forbidden in the relationship domain:

- `if (typeof window.foo === 'function')` dependency fallbacks for required modules.
- Default values fabricated when a dependency is missing (`1250`, `[]`, `null`, `0`).
- `||` for numeric values where `0` is valid.
- Returning live canonical records from Queries.
- Mutating the object a Query returned.
- Calling `saveMasterData()` outside a Command.
- Storing derived facts (marriage status, affair classification, kinship).
- Using `Math.random()` in Rules or Commands.
- Duplicating facts across `metadata` and top-level record fields.
- Reading character records from UI or domain modules instead of Queries.
- Reading relationship attributes by name outside the owning domain's `-queries.js`.
- A domain command reaching into `RelationshipState` directly instead of `RelationshipCommands`.
- Treating `attributes.includes('married')` as legal status anywhere outside a culture-aware projection.
- Persisting jealousy history on character records or in relationship `metadata`.
- Reintroducing sibling/grandparent/aunt-uncle/cousin archetypes as stored edges.
- Reintroducing `relationship-rules.js` as a base policy module.

## 28. Adding a New Archetype

1. Add the id to `RELATIONSHIP_ARCHETYPES` and its category, direction, and roles (if directional) in `relationship-types.js`.
2. Add a per-domain status subset if the archetype needs a status vocabulary that differs from the default.
3. Add presentation metadata in `relationship-ui-metadata.js`.
4. Add a `-rules.js` module or extend an existing one with the archetype's transition table, attribute set, and creation validator.
5. Add a `-queries.js` module or extend an existing one with the archetype's projection and lookup functions.
6. Add a `-commands.js` module or extend an existing one with the archetype's create/end operations.
7. Add a dispatch case in `modals-relationship.js`'s `_dispatchCreate`.
8. Add the module to `relationships-bootstrap.js`'s `REQUIRED_MODULES`.

If the archetype is a straight symmetric edge with no domain policy beyond validation, the vocabulary and a minimal rules module are sufficient.

---

## 29. Adding a New Attribute

1. Add the id to `RELATIONSHIP_ATTRIBUTES` in `relationship-types.js`.
2. Declare its scope (`universal` or `cultural`) in `ATTRIBUTE_SCOPE`.
3. Declare its owner (currently always `romance`) in `ATTRIBUTE_OWNER`.
4. Add the id to `ROMANCE_ALLOWED_ATTRIBUTES` in `romance-rules.js`.
5. If mutually exclusive with others, add it to an entry in `EXCLUSIVE_GROUPS`.
6. If it requires another attribute, add it to `REQUIRES`.
7. If cultural, ensure `CultureRules.supportsRelationshipAttribute` recognises it for the appropriate cultures.
8. Add presentation metadata in `relationship-ui-metadata.js`.
9. Add a checkbox in `modals-relationship.js`'s attribute list if it should be user-selectable.

## 30. Version History

**v1.0** — Rebuilt after the character / family / children / mortality refactor.

- Introduced strict layer separation: Vocabulary → Utils → State → Queries → Commands → Domain modules → UI.
- `RelationshipState` owns non-family edges. Parentage lives in `FamilyState`.
- Pair cardinality: N records per pair. `byPair` is `Set<relationshipId>`.
- `RelationshipRules` removed. Transition tables live per-domain; structural helpers live in `relationship-utils.js`.
- Per-domain attribute interpretation. Only `RomanceQueries` reads romance attributes by name.
- Cultural attributes are globally representable but culturally enabled.
- State treats status as opaque.
- Domain commands never bypass domain rules.
- Randomness injected. `Math.random` is never called in Rules or Commands.
- Sibling, grandparent, aunt/uncle, cousin archetypes removed. Kinship derived.
- Persisted jealousy history removed.
- `RelationshipIntegrations` centralises cross-domain hooks.
- `relationships-bootstrap.js` verifies modules, globals, vocabulary consistency, and domain tables at load time.
