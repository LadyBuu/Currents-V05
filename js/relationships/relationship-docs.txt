PART 1 — LAYER STACK AND FILE CLASSIFICATION
================================================================================

The relationship subsystem sits above the character, family, skill,
role, storage, and time domains. It owns ONE canonical collection on
masterData.data.relationships (a flat array of edges); every other
interaction with the world goes through another domain's public
command or query surface.

  VOCABULARY (leaf)
    js/social/relationship-types.js

  UTILITIES (leaf)
    js/social/relationship-utils.js

    js/social/relationship-state.js

    js/social/relationship-queries.js

    js/social/relationship-commands.js

2.3 STATE — relationship-state.js
--------------------------------------------------------------------------------

  js/social/relationship-state.js
    Owns: window.RelationshipState.

    Exports:
      Lifecycle: isInitialized, snapshot, replaceAll, clear
      Subscriptions: subscribe
      Reads: size, allIds, all, getRecordCopy,
             idsForCharacter, idsForType, idsForPair, hasId
      Batch mutations: applyInserts, applyUpdates, applyRemovals
      Canonical accessors (commands only): _getLiveRecord
      Reload: reload, validateIntegrity

    Load-time dependencies:
      window.RELATIONSHIP_TYPES       — HARD
      window.RelationshipUtils        — HARD

    Call-time dependencies:
      window.markDataDirty            — REQUIRED at first mutation
                                         (typeof-guarded, no throw)
      window.masterData.data.relationships
                                       — canonical array; reloaded on
                                         masterDataUpdated

    Consumed by:
      [load] relationship-queries.js
      [load] relationship-commands.js
      [load] relationship-bootstrap.js
      (indirect) every domain command

    Contracts:
      - Canonical array lives on masterData.data.relationships. State
        does not own it — it is a mirror.
      - Record schema is documented in the module header. Every record
        carries id, type, status, participantA, participantB,
        startYear, endYear, attributes (string[]), metadata (object),
        createdAt, updatedAt.
      - Public reads return defensive copies. _getLiveRecord returns
        the live object (reserved for commands).
      - applyInserts / applyUpdates / applyRemovals are BATCH. Each
        batch runs structural validation first; on any failure nothing
        is mutated. On success, all mutations applied, one
        markDataDirty, one subscriber notification.
      - Subscriber exceptions are ISOLATED: a throwing subscriber does
        not stop the rest, and does not escape into the command. This
        matches character-state.js / children-state.js /
        family-state.js.
      - _reloadFromMasterData wraps replaceAll in try/catch. A
        structurally invalid persisted record logs an error and
        PRESERVES the previous in-memory state; the next save overwrites
        the corrupt storage. This is the "fail loud, do not crash the
        page" pattern.
      - Indexes: byId, byChar (Map<charId, Set<relId>>), byType
        (Map<type, Set<relId>>), byPair (Map<pairKey, Set<relId>>).
        validateIntegrity cross-checks every index against the record
        set and vice versa.
      - duplicate ids at replaceAll throw. A single corrupt persisted
        record cannot partially hydrate state.

2.5 COMMANDS — relationship-commands.js
--------------------------------------------------------------------------------

  js/social/relationship-commands.js
    Owns: window.RelationshipCommands.

    Exports:
      create, createBatch, update, end, setWidowed, remove
      addAttribute, removeAttribute
      endAllActiveForCharacter, removeAllReferencesTo

    Load-time dependencies:
      window.RelationshipState       — HARD
      window.RelationshipUtils       — HARD
      window.RELATIONSHIP_TYPES      — HARD
      window.RELATIONSHIP_STATUS     — HARD
      window.RelationshipQueries     — HARD (for getById after mutations)

    Call-time dependencies:
      window.generateId              — REQUIRED at first create
                                       (typeof-guarded)

    Consumed by: every domain command; integrations.

    Contracts:
      - Single write boundary for relationship records.
      - Structural validation only: required fields present,
        participantA !== participantB, attributes is a string[],
        metadata is a plain object, endYear >= startYear.
      - The endYear < startYear check is applied at EVERY write path:
        create, createBatch, update (using current's other year when
        only one is supplied), end, setWidowed, and
        endAllActiveForCharacter (with rejected array).
      - One logical mutation = one State batch = one markDataDirty.
      - Commands do NOT save. Persistence is Storage's job (markDataDirty
        flags; saveMasterData is not called from this file).
      - addAttribute silently no-ops if the attribute is already present;
        removeAttribute silently no-ops if the attribute is not present.
        This is idempotent-by-design.
      - createBatch is ALL-OR-NOTHING. Per-record validation runs
        before State.applyInserts; duplicate id within the batch is
        rejected; State-level duplicate id against existing records is
        also rejected. Nothing is inserted on refusal.
      - endAllActiveForCharacter reports { ended, rejected, failed,
        count, rejectedCount, failedCount }. The rejected array carries
        records whose startYear > endYear (chronology-inconsistent);
        they are NOT silently ended.

    Refactor history highlights:
      - endAllActiveForCharacter now applies the same chronology check
        as the single-record paths. Prior revisions could end records
        into an impossible (startYear > endYear) state via the batch
        path.
      - create / createBatch / update / end / setWidowed reject
        endYear_before_startYear. Prior revisions only checked types.

    APPRENTICESHIP CLEANUP:

      handleCharacterDeath ends every active professional edge,
      including apprenticeships. The apprenticeship LIFECYCLE lives on
      ApprenticeshipCommands, not ProfessionalCommands:

        - ApprenticeshipCommands.terminateApprenticeship(masterId,
          apprenticeId, roleId, reason) is the terminal method.
        - ProfessionalCommands.endApprenticeship was NEVER implemented.
          Prior revisions called it (and then terminateApprenticeship
          incorrectly) and produced silent data-integrity bugs — the
          apprenticeship was never ended on death.
        - This revision calls the correct method and resolves roleId
          from the relationship record's metadata (the professional
          projection does not expose metadata.roleId).
        - If ApprenticeshipCommands is missing, the death cascade
          reports code: 'APPRENTICESHIP_COMMANDS_UNAVAILABLE' for each
          affected edge. If the record is malformed (missing metadata
          or roleId), code: 'APPRENTICESHIP_MISSING_ROLE'. Never
          silently skipped, never fabricated.

    ROLEID RESOLUTION:

      terminateApprenticeship requires roleId. ProfessionalQueries.
      getProfessionalRelationships returns a projection WITHOUT
      metadata. roleId lives on the underlying record's
      metadata.relationship so the cascade:

        1. reads the record via RelationshipQueries.getById
        2. extracts metadata.roleId
        3. calls terminateApprenticeship(participantA, participantB,
                                        roleId, 'death_of_participant')

      Malformed records (missing record or missing roleId) surface as
      APPRENTICESHIP_MISSING_ROLE, not a crash.

    PARTNERSHIP PROJECTIONS:

      getPartnershipProjection and getAllPartnershipProjections are
      AVAILABLE FOR CONSUMPTION. They are not consumed today because
      character-queries.js loads before the relationship domain, and
      mortality-queries.js has no current use case. The intended
      consumers are documented in the module header. Do not wire a
      consumer without updating that doc.

    DISPATCH MODEL:

      Two paths reach this module:

        1. Direct dispatch from CharacterLifecycle.killCharacter and
           CharacterDeletionCommands.deleteCharacter (a no-op under the
           documented load order — those modules load first).

        2. Registration hook: this file calls
           window.registerDeathHandler and window.registerDeleteHandler
           at load time. Both are the load-order-independent path.

      The two are additive. Double-dispatch is safe because the
      command layer is idempotent per relationship id.

      If registerDeathHandler or registerDeleteHandler is missing (a
      build before Phase 3.13), the corresponding registration is a
      no-op with a console warning. The direct dispatch path still
      fires for those builds — but only for the domains that load
      before the character subsystem.

    ANNUAL PASSES:

      processAnnualAffairDiscovery iterates every living character,
      rolls for each undiscovered affair, and applies discovery via
      AffairCommands.rollDiscovery. rollProvider may be supplied; else
      window.Random.next (with window.randomNext fallback).

      processAnnualLifecycle is a convenience aggregate: jealousy +
        affair discovery. Both halves are optional; a missing
        JealousyCommands yields an empty jealousy block.

        'polyamorous' | 'blocked'). It does not decide; it reports.

        which is the batch domain command. It reshapes the batch
        result (widowed / ended / failed) for the death cascade.

      window.FriendshipRules          — HARD

      window.getCurrentYearSafe       — REQUIRED

      createMutualFriendships          one commit (RC.createBatch)

                                       TWO commits when it does (metadata

                                       event does not end the friendship;
                                       TWO commits when it does

    ongoing; recoverable by calling end() again.

    Contracts:

        every record; Phase 2 calls RC.createBatch. If any pair fails
        preparation, NO records are inserted. State-level rejection
        (duplicate id, structural) also inserts nothing.
      - Skipped pairs (already friends) do not block the operation.
      - Already-friends pairs are skipped, reported in the `skipped`
        array. Missing characters or invalid input reject the whole
        call (return `failed`, no inserts).
