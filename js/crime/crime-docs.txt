================================================================================
PART 1 — FILE INVENTORY AND LAYERS
================================================================================

The crime subsystem follows the reference layer chain (constants ->
state -> queries -> commands -> view-models -> UI -> modals), with
two distinct additions:

  - A law-integration layer between constants and commands. It
    composes the settlement and religion domains to decide legality.
  - A compatibility shim (vendetta-system.js) that forwards legacy
    callers onto the canonical modules.

  CONSTANTS (leaf; pure vocabulary + helpers; NO dependencies)
    js/crime/crime-constants.js

  STATE (owns canonical crime + vendetta arrays + indexes)
    js/crime/crime-state.js

  LAW INTEGRATION (composes Settlement + Religion to evaluate
                   legality)
    js/crime/crime-law-integration.js

  QUERIES (read-only; composes State into derived statistics)
    js/crime/crime-queries.js

  COMMANDS (orchestration; the only saveMasterData site)
    js/crime/crime-commands.js

  VIEW MODELS (presentation shaping; NO DOM, NO reads)
    js/crime/crime-view-models.js

  UI STATS (DOM rendering for stats + crime + vendetta lists)
    js/crime/crime-ui-stats.js

  MODALS (DOM + commands; batch persist per successful action)
    js/crime/modals-crime.js

  BOOTSTRAP (load-time verification + hydration + namespace)
    js/crime/crime-bootstrap.js

  COMPATIBILITY SHIM (deprecated; forwards to CrimeState /
                     CrimeCommands / CrimeQueries)
    js/crime/vendetta-system.js

    Consumed by:
      [load] crime-law-integration.js   (indirect — reads via
                                          runtime, does not load-guard
                                          on CrimeState)
      [load] crime-queries.js           (LOAD-TIME GUARD on
                                          CrimeState namespace)
      [load] crime-commands.js          (LOAD-TIME GUARD)
      [load] crime-bootstrap.js         (LOAD-TIME VERIFICATION;
                                          hydrateFromMasterData;
                                          validateIntegrity)
      [load] vendetta-system.js         (LOAD-TIME GUARD + method

                                          delegating surface)

      - PERSISTENCE CONTRACT (from the header): State owns the
        canonical arrays on masterData.data.crimes and
        masterData.data.vendettas. Every mutation primitive calls
        _markDirty, which FIRST syncs in-memory indexes back to
        canonical storage (_syncToCanonical) and THEN calls
        window.markDataDirty. This is critical: prior revisions kept
        in-memory arrays and canonical arrays out of sync, so the
        commit tail's hydrateFromMasterData(true) rebuilt indexes
        from PRE-mutation canonical data and silently discarded the
        just-applied mutation.
      - READ CONTRACT: public reads return deep clones. Only the
        _getXCanonical accessors return live records, and they are
        reserved for CrimeCommands (and CrimeLawIntegration during a
        command).
      - MUTATION PRIMITIVES: recordCrime / solveCrime / deleteCrime
        / createVendetta / recordVendettaDeath / resolveVendetta /
        deleteVendetta each:
          1. Acquire a mutation lock (_mutatingState)
          2. Hydrate from masterData if not yet hydrated
          3. Perform the mutation
          4. Call markDataDirty (via _markDirty, which syncs to
             canonical first)
          5. Publish an in-process event via _publish
          6. Release the lock
          7. Return { success, data } or { success, reason, code }
        They do NOT save, do NOT dispatch CustomEvent, and do NOT
        modify other records' indexes.
      - LIFECYCLE INVARIANTS (from the header):
          * A crime is either solved or not. recordCrime NEVER
            records a solved crime (ignores data.solved). Solving
            is a transition performed by solveCrime().
          * A vendetta's status only reaches ESCALATED via
            recordVendettaDeath (automatic at the threshold) or via
            _setVendettaStatus (called by
            CrimeCommands.escalateVendetta). It only reaches RESOLVED
            via resolveVendetta.
          * Historical snapshot fields (perpetratorName,
            victimName, householdAName, householdBName,
            characterAName, characterBName) are NEVER refreshed from
            live sources.
      - CACHE MANAGEMENT:
          hydrateFromMasterData(force) — idempotent; forces rebuild
            when force is true.
          reload() — clears indexes and forces a full rebuild;
            publishes STATE_EVENTS.CACHE_RELOADED.
          invalidateCache() — legacy alias for reload().
          validateIntegrity() — warn-only; returns warning array
            and logs via console.warn; never throws.

      - CANONICAL LAW SOURCES (from the header): the settlement
        domain splits its reads across three modules —
          SettlementQueries.getSettlementData
          SettlementLawQueries.getCivilLaws
          SettlementReligionQueries.getDominantReligion
        The prior version probed SettlementState.getCivilLaws and
        SettlementQueries.getCivilLaws; neither method exists. Those
        probes were dead code and were removed. A future probe that
        resurrects them is a bug.

        In a theocracy this silently skipped religious law, and a
        murder that violated religious law could be recorded as
        lawful. The fallback is removed; the function throws.

          'universal'          Civil laws (apply to all residents)
          'follower'           Religious laws of the character's own

        opts in explicitly via crimeMapping.crimeType,
        crimeMapping.crimeTypes, or law.violationCheck. Matching the
        law's `domain` against the action's `domain` is NOT
        sufficient.
      - SUPREMACY: in a theocracy or useReligiousLawsAsCivil
        settlement, religious violations take precedence and civil
        violations are folded into them. Applied INSIDE
        evaluateAction, not as a separate post-step.
      - CONSEQUENCES: derived ONLY from enforced violations. A law
        that is applicable but not enforced produces no consequence.
        If an enforced law declares no consequence, the result
        carries { type: 'other', description: null } so the caller
        knows the law was enforced but no punishment was prescribed.
      - NO FABRICATED PUNISHMENTS: consequences come from the laws.
        Unknown consequence types surface to the caller unchanged.

      - RENDER REGISTRY: every render call registers its container,

        re-renders each container with its ORIGINAL options.
        Preserves showActions, emptyMessage, location filters, etc.
      - RENDER ERRORS: logged via console.error and return false.
        The renderer does not catch and hide errors — it surfaces
        them so a broken data shape is visible.
      - LOCATION vs HOUSEHOLD: crimes have locationId. Vendettas
        do NOT. The crime list accepts a location filter; the
        vendetta list accepts a household filter. Do not conflate.
      - The _getIcon helper requires window.getIcon. Prior revisions
        called window._getIcon, which does not exist.
      - Presentation formatters come from CrimeModals first; fall
        back to CrimeConstants-derived defaults only.

================================================================================
PART 6 — LOAD-ORDER INVARIANTS
================================================================================

Each invariant names the failure mode it prevents.

 1.  crime-constants.js before every other crime module.
     Failure without it: crime-state.js, crime-law-integration.js,
     crime-queries.js, crime-commands.js, crime-view-models.js,
     crime-bootstrap.js throw at load naming CrimeConstants.

 2.  crime-state.js before crime-queries.js, crime-commands.js,
     crime-bootstrap.js, vendetta-system.js.
     Failure without it: each throws at load on missing CrimeState
     (queries, commands, bootstrap) or on missing individual
     methods (vendetta-system.js).

 3.  crime-law-integration.js before crime-commands.js.
     Failure without it: crime-commands.js throws at load
     ("crime-commands.js requires CrimeLawIntegration").

 4.  crime-commands.js before crime-bootstrap.js and
     vendetta-system.js and modals-crime.js.
     Failure without it: each throws at load.

 5.  crime-queries.js before crime-bootstrap.js,
     vendetta-system.js, crime-ui-stats.js, modals-crime.js.
     Failure without it: each throws at load on the getVendettaStats
     method check (vendetta-system.js) or the namespace / call-site
     guard (others).

 6.  crime-view-models.js before modals-crime.js.
     Failure without it: modals-crime.js throws at load
     ("modals-crime.js requires CrimeViewModels").

 7.  modals-crime.js before crime-ui-stats.js.
     Failure without it: crime-ui-stats.js's _getModals calls
     throw when invoked; the module itself loads (no load-time
     guard on CrimeModals), but the crime-list and vendetta-list
     detail buttons fail at click time.

 8.  modals-core.js before modals-crime.js.
     Failure without it: modals-crime.js throws at load on
     openModal / closeTopModal.

 9.  formatting.js, icons.js, ui.js before modals-crime.js.
     Failure without it: modals-crime.js throws at load on
     escapeHtml / getIcon / showToast.

 10. selectors (modals-char-selector.js,
     modals-household-selector.js, locationDropdown.js) before
     modals-crime.js.
     Failure without it: modals-crime.js throws at load on
     openCharacterSelector / openHouseholdSelector /
     getFilteredLocationOptions.

 11. character-lifecycle.js (window.killCharacter, two-argument
     form) before crime-commands.js.
     Failure without it: crime-commands.js throws at load
     ("crime-commands.js requires killCharacter"). At runtime, if
     the wrong form is loaded, triggerMurder/triggerExecution
     fail with 'characterId is required.' and roll back.

 12. relationship-queries.js (getRelationshipsForCharacter,
     endRelationship) before crime-commands.js.
     Failure without it: crime-commands.js throws at load.

 13. household-commands.js (applyPerpetratorCrime,
     applyVictimCrime, applyExecutionToHousehold) before
     crime-commands.js.
     Failure without it: crime-commands.js throws at load naming
     the missing method.

 14. character-queries.js (getCharacterById,
     getCurrentLocationId) before crime-commands.js and
     crime-bootstrap.js.
     Failure without it: both throw at load.

 15. household-queries.js (getHouseholdById) before
     crime-state.js, crime-commands.js, and crime-bootstrap.js.
     Failure without it: all three throw at load.

 16. SettlementLawQueries (getCivilLaws) and
     SettlementReligionQueries (getDominantReligion) before
     crime-bootstrap.js AND before the first call to
     CrimeLawIntegration.evaluateAction that needs them.
     Failure without them: bootstrap init() throws; runtime
     evaluateAction throws if the caller resolves through them.

 17. ReligionLaws (getLawsByReligion) before crime-bootstrap.js
     AND before the first call to CrimeLawIntegration that needs
     religious laws.
     Failure without it: bootstrap init() throws; runtime throws
     if ReligionLaws and ReligionState are both missing.

 18. SettlementQueries (getSettlementData) before
     crime-bootstrap.js AND before the first call to
     CrimeLawIntegration that resolves settlement context.
     Failure without it: bootstrap throws; runtime throws if both
     SettlementState and window.getSettlementData are missing.

 19. SettlementGovernmentCommands — if present at bootstrap
     verification, must expose recordCrimeImpact. Present-but-
     missing-method is a hard failure, not an optional gap.
     Failure without it: bootstrap init() throws.
     Absent entirely: bootstrap warns once and continues.

 20. core/time.js (getCurrentYear) before crime-state.js,
     crime-queries.js, crime-commands.js, modals-crime.js,
     crime-bootstrap.js, crime-view-models.js (at first call to
     _currentYear).
     Failure without it: each throws at load (except
     crime-view-models.js, which throws at the first modal-default
     builder call).

 21. core/ids.js (generateId) before crime-state.js,
     crime-commands.js, crime-bootstrap.js.
     Failure without it: each throws at load.

 22. core/storage.js (markDataDirty) before crime-state.js.
     Failure without it: crime-state.js throws at load.
     core/storage.js (saveMasterData) before the first call to
     CrimeCommands.persist.
     Failure without it: persist returns { success: false, reason:
     'saveMasterData unavailable' }.

 23. core/randomness.js (chance, pickRandom) before
     crime-bootstrap.js.
     Failure without it: bootstrap throws at load.

 24. window.logEvent before crime-commands.js and
     crime-bootstrap.js.
     Failure without it: both throw at load.

 25. initializeStorage() before crime-bootstrap.js's hydrate path

 26. vendetta-system.js, if loaded, must load AFTER every
     canonical crime module it forwards to.
     Failure without it: vendetta-system.js throws at load naming
     the first missing module or method.


================================================================================
PART 7 — KNOWN HAZARDS
================================================================================

 1.  getCurrentYearSafe is PROHIBITED in crime.
     Every crime module uses window.getCurrentYear. The deprecated
     alias was migrated out in the v6.1 compatibility pass (see
     crime-docs.txt §3). No crime module may read
     getCurrentYearSafe; doing so is a regression.

 2.  window.CrimeState.createVendetta is called DIRECTLY from
     modals-crime.js::_submitVendetta.
     This is intentional per crime-docs.txt §9: CrimeCommands has
     no household-level vendetta creation command, and inventing
     one here would be the wrong layer. The modal collects
     households, not characters, so createBloodFeud (which derives
     households from characters) is not a fit. If CrimeCommands
     later gains createVendettaForHouseholds, the modal must call
     that instead. Do not "fix" this by routing through
     createBloodFeud.

 3.  SettlementQueries.getCivilLaws and
     SettlementQueries.getDominantReligion DO NOT EXIST.
     Those methods belong to SettlementLawQueries and
     SettlementReligionQueries respectively. Any resolver that
     probes SettlementQueries for them will always fail. Prior
     revisions of crime-law-integration.js had these dead probes;
     they were removed. crime-bootstrap.js verifies the correct
     surfaces. Do not reintroduce the dead probes.

 4.  _getDominantReligion has NO silent null fallback.
     Prior versions returned null when neither
     SettlementReligionQueries nor SettlementState provided the
     method. In a theocracy that meant religious law was silently
     skipped and a murder that violated religious law could be
     recorded as lawful. crime-docs.txt §19 prohibits silent
     failure. The current implementation throws. Do not add a
     fallback.

 5.  DEATH SIGNATURE: killCharacter(characterId, deathData).
     The two-argument form is the ONLY supported form. Prior
     revisions of crime-commands.js called the pre-refactor
     four-argument form killCharacter(character, year, cause,
     options), which passed a character object in the characterId
     slot and failed every invocation with 'characterId is
     required.' The current crime-commands.js passes the correct
     form at every call site:
       - triggerMurder passes isMurder: true, killerId, and
         (optional) murderMotive / murderMethod.
       - triggerExecution passes isExecution: true,
         executionReason, and (optional) executionMethod /
         executionLocation.
     mortality-rules.js::validateDeath requires killerId when
     isMurder === true and executionReason when isExecution ===
     true. Do not change these calls without checking that
     contract.

 6.  PERSISTENCE uses Pattern A.
     CrimeCommands.persist() inspects the boolean return value of
     saveMasterData() and, on failure, reads getLastSaveError().
     Pattern C (discard the return value, report success) is
     banned. Prior revisions of persist() called saveMasterData()
     inside a try/catch and returned { success: true }
     unconditionally.

 7.  The commit tail does NOT save.
     _commit(eventName, payload) calls:
       State.hydrateFromMasterData(true)
       window.markDataDirty()
       State.publish(eventName, payload)
       dispatchEvent(CustomEvent)
     It does NOT call saveMasterData. Persistence is
     CrimeCommands.persist(). The UI calls persist() exactly once
     per user action.

 8.  CrimeState._markDirty MUST sync in-memory indexes to
     canonical storage BEFORE calling markDataDirty.
     Prior revisions did not, and the commit tail's
     hydrateFromMasterData(true) rebuilt indexes from the
     pre-mutation canonical arrays, silently discarding every
     mutation. The _syncToCanonical helper closes this gap. Do
     not remove it.

 9.  The commit tail's State.hydrateFromMasterData(true) call
     relies on crime-state.js's _markDirty having already synced.
     Do not call _commit without going through State mutations
     first (which is impossible in the current code, but is a
     hazard for future additions).

 10. Crime UI helpers must use the CANONICAL names.
     - window.escapeHtml (NOT window._escapeHtml)
     - window.showToast (NOT window._showToast)
     - window.getIcon (NOT window._getIcon)
     Prior revisions of crime-ui-stats.js used window._getIcon
     (which does not exist); modals-crime.js used all three
     deprecated names. Both files have been migrated.

 11. Modal infrastructure:
     - window.openModal accepts titleHtml / contentHtml, NOT
       title / content. Passing the deprecated keys renders with
       the default title ("Modal") and an empty body.
     - openModal returns { element, close }. Event delegation
       attaches to result.element, NOT result.content.
     - window.ModalsCore does not exist; use the direct globals
       from modals-core.js.

 12. Vendor-system.js forwards STRUCTURED results.
     The old VendettaSystem unwrapped CrimeState results into
     bare objects (or null on failure). The current shim forwards
     the canonical { success, data } / { success, reason, code }
     shape. Callers that used `if (result === null)` must migrate
     to `if (!result.success)`.

 13. CrimeStatsUI's render errors are logged, not swallowed.
     Render errors go to console.error and return false. Prior
     revisions of analogous modules silently swallowed render
     errors; do not reintroduce that pattern.

 14. CrimeStatsUI's _renderRegistry preserves options across
     refreshAll(). Every render call registers its container,
     kind, and options. If a container is unmounted from the DOM,
     call unmount(containerId) so refreshAll() does not attempt to
     render into a stale element.

 15. SEVERITY BANDS and classifySeverity are the SINGLE source
     of severity classification.
     Every crime module that classifies a severity delegates to
     CrimeConstants.classifySeverity. Do not re-derive the
     thresholds anywhere.

 16. CONSEQUENCE EXECUTION is deliberately incomplete.
     Only EXECUTION is handled. IMPRISONMENT, EXILE, FINE,
     PENANCE, EXCOMMUNICATION, and OTHER all return { applied:
     false, reason: 'no-handler' }. The caller is NEVER told a
     consequence was applied that was not. Do not add silent
     handlers that "apply" a consequence without a real domain
     effect.

 17. Violation detection requires EXPLICIT opt-in.
     A law only criminalises an action if it opts in via
     crimeMapping.crimeType, crimeMapping.crimeTypes, or
     law.violationCheck. Matching the law's `domain` against the
     action's `domain` is NOT sufficient.

 18. Precedence applies INSIDE evaluateAction.
     In a theocracy or useReligiousLawsAsCivil settlement,
     religious violations take precedence and civil violations
     are folded into them. Do not apply supremacy as a
     post-process; it is part of evaluateAction's contract.

 19. crimes and vendettas live on masterData.data directly.
     CrimeState owns the in-memory indexes; canonical arrays are
     written through _syncToCanonical. Do not write to
     masterData.data.crimes or masterData.data.vendettas from any
     module other than CrimeState.

 20. Family / children / mortality / role / industry are NOT
     dependencies of crime.
     crime-docs.txt §1 states that crime does not own these data
     and does not read them. Do not add new dependencies on these
     domains without a documented reason.

 21. getLocationPopulationCount is [UNVERIFIED].
     Used by crime-queries.js for burden metrics. Missing ->
     crimeBurden / recentCrimeBurden are null (NOT 0).
     crime-bootstrap.js warns once if absent. Do not add a
     fabricated population fallback.

 22. crime-constants.js and crime-bootstrap.js declare
     "LOCATION: js/core/crime/<file>" in their headers, but the
     physical path is js/crime/<file>.
     The js/core/crime/ path is pre-refactor and must not appear
     in any HTML script tag. crime-docs.txt §18 calls this out.

 23. Randomness fallbacks exist but must never fire.
     getRandomMurderReason falls back to 'Unspecified' if
     window.pickRandom is missing. _randomExecutionMethod falls
     back to { id: 'unknown', name: 'Unknown' }. The killerGotAway
     roll falls back to Math.random() < 0.3 if window.chance is
     missing. Under the documented full-app order these fallbacks
     are unreachable because crime-bootstrap.js verifies chance
     and pickRandom as LOAD-TIME GUARDS. Do not remove the
     bootstrap checks while leaving the fallbacks; that would
     make the fallbacks live.

 24. crime-state.js mutation primitives use a scoped recursion
     guard (_mutatingState), scoped to State only.
     The crime domain does NOT use a module-wide recursion guard
     on queries, commands, or renderers. crime-docs.txt §16 calls
     this out as policy.

 25. window.Crime namespace is installed by crime-bootstrap.js
     only.
     It is NOT installed at script load. Callers that reach for
     window.Crime before init() runs get undefined. Use the
     individual namespaces (CrimeConstants, CrimeState,
     CrimeLawIntegration, CrimeQueries, CrimeCommands,
     CrimeViewModels, CrimeStatsUI, CrimeModals) for pre-init
     access.

 26. vendetta-system.js is deprecated.
     New code must not use it. The shim must not become:
       - a second storage layer,
       - a second index set,
       - a second VENDETTA_STATUS constant,
       - a second createBloodFeud implementation,
       - anything that writes to masterData.data.vendettas
         directly.
     If any of those reappear, the file has regressed.

 27. crime-bootstrap.js auto-init catches and logs init errors,
     but does NOT throw them.
     A page that loads the crime domain against a broken
     dependency set fails with a console.error at load, and
     window.Crime is not installed. Callers that need to gate on
     crime availability must call window.CrimeBootstrap.init()
     explicitly and catch the throw.

 28. Household side effects have a warn-once path only for
     entire-module absence.
     If HouseholdCommands is missing entirely, crime-commands.js's
     LOAD-TIME GUARD throws. If HouseholdCommands is present but
     missing one of the three apply* methods, the same load-time
     guard throws. There is no warn-and-skip path for household
     side effects. Only settlement side effects (via
     SettlementGovernmentCommands.recordCrimeImpact) have a
     warn-once-and-skip path.

 29. The auto-graduation analogue in crime is the escalation
     retry path.
     escalateVendetta without force requires the vendetta to have
     reached the escalation threshold. Automatic escalation
     already fires inside recordVendettaDeath. The explicit
     escalateVendetta({ force: true }) requires a reason. The
     non-force path is the retry path for a missed automatic
     escalation.

 30. Crime modals do not use onMount to attach handlers for
     repeated-open cases.
     Each modal re-binds its handlers on every open (via the
     callback parameter the core passes to onMount/onConfirm).
     There is no module-level "already bound" state. Do not
     introduce a module-wide binding cache; each open is a fresh
     DOM subtree.

 31. crime-docs.txt §18 enumerates a mechanical completion
     standard. Key points:
       - No getCurrentYearSafe.
       - No _escapeHtml, _showToast, _getIcon.
       - No title:/content: in openModal calls.
       - No result.content reads.
       - No SettlementQueries.getDominantReligion /
         SettlementQueries.getCivilLaws probes.
       - No window.ModalsCore references.
       - Every module's LOCATION header must read js/crime/<file>.
     Any deviation is a regression, not a variant.

 32. The crime-bootstrap.js OPTIONAL block for
     SettlementGovernmentCommands is present-but-missing-method
     is a HARD failure; absent-entirely is a WARN.
     This is intentional and matches crime-docs.txt §17's
     dependency policy. Do not weaken the present-but-broken path
     to a warn.
