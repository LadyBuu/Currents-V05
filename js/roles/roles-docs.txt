================================================================================
PART 1 — FILE INVENTORY AND LAYERS
================================================================================

The role subsystem follows the same layer chain as the reference
subsystems (rank / culture / location / settlement / government /
religion):

  SKILL TAXONOMY (no role deps; provides SkillUtils)
    js/skill/skill-utils.js

  CONSTANTS (depends on SkillUtils at load)
    js/systems/roles/role-constants.js

  STATE (owns canonical catalogue + derived indexes)
    js/systems/roles/role-state.js

  QUERIES (read-only; composes State + CharacterState +
           CharacterCommands + CharacterQueries)
    js/systems/roles/role-queries.js

  COMMANDS (writes via State + CharacterCommands; the only
            saveMasterData site)
    js/systems/roles/role-commands.js

  COMPATIBILITY SHIM (one-way aliases onto the canonical modules;
                       loads AFTER role-queries.js)
    js/systems/roles/role-system.js

  UI LIST (DOM rendering; consumes RoleQueries)
    js/systems/roles/role-ui-list.js

  MODALS (DOM + commands; batch persist per successful action)
    js/systems/roles/modals-roles.js
    js/core/modals/modals-role-select.js

  js/systems/roles/role-system.js
    Owns: legacy flat window.* aliases (getAllRoles, getRoles,
      createRole, updateRole, deleteRole, etc.) onto the canonical

    Load-time dependencies (HARD — throw at load if missing):
      window.RoleConstants        [core]
      window.RoleState            [core]
      window.RoleQueries          [core]
      window.RoleCommands         [core]
      window.SkillUtils           [skill]
    Load-time check (HARD): a REQUIRED_FUNCTIONS block names every
      specific function it aliases. If any is missing, the whole
      shim refuses to install (partial aliasing is more dangerous
      than no aliasing).
    Call-time dependencies:
      window.accessorsGetRoles / window.accessorsGetRoleById
                                  (re-export of accessors.js
                                   functions; captured at shim
                                   load; used only by callers
                                   that need live records)
    Consumed by: legacy call sites (compatibility only).
    Notes:
      - CLONE SEMANTICS: every read alias returns CLONES. The
        first window.getAllRoles call fires a one-shot
        console.warn so a debugging session that starts with
        "why did my push do nothing" resolves fast.
      - window.getRoleById is aliased to RoleState.getRole
        (clones), NOT accessors.getRoleById (live). This closes the
        apprenticeship-commands.js fallback hazard the queries
        header warns against.
      - window.accessorsGetRoles and window.accessorsGetRoleById
        are the explicit live-accessor re-exports. Callers that
        specifically need the live records use these; everyone else
        uses the clone-returning aliases.
      - LOAD ORDER IS CRITICAL: role-system.js MUST load AFTER
        role-queries.js. role-queries.js captures window.getRoles
        at its own load time (before this shim overwrites it) and
        uses the captured reference internally. If load order flips,
        the capture in role-queries.js will resolve to this shim's
        alias, and any call to getRoles() will recurse until stack
        overflow. See HAZARDS §2.

================================================================================
PART 7 — KNOWN HAZARDS
================================================================================

 1.  roles-docs.txt §3 path drift for role-ui-list.js.
     roles-docs.txt §3 says `js/core/ui/role-ui-list.js`; the
     file is at `js/systems/roles/role-ui-list.js` (its own
     header says so too). Do not load the file from
     js/core/ui/ — that path does not exist in the tree.

 2.  role-queries.js captures window.getRoles BEFORE
     role-system.js aliases it. This is intentional and
     load-order-critical.
     If role-system.js loads BEFORE role-queries.js:
       - role-queries.js captures window.getRoles = the shim's
         alias, which is RoleQueries.getRoles itself.
       - Every call to getRoles recurses to stack overflow.
     There is no runtime guard for this; the capture-and-document
     IS the guard. roles-docs.txt §3 places role-queries.js
     before role-system.js. Any future change to that order must
     also remove or rewrite the aliasing in role-system.js.
     See role-system.js's LOAD ORDER (IMPORTANT) section.

 3.  role-system.js's read aliases return CLONES, not live
     records.
     Legacy callers that used to mutate the returned array or a
     role object will silently no-op. The first
     window.getAllRoles call fires a one-shot console.warn so
     the semantic change is discoverable. Callers that need the
     live array use window.accessorsGetRoles;
     window.accessorsGetRoleById is the live-record accessor.
     See CLONE SEMANTICS in role-system.js's header.

 4.  window.getRoleById reconciliation.
     accessors.js exports getRoleById (live). RoleState exports
     getRole (clones). Prior revisions left window.getRoleById
     aliased to accessors.getRoleById, which meant
     apprenticeship-commands.js's fallback (if RoleState
     unavailable, use window.getRoleById) resolved to the LIVE
     record even when RoleState was available. The shim now
     aliases window.getRoleById to RoleState.getRole (clones).
     The live accessor is re-exported as
     window.accessorsGetRoleById. See GETROLEBYID
     RECONCILIATION in role-system.js's header.

 5.  RoleState.reset() clears ONLY ephemeral UI state.
     reset() clears _uiState.selectedRoleId and
     _uiState.roleSearchTerm. It does NOT clear _roles or
     _categories. This matches core/state.js's runtime-state-only
     contract. Do not assume reset() reloads canonical data.

 6.  RoleState's reload path does NOT mark data dirty.
     When masterDataUpdated fires, RoleState re-hydrates indexes
     but does NOT call markDataDirty. The inbound data IS the
     canonical truth; scheduling a save would be a redundant
     write. Prior revisions contradicted this contract.
     The accessor cache IS invalidated on reload — that is a
     cache refresh, not a local mutation.

 7.  Duplicate role ids on the reload path are dropped and
     logged, not thrown. The init() path throws on duplicates.
     A cross-tab reload is inbound data; a corrupt write in
     another tab must not break the current tab. A first boot
     with duplicate ids is a load-order or corruption bug and
     must surface as an error.

 8.  modals-roles.js and role-ui-list.js use inline styles.
     This is a documented deferral. Do not assume either file is
     CSS-only. Extracting ~200 lines of layout to a stylesheet
     is a follow-up PR.

 9.  Persistence divergence across domains.
       - SettlementCommandCommit throws on persist failure.
       - GovernmentCommands.persist returns { success: false }
         but does not throw (does not read getLastSaveError).
       - ReligionCommands.persist returns { success, reason? }
         and DOES read getLastSaveError.
       - RankCommands.persist returns { success, reason? } and
         DOES read getLastSaveError.
       - RoleCommands.persist returns { success, reason? } and
         DOES read getLastSaveError (typeof-guarded).
       - CultureCommands.persist returns { success, reason? }
         but does NOT read getLastSaveError; reports the generic
         'saveMasterData returned false'.
       Do not unify without updating every caller's
       error-handling.

 10. bulkAssignRole's `success` field is a BOOLEAN, not a
     count.
     shape: { success: boolean, assignedCount, failedCount,
     errors }. success is true iff EVERY character was assigned
     without error. assignedCount is the number of successes.
     modals-roles.js reads assignedCount for the "did anything
     succeed" check, not .success. Prior revisions returned
     { success: number, failed: number }, which collided with the
     boolean convention. Do not reintroduce the numeric shape.

 11. Two skill writes exist with different semantics.
       updateCharacterSkill(cid, rid, level)      — override;
                                                     can raise OR
                                                     lower; blind
                                                     write.
       recordCharacterSkillProgress(cid, rid, level)
                                                    — progression;
                                                     can raise;
                                                     NEVER lowers;
                                                     returns
                                                     { unchanged:
                                                       true } for
                                                     no-op.
     No progression system may reduce a character's canonical
     role skill. An administrator can, deliberately. Do not
     "simplify" by routing progression through the override.

 12. role-commands.js is the ONLY module that used to fall back
     to year 1250.
     Prior revisions had _getCurrentYear return 1250 when
     getCurrentYear was unavailable. That violated the core's
     explicit invariant ("no magic year 1250") and made it the
     only module in the tree that broke it. The current revision
     requires time.js and throws at load if getCurrentYear is
     missing. Do not reintroduce the fallback.

 13. Role assignment provenance fields are forwarded, not
     interpreted.
     assignRoleToCharacter accepts options.learnedVia and
     options.institutionId and forwards them to
     CharacterCommands.addProfession / updateProfession. Role
     does not interpret them. Education's graduation path
     depends on this forwarding. Prior revisions silently dropped
     both fields, which meant education's graduation role grant
     lost its provenance. Do not strip them again.

 14. _validCategory consults live RoleState categories.
     role-commands.js validates category ids against
     RoleState.getCategories() (which includes persisted custom
     categories), then falls back to
     RoleConstants.DEFAULT_ROLE_CATEGORIES. Prior revisions
     validated only against the static defaults, making every
     custom category unusable for new roles. Do not
     reintroduce the static-only check.

 15. modals-roles.js character projection contract.
     The file reads ONLY the following character fields from the
     projection:
       id, name, surname, gender, birthYear, isDeceased.
     Professions are read via
     CharacterQueries.getCharacterProfessions(id), which
     delegates to CharacterCommands.getProfessions. Prior
     revisions read character.professions directly and produced
     a silently-wrong role count when the projection stripped
     professions. If any of the six projection fields is removed,
     the reads here break silently — that is the contract
     character-queries.js::CHARACTER PROJECTION CONTRACT exists
     to enforce.

 16. modals-roles.js _confirmThen uses the THREE-argument
     confirmDialog form.
     window.confirmDialog(message, title, onConfirm). The old
     two-argument form passed onConfirm as the title and left the
     confirm callback undefined; the dialog appeared and closed
     but the callback never ran. Do not change to the
     two-argument form.

 17. modals-roles.js category source returns {} if RoleState has
     not initialized.
     _getCategoriesOrEmpty catches the RoleState.getCategories
     throw and returns {}. Category dropdowns render empty
     rather than failing the modal. In a normal load order this
     is unreachable (role UI mounts after role bootstrap).

 18. modals-roles.js icon policy is STRICT.
     _icon throws on unknown names. This is deliberate — an
     unknown icon name is a data error that should surface at
     render. (modals-role-select.js::_iconOr falls back to
     CIRCLE; that is a different module with a different
     tolerance policy.)

 19. modals-role-select.js is READ-ONLY.
     It does NOT require RoleCommands. It does not create roles.
     Callers pick from the existing catalogue. Do not add write
     paths to this module.

 20. modals-role-select.js::_iconOr falls back to Icons.CIRCLE.
     Icons.CIRCLE MUST be present. If it is not, the module
     throws. Do not reintroduce an inline Unicode fallback.

 21. role-ui-list.js statistics batching is the correct cost.
     renderRoleList and renderRoleDetailPanel call
     RoleQueries.getRoleStatisticsBatch ONCE per render for the
     full role id set. renderRoleCard accepts options.stats for
     callers rendering N cards. Do not regress to per-role
     getRoleStatistics calls in a loop; that is the O(roles ×
     characters × avg professions) cost the batch API was
     introduced to avoid.

 22. role-ui-list.js::_masterTierName guards against missing
     SkillUtils.
     The default master-filter label reads the Master tier name
     via SkillUtils. If SkillUtils is missing, the label falls
     back to the literal 'Masters'. Prior revisions called
     SU.getTier(...).name unguarded and would throw on a
     SkillUtils load-order regression.

 23. role-queries.js _cloneRoleRecord field list must stay in
     sync with RoleState._cloneRoleForRead.
     The load-time _verifyCloneFieldParity throws on divergence.
     Any field added to one must be added to the other in the
     same change. This is not optional.

 24. role-system.js's REQUIRED_FUNCTIONS block throws if any
     aliased function is missing.
     Prior revisions could install `window.foo = undefined`,
     which produces a TypeError far from the load site. The
     current revision refuses to install if ANY alias would
     resolve to undefined. Adding a new alias requires adding the
     corresponding function to REQUIRED_FUNCTIONS.

 25. role-system.js's REQUIRED_MODULES block checks namespace
     presence. The REQUIRED_FUNCTIONS block checks the specific
     functions the shim aliases. Both run at load. Neither
     tolerates absence.

 26. modals-roles.js and modals-role-select.js use titleHtml /
     contentHtml / onMount (not title / content / onOpen).
     modals-core.js reads ONLY titleHtml / contentHtml. It
     provides onOpen as a compatibility alias for onMount, but
     the canonical name is onMount. Every call site in this
     batch uses the canonical forms.
