================================================================================
PART 1 — LAYER STACK AND FILE CLASSIFICATION
================================================================================

The disaster subsystem sits above the settlement, character, household,
location, education, industry, and residence domains. It orchestrates
them; it does not own them.

  CONSTANTS (leaf)
    js/core/disaster/disaster-constants.js

  STATE (canonical in-memory store for disasters)
    js/core/disaster/disaster-state.js

  QUERIES (semantic reads over DisasterState)
    js/core/disaster/disaster-queries.js

  DAMAGE (structural damage coordinator; orchestrates into the owning
          domains' commands)
    js/core/disaster/disaster-damage.js

  COMMANDS (single write boundary for disaster lifecycle; cross-domain
            effect orchestration)
    js/core/disaster/disaster-commands.js

  VIEW MODELS (presentation shaping)
    js/core/disaster/disaster-view-models.js

  UI STATS (renderers over view models)
    js/core/disaster/disaster-ui-stats.js

  MODALS (input gathering + command invocation)
    js/core/disaster/modals-disaster.js

  BOOTSTRAP (verification + hydration + diagnostics + namespace)
    js/core/disaster/disaster-bootstrap.js

Dependency direction:

  constants
      |
      v
  state
      |
      v
  queries, view-models
      |
      v
  damage   (uses state; calls into cross-domain commands)
      |
      v
  commands (uses state, damage)
      |
      v
  modals, ui-stats (use queries + view-models + commands)
      |
      v
  bootstrap

        ignore it.

        STATE_EVENTS.CACHE_INVALIDATED so subscribers keyed on either
        name fire.
      - validateIntegrity warns, does not throw.
      - The state does NOT invalidate accessor caches. accessors.js does
        not cache disasters, so no cache invalidation is required.
        DisasterCommands.persist calls invalidateAccessorCaches after
        save; see §2.5.

        Steps 1, 2, and 3 are best-effort: exceptions are logged, the
        command proceeds. Step 4 is called if DisasterDamage is present;
        failures there are logged, the command proceeds.
      - simulateRandomDisaster picks a populated location by
        population-weighted selection, then calls triggerDisaster with
        a random type and applyEffects: true.

================================================================================
PART 3 — THE DISASTER → OTHER-DOMAIN DAMAGE CONTRACT
================================================================================

The disaster domain owns exactly ONE canonical collection: the
masterData.data.disasters array. Every other interaction with the world
is through another domain's public command or query surface.

THE FIVE DAMAGE CATEGORIES
--------------------------

  Category        Owning domain        Read via                        Write via
  ---------------------------------------------------------------------------
  features        Settlement           SettlementQueries              SettlementFeatureCommands
                                       .getSettlementData +           .demolishFeature
                                       SettlementFeatureQueries
                                       .getFeatureById
  schools         Education            EducationState                 EducationCommands
                                       .getInstitutionsByLocation     .demolishInstitution
  enterprises     Industry             IndustryState                  IndustryCommands
                                       .getEnterprisesByLocation      .demolishEnterprise
  residences      Residence            ResidenceSystem                ResidenceSystem
                                       .getResidencesByLocation       .demolishResidence
  households      Household            HouseholdState                 HouseholdCommands
                                       .getHouseholdsByLocation       .demolishHousehold

Every destruction is that owning domain's OWN transaction. The disaster
domain does not commit those transactions; it calls each owning domain's
command, which owns its own persistence boundary (or, in the industry /
household case, its own dirty-marking, with the caller handling the
save — see CROSS-DOMAIN PERSISTENCE below).

DAMAGE SELECTION
----------------

  DisasterDamage._selectItemsToDestroy applies:

    adjustedChance =
      (severity / 100) * DAMAGE_CHANCE.maxBaseChance
      * DISASTER_TYPE_DAMAGE_MULTIPLIERS[disasterId]
      * DAMAGE_SYSTEM_MULTIPLIERS[category]

  clamped to DAMAGE_CHANCE.maxAdjustedChance.

  Each item in the category is independently rolled against
  adjustedChance.

  IMPORTANT: this uses Math.random() directly. There is no
  caller-supplied RNG. This is the only Math.random call in the
  disaster subsystem. See HAZARDS §3.

HOUSEHOLD PROTECTION
--------------------

  The household destroyer refuses to destroy "protected" households:
    hasMembers && hasWealth (>= 20) && hasResidence.

  Households that are already status === 'destroyed' are skipped.
  The others are eligible.

  Household destruction is OFF by default (demolishHouseholds option
  defaults to false in applyStructuralDamage). DisasterCommands.
  applyDisasterEffects explicitly passes demolishHouseholds: true.

CROSS-DOMAIN PERSISTENCE
------------------------

  The disaster domain does NOT save on behalf of another domain.
  Each destruction goes through the owning domain's command:

    SettlementFeatureCommands.demolishFeature    -> its own dirty-flag;
                                                    the caller flushes.
    EducationCommands.demolishInstitution         -> its own dirty-flag.
    IndustryCommands.demolishEnterprise           -> its own dirty-flag.
    HouseholdCommands.demolishHousehold           -> its own dirty-flag.
    ResidenceSystem.demolishResidence             -> its own dirty-flag.

  DisasterCommands.persist (via saveMasterData) flushes EVERYTHING at
  once, because saveMasterData writes the whole masterData envelope.

  The consequence: calling DisasterCommands.persist() after
  applyDisasterEffects saves the disaster record AND every cross-domain
  change those commands made. This is intentional. Do NOT additionally
  call another domain's persist() — that would produce a redundant
  second save with nothing new to write.

THE COMMIT TAIL
---------------

  DisasterCommands._commit:
    1. DisasterState.hydrateFromMasterData(true) — rebuild indexes.
    2. markDataDirty() — flag for next save.
    3. DisasterState.publish(eventName, payload) — in-process
       subscribers.
    4. dispatchEvent(CustomEvent) — cross-domain consumers.

  DisasterState's own mutation primitives (addDisaster, updateDisaster,
  deleteDisaster) call markDataDirty but NOT publish, dispatch, or
  hydrate. The commit is the command's job.

WHAT DISASTER DOES NOT WRITE
----------------------------

  - character.deathYear, character.isDeceased, or any character field.
    Character deaths go through killCharacter, which is CharacterCommands
    territory.
  - settlement.prosperity or settlement.crimeRate directly. These go
    through modifySettlementProsperity / modifySettlementCrimeRate.
  - household.status, household.members, household.residenceId, or any
    household field directly. These go through HouseholdCommands.
  - enterprise.status or enterprise.ownerType directly. These go
    through IndustryCommands.demolishEnterprise.
  - residence.isDemolished, residence.status, or any residence field
    directly. These go through ResidenceSystem.demolishResidence.
  - education institution records directly. These go through
    EducationCommands.demolishInstitution.

WHAT DISASTER DOES NOT READ DIRECTLY
------------------------------------

  All reads go through the owning domain's public query/state surface,
  never through window.masterData.data.<domain>. The one exception is
  DisasterState's own read of masterData.data.disasters (which it
  owns).

  Exception noted: DisasterState.hydrateFromMasterData reads
  masterData.data.disasters directly (canonical). This is correct —
  DisasterState owns that array.

================================================================================
PART 7 — KNOWN HAZARDS
================================================================================

  1.  DISASTER-DOC.TXT IS TRUNCATED IN THE SUPPLIED BATCH.
      The supplied narrative doc ends at §2 "Load order:" with no
      further content. This document is derived from the code, not from
      the (missing) narrative sections. Update the narrative doc before
      citing it as authoritative.

  2.  THE BOOTSTRAP DOES NOT LISTEN FOR masterDataUpdated.
      Every other subsystem bootstrap (household, industry) registers
      a masterDataUpdated listener to re-hydrate. disaster-bootstrap.js
      does NOT. A caller that replaces masterData out-of-band must call
      DisasterBootstrap.reinit() explicitly. Failing to do so leaves
      DisasterState's indexes pointing at the old (pre-reload) records
      until the next mutation forces a hydrate. This is documented as a
      known gap; the fix is a one-line addEventListener in the
      bootstrap.

  3.  DISASTER-DAMAGE.JS IS THE ONLY FILE THAT CALLS Math.random.
      _selectItemsToDestroy uses Math.random() directly. Every other
      disaster file routes randomness through window.chance /
      randomInt / pickRandom / pickWeighted (which respect the seeded
      RNG). The consequence: seeded-simulation reproducibility is
      BROKEN for damage selection. A future revision should accept a
      caller-supplied RNG or route through window.random.

  4.  DOUBLE-WRITE OF STRUCTURAL DAMAGE.
      DisasterDamage.applyStructuralDamage ends with _saveDamageRecord,
      which calls State.updateDisaster with the structuralDamage
      payload. DisasterCommands.applyDisasterEffects ALSO calls
      State.updateDisaster with the same payload after the damage
      coordinator returns. The second write is redundant. It currently
      succeeds harmlessly (both writes carry the same data). A future
      revision should remove one of them; the redundant write is a
      maintenance trap if the two ever diverge.

  5.  killCharacter SIGNATURE DIVERGENCE.
      disaster-commands.js calls:
        window.killCharacter(char, year, disasterType, { disasterId,
        disasterType });
      crime-commands.js (per crime docs) calls killCharacter with a
      two-argument signature killCharacter(characterId, deathData).
      household-doc.txt's maternal-death path routes through
      CharacterLifecycle.killCharacter.
      The character-lifecycle API must accept BOTH forms for the
      disaster path to work AND the crime path to work. Confirm the
      deployed character-lifecycle.js handles the 4-argument form;
      otherwise disaster-commands.js's character-death effect silently
      fails (the failure is logged to console.error from
      _killVictims). See HAZARDS §7 in the character doc.

  6.  DISASTERCOMMANDS DOES NOT VERIFY ALL ITS CROSS-DOMAIN
      DEPENDENCIES ITSELF.
      The load-time verification covers only the direct requires
      (settlement, character, randomness, time, storage). The
      Education / Industry / Household / Residence damage commands are
      verified by DisasterDamage through its _isLoaded* checks, which
      are CALL-TIME. The bootstrap verifies them at INIT time. A
      reduced test harness that loads disaster-commands.js in
      isolation and calls triggerDisaster would:
        - pass load
        - pass generateDisaster, addDisaster
        - pass settlement effects (they're load-required)
        - pass character deaths (killCharacter is load-required)
        - fail structural damage silently (skipped by _isLoaded*
          checks)
      This is by design (matching the "systems that are not loaded are
      skipped" policy), but callers that need to know whether damage
      was applied must check the resulting destructionList, not assume
      the damage coordinator's return value indicates "all applied".

  7.  DisasterCommands.persist CALLS invalidateAccessorCaches.
      This is correct: an accessor for disasters doesn't exist, but
      the cross-domain effects (character deaths, settlement changes,
      household demolitions, residence demolitions) have changed the
      collections those accessors DO index. The invalidation clears
      the character / household / place caches. Failing to call it
      would leave getCharacterById, getHouseholdById, and getPlaceById
      returning stale records after a disaster.

  8.  SIMULATE-RANDOM-DISASTER CHANCE MECHANISM.
      simulateRandomDisaster uses window.chance(chanceRate) for the
      "does a disaster happen this year" roll, then pickWeighted over
      populated locations, then triggerDisaster with disasterType: null.
      Inside triggerDisaster → generateDisaster, the TYPE selection
      uses pickWeighted over the disaster types with a location
      modifier. The two weighted selections are INDEPENDENT.
      Each consumes the seeded RNG (chance, pickWeighted), so the
      overall system is reproducible IF damage selection is also
      reproducible. See HAZARDS §3.

  9.  STRUCTURAL DAMAGE ON NON-HOUSEHOLD LOCATIONS.
      The household destroyer skips "protected" households (has
      members, has wealth >= 20, has residence). A wealthy household
      with a residence is IMMUNE to disaster destruction. This is
      intentional game policy, not a bug; but it is non-obvious from
      the API surface. Callers that expect all households in a location
      to be destroyed will be surprised.

 10.  RESIDENCE-DEMOLISH CASCADES HOUSEHOLD DISASSOCIATION.
      ResidenceSystem.demolishResidence disassociates every household
      occupying any unit (calls HouseholdCommands.disassociateFromResidence).
      Because the disaster damage coordinator calls demolishResidence,
      every disaster that destroys a residence ALSO clears the
      residence.reverse index on any household living in it. A caller
      that inspects households after applyStructuralDamage sees the
      pre-demolition household shape (with residenceId cleared) unless
      it separately checks residence.isDemolished. Do not assume a
      household's state reflects its residence's state at any point
      during the damage pass.

 11.  DESTROYED-ITEM RECORDS CARRY THE OWNING DOMAIN'S ID ONLY.
      Each entry in structuralDamage.destructionList carries an `id`
      (the destroyed entity's id), a `name`, a `type`
      (settlement_feature / school / enterprise / residence / household),
      a `demolished: true`, a `year`, plus a few domain-specific
      extras (category, residenceType, unitsDemolished, membersRemoved).
      There is no link BACK to the destroyed entity's history; the
      owning domain's records are the source of truth. A caller that
      needs details of a destroyed enterprise must query the industry
      domain's tombstone (enterprise.status === 'demolished',
      enterprise.demolishedRecord).

 12.  DUPLICATE IDs ARE A HARD FAILURE.
      DisasterState.hydrateFromMasterData throws on duplicate ids.
      A corrupted masterData.data.disasters array is NOT silently
      repaired; it must be fixed before the domain can load. The
      bootstrap's _verifyCanonical checks shape (array-ness) only; the
      duplicate check happens at hydration, which bootstrap calls.

 13.  THE BOOTSTRAP VERIFIES DisasterState._initialize AS A FALLBACK.
      If DisasterState has neither hydrateFromMasterData nor
      _initialize, bootstrap throws. The current DisasterState exposes
      both (hydrateFromMasterData is the canonical; _initialize is the
      legacy alias used by callers that predate the refactor). Do not
      remove _initialize without updating the bootstrap's fallback
      logic.

 14.  DAMAGE COORDINATOR CALLS State.updateDisaster.
      DisasterDamage is documented as a coordinator, not a command.
      But it calls State.updateDisaster via _saveDamageRecord after
      applying damage. This is a WRITE from a coordinator. The
      disaster record's structuralDamage is set ONCE by
      applyStructuralDamage's internal _saveDamageRecord, then SET
      AGAIN by DisasterCommands.applyDisasterEffects. See HAZARDS §4.

 15.  THE UI-STATS RENDERERS SCAN FOR CONTAINERS BY CLASS.
      refreshAll uses document.querySelectorAll('.disaster-stats-panel'
      etc.) to find containers. If a caller dynamically mounts a
      disaster panel with a different class name, refreshAll will not
      find it. The current design assumes the modal files (or the
      disaster UI host page) apply the expected class names. A future
      revision could switch to a render registry, matching the
      pattern used in crime-ui-stats.

 16.  THE BOOTSTRAP DOES NOT VERIFY DisasterViewModels.
      DisasterViewModels is a dependency of modals-disaster.js and
      disaster-ui-stats.js, both of which verify it at load. The
      bootstrap does not add it to _verifyDisasterModules, so a
      missing DisasterViewModels is caught only when the modal or UI
      file tries to load. The bootstrap's current surface is:
      DisasterConstants, DisasterState, DisasterQueries,
      DisasterCommands (plus optional DisasterDamage). Adding
      DisasterViewModels to _verifyDisasterModules is a harmless
      hardening.

 17.  THE BOOTSTRAP DOES NOT VERIFY modals-disaster.js OR
      disaster-ui-stats.js.
      Both are OPTIONAL UI layers. The bootstrap's surface stops at
      the domain (commands + queries + state + constants + optional
      damage). A missing modals-disaster.js produces a runtime
      missing-global error when a button tries to open a modal. This
      matches the pattern in household-bootstrap.js (which verifies
      HouseholdModals only when present). Adding a warn-once for the
      modal surface is a future improvement.

 18.  THE STATE'S HYDRATE THROWS ON DUPLICATE IDs.
      The bootstrap catches this via try/catch? NO — the bootstrap
      calls _hydrate() OUTSIDE the try/catch that wraps _runIntegrityCheck.
      A duplicate-id corruption therefore fails init() with a hard
      throw, which is the intended behavior. Do not wrap _hydrate in
      a swallow; the throw is the point.

 19.  THE DAMAGE COORDINATOR COMMITS THE DISASTER RECORD'S DAMAGE
      FIELD, NOT THE DISASTER RECORD AS A WHOLE.
      The coordinator's State.updateDisaster call only writes
      structuralDamage (and the aligned convenience mirrors). The
      disaster's other fields (deaths, description, etc.) are written
      by DisasterState.addDisaster (initial write) or by
      DisasterCommands's own State.updateDisaster (via
      applyDisasterEffects' callback for the aggregate report). There
      is no single write that produces the final disaster record;
      callers must inspect the aggregate across both writes.

 20.  THE COMMANDS' VICTIM COLLECTION USES displayName MATCHING.
      _getCharactersAtLocation builds a displayName → locationId map
      from getPlaces(), then matches each character's
      getCurrentLocation result (which returns a display name, not an
      id) against that map. A character whose location's displayName
      has changed since the character record was written (rare, but
      possible if a place is renamed) will not match. A character at
      a sub-location is included only if the sub-location's
      displayName maps to an id in getAllSubLocationIds. This is the
      current contract; migrating getCurrentLocation to return an id
      would remove the displayName-matching fragility.

 21.  THE LOCATION-MODIFIER CLAMP.
      getDisasterLocationModifier multiplies modifiers for every
      matching terrain, then clamps to [0.5, 3.0]. A location whose
      name matches both "coastal" and "island" (e.g. a harbor on an
      island named "Port Isle") gets 2.0 × 1.8 = 3.6 → clamped to 3.0.
      A location matching three terrains with modifiers >= 1.5 hits
      the cap quickly. The cap is intentional; a future revision that
      removes it must add a different bound (e.g. geometric mean) to
      prevent runaway.

 22.  THE DISASTER TYPE DISTRIBUTION IS WEIGHTED BY DISASTER_TYPES'
      WEIGHT FIELD * locationModifier.
      generateDisaster's weightedTypes array multiplies weight by the
      location modifier (a decimal). The pickWeighted call consumes
      those weights. A location whose modifiers produce fractional
      weights (e.g. 25 * 0.7 = 17.5) is fine — pickWeighted handles
      non-integer weights. A location whose modifiers produce zero
      weight for all types is impossible (base weights are positive,
      modifier is clamped to >= 0.5), so pickWeighted is never called
      with an all-zero array.

 23.  THE COMMANDS' SPOT-CHECK OF THE DAMAGE COORDINATOR.
      disaster-commands.js verifies at load that window.DisasterDamage
      exists and is truthy. It does NOT verify that
      applyStructuralDamage is a function (the bootstrap does that if
      DisasterDamage is present). At RUNTIME, disaster-commands.js
      checks typeof window.DisasterDamage.applyStructuralDamage ===
      'function' before calling it, so a partial
      DisasterDamage (loaded but missing applyStructuralDamage) would
      cause structural damage to be silently skipped. The bootstrap
      catches this case at init, but only when the bootstrap actually
      runs. If a caller loads disaster-commands.js without ever calling
      DisasterBootstrap.init(), the missing-method case is a runtime
      no-op, not a load-time throw.

 24.  THE MODAL PERSISTENCE MODEL IS SINGLE-SHOT.
      modals-disaster.js's _commitAndPersist calls
      DisasterCommands.persist once per modal action and toasts a
      warning if persist fails but leaves the modal closed (the modal's
      onConfirm already returned true after the command succeeded).
      Retrying requires the user to re-open the modal and re-enter.
      This matches the pattern the disaster doc describes for its
      persistence model, but it diverges from the retry-idempotency
      pattern used in modals-household.js. Do not assume persistent
      retry is available in the disaster modal flow.

 25.  modals-disaster.js DOES NOT DEDUPLICATE THE OUT-OF-BAND
      State.updateDisaster.
      If a caller runs applyDisasterEffects a second time on the same
      disaster (re-application), State.updateDisaster is called again
      with the new aggregate. The damage coordinator's
      _saveDamageRecord also runs again. Two writes per application.
      Callers must not re-apply unless they expect the aggregate to
      reflect the second damage pass. The design is single-shot; the
      code does not prevent double-application.

 26.  disaster-ui-stats.js DOES NOT DELEGATE TO _processingRender
      GUARD.
      This is by design. But a component that renders in a tight loop
      against a shared container can produce flicker. The current
      refreshAll scans DOM and re-renders each panel; if the underlying
      queries are expensive (getGlobalDestructionStatistics iterates
      every disaster), the refresh can be slow. Consider debouncing
      refreshAll at the call site.

 27.  modals-disaster.js's _detailGrid USES A SINGLE HELPER THAT
      ESCAPES ITS VALUE.
      _detail('Label', _escape(value)) — the VALUE is escaped by the
      caller, and _detail escapes only the label. A caller that passes
      raw HTML as the value (intentional markup) will see it rendered;
      a caller that passes user data without _escape will inject HTML.
      The current call sites all _escape the value; a future addition
      must not forget.

 28.  THE DAMAGE REPORT'S `errors` ARRAY DISTINGUISHES FAILURES FROM
      SKIPS.
      A skipped category (owning system not loaded) is NOT in `errors`;
      it's implicitly represented by the empty destruction list. A
      failed destruction IS in `errors` with the system name and the
      specific item. A caller that wants to know "was this category
      attempted" must check the owning domain's presence directly (or
      compare destruction list length to the location's category size).
      The design is intentional (errors must mean errors), but the
      absence of an attempted/skipped flag means the caller cannot
      distinguish "nothing to destroy" from "damage coordinator not
      loaded" from the report alone.


================================================================================
PART 8 — SUMMARY
================================================================================

The disaster subsystem is a self-contained domain with exactly one
canonical collection (masterData.data.disasters). Every interaction with
the world outside its own collection is through another domain's public
command or query surface.

The load-bearing contracts are:

  1. Constants are frozen and never re-derived elsewhere.
  2. DisasterState is the single writer of the canonical collection.
  3. DisasterCommands is the single public command boundary.
  4. DisasterDamage is a coordinator, not a command; it calls each
     owning domain's command.
  5. DisasterBootstrap verifies the module set at init time and treats
     a present-but-broken optional cross-domain module as a hard
     failure (absent-entirely is a warn).
  6. Persistence flows through DisasterCommands.persist once per
     logical operation. saveMasterData writes the whole envelope, so
     it flushes every cross-domain change the disaster applied.

Load order is dictated by:
  - core prerequisites (constants, formatting, icons, ids, time,
    storage, accessors, world, randomness, eventLogger, ui,
    modals-core, locationDropdown);
  - character / settlement prerequisites (both HARD);
  - optional cross-domain prerequisites (education, industry,
    household, residence) — present-but-complete or absent;
  - the disaster files in the strict order
    constants → state → queries → damage → commands → view-models →
    modals → ui-stats → bootstrap;
  - application-level DisasterBootstrap.init() (or auto-init if
    masterData is already present).

Do not reorder the disaster files. The invariants in PART 6 are load-
bearing; failure modes range from a clean load-time throw (module
missing) to silent damage skip (optional cross-domain module missing at
runtime) to a hard hydration failure (corrupted canonical data).
