**Location:** `js/core/rank/`
**Version:** 3.0
**Last regenerated from:** the code in this folder after the
rank integration refactor.

---

## 1. Overview

The rank domain owns the **catalogue of formal ranks** and the
**assignment of those ranks to characters**.

A rank is a record in a catalogue: a name, a level, a symbol, a set of
policy flags (numbered, gender-restricted, deprecate-on-death), optional
inheritance configuration, and an optional surname rule. A rank is not
attached to a character — it exists independently.

A rank **assignment** is a record on a character: which rank they hold,
since when, with what number, whether it is active, whether it is
deprecated, and from whom it was inherited.

The rank domain owns:

- the rank catalogue (`RankState`)
- inheritance rules between ranks (`RankState`)
- the arithmetic of numbering holders (`RankAssignment`)
- detection and repair of rank configuration problems (`RankIssues`)
- the modal and list UI for managing ranks (`RankModals`, `RankUI`)

The rank domain does **not** own:

- the character record (`CharacterState`)
- the write path for character fields, including rank assignments
  (`CharacterCommands`)
- relationship facts — who is married to whom (`RomanceQueries`)
- family facts — who is whose parent (`FamilyQueries`)
- numbering display vocabulary — ordinal / roman formatting (`RankRules`)
- role skill (education and apprenticeship own that; rank does not
  interact with role skill at all)

The rank catalogue answers "what does a Duke look like." It does not
answer "is Bruna a Duke." A character's rank assignments answer that
question, and they live on the character record.

---

## 2. Principles

| Principle | Rule |
|---|---|
| **Single source of truth** | `RankState` owns the rank catalogue. `CharacterState` owns the character record. No other module stores rank data. |
| **Command-query separation** | `RankQueries` reads. `RankCommands` writes. `RankState` provides the state primitives that `RankCommands` calls. |
| **One writer per field** | Rank records: `RankCommands`. Inheritance rules: `RankCommands`. Character rank assignments: `CharacterCommands`. |
| **Fail loud** | Missing required dependency throws at load. Missing required method throws at load. Nothing fabricates `0`, `[]`, `null`, or `1250`. |
| **Reads return clones** | `RankState` public reads return defensive projections. Live records never leave the state layer. |
| **One persist per batch** | Commands mutate in memory and call `markDataDirty` via `RankState`. The caller calls `RankCommands.persist()` once. |
| **No recursion guards** | Mutations are synchronous and side-effect explicit. Commands may chain freely. |
| **Policy is pure** | `RankRules` has no state access, no I/O, no randomness. |
| **Numbering is arithmetic, not policy** | `RankAssignment` computes numbers. `RankRules` classifies which numbering group a holder belongs to. |
| **Issues detect; callers apply** | `RankIssues.checkAll()` returns issues with fix closures. `RankIssues.applyFixes()` applies them. Nothing auto-fixes silently. |

## 5. Ownership contract

| Concept | Owner | Readers |
|---|---|---|
| Rank catalogue | `RankState` | `RankQueries` |
| Inheritance rules | `RankState` | `RankQueries` |
| Rank record mutations | `RankCommands` (via `RankState._` methods) | — |
| Inheritance rule mutations | `RankCommands` (via `RankState._` methods) | — |
| Rank policy | `RankRules` | `RankCommands`, `RankAssignment`, `RankIssues` |
| Numbering arithmetic | `RankAssignment` | `RankCommands` |
| Character rank assignments | `CharacterState` (record), `CharacterCommands` (writes) | `RankQueries`, `RankIssues` |
| Numbering info (`number`, `activeRankId`) | `CharacterCommands` (derived) | everyone |
| Rank-to-character lookup | `RankQueries.getCharactersWithRank` | cross-domain callers |
| Inheritance source resolution | `RankQueries.getInheritanceSource` | `RankAssignment`, `RankIssues` |
| Committed-partner facts | `RomanceQueries` | `RankQueries`, `RankAssignment`, `RankIssues` |
| Parent facts | `FamilyQueries` | `RankQueries`, `RankAssignment`, `RankIssues` |
| Persistence | `RankCommands.persist` (the only `saveMasterData` call site) | — |
| Annual pipeline | `RankIssues.processAnnualRank` | callers |

| Hard-delete cleanup | `RankIssues.removeAllReferencesTo` | `CharacterDeletionCommands` (directly or via hook) |

**Reads outside the owning domain:** only through the owner's query
surface. No module outside `RomanceQueries` may read committed-partner
facts by walking `character.relationships`. No module outside
`CharacterState` may hold a live character record.

## 6. Data schemas

### Rank record (in `RankState`)

```
{
    id:                     string,   unique
    name:                   string,
    priority:               number,   1..10
    numbered:               boolean,
    numberingType:          'reign' | 'ordinal' | 'roman',
    numberingGroup:         'global' | 'parent' | 'spouse' | 'source',
    numberingPrefix:        string,
    numberingSuffix:        string,
    sourceRankId:           string | null,
    inheritanceSource:      'none' | 'parent' | 'spouse',
    symbol:                 string,
    genderRestriction:      'either' | 'male' | 'female',
    locationTypeId:         string | null,
    deprecateOnDeath:       boolean,
    spouseInheritance:      string | null,   // legacy; prefer sourceRankId
    allowsMultipleSpouses:  boolean,
    parentRankId:           string | null,
    customSurnameRule:      boolean,
    surnameConnector:       string,
    surnamePrefix:          string,
    surnameSuffix:          string,
    createdAt:              number | null,
    updatedAt:              number | null
}
```

### Inheritance rule (in `RankState`)

```
{
    childRankId:            string | null,
    childRankIdFemale:      string | null,
    minChildAge:            number,    default 0
    maxChildren:            number | null,
    order:                  number,    default 10
}
```

Stored as `{ [parentRankId]: RankRule[] }`.

### Rank assignment (on the character record)

Written only by `CharacterCommands`.

```
{
    rankId:                 string,
    customTitle:            string | null,
    address:                string | null,
    number: {
        rawNumber:          number,
        display:            string,
        type:               'ordinal' | 'roman' | 'custom',
        groupId:            string | null,
        holdersInGroup:     number | null
    } | null,
    order:                  number,
    isActive:               boolean,
    isDeprecated:           boolean,
    assignedYear:           number | null,
    notes:                  string,
    inheritedFrom:          string | null
}
```

### Character rank pointers

Derived by `CharacterCommands._reconcileRankActives` on every write.
Never written directly.

```
activeRankId:               string | null
activeRankNumber:           number | null
```

Invariant: exactly one non-deprecated assignment has `isActive: true`
when any non-deprecated assignment exists. `activeRankId` matches that
assignment's `rankId`. When no non-deprecated assignment exists,
`activeRankId` and `activeRankNumber` are `null`.

## 7. State — `rank-state.js`

The single in-memory catalogue for ranks and inheritance rules.

### Hydration

```
RankState.hydrateFromMasterData(ranks, inheritanceRules)
RankState.isHydrated()
```

Hydration is explicit. `rank-bootstrap.js` calls it once. Rehydrating is
allowed (`masterDataUpdated` triggers it automatically). Duplicate rank
ids throw.

### Public reads (clones)

| Function | Returns |
|---|---|
| `getAllRanks()` | Clone of the rank array |
| `getRank(id)` | Clone or null |
| `getRanksByPriority(p)` | Clone array |
| `getRankHierarchy()` | Array of nodes with `children` arrays |
| `getRankCount()` | Number |
| `getInheritanceRules()` | Clone of the rules map |
| `getInheritanceRulesForRank(id)` | Clone of the rule array |

### Subscriptions

```
RankState.subscribe(callback) -> unsubscribe
```

Receives `{ type, data }` on every mutation. Types: `rankAdded`,
`rankUpdated`, `rankDeleted`, `inheritanceRuleAdded`,
`inheritanceRuleRemoved`, `inheritanceRulesSet`, `stateReloaded`.

### Diagnostics

```
RankState.validateIntegrity() -> { valid: boolean, errors: string[] }
```

Checks: every rank has a valid id, no duplicate ids, priority 1–10,
parent and source references resolve, no self-parent or self-source,
inheritance rules reference existing parents and children. Never throws.

### Internal (reserved for `RankCommands`)

`_getRankCanonical(id)`, `_getAllRanksCanonical()`, `_addRank`,
`_updateRank`, `_removeRank`, `_addInheritanceRule`,
`_removeInheritanceRule`, `_setInheritanceRules`, `_indexesRebuild`.

Every mutator syncs `masterData.data.ranks` and
`masterData.data.rankInheritanceRules` in memory, then calls
`markDataDirty`. It does not call `saveMasterData`.

## 8. Queries — `rank-queries.js`

### Rank queries

Delegate to `RankState`. Every function returns clones.

`getRank`, `getAllRanks`, `getRanksByPriority`, `getRankHierarchy`,
`getRankCount`, `getInheritanceRules`, `getInheritanceRulesForRank`.

### Level helpers

| Function | Source |
|---|---|
| `getRankLevelName(priority)` | `RANK_LEVELS` in `rank-constants.js` |
| `getRankLevelDescription(priority)` | `RANK_LEVELS` |
| `getRankLevelIcon(priority)` | `icons.js` via `getRankLevelIcon` |
| `getAvailableSymbols()` | `AVAILABLE_SYMBOLS` |

The icon and the name are separate concerns. Level names come from
constants. Level icons come from `icons.js` and return SVG markup.

### Character queries

| Function | Behaviour |
|---|---|
| `getCharactersWithRank(rankId, includeDeprecated)` | Reads `character.rankAssignments` from the projection. Includes any character whose active pointer matches even if the assignment array is stale (defensive). |
| `getRankHolderCount(rankId, includeDeprecated)` | Length of the above. |
| `getRankHolderStats(rankId)` | Counts by gender, living/deceased, age band. Characters whose age cannot be resolved are counted separately, not as minors. |
| `getRankAssignmentsForCharacter(characterId, includeDeprecated)` | Assignment array from the projection, sorted by `order`. |
| `getActiveRankAssignment(characterId)` | The assignment matching the active pointer, or the first `isActive` one. |

### Spouse inheritance queries

`getSpouseInheritanceRanks(characterId)` — the ranks the character is
**entitled** to by virtue of their current committed partner's rank.

`getReceivedSpouseInheritanceRanks(characterId)` — the ranks the
character **actually holds** where `inheritedFrom` is set.

Both read committed partners via
`RomanceQueries.getActiveCommittedPartners`. Neither walks
`character.relationships`.

### Inheritance source (canonical)

```
RankQueries.getInheritanceSource(characterId, rankId) -> string | null
```

The single implementation. Previously duplicated in `rank-assignment.js`
and `rank-issues.js`. Uses `RomanceQueries` for spouse inheritance and
`FamilyQueries.getParents` for parent inheritance.

`getParents` may return an object (`{ father, mother }`) or an array of
edges. Both shapes are handled. The parent reference may be a string id,
a character projection with `id` and `activeRankId`, or an edge with
`parentId`. All three are normalised.

### Surname rule queries

`getRanksWithSurnameRules()`, `getRankSurnameRule(rankId)`.

### Validation helper

`isValidRank(rank)` — delegates to `RankRules.validate`.

## 9. Rules — `rank-rules.js`

Pure policy. No state access. No side effects.

### Shape

```
RankRules.applyDefaults(raw) -> RankRecord
```

Produces a normalised record shape from raw input. Does not assign `id`
or timestamps — that is the command layer's job.

The function preserves unknown fields (forward compatibility). It
coerces known fields. It enforces coherence: `sourceRankId` requires an
`inheritanceSource` other than `'none'`; `numberingGroup: 'source'`
requires `inheritanceSource` to be set. Falls back to `DEFAULT_RANK`
values when a field is missing, and to hardcoded literals when
`DEFAULT_RANK` itself is not loaded.

### Validation

```
RankRules.validate(rank) -> { valid, errors }
RankRules.validatePatch(current, patch) -> { valid, errors }
RankRules.validateInheritanceRule(rule) -> { valid, errors }
```

`validate` checks: name non-empty, priority integer 1–10, symbol
non-empty and in `AVAILABLE_SYMBOLS`, gender restriction valid, numbering
config coherent, inheritance config coherent, surname rule coherent,
no self-parent, no self-source.

`validatePatch` merges the patch onto the current record and validates
the result. This catches coherence errors a per-field check would miss.

`validateInheritanceRule` checks shape and coherence. It does not check
that referenced ranks exist — that is a state question.

### Assignment policy

```
RankRules.canAssignRank(character, rank, options) -> { valid, reason? }
RankRules.canDeprecateRankAssignment(character, rankId) -> { valid, reason? }
```

`canAssignRank` checks: character exists and is not deleted or deceased,
gender restriction, no duplicate non-deprecated assignment,
`numberingGroup: 'source'` ranks require a source. It reads only from the
supplied arguments and never touches state.

### Romance bridge

```
RankRules.allowsMultipleSpouses(rank) -> boolean
```

Exists so that `RomanceCommands` can ask "does this rank permit multiple
spouses" without reading the field directly. The answer is a policy
question and belongs to rank.

### Numbering classification

```
RankRules.classifyNumberingGroup(rank, sourceId) -> string
```

Returns the bucket key for a holder: `'global'` or a source character id.
When the rank wants grouping but no source is available, returns
`'global'` rather than erroring. The assignment layer decides whether the
missing source is a hard error.

### Number formatting

```
RankRules.formatNumber(n, type) -> string
```

`'ordinal'` → `'1st'`, `'2nd'`, `'3rd'`, `'4th'`, `'11th'`, `'21st'`…
`'roman'` / `'reign'` → `'I'`, `'II'`, `'III'`… up to XXXIX; arabic
above.

Handles the teen exceptions correctly (`11th`, `12th`, `13th`). The old
`RankAssignment.toOrdinal` did not.

## 10. Commands — `rank-commands.js`

The write boundary. Every public command returns
`{ success: true, ... }` or `{ success: false, reason }`. Domain errors
never throw.

### Persistence

```
RankCommands.persist() -> { success, reason? }
```

The only `saveMasterData` call site in the rank domain. Callers batch:
mutate, then persist once.

### Rank CRUD

```
createRank(rankData)              -> { success, rank? }
updateRank(rankId, updates)       -> { success, rank? }
deleteRank(rankId, options)       -> { success, ... }
```

`createRank` runs `RankRules.applyDefaults`, checks cross-rank
references, runs `RankRules.validate`, stamps the id and timestamps,
writes via `RankState._addRank`.

`updateRank` checks that any new parent or source reference exists,
runs `RankRules.validatePatch`, writes via `RankState._updateRank`.

`deleteRank` refuses if there are non-deprecated holders or referencing
ranks, unless `{ force: true }`. With force: it removes every holder's
assignment via `CharacterCommands.removeRankAssignment`, nulls every
`parentRankId` and `sourceRankId` reference in other ranks, drops the
rank's own inheritance rules (via `RankState._removeRank`), and deletes
the record. Returns counts of everything cleaned.

### Inheritance rules

```
addInheritanceRule(parentRankId, rule)         -> { success, rule? }
removeInheritanceRule(parentRankId, ruleIndex) -> { success }
setInheritanceRules(parentRankId, rules)       -> { success }
```

`setInheritanceRules` is bulk replacement. Useful for a full edit.

### Assignment (delegates to `CharacterCommands`)

```
assignRankToCharacter(characterId, rankId, options) -> { success, assignment?, ... }
deprecateRankAssignment(characterId, rankId)        -> { success, unchanged? }
removeRankAssignment(characterId, rankId)           -> { success }
setActiveRank(characterId, rankId)                  -> { success, unchanged? }
clearActiveRank(characterId)                        -> { success, unchanged? }
```

`assignRankToCharacter` validates via `RankRules.canAssignRank`, computes
the numbering info (see §11), and writes via
`CharacterCommands.addRankAssignment`. The `options.number` field accepts
four forms: undefined (auto-compute for numbered ranks), `null` (no
number), a number (raw; display computed via `RankRules.formatNumber`),
or an object (passed through as-is).

`deprecateRankAssignment` validates via
`RankRules.canDeprecateRankAssignment` and writes via
`CharacterCommands.deprecateRankAssignment`. The record stays on the
character, marked deprecated. The active pointer is recomputed.

`removeRankAssignment` hard-removes. Distinct from deprecate: the record
ceases to exist.

`setActiveRank` requires the rank to exist on the character and not be
deprecated. Idempotent.

`clearActiveRank` forces a reselection among the remaining non-deprecated
assignments (or `null` if none).

### Bulk operations

```
bulkAssignRank(characterIds, rankId, options) -> { totalProcessed, successful, failed, results, errors }
bulkDeprecateRank(characterIds, rankId)       -> { totalProcessed, successful, failed, succeeded, errors }
```

Each character is attempted independently. The envelope reports counts
and per-character errors.

### Numbering

```
renumberRankHolders(rankId)      -> { success, fixedCount, errors }
rebuildAllRankNumbering()        -> { success, totalFixed, fixedCounts, errors }
```

Both delegate to `RankAssignment`. `rebuildAllRankNumbering` iterates
every numbered rank.

### Surname rule

```
updateRankSurnameRule(rankId, ruleSettings) -> { success, rank? }
```

`ruleSettings` shape: `{ enabled, connector, prefix, suffix }`. Delegates
to `updateRank` so coherence checks apply.

### Spouse inheritance

```
applySpouseInheritanceFixes(fixes) -> { applied, failed, errors }
```

`fixes` is an array shaped as produced by
`RankIssues.checkSpouseInheritance`: `{ characterId, rankId, spouseId,
spouseName, sourceRankName, ... }`. The command assigns each rank with
`inheritedFrom` set to `spouseId`. Does not persist — the caller persists
once after the batch.

### Death hook

```
deprecateRanksOnDeath(characterId, options) -> { deprecated, renumbered, errors }
```

Scans the character's non-deprecated assignments, finds every rank with
`deprecateOnDeath: true`, deprecates each, and renumbers the affected
ranks. Does not persist. Called by `RankIssues.handleCharacterDeath` and
by the death cascade.

## 11. Assignment — `rank-assignment.js`

Numbering arithmetic. No assignment writes.

### Get next number

```
RankAssignment.getNextRankNumber(rankId, characterId, characterName, gender, sourceCharacterId) -> NumberInfo | null
```

Returns `null` for unnumbered ranks. Otherwise returns
`{ rawNumber, display, type, groupId, holdersInGroup }`.

Algorithm:

1. Collect every character other than `characterId` who holds a
   non-deprecated assignment for `rankId`.
2. Filter to the holder's numbering group. Group key comes from
   `RankRules.classifyNumberingGroup(rank, sourceCharacterId)`.
   - `'global'` → all holders
   - source id → holders whose parent / spouse / inheritance source
     matches that id
3. Sort. Reign-numbered ranks sort by assignment year ascending.
   Ordinal-numbered ranks sort by birth year ascending. Both tie-break
   by character name.
4. `nextRaw = filtered.length + 1`.
5. `display = RankRules.formatNumber(nextRaw, rank.numberingType)`.

### Renumber holders

```
RankAssignment.renumberRankHolders(rankId) -> { success, fixedCount, errors }
```

Groups holders, sorts each group, walks each holder in order, and
compares the recorded number against the expected one. On mismatch,
writes via `CharacterCommands.updateRankAssignment`. Returns a count of
what was actually changed.

Group key precedence:

1. `assignment.inheritedFrom` (what the assignment was created with)
2. `RankQueries.getInheritanceSource(characterId, rankId)` (resolves
   from current state)
3. `'unknown'` bucket

This means a character whose spouse has died still groups under the
deceased spouse's id, matching the historical assignment.

### Fix all numbering for a character

```
RankAssignment.fixAllNumberingForCharacter(characterId) -> { fixedCount, ranksProcessed, errors }
```

For each numbered rank the character holds, renumbers the whole rank.

### Surname generation

```
RankAssignment.generateSurnameFromRankRule(character, context) -> string | null
```

`context.locationName` is the base. The rank's
`connector` / `prefix` / `suffix` are applied. Capitalises the first
letter.

### Spouse inheritance detection

```
RankAssignment.checkAndFixSpouseInheritance() -> { success, fixes, count }
```

Scans the population for characters who should hold a rank by virtue of
spouse inheritance but do not. Returns a list of fixes shaped for
`RankCommands.applySpouseInheritanceFixes`. Does not write.

Reads committed partners via `RomanceQueries`. Never walks
`character.relationships`.

### Surname rule shim

`RankAssignment.updateRankSurnameRule(rankId, ruleSettings)` — delegating
shim to `RankCommands.updateRankSurnameRule`. Kept for callers that only
import `RankAssignment`. Prefer `RankCommands` directly. Scheduled for
deletion once callers migrate.

## 12. Issues — `rank-issues.js`

Detection and repair. Every issue carries a `fix` closure that returns
`{ success, reason? }`.

### Main checker

```
RankIssues.checkAll() -> { success, issues, count, bySeverity }
```

`bySeverity` is `{ error, warning, info }`, each an array.

### Issue types

| Type | Severity | Fix |
|---|---|---|
| Spouse Inheritance | error | `RankCommands.assignRankToCharacter` with `inheritedFrom` set |
| Child Inheritance | warning | `RankCommands.assignRankToCharacter` |
| Gender Mismatch | error | `RankCommands.deprecateRankAssignment` |
| Numbering Error | error | `RankCommands.renumberRankHolders` |
| Deprecation Error | error | `RankCommands.deprecateRankAssignment` |
| Broken Inheritance Rule | error | `RankCommands.removeInheritanceRule` (or manual for orphan parents) |

### Batch apply

```
RankIssues.applyFixes(issues, options) -> { applied, failed, skipped, errors }
```

Applies every `issue.fix()` in order. `options.filter` can restrict which
issues are applied. Does not persist.

### Annual pipeline

```
RankIssues.processAnnualRank(year, options) -> AnnualEnvelope
```

Envelope shape:

```
{
    year,
    status:                 'completed' | 'completed_with_errors' | 'partial',
    issueCount,
    issuesBySeverity:       { error, warning, info },
    fixResults:             { applied, failed, skipped, errors },
    renumberResults:        { totalFixed, fixedCounts, errors },
    persisted:              boolean,
    persistError:           string | null
}
```

Pipeline: detect → apply fixes → rebuild all numbering → persist once.
`options.skipFixes: true` runs detection only. `options.persist: false`
skips the final save.

### Death hook

```
RankIssues.handleCharacterDeath(characterId, options) -> { success, deprecated, renumbered, errors }
```

Delegates to `RankCommands.deprecateRanksOnDeath`. Does not persist.

If `registerLifecycleHook` exists, `rank-issues.js` registers itself for
`'death'` at load. Otherwise the caller invokes this directly.

### Hard-delete cleanup

```
RankIssues.removeAllReferencesTo(characterId) -> { success, cleaned, ranksRenumbered, renumberErrors }
```

The character's own assignments vanish with the record. This function
scans every other character for assignments whose `inheritedFrom` names
the deleted character, nulls those pointers, and renumbers the affected
ranks. Does not persist.

If `registerLifecycleHook` exists, `rank-issues.js` registers itself for
`'delete'` at load.

## 13. Modals and UI

### Modals — `modals-rank.js`

| Function | Purpose |
|---|---|
| `RankModals.openCreateRankModal(options)` | Create rank modal. Exposes name, priority, symbol, gender restriction, parent, numbered + numbering config, deprecate-on-death, allows-multiple-spouses, inheritance source + source rank, surname rule. |
| `RankModals.openEditRankModal(rankId, options)` | Same fields, pre-populated. |
| `RankModals.openAssignRankModal(options)` | Inline character picker. `options.mode: 'bulk'` enables multi-select. |
| `RankModals.openRankDetailsModal(rankId, options)` | Detail view with stats, config, inheritance rules. |

Every modal:

- passes `titleHtml` and `contentHtml` to `openModal` (the modal core
  reads these names)
- calls `RankCommands.*` only
- calls `RankCommands.persist()` exactly once per successful write
- shows a toast on success or failure via `_showToast`
- has no `_processingModal` guard (the modal core enforces the stack)

The character picker is inline. There is no dependency on a separate
`openCharacterSelector`.

### UI list — `rank-ui-list.js`

| Function | Purpose |
|---|---|
| `RankUI.renderRankList(containerOrId, options)` | Flat list, grouped by priority level |
| `RankUI.renderRankCard(rankId, containerOrId?, options?)` | Single card. Returns HTML when `containerOrId` is omitted. |
| `RankUI.renderRankHierarchy(containerOrId, options)` | Hierarchy tree |
| `RankUI.renderRankTree(containerOrId, options)` | Compact tree, used as a picker |
| `RankUI.renderRankSelector(containerOrId, options)` | Dropdown |
| `RankUI.renderRankStatistics(rankId, containerOrId?, options?)` | Stats grid |

`RankUI.registerContainer(containerId, kind, options)` registers a
container for `RankUI.refreshAll()`. Every render registers itself by
default unless `autoRegister: false` is passed.

`RankUI.refresh(containerId)` refreshes one container.
`RankUI.refreshAll()` iterates registered containers and prunes any whose
element is no longer in the document.

Click handling is delegated: one listener per container, tracked via
`WeakMap`, replaced on re-render. Actions are dispatched by
`data-rank-action`: `details`, `edit`, `select`. Callers can override
with `options.onAction`.

Icons come from `Icons.NAME` via `_icon(name)`. Missing icon throws. No
silent empty-string fallback.

Level icons route through `RankQueries.getRankLevelIcon` → `icons.js`.
Rank symbols are displayed as-is (they are user data, and the
`AVAILABLE_SYMBOLS` list is Unicode punctuation, not emoji).

## 14. Cross-domain integration

### Character

| Read | Source |
|---|---|
| Character projection | `CharacterState.getCharacter(id)` |
| All characters | `CharacterState.getAllCharacters()` |

| Write | Caller |
|---|---|
| Rank assignments | `CharacterCommands.addRankAssignment` etc. |
| `activeRankId` / `activeRankNumber` | `CharacterCommands` (derived) |

Rank does not read `CharacterState._getLiveCharacterForMutation`. It does
not write to the character record directly. The `rankAssignments` array
and the two active pointers are domain-owned fields on the character
record; `CharacterCommands` is the only writer.

### Relationship

| Read | Source |
|---|---|
| Committed partners | `RomanceQueries.getActiveCommittedPartners(id)` |

Rank does not read `character.relationships` anywhere. The old fallback
chain is gone.

### Family

| Read | Source |
|---|---|
| Parents of a character | `FamilyQueries.getParents(id)` |
| Children of a character | `FamilyQueries.getChildIds(id)` or `getChildren(id)` (both shapes accepted) |

### Role

`role-queries.js` exposes `getRankSummary(rankId)` which reads rank fields
via `accessors.getRankById`. This means the four fields `id`, `name`,
`symbol`, `priority` must remain on every rank record. They do.

### Romance (reverse direction)

`romance-commands._getExternalMultiPartnerFacts` reads
`character.activeRankId` and asks the rank record for
`allowsMultipleSpouses`. The field must remain on every rank record. It
does. `RankRules.allowsMultipleSpouses(rank)` is the semantic wrapper if
romance wants to route through it.

### Education / Apprenticeship

Rank has **no** interaction with education or apprenticeship. Rank skill
and role skill are separate concepts. If a future feature needs "only a
scholar may hold this rank," the correct place for that policy is
`RankRules.canAssignRank` reading the education domain via a query. It is
not implemented today.

### Death cascade

`RankIssues.handleCharacterDeath` and `RankIssues.removeAllReferencesTo`
are the two integration points. They register via
`registerLifecycleHook('death' | 'delete', ...)` if that API exists, and
are exported for direct call otherwise.

**Caller responsibility:** `CharacterLifecycle.killCharacter` must
trigger `handleCharacterDeath`, either by dispatching the hook or by
calling it directly. `CharacterDeletionCommands.deleteCharacter` must
call `removeAllReferencesTo`. This is not something the rank domain can
enforce from its own code.

## 15. Persistence

Every mutation writes into `masterData.data.ranks` and
`masterData.data.rankInheritanceRules` in memory, then calls
`markDataDirty` via `RankState._syncToMasterData`. Storage flushes on
its own schedule.

`RankCommands.persist()` calls `saveMasterData()` once. It is the only
`saveMasterData` call site in the rank domain.

Batch callers:

- `RankIssues.processAnnualRank` persists once at the end.
- `modals-rank.js` persists once per successful modal.
- External orchestrators persist once after their batch.

Character rank assignments are on the character record and are persisted
by `CharacterState` when `CharacterCommands` writes them. Rank has no
separate storage for assignments.

---

## 16. Lifecycle hooks

`rank-issues.js` and `rank-bootstrap.js` attempt to register:

- `registerLifecycleHook('death', payload)` → `handleCharacterDeath(payload.characterId, { deathYear })`
- `registerLifecycleHook('delete', payload)` → `removeAllReferencesTo(payload.characterId)`

If `registerLifecycleHook` is not defined, both registration attempts are
skipped silently. The exported functions remain available for direct
call. This is the fallback path:

- `CharacterLifecycle.killCharacter` → `RankIssues.handleCharacterDeath`
- `CharacterDeletionCommands.deleteCharacter` → `RankIssues.removeAllReferencesTo`

The rank domain does not reach into the character lifecycle. It exposes
the functions; the character subsystem decides when to invoke them.

## 17. Recursion guards

There are none.

The old `rank-state.js` had `_processingState`. The old
`rank-commands.js` had `_processingCommand`. The old
`rank-assignment.js` had `_processingAssignment`. The old
`modals-rank.js` had `_processingModal`. They are all removed.

Rationale: mutations are synchronous. Commands may call other commands.
The recursion guard on `modals-rank.js` was cleared in a `finally` block
that ran before the modal's `onConfirm` was invoked, so it protected
nothing. The state guard prevented nothing that a single-writer-per-field
discipline does not prevent. The role, education, and apprenticeship
domains have none. Rank now matches.

The one place a re-entrancy concern could theoretically arise is the
lifecycle hook: `handleCharacterDeath` deprecates rank assignments and
triggers a renumber. The renumber reads projections and writes through
`CharacterCommands.updateRankAssignment`, which itself does not emit a
character-death event. No cycle.

## 18. Known deferrals

- **`RankRules.applyDefaults` and `RankState._normaliseRank` are two
  implementations of the same shape.** They are kept separate to avoid a
  load-time dependency between `rank-rules.js` and `rank-state.js`.
  They must be kept in sync. A future consolidation could make
  `RankState` call `RankRules.applyDefaults` if the load order is
  adjusted.

- **`RankAssignment.updateRankSurnameRule` is a delegating shim.** It
  exists because the old file exported it. Once callers are confirmed to
  use `RankCommands.updateRankSurnameRule`, the shim can be removed.

- **`RankAssignment.checkAndFixSpouseInheritance` and
  `RankIssues.checkSpouseInheritance` overlap.** `RankAssignment`'s
  version returns a fix list; `RankIssues`' version returns issue records
  with fix closures. Both are used. The `RankAssignment` version exists
  because `applySpouseInheritanceFixes` in `RankCommands` accepts its
  output shape. A consolidation pass could make `RankIssues` consume
  `RankAssignment.checkAndFixSpouseInheritance` and drop the duplicate
  scan.

- **`RankIssues._findFirstNumberingDiscrepancy` duplicates the grouping
  logic of `RankAssignment.renumberRankHolders`.** Issues must predict
  what the fix will produce. An alternative is a
  `RankAssignment.previewRenumber(rankId)` that returns the diffs without
  writing. Deferred; the current design keeps `RankAssignment` free of a
  read-only preview API.

- **`RankState._normaliseInheritanceRules` drops rules with no child
  reference.** A rule with both `childRankId` and `childRankIdFemale`
  null is dropped at hydration. This is a silent repair of structural
  damage. If you would rather it throw, change the function.

- **`RankIssues.checkNumberingIssues` reports one issue per rank, not
  one per holder.** The fix renumbers the whole rank. For a large rank
  with many discrepancies, only the first is named in the message. The
  fix corrects all of them. This is deliberate.

- **`RomanceCommands._getExternalMultiPartnerFacts` still reads
  `rank.allowsMultipleSpouses` directly.** The rank policy wrapper
  `RankRules.allowsMultipleSpouses` exists; romance has not been updated
  to call it. That is a romance-side change, not a rank-side change.

- **No annual orchestrator at the top level.** `RankIssues.processAnnualRank`
  exists. The application-level annual tick that would call it, along
  with `EducationAnnual.processAnnualEducation` and the mortality
  pipeline, is not written. Out of scope for this domain.

- **`RankState.validateIntegrity` runs at bootstrap but does not throw.**
  Integrity failures are logged as warnings. The application starts so
  that repair tooling is reachable. If you would rather a broken
  catalogue halt boot, change `rank-bootstrap.js`.

## 19. Rules of use

### Do

- Use `RankQueries` for every read.
- Use `RankCommands` for every write.
- Call `RankCommands.persist()` once per batch.
- Read character rank assignments from the character projection, not
  from live character state.
- Read committed partners via `RomanceQueries.getActiveCommittedPartners`.
- Read parents via `FamilyQueries.getParents`.
- Use `RankRules.formatNumber` for display formatting.
- Use `RankRules.classifyNumberingGroup` for grouping decisions.
- Use `RankQueries.getInheritanceSource` — never reimplement it.
- Route character rank assignment writes through `CharacterCommands`.
- Register containers for refresh via `RankUI.registerContainer`.

### Don't

- Don't call `saveMasterData` outside `RankCommands.persist`.
- Don't hold a live rank record outside `RankCommands` — use
  `RankQueries.getRank` (clone) or `RankState.getRank` (clone).
- Don't write `character.rankAssignments`, `character.activeRankId`, or
  `character.activeRankNumber` directly. Use `CharacterCommands`.
- Don't read `character.relationships`. Use `RomanceQueries`.
- Don't call `Math.random` in rules or commands.
- Don't fabricate `0`, `[]`, `null`, or `1250` when a dependency is
  missing. Throw.
- Don't use `||` for numeric values where `0` is valid.
- Don't reintroduce the `_processing` recursion guards.
- Don't reintroduce `RankAssignment.assignRankToCharacter`,
  `deprecateRankAssignment`, `applySpouseInheritanceFixes`, or
  `getInheritanceSource`. All four now live in `RankCommands` or
  `RankQueries`.
- Don't reintroduce `RankCommands.*Direct` helpers. They bypassed every
  boundary.
- Don't read `character.rankAssignments` from `_getLiveCharacterForMutation`.
  Read it off the projection.

## 20. Anti-patterns (removed)

The following patterns existed in the old code and are banned:

- Lazy `_initialize()` on first read. Replaced by explicit
  `hydrateFromMasterData`.
- `saveMasterData` inside every mutation. Replaced by
  `markDataDirty` + one `persist`.
- Public reads returning live canonical records. Replaced by clones.
- `character.relationships` walking for spouse detection. Replaced by
  `RomanceQueries.getActiveCommittedPartners`.
- Duplicated `getInheritanceSource` in two files. Consolidated to
  `RankQueries.getInheritanceSource`.
- `toOrdinal` / `toRoman` hand-rolled in `RankAssignment`. Replaced by
  `RankRules.formatNumber`.
- `1250` year fallback in four files. Removed; `time.js` owns the
  fallback.
- Per-fix `_saveMasterData` calls in `RankIssues`. Replaced by batch
  persist.
- `openCharacterSelector` dependency that did not exist. Replaced by an
  inline character picker.
- `title` / `content` modal options. Replaced by `titleHtml` /
  `contentHtml`.
- `_processingModal` guard that was cleared before the modal closed.
  Removed.
- `refreshAll` walking `.parentElement`. Replaced by container
  registration.
- `_getIcon` with an empty-string fallback. Replaced by `_icon(name)`
  which throws on unknown names.
- Raw Unicode level glyphs in the UI. Replaced by
  `RankQueries.getRankLevelIcon` → `icons.js`.
