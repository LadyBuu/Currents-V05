## 1. Overview

The rank domain owns the **catalogue of formal ranks** and the
**assignment of those ranks to characters**.

A rank is a record in a catalogue: a name, a level, a symbol, a set of
policy flags (numbered, gender-restricted, deprecate-on-death), optional
inheritance configuration, and an optional surname rule. A rank is not
attached to a character — it exists independently.

A rank **assignment** is a record on a character: which rank they hold,
since when, with what number, whether it is active, whether it is
deprecated, and from whom it was inherited.

The rank domain owns:

- the rank catalogue (`RankState`)
- inheritance rules between ranks (`RankState`)
- the arithmetic of numbering holders (`RankAssignment`)
- detection and repair of rank configuration problems (`RankIssues`)
- the modal and list UI for managing ranks (`RankModals`, `RankUI`)

The rank domain does **not** own:

- the character record (`CharacterState`)
- the write path for character fields, including rank assignments
  (`CharacterCommands`)
- relationship facts — who is married to whom (`RomanceQueries`)
- family facts — who is whose parent (`FamilyQueries`)
- numbering display vocabulary — ordinal / roman formatting (`RankRules`)
- role skill (education and apprenticeship own that; rank does not
  interact with role skill at all)

The rank catalogue answers "what does a Duke look like." It does not
answer "is Bruna a Duke." A character's rank assignments answer that
question, and they live on the character record.

## 2. Principles

| Principle | Rule |
|---|---|
| **Single source of truth** | `RankState` owns the rank catalogue. `CharacterState` owns the character record. No other module stores rank data. |
| **Command-query separation** | `RankQueries` reads. `RankCommands` writes. `RankState` provides the state primitives that `RankCommands` calls. |
| **One writer per field** | Rank records: `RankCommands`. Inheritance rules: `RankCommands`. Character rank assignments: `CharacterCommands`. |
| **Fail loud** | Missing required dependency throws at load. Missing required method throws at load. Nothing fabricates `0`, `[]`, `null`, or `1250`. |
| **Reads return clones** | `RankState` public reads return defensive projections. Live records never leave the state layer. |
| **One persist per batch** | Commands mutate in memory and call `markDataDirty` via `RankState`. The caller calls `RankCommands.persist()` once. |
| **No recursion guards** | Mutations are synchronous and side-effect explicit. Commands may chain freely. |
| **Policy is pure** | `RankRules` has no state access, no I/O, no randomness. |
| **Numbering is arithmetic, not policy** | `RankAssignment` computes numbers. `RankRules` classifies which numbering group a holder belongs to. |
| **Issues detect; callers apply** | `RankIssues.checkAll()` returns issues with fix closures. `RankIssues.applyFixes()` applies them. Nothing auto-fixes silently. |
| **One implementation per rule** | The parent/child normalisation, the numbering group classification, and the Roman numeral / ordinal formatters each have a single owner. Duplicates are delegated, not re-implemented. |

modules as long as they are present before any rank operation runs.

## 6. Data schemas

### Rank record (in `RankState`)

```
{
    id:                     string,   unique
    name:                   string,
    priority:               number,   1..10
    numbered:               boolean,
    numberingType:          'reign' | 'ordinal' | 'roman',
    numberingGroup:         'global' | 'parent' | 'spouse' | 'source',
    numberingPrefix:        string,
    numberingSuffix:        string,
    sourceRankId:           string | null,
    inheritanceSource:      'none' | 'parent' | 'spouse',
    symbol:                 string,
    genderRestriction:      'either' | 'male' | 'female',
    locationTypeId:         string | null,
    deprecateOnDeath:       boolean,
    spouseInheritance:      string | null,   // legacy; prefer sourceRankId
    allowsMultipleSpouses:  boolean,
    parentRankId:           string | null,
    customSurnameRule:      boolean,
    surnameConnector:       string,
    surnamePrefix:          string,
    surnameSuffix:          string,
    createdAt:              number | null,
    updatedAt:              number | null
}
```

### Inheritance rule (in `RankState`)

```
{
    childRankId:            string | null,
    childRankIdFemale:      string | null,
    minChildAge:            number,    default 0
    maxChildren:            number | null,
    order:                  number,    default 10
}
```

Stored as `{ [parentRankId]: RankRule[] }`.

### Rank assignment (on the character record)

Written only by `CharacterCommands`.

```
{
    rankId:                 string,
    customTitle:            string | null,
    address:                string | null,
    number: {
        rawNumber:          number,
        display:            string,
        type:               'ordinal' | 'roman' | 'custom',
        groupId:            string | null,
        holdersInGroup:     number | null
    } | null,
    order:                  number,
    isActive:               boolean,
    isDeprecated:           boolean,
    assignedYear:           number | null,
    notes:                  string,
    inheritedFrom:          string | null
}
```

### Character rank pointers

Derived by `CharacterCommands._reconcileRankActives` on every write.
Never written directly.

```
activeRankId:               string | null
activeRankNumber:           number | null
```

Invariant: exactly one non-deprecated assignment has `isActive: true`
when any non-deprecated assignment exists. `activeRankId` matches that
assignment's `rankId`. When no non-deprecated assignment exists,
`activeRankId` and `activeRankNumber` are `null`.

### Coherence rules (enforced by `RankRules.validate`)

- `sourceRankId` present requires `inheritanceSource !== 'none'`.
- `inheritanceSource !== 'none'` requires `sourceRankId` present.
- `numbered && numberingGroup === 'source'` requires
  `inheritanceSource !== 'none'`.
- Self-parent and self-source references are rejected.
- `customSurnameRule === true` requires at least one of
  `surnameConnector`, `surnamePrefix`, `surnameSuffix` to be non-empty.

`applyDefaults` does NOT silently infer `inheritanceSource` from a set
`sourceRankId`. A caller that produces an incoherent record receives an
error, not a guess.

## 7. State — `rank-state.js`

The single in-memory catalogue for ranks and inheritance rules.

### Hydration

```
RankState.hydrateFromMasterData(ranks, inheritanceRules)
RankState.isHydrated()
```

Hydration is explicit. `rank-bootstrap.js` calls it once. Rehydrating
is allowed (`masterDataUpdated` triggers it automatically, and callers
may call it directly for tests). Duplicate rank ids throw.

`hydrateFromMasterData` normalises each record via
`RankRules.applyDefaults` (delegating to the canonical shape), then
applies state-layer post-processing: id preservation, self-reference
guards, `createdAt` / `updatedAt` preservation.

`hydrateFromMasterData` invalidates the accessor cache at the end.
See ACCESSOR CACHE CONTRACT below.

### Public reads (clones)

| Function | Returns |
|---|---|
| `getAllRanks()` | Clone of the rank array |
| `getRank(id)` | Clone or null |
| `getRanksByPriority(p)` | Clone array |
| `getRankHierarchy()` | Array of nodes with `children` arrays |
| `getRankCount()` | Number |
| `getInheritanceRules()` | Clone of the rules map |
| `getInheritanceRulesForRank(id)` | Clone of the rule array |

### Subscriptions

```
RankState.subscribe(callback) -> unsubscribe
```

Receives `{ type, data }` on every mutation. Types: `rankAdded`,
`rankUpdated`, `rankDeleted`, `inheritanceRuleAdded`,
`inheritanceRuleRemoved`, `inheritanceRulesSet`, `stateReloaded`.

### Diagnostics

```
RankState.validateIntegrity() -> { valid: boolean, errors: string[] }
```

Checks: every rank has a valid id, no duplicate ids, priority 1–10,
parent and source references resolve, no self-parent or self-source,
inheritance rules reference existing parents and children.

**Graph consistency only.** Semantic incoherence (e.g. `sourceRankId`
set with `inheritanceSource: 'none'`) is preserved by normalisation and
reported by `RankRules.validate`, not by `validateIntegrity`. This
split is deliberate: integrity is about graph consistency, policy is
about semantics.

Never throws.

### Internal (reserved for `RankCommands`)

`_getRankCanonical(id)`, `_getAllRanksCanonical()`, `_addRank`,
`_updateRank`, `_removeRank`, `_addInheritanceRule`,
`_removeInheritanceRule`, `_setInheritanceRules`, `_indexesRebuild`.

Every mutator syncs `masterData.data.ranks` and
`masterData.data.rankInheritanceRules` in memory, invalidates the
accessor cache, then calls `markDataDirty`. It does not call
`saveMasterData`.

### Accessor cache contract

Three boundaries invalidate the accessor cache (`accessors._rankMap`):

1. **Mutation boundary.** Every mutator in `RankState` calls
   `_syncToMasterData`, which calls `invalidateAccessorCaches`.
2. **Hydration boundary.** `hydrateFromMasterData` calls
   `invalidateAccessorCaches` at the end, so bootstrap and reload paths
   see fresh data.
3. **Cross-tab reload.** `storage.js` invalidates before dispatching
   `masterDataUpdated`, so every domain subscribing to the event sees
   a fresh cache. RankState's own reload handler calls
   `hydrateFromMasterData`, which invalidates again — redundant but
   harmless.

### Namespace

`__owner === 'core/rank/rank-state.js'`. A collision guard throws if
`window.RankState` was previously defined by another module.

## 8. Queries — `rank-queries.js`

### Hard dependencies

- `rank-state.js` (RankState)
- `rank-rules.js` (RankRules)
- `rank-constants.js` (`RANK_LEVELS`, `AVAILABLE_SYMBOLS`) — the module
  throws at load if either is missing
- `character-state.js` (CharacterState)
- `time.js` (`getCurrentYear`, `calculateAge`)

### Rank queries

Delegate to `RankState`. Every function returns clones.

`getRank`, `getAllRanks`, `getRanksByPriority`, `getRankHierarchy`,
`getRankCount`, `getInheritanceRules`, `getInheritanceRulesForRank`.

### Level helpers

| Function | Source |
|---|---|
| `getRankLevelName(priority)` | `RANK_LEVELS` in `rank-constants.js` |
| `getRankLevelDescription(priority)` | `RANK_LEVELS` |
| `getRankLevelIcon(priority)` | `icons.js` via `getRankLevelIcon` |
| `getAvailableSymbols()` | `AVAILABLE_SYMBOLS` |

Level names come from constants. Level icons come from `icons.js` and
return SVG markup. A missing `RANK_LEVELS` throws at load. A missing
`getRankLevelIcon` returns `''` (icons.js is required at the module
level via `rank-ui-list.js`, so this only fires in bare test harnesses).

### Character queries

| Function | Behaviour |
|---|---|
| `getCharactersWithRank(rankId, includeDeprecated)` | Reads `character.rankAssignments` from the projection. Includes any character whose active pointer matches even if the assignment array is stale (defensive). |
| `getRankHolderCount(rankId, includeDeprecated)` | Length of the above. |
| `getRankHolderStats(rankId)` | Counts by gender, living/deceased, age band. Characters whose age cannot be resolved are counted separately, not as minors. |
| `getRankAssignmentsForCharacter(characterId, includeDeprecated)` | Assignment array from the projection, sorted by `order`. |
| `getActiveRankAssignment(characterId)` | The assignment matching the active pointer, or the first `isActive` one. |

### Spouse inheritance queries

`getSpouseInheritanceRanks(characterId)` — the ranks the character is
**entitled** to by virtue of their current committed partner's rank.

`getReceivedSpouseInheritanceRanks(characterId)` — the ranks the
character **actually holds** where `inheritedFrom` is set.

Both read committed partners via
`RomanceQueries.getActiveCommittedPartners`. Neither walks
`character.relationships`. If `RomanceQueries` is not loaded,
`getSpouseInheritanceRanks` returns `[]`; `getReceivedSpouseInheritanceRanks`
continues to work (it reads `inheritedFrom` off the assignment, not the
romance domain).

### Parent / child id normalisation (shared)

```
RankQueries.getParentIds(characterId) -> string[]
RankQueries.getChildIds(characterId) -> string[]
```

Single normalisers for `FamilyQueries`' multiple return shapes:

- `{ father, mother }` object.
- Array of edges (`{ parentId, parentType, ... }`).
- Array of projections (`{ id, activeRankId }`).
- Array of strings (character ids).

Both deduplicate. Both return `[]` on missing `FamilyQueries`, missing
character, or `FamilyQueries` throw.

**Shared with `RankAssignment` (for numbering group filtering) and
`RankIssues` (for child inheritance detection).** This is the single
implementation. Do not reimplement the normalisation in other modules.

### Inheritance source (canonical)

```
RankQueries.getInheritanceSource(characterId, rankId) -> string | null
```

The single implementation. Uses `RomanceQueries` for spouse
inheritance and `FamilyQueries.getParents` for parent inheritance. The
parent reference normaliser (`_normaliseParentRef`) is internal to this
file; `getParentIds` is the public face of the same logic.

Precedence:
1. `rank.sourceRankId` with `inheritanceSource === 'spouse'` (via
   `RomanceQueries`).
2. `rank.spouseInheritance` (legacy field).
3. `rank.sourceRankId` with `inheritanceSource === 'parent'` (via
   `FamilyQueries`).

### Surname rule queries

`getRanksWithSurnameRules()`, `getRankSurnameRule(rankId)`.

### Validation helper

`isValidRank(rank)` — delegates to `RankRules.validate`.

## 9. Rules — `rank-rules.js`

Pure policy. No state access. No side effects.

### Shape

```
RankRules.applyDefaults(raw) -> RankRecord
```

Produces a normalised record shape from raw input. Does not assign `id`
or timestamps — that is the command layer's job.

The function preserves unknown fields (forward compatibility). It
coerces known fields. Coherence: if `sourceRankId === null` but
`inheritanceSource !== 'none'`, the inheritance source is reset to
`'none'` (safe correction). If `sourceRankId` is set but
`inheritanceSource === 'none'`, it is NOT corrected — `validate()`
rejects the combination. This is the "do not guess" rule.

### Validation

```
RankRules.validate(rank) -> { valid, errors }
RankRules.validatePatch(current, patch) -> { valid, errors }
RankRules.validateInheritanceRule(rule) -> { valid, errors }
```

`validate` checks: name non-empty, priority integer 1–10, symbol
non-empty and in `AVAILABLE_SYMBOLS`, gender restriction valid, numbering
config coherent, inheritance config coherent, surname rule coherent,
no self-parent, no self-source.

`validatePatch` merges the patch onto the current record and validates
the result. This catches coherence errors a per-field check would miss.

`validateInheritanceRule` checks shape and coherence. It does not check
that referenced ranks exist — that is a state question.

### Assignment policy

```
RankRules.canAssignRank(character, rank, options) -> { valid, reason? }
RankRules.canDeprecateRankAssignment(character, rankId) -> { valid, reason? }
```

`canAssignRank` checks: character exists and is not deleted or deceased,
gender restriction, no duplicate non-deprecated assignment,
`numberingGroup: 'source'` ranks require an inheritance source. It reads
only from the supplied arguments and never touches state.

### Romance bridge

```
RankRules.allowsMultipleSpouses(rank) -> boolean
```

Exists so that `RomanceCommands` can ask "does this rank permit multiple
spouses" without reading the field directly.

### Numbering classification

```
RankRules.classifyNumberingGroup(rank, sourceId) -> string
```

Returns the bucket key for a holder: `'global'` or a source character id.
When the rank wants grouping but no source is available, returns
`'global'`. The assignment layer decides whether the missing source is
a hard error.

### Number formatting

```
RankRules.formatNumber(n, type) -> string
```

`'ordinal'` → `'1st'`, `'2nd'`, `'3rd'`, `'4th'`, `'11th'`, `'21st'`…
`'roman'` / `'reign'` → `'I'`, `'II'`, `'III'`… up to the range of
`window.formatRomanFull` (1–3999 when names.js is loaded; 1–20 via
`window.formatRomanNumeral`; 1–39 via the local fallback).

Handles the teen exceptions correctly (`11th`, `12th`, `13th`).

**Delegation:**

- `_toOrdinal` delegates to `window.formatOrdinal` (formatting.js) when
  present, falls back to local.
- `_toRoman` delegates to `window.formatRomanFull` (names.js), then
  `window.formatRomanNumeral` (formatting.js), then the local 1–39
  table. Full Roman range is available when names.js is loaded.

### Coherence policy

`applyDefaults` does not fabricate inheritance semantics. A record with
`sourceRankId` set but `inheritanceSource: 'none'` is rejected by
`validate`. A record with `inheritanceSource` set but `sourceRankId:
null` is silently reset (safe, because the record cannot fulfill the
inheritance claim without a target).

## 10. Commands — `rank-commands.js`

The write boundary. Every public command returns
`{ success: true, ... }` or `{ success: false, reason }`. Domain errors
never throw.

### Persistence

```
RankCommands.persist() -> { success, reason? }
```

The only `saveMasterData` call site in the rank domain. Callers batch:
mutate, then persist once.

`persist()` uses Pattern A from `storage.js`'s DOMAIN PERSIST CONTRACT:
it inspects the boolean return of `saveMasterData()` and, on failure,
returns `{ success: false, reason }` carrying `getLastSaveError().message`
when available. It does NOT assume `saveMasterData()` throws.

### Rank CRUD

```
createRank(rankData)              -> { success, rank? }
updateRank(rankId, updates)       -> { success, rank? }
deleteRank(rankId, options)       -> { success, ... }
```

`createRank` runs `RankRules.applyDefaults`, checks cross-rank
references, runs `RankRules.validate`, stamps the id and timestamps,
writes via `RankState._addRank`.

`updateRank` checks that any new parent or source reference exists,
runs `RankRules.validatePatch`, writes via `RankState._updateRank`.

`deleteRank` refuses if there are non-deprecated holders or referencing
ranks, unless `{ force: true }`. With force: it removes every holder's
assignment via `CharacterCommands.removeRankAssignment`, nulls every
`parentRankId` and `sourceRankId` reference in other ranks, drops the
rank's own inheritance rules, and deletes the record. Returns counts of
everything cleaned.

### Inheritance rules

```
addInheritanceRule(parentRankId, rule)         -> { success, rule? }
removeInheritanceRule(parentRankId, ruleIndex) -> { success }
setInheritanceRules(parentRankId, rules)       -> { success }
```

`setInheritanceRules` is bulk replacement.

### Assignment (delegates to `CharacterCommands`)

```
assignRankToCharacter(characterId, rankId, options) -> { success, assignment?, ... }
deprecateRankAssignment(characterId, rankId)        -> { success, unchanged? }
removeRankAssignment(characterId, rankId)           -> { success }
setActiveRank(characterId, rankId)                  -> { success, unchanged? }
clearActiveRank(characterId)                        -> { success, unchanged? }
```

`assignRankToCharacter` validates via `RankRules.canAssignRank`,
computes the numbering info via
`RankAssignment.getNextRankNumber(rankId, characterId, sourceCharacterId)`
(3 args; the previous `characterName` and `gender` were dead
parameters), and writes via `CharacterCommands.addRankAssignment`.

The `options.number` field accepts four forms: undefined (auto-compute
for numbered ranks), `null` (no number), a number (raw; display computed
via `RankRules.formatNumber`), or an object (passed through as-is).

### Bulk operations

```
bulkAssignRank(characterIds, rankId, options) -> { totalProcessed, successful, failed, results, errors }
bulkDeprecateRank(characterIds, rankId)       -> { totalProcessed, successful, failed, succeeded, errors }
```

Each character is attempted independently.

### Numbering

```
renumberRankHolders(rankId)      -> { success, fixedCount, errors }
rebuildAllRankNumbering()        -> { success, totalFixed, fixedCounts, errors }
```

Both delegate to `RankAssignment`.

### Surname rule

```
updateRankSurnameRule(rankId, ruleSettings) -> { success, rank? }
```

`ruleSettings` shape: `{ enabled, connector, prefix, suffix }`. Delegates
to `updateRank` so coherence checks apply.

### Spouse inheritance

```
applySpouseInheritanceFixes(fixes) -> { applied, failed, errors }
```

`fixes` is an array shaped as produced by
`RankIssues.checkSpouseInheritance` or by
`RankAssignment.checkAndFixSpouseInheritance`: `{ characterId, rankId,
spouseId, spouseName, sourceRankName, ... }`.

Does not persist — the caller persists once after the batch.

### Death hook

```
deprecateRanksOnDeath(characterId, options) -> { deprecated, renumbered, errors }
```

Scans the character's non-deprecated assignments, finds every rank with
`deprecateOnDeath: true`, deprecates each, and renumbers the affected
ranks. Does not persist. Called by `RankIssues.handleCharacterDeath`
and by the death cascade.

## 11. Assignment — `rank-assignment.js`

Numbering arithmetic. No assignment writes.

### Get next number

```
RankAssignment.getNextRankNumber(rankId, characterId, sourceCharacterId)
    -> NumberInfo | null
```

Returns `null` for unnumbered ranks. Otherwise returns
`{ rawNumber, display, type, groupId, holdersInGroup }`.

Algorithm:

1. Collect every character other than `characterId` who holds a
   non-deprecated assignment for `rankId`.
2. Filter to the holder's numbering group. Group key comes from
   `RankRules.classifyNumberingGroup(rank, sourceCharacterId)`.
3. Sort. Reign-numbered ranks sort by assignment year ascending.
   Ordinal-numbered ranks sort by birth year ascending. Both tie-break
   by character name.
4. `nextRaw = filtered.length + 1`.
5. `display = RankRules.formatNumber(nextRaw, rank.numberingType)`.

The 3-argument signature replaced a 5-argument signature. The two
removed arguments (`characterName`, `gender`) were never read inside
the function. `rank-commands.js::assignRankToCharacter` is the only
caller.

### Renumber holders

```
RankAssignment.renumberRankHolders(rankId) -> { success, fixedCount, errors }
```

Groups holders, sorts each group, walks each holder in order, and
compares the recorded number against the expected one. On mismatch,
writes via `CharacterCommands.updateRankAssignment`.

Group key precedence (via `getHolderGroupKey`):

1. `assignment.inheritedFrom` (what the assignment was created with).
2. `RankQueries.getInheritanceSource(characterId, rankId)` (resolves
   from current state).
3. `'unknown'` bucket.

### Get holder group key (exported)

```
RankAssignment.getHolderGroupKey(rank, character, assignment) -> string
```

The single implementation of the numbering group classification rule.
Shared with `RankIssues._findFirstNumberingDiscrepancy` so that
"predict what renumber will produce" and "produce it" agree.

Precedence is the same as the group key used by `renumberRankHolders`.

### Fix all numbering for a character

```
RankAssignment.fixAllNumberingForCharacter(characterId) -> { fixedCount, ranksProcessed, errors }
```

For each numbered rank the character holds, renumbers the whole rank.

### Surname generation

```
RankAssignment.generateSurnameFromRankRule(character, context) -> string | null
```

`context.locationName` is the base. The rank's
`connector` / `prefix` / `suffix` are applied. Capitalises the first
letter.

### Spouse inheritance detection

```
RankAssignment.checkAndFixSpouseInheritance() -> { success, fixes, count }
```

Scans the population for characters who should hold a rank by virtue of
spouse inheritance but do not. Returns fix data records shaped for
`RankCommands.applySpouseInheritanceFixes`.

Reads committed partners via `RomanceQueries`. Never walks
`character.relationships`. If `RomanceQueries` is not loaded, returns
`{ success: false, reason: 'RomanceQueries.getActiveCommittedPartners is required.' }`.

**Relationship to `RankIssues.checkSpouseInheritance`:** both scan for
the same condition. They return different shapes (fix-data records vs
`RankIssue` with fix closure). They are intentionally NOT consolidated.
See §17 for the rationale.

## 12. Issues — `rank-issues.js`

Detection and repair. Every issue carries a `fix` closure that returns
`{ success, reason? }`.

### Main checker

```
RankIssues.checkAll() -> { success, issues, count, bySeverity }
```

`bySeverity` is `{ error, warning, info }`, each an array.

### Issue types

| Type | Severity | Fix |
|---|---|---|
| Spouse Inheritance | error | `RankCommands.assignRankToCharacter` with `inheritedFrom` set |
| Child Inheritance | warning | `RankCommands.assignRankToCharacter` |
| Gender Mismatch | error | `RankCommands.deprecateRankAssignment` |
| Numbering Error | error | `RankCommands.renumberRankHolders` |
| Deprecation Error | error | `RankCommands.deprecateRankAssignment` |
| Broken Inheritance Rule | error | `RankCommands.removeInheritanceRule` (or manual for orphan parents) |

Numbering issues report one issue per rank. The message names the first
discrepant holder and clarifies that re-numbering fixes all holders.

### Batch apply

```
RankIssues.applyFixes(issues, options) -> { applied, failed, skipped, errors }
```

Applies every `issue.fix()` in order. `options.filter` can restrict
which issues are applied. Does not persist.

### Annual pipeline

```
RankIssues.processAnnualRank(year, options) -> AnnualEnvelope
```

Envelope shape:

```
{
    year,
    status:                 'completed' | 'completed_with_errors' | 'partial',
    issueCount,
    issuesBySeverity:       { error, warning, info },
    fixResults:             { applied, failed, skipped, errors },
    renumberResults:        { totalFixed, fixedCounts, errors },
    persisted:              boolean,
    persistError:           string | null
}
```

Pipeline: detect → apply fixes → rebuild all numbering → persist once.
`options.skipFixes: true` runs detection only. `options.persist: false`
skips the final save.

### Death hook

```
RankIssues.handleCharacterDeath(characterId, options) -> { success, deprecated, renumbered, errors }
```

Delegates to `RankCommands.deprecateRanksOnDeath`. Does not persist.

Called by `CharacterLifecycle._notifyCrossDomainDeath`. There is no
listener registry and no lifecycle hook registration — the character
subsystem calls this function directly.

### Hard-delete cleanup

```
RankIssues.removeAllReferencesTo(characterId) -> { success, cleaned, ranksRenumbered, renumberErrors }
```

The character's own assignments vanish with the record. This function
scans every other character for assignments whose `inheritedFrom` names
the deleted character, nulls those pointers, and renumbers the affected
ranks. Does not persist.

Called by `CharacterDeletionCommands._dispatchCleanup`.

### Delegated helpers

`rank-issues.js` delegates three scans to their canonical owners:

- `_getParentIds` → `RankQueries.getParentIds`
- `_getChildIds` → `RankQueries.getChildIds`
- `_resolveHolderGroupKey` → `RankAssignment.getHolderGroupKey`

The three scans were previously duplicated inline. Each duplicate was
byte-for-byte identical (or a subset) of the canonical version.
Delegation eliminates the drift risk.

The load-time guard verifies all three delegations are available before
the module loads. Deploying `rank-issues.js` against a pre-Phase-3
`rank-queries.js` or a pre-Phase-4 `rank-assignment.js` throws at load.

## 13. Modals and UI

### Modals — `modals-rank.js`

| Function | Purpose |
|---|---|
| `RankModals.openCreateRankModal(options)` | Create rank modal. |
| `RankModals.openEditRankModal(rankId, options)` | Same fields, pre-populated. |
| `RankModals.openAssignRankModal(options)` | Inline character picker. `options.mode: 'bulk'` enables multi-select. |
| `RankModals.openRankDetailsModal(rankId, options)` | Detail view with stats, config, inheritance rules. |

Every modal:

- passes `titleHtml` and `contentHtml` to `openModal` (the modal core
  reads these names)
- calls `RankCommands.*` only
- calls `RankCommands.persist()` exactly once per successful write
- shows a toast on success or failure via `ui.js::showToast`
- has no `_processingModal` guard (the modal core enforces the stack)
- **reads every input via `modal.element.querySelector`**

The character picker is inline. There is no dependency on a separate
`openCharacterSelector`.

### Return-value contract (rank-ui-list.js)

| Function | Return |
|---|---|
| `renderRankList(container, options)` | `boolean` |
| `renderRankHierarchy(container, options)` | `boolean` |
| `renderRankTree(container, options)` | `boolean` |
| `renderRankSelector(container, options)` | `boolean` |
| `renderRankCard(rankId, container?, options?)` | `string \| null` |
| `renderRankStatistics(rankId, container?, options?)` | `string \| null` |

The container-writing renderers return `boolean` (`true` on success).
The card and statistics renderers return HTML (both when called without
a container and when written to one) or `null` when the rank is missing.

### Hierarchy CSS contract

`renderRankHierarchy` emits elements with class
`rank-hierarchy-node` and attribute `data-depth="N"` where N is the
nesting level. Presentation is owned by CSS. The stylesheet must define
rules such as:

```css
.rank-hierarchy-node[data-depth="0"] { padding-left: 0; }
.rank-hierarchy-node[data-depth="1"] { padding-left: 20px; }
.rank-hierarchy-node[data-depth="2"] { padding-left: 40px; }
.rank-hierarchy-node[data-depth="3"] { padding-left: 60px; }
.rank-hierarchy-node[data-depth="4"] { padding-left: 80px; }
```

Without these rules, hierarchy nodes render flat (depth 0 visually).
The renderer no longer emits inline `margin-left`.

### UI list — `rank-ui-list.js`

| Function | Purpose |
|---|---|
| `RankUI.renderRankList(containerOrId, options)` | Flat list, grouped by priority level |
| `RankUI.renderRankCard(rankId, containerOrId?, options?)` | Single card. Returns HTML when `containerOrId` is omitted. |
| `RankUI.renderRankHierarchy(containerOrId, options)` | Hierarchy tree |
| `RankUI.renderRankTree(containerOrId, options)` | Compact tree, used as a picker |
| `RankUI.renderRankSelector(containerOrId, options)` | Dropdown |
| `RankUI.renderRankStatistics(rankId, containerOrId?, options?)` | Stats grid |

`RankUI.registerContainer(containerId, kind, options)` registers a
container for `RankUI.refreshAll()`. Every render registers itself by
default unless `autoRegister: false` is passed.

`RankUI.refresh(containerId)` refreshes one container. Returns

with `options.onAction`.

Icons come from `Icons.NAME` via `_icon(name)`. Missing icon throws.
`escapeHtml` is required at load (formatting.js). Level icons route
through `RankQueries.getRankLevelIcon` → `icons.js`.

## 14. Cross-domain integration

### Character

| Read | Source |
|---|---|
| Character projection | `CharacterState.getCharacter(id)` |
| All characters | `CharacterState.getAllCharacters()` |

| Write | Caller |
|---|---|
| Rank assignments | `CharacterCommands.addRankAssignment` etc. |
| `activeRankId` / `activeRankNumber` | `CharacterCommands` (derived) |

Rank does not read `CharacterState._getLiveCharacterForMutation`. It
does not write to the character record directly. The `rankAssignments`
array and the two active pointers are domain-owned fields on the
character record; `CharacterCommands` is the only writer.

### Relationship

| Read | Source |
|---|---|
| Committed partners | `RomanceQueries.getActiveCommittedPartners(id)` |

Rank does not read `character.relationships` anywhere. `RomanceQueries`
is an **optional** dependency — see §16.

### Family

| Read | Source |
|---|---|
| Parents of a character | `FamilyQueries.getParents(id)` via `RankQueries.getParentIds` |
| Children of a character | `FamilyQueries.getChildIds(id)` or `getChildren(id)` via `RankQueries.getChildIds` |

`FamilyQueries` is a **required** dependency. Parent inheritance is
fundamental to the rank domain.

### Role

`role-queries.js` exposes `getRankSummary(rankId)` which reads rank
fields via `accessors.getRankById`. This means the four fields `id`,
`name`, `symbol`, `priority` must remain on every rank record. They do.

### Romance (reverse direction)

`romance-commands._getExternalMultiPartnerFacts` reads
`character.activeRankId` and asks the rank record for
`allowsMultipleSpouses`. The field remains on every rank record.
`RankRules.allowsMultipleSpouses(rank)` is the semantic wrapper if
romance wants to route through it.

### Education / Apprenticeship

Rank has no interaction with education or apprenticeship. If a future
feature needs "only a scholar may hold this rank," the correct place
for that policy is `RankRules.canAssignRank` reading the education
domain via a query. Not implemented today.

### Death cascade

`RankIssues.handleCharacterDeath` and
`RankIssues.removeAllReferencesTo` are the two integration points.

**Caller responsibility:** `CharacterLifecycle.killCharacter` must
trigger `handleCharacterDeath`, either by calling it directly or via
its own `_notifyCrossDomainDeath`. `CharacterDeletionCommands.deleteCharacter`
must call `removeAllReferencesTo`. This is not something the rank
domain can enforce from its own code.

The rank domain exposes the functions; the character subsystem
dispatches them directly. There is no listener registry and no
`registerLifecycleHook` mechanism.

## 15. Persistence

Every mutation writes into `masterData.data.ranks` and
`masterData.data.rankInheritanceRules` in memory, invalidates the
accessor cache, and calls `markDataDirty` via
`RankState._syncToMasterData`. Storage flushes on its own schedule.

`RankCommands.persist()` calls `saveMasterData()` once. It is the only
`saveMasterData` call site in the rank domain.

Batch callers:

- `RankIssues.processAnnualRank` persists once at the end.
- `modals-rank.js` persists once per successful modal.
- External orchestrators persist once after their batch.

Character rank assignments are on the character record and are
persisted by `CharacterState` when `CharacterCommands` writes them.
Rank has no separate storage for assignments.

### Domain persist contract

`RankCommands.persist()` uses Pattern A from `storage.js`'s DOMAIN
PERSIST CONTRACT:

```javascript
var ok = window.saveMasterData();
if (ok === true) return { success: true };
var lastError = window.getLastSaveError();
return {
    success: false,
    reason: lastError && lastError.message
        ? lastError.message
        : 'saveMasterData returned false'
};
```

`saveMasterData()` returns a boolean and does NOT throw on write
failure. It must be inspected, not wrapped in try/catch that assumes a
throw. `name-commands.js` was broken by this assumption (Pattern C);
`rank-commands.js` uses Pattern A correctly.

## 16. Required vs optional dependencies

Bootstrap verifies dependencies in two categories.

**REQUIRED** — absence means the rank domain cannot function. Bootstrap
throws. The application does not start with a broken rank domain.

| Module / global | Why required |
|---|---|
| `RankRules`, `RankState`, `RankQueries`, `RankCommands`, `RankAssignment`, `RankIssues`, `RankUI`, `RankModals` | Core rank modules |
| `masterData`, `markDataDirty`, `saveMasterData` | Persistence |
| `getCharacters`, `getCharacterById` | Character enumeration |
| `getCurrentYear`, `calculateAge` | Time facts |
| `generateId` | Ids |
| `CharacterState`, `CharacterCommands` (+ the rank-assignment methods) | Rank assignment writes |
| `FamilyQueries.getParents` | Parent inheritance resolution |
| `RANK_LEVELS` (`rank-constants.js`) | Priority names; required by `rank-queries.js` and `modals-rank.js` |
| `getRankLevelIcon` (`icons.js`) | Level icon rendering |

**OPTIONAL** — absence degrades a specific feature. Bootstrap warns.
The application starts.

| Module / global | Feature impact when absent |
|---|---|
| `RomanceQueries.getActiveCommittedPartners` | Spouse inheritance (`inheritanceSource: 'spouse'`) cannot resolve its source. All other rank features work. |
| `CharacterLifecycle.killCharacter` | The death cascade does not call `RankIssues.handleCharacterDeath` automatically. Callers must invoke it directly after a character dies. |
| `SkillUtils`, `EducationCommands`, `EducationQueries` | No current rank feature depends on these. Listed as optional to detect a future dependency that lacks a bootstrap update. |
| `Icons`, `openModal`, `closeTopModal`, `_showToast`, `showToast` | UI-only. Their absence fails `RankUI` / `RankModals` at their own load, not at bootstrap. |

### Why `RomanceQueries` is optional

The rank catalogue's core features — create, edit, delete, list, assign,
deprecate, renumber, check integrity — do not touch `RomanceQueries`.
Only the spouse-inheritance scan uses it, and that scan only matters for
ranks configured with `inheritanceSource: 'spouse'`.

`rank-queries.js`, `rank-assignment.js`, and `rank-issues.js` all
already degrade gracefully when `RomanceQueries` is absent:

- `RankQueries.getInheritanceSource` returns `null` for spouse-
  inheritance resolution.
- `RankAssignment.checkAndFixSpouseInheritance` returns a specific
  failure naming the missing module.
- `RankIssues._checkSpouseInheritance` returns `[]`.

Bootstrap's previous behavior — throw — was the only place that
hard-failed. It was a design inconsistency, not a correctness guarantee.
The current design matches the actual dependency posture of the code
paths.

### Why `FamilyQueries` is required

Parent inheritance (`inheritanceSource: 'parent'`) is a fundamental rank
feature. A world with a rank catalogue and no parent domain has no way
to resolve parent inheritance, and the child-inheritance scan cannot
run. `RankRules` treats parent inheritance as a first-class source, not
an optional extension. The classification reflects this.

## 17. Design deferrals

These are known, documented decisions to defer work rather than do it
now.

### `RankIssues.checkSpouseInheritance` and `RankAssignment.checkAndFixSpouseInheritance` are not consolidated

Both scan the population for the same condition (a character is married
to a rank holder whose rank grants spouse inheritance but does not hold
the inherited rank). They return different shapes:

- `RankAssignment.checkAndFixSpouseInheritance` returns fix-data records
  (`{ characterId, rankId, spouseId, spouseName, ... }`), consumed by
  `RankCommands.applySpouseInheritanceFixes`.
- `RankIssues.checkSpouseInheritance` returns `RankIssue` records
  carrying severity, fix label, human-readable message, and fix closures.

Consolidation would require either:

1. `RankCommands.applySpouseInheritanceFixes` accepting `RankIssue`
   records (which would make `RankCommands` depend on `RankIssues` —
   a new coupling), or
2. `RankIssues` reconstructing `RankIssue` metadata from fix-data
   records (which would duplicate the classification logic the two
   scans currently share).

Neither is a net simplification today. The scan is cheap
(O(population × partners)); duplication is not a performance concern.
The two could diverge in the future if `RankIssues` adds severity
filtering or policy controls that `RankCommands` does not have. Keeping
them separate preserves that flexibility.

### `modals-rank.js` inline styles

The modals use inline `style=` attributes for layout. Every other modal
file in the tree uses some inline styles, but `modals-rank.js` uses more
than the others.

Extraction to classes (`rank-modal__field`, `rank-modal__grid-2`,
`rank-modal__section`, etc.) is deferred to a follow-up PR that touches
only `modals-rank.js` and a new `rank-modals.css`. The correctness fixes
in this revision (modal input scoping, options shadowing, escapeHtml
requirement, DEFAULT_SYMBOL, RANK_LEVELS requirement, enum reference)
are independent of the extraction.

The extraction is presentation-only. It does not fix bugs. It is
documented here so a future contributor knows the inline styles are a
known deferral, not an oversight.

### `spouseInheritance` legacy field

`rank.spouseInheritance` is a legacy field used by rank records created
before the refactor. New code reads it as a fallback when
`inheritanceSource === 'spouse'` and `sourceRankId` is null. New ranks
should not set it; `inheritanceSource` + `sourceRankId` is the
canonical shape.

The field is not scheduled for removal until every persisted record is
confirmed to use the canonical shape.

## 18. Rules of use

### Do

- Use `RankQueries` for every read.
- Use `RankCommands` for every write.
- Call `RankCommands.persist()` once per batch.
- Read character rank assignments from the character projection, not
  from live character state.
- Read committed partners via `RomanceQueries.getActiveCommittedPartners`.
- Read parents via `RankQueries.getParentIds` (which delegates to
  `FamilyQueries.getParents`).
- Use `RankRules.formatNumber` for display formatting.
- Use `RankRules.classifyNumberingGroup` for grouping decisions.
- Use `RankQueries.getInheritanceSource` — never reimplement it.
- Use `RankAssignment.getHolderGroupKey` when a caller needs to predict
  which group a holder belongs to.
- Route character rank assignment writes through `CharacterCommands`.
- Register containers for refresh via `RankUI.registerContainer`.
- Read modal inputs via `modal.element.querySelector`, never
  `document.getElementById`.

### Don't

- Don't call `saveMasterData` outside `RankCommands.persist`.
- Don't hold a live rank record outside `RankCommands` — use
  `RankQueries.getRank` (clone) or `RankState.getRank` (clone).
- Don't write `character.rankAssignments`, `character.activeRankId`, or
  `character.activeRankNumber` directly. Use `CharacterCommands`.
- Don't read `character.relationships`. Use `RomanceQueries`.
- Don't read `character.motherId` or `character.fatherId`. Use
  `FamilyQueries` (or `RankQueries.getParentIds`).
- Don't call `Math.random` in rules or commands.
- Don't fabricate `0`, `[]`, `null`, or `1250` when a dependency is
  missing. Throw or return the documented empty value.
- Don't use `||` for numeric values where `0` is valid.
- Don't reintroduce the `_processing` recursion guards.
- Don't reintroduce `RankAssignment.assignRankToCharacter`,
  `deprecateRankAssignment`, `applySpouseInheritanceFixes`, or
  `getInheritanceSource`. All four live in `RankCommands` or
  `RankQueries`.
- Don't reintroduce `RankCommands.*Direct` helpers.
- Don't read `character.rankAssignments` from `_getLiveCharacterForMutation`.
  Read it off the projection.
- Don't use `document.getElementById` inside a modal. Use
  `modal.element.querySelector`.
- Don't pass 5 arguments to `RankAssignment.getNextRankNumber`. It takes
  3 (`rankId`, `characterId`, `sourceCharacterId`).
- Don't assume `saveMasterData()` throws. Inspect the boolean.

## 19. Anti-patterns (removed)

The following patterns existed in the old code and are banned:

- Lazy `_initialize()` on first read. Replaced by explicit
  `hydrateFromMasterData`.
- `saveMasterData` inside every mutation. Replaced by `markDataDirty` +
  one `persist`.
- Public reads returning live canonical records. Replaced by clones.
- `character.relationships` walking for spouse detection. Replaced by
  `RomanceQueries.getActiveCommittedPartners`.
- Duplicated `getInheritanceSource` in two files. Consolidated to
  `RankQueries.getInheritanceSource`.
- Duplicated `_getParentIds` and `_getChildIds` in three files.
  Consolidated to `RankQueries.getParentIds` / `getChildIds`.
- Duplicated `_resolveHolderGroupKey` in two files. Consolidated to
  `RankAssignment.getHolderGroupKey`.
- `toOrdinal` / `toRoman` hand-rolled in `RankAssignment`. Replaced by
  `RankRules.formatNumber`, which delegates to canonical formatters.
- `1250` year fallback in four files. Removed; `time.js` owns the
  fallback.
- Per-fix `_saveMasterData` calls in `RankIssues`. Replaced by batch
  persist.
- `openCharacterSelector` dependency that did not exist. Replaced by an
  inline character picker.
- `title` / `content` modal options. Replaced by `titleHtml` /
  `contentHtml`.
- `_processingModal` guard that was cleared before the modal closed.
  Removed.
- `refreshAll` walking `.parentElement`. Replaced by container
  registration.
- `_getIcon` with an empty-string fallback. Replaced by `_icon(name)`
  which throws on unknown names.
- Raw Unicode level glyphs in the UI. Replaced by
  `RankQueries.getRankLevelIcon` → `icons.js`.
- Inline `margin-left` on hierarchy nodes. Replaced by `data-depth`
  attribute + CSS rules.
- `document.getElementById` inside modals. Replaced by
  `modal.element.querySelector`.
- `var options` shadowing inside modal `onConfirm` handlers. Renamed
  to avoid shadowing; the outer `options` is correctly referenced.
- `[1, 2, 3, 4, 5]` priority fallback in `_buildPriorityOptions`.
  Removed; `RANK_LEVELS` is required.
- Hardcoded enum literals in modal dropdown builders. Replaced by
  references to `window.NUMBERING_TYPE`, `window.NUMBERING_GROUP`,
  `window.INHERITANCE_SOURCE`.
- Hardcoded `'⟡'` fallback. Replaced by `DEFAULT_SYMBOL` from
  `window.DEFAULT_RANK.symbol`.
- `_escapeHtml` fallback chain. Removed; `formatting.js` is required.
- Silent toast no-op when `ui.js` is missing. Replaced by a load-time
  requirement + a runtime throw in `_toast`.

## 20. Version history

**v1 — original design.** Rank catalogue plus assignment, both in the
rank folder. Lazy state init. `saveMasterData` on every mutation.
Assignment logic in `rank-assignment.js` with its own write path.

**v2 — issue detection added.** `rank-issues.js` introduced.
Auto-fix closures. Still coupled to `character.relationships` and
`masterData` directly.

**v3 — integration refactor.**

- `RankState` rewritten: explicit hydration, clone-returning reads,
  `_`-prefixed mutators, `validateIntegrity`, reload on
  `masterDataUpdated`, no internal persistence.
- `rank-rules.js` introduced as a pure policy layer.
- `rank-queries.js` rewritten to read `character.rankAssignments` off
  the character projection and to use `RomanceQueries` for spouse facts.
- `rank-commands.js` rewritten as the single write boundary with
  `persist()`, `deprecateRanksOnDeath`, and cross-rank reference checks.
- `rank-assignment.js` trimmed to numbering arithmetic only.
- `rank-issues.js` rewritten with `processAnnualRank`,
  `handleCharacterDeath`, and `removeAllReferencesTo`.
- `modals-rank.js` rewritten with `titleHtml` / `contentHtml`, inline
