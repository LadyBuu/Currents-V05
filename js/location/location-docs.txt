================================================================================

Scope of this document:
  - Every file in the location subsystem that was provided:
      js/location/location-state.js
      js/location/location-commands.js
      js/location/location-hierarchy.js
      js/location/location-queries.js
      js/location/location-movement.js

      js/location/modals-location-helper.js
      js/location/modals-location.js
      js/location/modals-moves.js
      js/location/location-bootstrap.js

  - Every core (js/core/) and character (js/character/) file the
    location subsystem depends on, either at load time (module-level
    guards) or at call time (typeof-guarded lookups), and how each
    dependency is used.

  - The feature-state modules and selector modules the location
    domain consumes or is consumed by in the documented application
    load order.

Cross-references:
  - stillwaters-docs.txt (core-level documentation and load order).
  - stillwaters-character-docs.txt (character-subsystem documentation).
  - location-docs.txt (the location subsystem's own narrative doc).

PATHS NOTE:
  This document uses the paths shown in the repository tree, not the
  paths written in individual file headers. Where a header says
  `js/location/...` but the tree says `js/location/...`, the tree is
  authoritative. All location files are at `js/location/...` in the
  tree, and all core files are at `js/core/...` in the tree. There is
  no `js/core/ui/` directory in the tree; `collapsible.js` lives at
  `js/core/collapsible.js` and `ui.js` lives at `js/core/ui.js`. This
  document uses tree paths.

Anything not provable from the supplied files is marked [UNVERIFIED].


================================================================================
PART 1 — DEPENDENCIES
================================================================================

Terminology:
  REQUIRED (load-time)  — a module-level guard throws if the
                          dependency is missing when this file loads.
  REQUIRED (call-time)  — a function or method throws/refuses if the
                          dependency is missing when the function is
                          invoked, and the module is loadable without
                          it.
  OPTIONAL              — the module checks for the dependency and
                          falls back (usually skipping the feature or
                          using a local fallback) when it is absent.

--------------------------------------------------------------------------------
1.1 CORE FILES THE LOCATION SUBSYSTEM DEPENDS ON
--------------------------------------------------------------------------------

  js/core/time.js
    Provides: TIME_CONSTANTS, getCurrentYear, isValidYear,
              calculateAge.
    Used for: current-year defaults in createPlace/recordMove/
              assignLeader/endLeaderTerm/handleCharacterDeath;
              age-at-year in location-movement.
    Deprecated aliases NOT used: getCurrentYearSafe, _getCurrentYear.

  js/core/ids.js
    Provides: generateId (place, loctype, lead prefixes).
    Used for: place ids, location-type ids, leader-assignment ids.

  js/core/storage.js
    Provides: masterData, markDataDirty, saveMasterData,
              getLastSaveError, initializeStorage.
    Used for: canonical collection access, dirty marker after every
              mutation primitive, the persist boundary
              (LocationCommands.persist), and the bootstrap-time
              masterData availability check.

  js/core/accessors.js
    Provides: invalidateAccessorCaches (via window.invalidateAccessorCaches).
    Used for: invalidation of the id→record caches
              (_placeMap, _locationTypeMap) after every mutation and
              after hydration. Called from location-state.js.

  js/core/collections.js
    Provides: deepClone.
    Used for: public reads from location-state.js MUST return deep
              clones. collections.js is a HARD load-time dependency
              of location-state.js. A missing collections.js makes
              location-state.js throw at load.

  js/core/formatting.js
    Provides: escapeHtml.
    Used for: HTML escaping in location-ui-list.js, modals-location.js
              and modals-moves.js (via modals-location-helper.js's
              escapeHtml fallback), location-presentation.js (does not
              escape), and by the bootstrap's UI dependency check.

  js/core/icons.js
    Provides: Icons.
    Used for: location-ui-list.js icon injection. Required at load
              time by location-ui-list.js. Required at load time by
              location-bootstrap.js's UI dependency check (via
              _requireGlobalObject('Icons')).

  js/core/modals-core.js
    Provides: openModal, closeTopModal.
    Used for: every modal in modals-location.js and modals-moves.js.
              openModal is required at load time by both modal files.
              closeTopModal is used by modals-location-helper.js's
              close() (with a typeof guard).

  js/core/ui.js
    Provides: showToast (and lockBodyScroll/unlockBodyScroll, which
              the location subsystem does not use directly).
    Used for: user-visible error and success toasts in the modals.
              Optional: modals-location-helper.js's toast() is a
              typeof-guarded call to window.showToast. The bootstrap
              verifies showToast is present at load time.

  js/core/world.js
    Provides: getCurrentLocationId.
    Used for: the semantic current-location resolver. Used by
              location-queries.js (population and current-location
              reads) and location-commands.js (deletePlace's
              character-cleanup sweep). Verified at bootstrap time by
              _verifyCrossDomain.

  js/core/simulation-generators.js
    Provides: randomRealisticAge, randomYear, randomFertilityModifier,
              randomLifespan.
    Not used by the location subsystem. Listed here only for
    completeness of the core-file mapping; the location domain does
    not reference it.

  js/core/names.js
    Not used by the location subsystem.

  js/core/validation.js
    Not used directly by the location subsystem. Validation.js
    validates place records on import (via storage.js's import path),
    which is the only interaction.

  js/core/integrity.js
    Provides: findBrokenPlaceHierarchy, repairBrokenPlaceHierarchy.
    Not used directly by the location subsystem. Integrity.js reads
    places via accessors.js, not via LocationState. The location
    domain's own cycle-prevention lives in location-hierarchy.js and
    location-commands.js.

  js/core/maintenance.js
    Not used by the location subsystem.

  js/core/state.js
    Provides: the compatibility facade. Requires LocationUIState (per
    its own header) among other feature state modules. Reads
    LocationUIState, not LocationState or LocationCommands. The
    location subsystem does not depend on state.js; the dependency
    flows the other direction.

  js/core/ui-state.js
    Not used directly by the location subsystem. UIState is a
    generic per-panel UI state store; the location domain's UI state
    lives in location-ui-state.js with its own localStorage key.

  js/core/constants/constants.js
    Provides: LOCAL_STORAGE_KEYS.LOCATION_TREE_STATE (and other keys).
    Used (softly) by location-ui-state.js. When constants.js is
    loaded, location-ui-state.js reads the canonical key name; when
    it is not, it uses the fallback literal
    'location_tree_expanded'. The canonical key value is
    'location_tree_expanded' per constants.js.

  js/core/constants/location-constants.js
    Provides: LOCATION_LEVELS.
    Not used by the location subsystem directly. The location domain
    uses location types from masterData (each with its own priority
    field), not LOCATION_LEVELS. LOCATION_LEVELS documents the five
    canonical levels and is consumed by other domains.

  Other constants files (age-constants.js, character-constants.js,
  character-traits.js, relationship-constants.js)
    Not used by the location subsystem.

1.3 HOUSEHOLD SUBSYSTEM FILES THE LOCATION SUBSYSTEM DEPENDS ON
--------------------------------------------------------------------------------

  js/households/household-commands.js
    Provides: HouseholdCommands.clearLocationReferences(placeId).
    Used by: location-commands.js's deletePlace household cleanup

1.4 CULTURE AND RELIGION SUBSYSTEM FILES THE LOCATION SUBSYSTEM DEPENDS ON
--------------------------------------------------------------------------------

  js/culture/culture-queries.js
    Provides: CultureQueries.getCulture(cultureId).
    Used by: location-commands.js (createPlace, updatePlaceCulture),
             location-view-models.js (resolveCultureLabel).
    Both usages are CALL-TIME lookups guarded by
    `typeof window.CultureQueries === 'undefined' || typeof
    window.CultureQueries.getCulture !== 'function'` checks. If
    CultureQueries is absent, the corresponding command returns a
    structured failure ("CultureQueries required to assign a culture")
    and resolveCultureLabel returns null. No load-time dependency.

  Note: no other culture file is used by the location subsystem.
        Culture state and rendering live in the culture domain.

  Note: no religion file is used by the location subsystem.

1.5 SELECTOR SUBSYSTEM FILES THE LOCATION SUBSYSTEM DEPENDS ON
--------------------------------------------------------------------------------

  js/selectors/locationDropdown.js
    Overwrites window.getLocationCountry and window.getLocationDistrict
    with a SUPERSET of world.js's versions (accepts place object OR
    place id). Under the documented load order, locationDropdown.js
    loads AFTER world.js, so its version wins the runtime race. The
    location subsystem does not call these functions, so this
    shadowing does not affect it.

  The location subsystem itself does not call any selector. The
  selectors are consumed by the modals of OTHER domains (character,
  household) that pick a location. The location modals do not open
  selectors. See modals-location.js and modals-moves.js.

  Note: no location file requires any selector at load time.

PART 2 — MODULE CATALOGUE
================================================================================

2.1 location-state.js
--------------------------------------------------------------------------------

  Location: js/location/location-state.js
  Owner of: window.LocationState (domain index layer).

  Scope:
    - Derived indexes over masterData.data.places and
      masterData.data.locationTypes.
    - Subscriptions and change notification (non-reentrant publish
      queue).
    - Explicit hydration (hydrateFromMasterData) and manual refresh
      (refresh).
    - Live-reference access for LocationCommands and
      LocationHierarchy (via _getPlaceCanonical and friends).
    - Mutation primitives (_addPlace, _removePlace,
      _addLocationType, _removeLocationType) reserved for
      LocationCommands.

  Out of scope:
    - Canonical record storage (lives in masterData.data).
    - Persistence (markDataDirty is called; saveMasterData is called
      by LocationCommands.persist).
    - Queries (LocationQueries interprets).
    - UI state (LocationUIState owns that).

  Exports:
    hydrateFromMasterData, refresh,
    getPlaceById, getLocationTypeById, getPlacesByParentId,
    getPlacesByTypeId, getAllPlaceIds, getAllLocationTypeIds,
    subscribe, publish,
    _getPlaceCanonical, _getLocationTypeCanonical,
    _getPlacesByParentIdCanonical, _getPlacesByTypeIdCanonical,
    _addPlace, _removePlace, _addLocationType, _removeLocationType.

  Contracts:
    - Public reads return deep clones via window.deepClone. Nested
      arrays (leaderAssignments, demolitionHistory) are cloned; a
      caller mutating a nested field does not corrupt canonical data.
    - collections.js is a HARD load-time dependency.
    - Every mutation primitive calls window.markDataDirty() AND
      window.invalidateAccessorCaches() after a successful write.
      The accessor cache (accessors.js _placeMap / _locationTypeMap)
      is invalidated so getPlaceById / getLocationTypeById return
      fresh records.
    - hydrateFromMasterData also calls invalidateAccessorCaches,
      because the in-memory catalogue is replaced wholesale.
    - Listens for masterDataUpdated and re-hydrates indexes; this
      closes the cross-tab reload correctness gap.
    - Collision guard: throws at load if window.LocationState is
      already defined and does not have hydrateFromMasterData.

  Load order:
    After storage.js, collections.js, and accessors.js (the guard
    checks markDataDirty and deepClone at load; accessors.js is
    call-time).
    Before every other location module.

2.2 location-commands.js
--------------------------------------------------------------------------------

  Location: js/location/location-commands.js
  Owner of: window.LocationCommands.

  Scope:
    - Every location-domain mutation, in one place:
      createPlace, updatePlace, deletePlace,
      createLocationType, updateLocationType, deleteLocationType,
      recordMove, bulkRecordMoves,
      assignGovernment, assignLeader, endLeaderTerm,
      updatePlaceCulture,
      handleCharacterDeath (the death hook).

  Out of scope:
    - Storage (uses markDataDirty and saveMasterData; does not touch
      localStorage directly).
    - Character mutation (routes through CharacterCommands).
    - Household mutation (routes through HouseholdCommands).
    - Culture lookups (routes through CultureQueries).

  Exports:
    persist,
    createPlace, updatePlace, deletePlace,
    createLocationType, updateLocationType, deleteLocationType,
    recordMove, bulkRecordMoves,
    assignGovernment, assignLeader, endLeaderTerm,
    updatePlaceCulture,
    handleCharacterDeath.

  Contracts:
    - Persist contract (Pattern A from storage.js):
      persist() calls saveMasterData() and inspects the boolean
      return. On false, it calls getLastSaveError() and returns the
      actual failure message. No silent success.
    - Commands mutate in memory, hydrate, mark dirty, and publish.
      The caller (modal, batch, annual pipeline) calls persist()
      exactly once per batch.
    - Result envelope: _ok() refuses to let the payload overwrite
      the success field. bulkRecordMoves uses `succeededList` (not
      `success`) to avoid the collision.
    - deletePlace dispatches:
        1. character cleanup (required — CharacterCommands is a
           load-time dependency),
        2. household cleanup (optional — HouseholdCommands.
           clearLocationReferences at call time),
        3. no residence cleanup (ResidenceSystem owns residence
           lifecycle; deleting a place does not delete its
           residences).
    - Character cleanup resolves each character's current location
      semantically (World.getCurrentLocationId with
      CharacterQueries.getCurrentLocationId as fallback) and clears
      BOTH currentLocationId (when resolved location is being removed)
      AND moves entries pointing at removed places. Batched through
      CharacterCommands.updateCharacters (one commit) when the batch
      API is present; falls back to per-character
      updateCharacterFields otherwise.
    - Cross-domain leader cleanup: handleCharacterDeath ends every
      active leader assignment held by the character across every
      place, and clears place.leaderId when it pointed at the
      character. Registers itself at load via
      window.registerDeathHandler (from character-lifecycle.js).
      Under the documented load order, character-lifecycle.js loads
      before this file, so the registration succeeds. If not, the
      registration is skipped with a debug log and the caller must
      wire handleCharacterDeath.

  Load order:
    After location-state.js, location-hierarchy.js,
    character-commands.js, character-queries.js, time.js, ids.js,
    storage.js.
    Before location-queries.js, location-movement.js,
    location-view-models.js, location-bootstrap.js. Also before the
    modal files.

2.3 location-hierarchy.js
--------------------------------------------------------------------------------

  Location: js/location/location-hierarchy.js
  Owner of: window.LocationHierarchy.

  Scope:
    - Ancestry / descent relationships (delegates to LocationQueries
      for the actual walks).
    - Structural validation (cycle prevention, type-priority rules).
    - Nearest ancestor at priority, depth, inheritance chain.

  Exports:
    validateHierarchy, isValidParentType,
    isAncestorOf, areInSameCountry, findLowestCommonAncestor,
    getLocationDepth, getNearestAncestorAtPriority,
    getDescendantsAtPriority, hasChildAtPriority,
    getRegionId, getCountyId, getCountryId, isRootPlace,
    getInheritanceChain,
    getTypeHierarchy, getAncestorAtPriority,
    getImmediateAncestorAtPriority,
    getRegionName, getCountyName,
    getHierarchyDistance, areLocationsRelated, getCommonAncestor,
    getHierarchyPath.

  Contracts:
    - Only LocationState is a load-time dependency.
    - LocationQueries is a CALL-TIME dependency. Every function that
      reaches into LocationQueries calls _requireQueries() first,
      which throws a clear error when the queries module is missing.
    - This is intentional: the documented HTML order is
      state → hierarchy → commands → queries. The hierarchy module
      loads before the queries module, so a load-time check for
      queries would throw at load. Resolving at call time is the
      correct dependency shape.
    - Public functions that only touch LocationState (isRootPlace)
      work without LocationQueries.

  Load order:
    After location-state.js.
    Before location-commands.js (which load-requires
    LocationHierarchy.validateHierarchy), location-movement.js,
    location-view-models.js, location-bootstrap.js.
    Before location-queries.js in the documented HTML order (the
    reverse dependency is call-time only).

2.4 location-queries.js
--------------------------------------------------------------------------------

  Location: js/location/location-queries.js
  Owner of: window.LocationQueries.

  Scope:
    - Hierarchy interpretation (walks, ancestry, projection).
    - Search and filtering.
    - Population analytics.
    - Movement interpretation (delegates to CharacterQueries).

2.10 modals-location-helper.js
--------------------------------------------------------------------------------

  Location: js/location/modals-location-helper.js
  Owner of: window.LocationModals.{escapeHtml, toast, close,
            runCommand} (additive — modals-location.js also installs
            its own entry points on the same namespace).

  Scope:
    - Shared helpers for modals-location.js and modals-moves.js.
    - escapeHtml: prefers formatting.js, falls back to a local
      implementation.
    - toast: calls window.showToast if present, no-op otherwise.
    - close: calls window.closeTopModal if present, no-op otherwise.
    - runCommand(commandFn, onSuccess, options): invokes commandFn,
      persists via LocationCommands.persist() on success, toasts on
      failure, closes the modal unless options.keepOpen.

  Exports:
    escapeHtml, toast, close, runCommand (installed on the
    window.LocationModals namespace).

  Contracts:
    - The ONLY hard dependency is LocationCommands.persist. The
      load-time guard throws if window.LocationCommands or its
      persist method is missing.
    - escapeHtml, toast, and close are soft: the modals continue
      to work in a bare test harness that lacks formatting.js or
      ui.js.
    - runCommand NEVER reports success unless BOTH the command and
      persist succeeded. A throw in either is toasted and returns
      false.
    - A throw in onSuccess is logged and swallowed; the modal has
      already closed. onSuccess is a notification, not a step in
      the close sequence.

  Load order:
    After location-commands.js. Before modals-location.js and
    modals-moves.js.

2.13 location-bootstrap.js
--------------------------------------------------------------------------------

  Location: js/location/location-bootstrap.js
  Owner of: window.LocationBootstrap and window.Location (the domain
            namespace).

  Scope:
    - Load-time verification of every required module, global, and
      cross-domain method.
    - Canonical data shape verification.
    - Hydration of LocationState indexes from canonical data.
    - Exposure of window.Location as the domain namespace
      ({ state, commands, queries, hierarchy, movement }).
    - Idempotent init().

  Exports:
    window.LocationBootstrap.init,
    window.Location (installed by init).

  Contracts:
    - Does NOT register lifecycle hooks. Direct dispatch model.
    - Does NOT flush storage. Persistence is LocationCommands.persist.
    - Does NOT mutate canonical data. Hydration only.
    - Verifies the following at init (all LOAD-TIME guards):
        - generateId, markDataDirty, saveMasterData, getCurrentYear,
          calculateAge (globals),
        - LocationState, LocationCommands, LocationQueries,
          LocationHierarchy, LocationMovement (modules),
        - CharacterCommands.updateCharacters,
          CharacterCommands.updateCharacterFields,
          CharacterQueries.getAllCharacters,
          CharacterQueries.getCharacterById,
          CharacterQueries.getCurrentLocationId,
          CharacterQueries.getMoveHistory,
          getCurrentLocationId (World) — cross-domain surface,
        - masterData.data.places (array), masterData.data.locationTypes
          (array) — canonical data shape,
        - Icons, getIcon, openModal, closeTopModal, escapeHtml,
          showToast — UI dependencies,
        - Full LocationState surface (hydrateFromMasterData + every
          read and primitive),
        - Full LocationCommands surface (persist + every command,
          including updatePlaceCulture and handleCharacterDeath),
        - Full LocationQueries surface,
        - Full LocationHierarchy surface,
        - Full LocationMovement surface.
    - init() is idempotent. Re-invocation re-hydrates and returns
      { success: true, alreadyInitialized: true }.
    - Auto-runs init() at load if window.masterData is already
      present. Logs errors but does not throw (the auto path is
      best-effort; the caller can invoke init() explicitly).

  Load order:
    LAST in the location script group.
    After every other location module plus every core and character
    dependency above.
    After initializeStorage() has been called.

PART 3 — LOAD ORDER
================================================================================

The order below is derived from:
  (a) module-level guard blocks (which throw if a dependency is not
      loaded),
  (b) call-time window.X lookups in code,
  (c) the location-bootstrap.js verification list,
  (d) location-commands.js's own load-time guards,
  (e) the documented core and character load order (see
      stillwaters-docs.txt and stillwaters-character-docs.txt),
  (f) location-docs.txt's own load-order section, extended for
      cross-domain dependencies that doc does not cover.

The groups below are ordered. Each group depends on the ones before
it. Groups L0..L9 are the location subsystem. Groups C0..C3 and R0..R3
are the core and character prerequisites.

GROUP C0 — CORE FILES REQUIRED BY THE LOCATION SUBSYSTEM
--------------------------------------------------------------------------------

  js/core/constants/constants.js

  js/core/icons.js
  js/core/collections.js
  js/core/ids.js

    - constants.js: soft dependency via location-ui-state.js's

      when constants.js is absent. Loading it first gives every

      location-view-models.js.

      time.js and the character subsystem requires it. Including it
      here keeps the location-subsystem dependency list
      self-consistent with the documented overall load order.
    - storage.js: masterData, markDataDirty, saveMasterData,
      getLastSaveError, initializeStorage. Required at load time by
      location-state.js (markDataDirty) and location-commands.js
      (markDataDirty, saveMasterData, getLastSaveError).

  BOOTSTRAP CALL:
    After storage.js is loaded and before any location file loads,
    the application MUST invoke window.initializeStorage(). This
    populates window.masterData, which location-state.js and
    location-bootstrap.js check for.

  If initializeStorage() is not called before location-state.js
  loads, location-state.js's load-time dependency guards pass
  (markDataDirty and deepClone are present) but its first call to

  available." The location-bootstrap.js auto-init also throws on its
  canonical-data check. Order:
    storage.js  →  initializeStorage()  →  location-state.js

GROUP R2 — CHARACTER FILES THAT MAY REGISTER DEATH HANDLERS BEFORE
            LOCATION-COMMANDS LOADS
--------------------------------------------------------------------------------

  js/character/character-lifecycle.js

  Rationale:
    - location-commands.js's DEATH HANDLER REGISTRATION block calls
      window.registerDeathHandler at load time to register
      LocationCommands.handleCharacterDeath.
    - window.registerDeathHandler is installed by
      character-lifecycle.js at ITS load time.
    - Under the documented load order,
      character-lifecycle.js loads BEFORE location-commands.js.
      That is the only ordering in which the registration succeeds.
    - If character-lifecycle.js is not loaded before
      location-commands.js, the registration is skipped with a debug
      log, and the caller must wire LocationCommands.
      handleCharacterDeath manually.

  character-lifecycle.js requires:
    - character-state.js
    - character-commands.js
    - mortality-rules.js (js/character/mortality-rules.js)
    - time.js (getCurrentYear, isValidYear)
    - randomness.js (window.random)

  If you load character-lifecycle.js, you must also load
  mortality-rules.js. character-lifecycle.js throws at load without
  it. Because the location subsystem does not require
  character-lifecycle.js for its own operation (the death handler
  registration is best-effort), you may skip this entire group if you
  do not intend to register the leader-cleanup death handler. The
  location subsystem still works; the caller wires
  handleCharacterDeath itself if they want leader cleanup.

  Under the FULL documented load order (with the whole character
  subsystem present), the full character block loads:
    character-state.js → character-commands.js → character-queries.js
    → mortality-rules.js → character-lifecycle.js.

GROUP L4 — LOCATION QUERIES
--------------------------------------------------------------------------------

  js/location/location-queries.js

  Rationale:
    - Requires location-state.js and character-queries.js at load

      not exist — location-commands.js does not require

      location-presentation.js, modals-location.js, modals-moves.js

      queries directly, but location-view-models requires queries),
      location-bootstrap.js.

  Note: location-hierarchy.js loads before this file, but resolves
  LocationQueries at call time. That is not a contradiction; the
  HTML order reflects the load-time dependency graph, not the
  call-time one.

--------------------------------------------------------------------------------

  js/location/location-bootstrap.js

    - Auto-runs init() if window.masterData is present at load time.

GROUP A1 — APPLICATION BOOTSTRAP
--------------------------------------------------------------------------------

  Between Group L0 and Group L1, the application must call:
    window.initializeStorage();

  After Group L9, if the bootstrap auto-init did not run (because
  masterData was not yet installed), the caller invokes:
    window.LocationBootstrap.init();

  After LocationBootstrap.init() returns, window.Location is
  available as the domain namespace:
    window.Location.state     → LocationState
    window.Location.commands  → LocationCommands
    window.Location.queries   → LocationQueries
    window.Location.hierarchy → LocationHierarchy
    window.Location.movement  → LocationMovement

================================================================================
PART 5 — LOAD-ORDER INVARIANTS
================================================================================

Each invariant names the failure mode it prevents.

 1. constants.js before location-ui-state.js.
    Failure without it: none (soft fallback to the literal storage
    key). Loading it first gives the canonical key.

 2. storage.js and a successful initializeStorage() call before
    location-state.js.
    Failure without it: location-state.js's load-time guard passes
    (markDataDirty exists), but its first hydrateFromMasterData call
    throws "masterData.data.places is not available."

 3. collections.js before location-state.js.
    Failure without it: location-state.js throws at load ("deepClone
    missing"). The prior local fallback (one-level shallow clone) is
    removed deliberately; deep-clone correctness is not optional.

 4. icons.js before location-ui-list.js.
    Failure without it: location-ui-list.js throws at load ("Icons
    missing").

 5. formatting.js, icons.js, modals-core.js before
    modals-location.js and modals-moves.js (via the helper's soft
    fallbacks for formatting.js; hard for modals-core.js).
    Failure without modals-core.js: the modal files throw at load
    ("openModal missing").

 6. time.js before location-commands.js, location-movement.js,
    location-view-models.js.
    Failure without it: each throws at load ("getCurrentYear
    missing").

 7. ids.js before location-commands.js.
    Failure without it: location-commands.js throws at load
    ("generateId missing").

 8. accessors.js before location-state.js.
    Failure without it: the load-time guard passes (accessors.js is
    not required at load), but every mutation calls
    window.invalidateAccessorCaches (typeof-guarded). The accessor
    cache (getPlaceById / getLocationTypeById) stays stale after
    every location write, and downstream readers see the
    pre-mutation shape.

 9. world.js before location-queries.js and location-commands.js.
    Failure without it: the semantic current-location resolver is
    unavailable; the two modules fall back to the raw-field
    resolver (CharacterQueries.getCurrentLocationId) and under-count
    populations and miss characters placed via moves. Not a
    load-time throw, but a correctness regression. Verified at
    bootstrap time by _verifyCrossDomain.

10. character-state.js, character-commands.js, character-queries.js
    before location-commands.js, location-queries.js,
    location-movement.js, location-view-models.js.
    Failure without them: each location file throws at load
    ("CharacterCommands.updateCharacterFields missing", etc.).

11. character-lifecycle.js before location-commands.js (for the
    death handler registration).
    Failure without it: location-commands.js's death handler
    registration block is skipped with a debug log; the caller must
    wire LocationCommands.handleCharacterDeath manually. Not a load-
    time throw.

12. mortality-rules.js before character-lifecycle.js.
    Failure without it: character-lifecycle.js throws at load
    ("MortalityRules missing"). Only relevant if you load
    character-lifecycle.js.

13. location-state.js before location-hierarchy.js.
    Failure without it: location-hierarchy.js throws at load.

14. location-state.js, location-queries.js, location-hierarchy.js,
    character-queries.js, time.js before location-movement.js.
    Failure without them: location-movement.js throws at load.

15. location-hierarchy.js before location-commands.js.
    Failure without it: location-commands.js throws at load
    ("LocationHierarchy missing").

16. location-queries.js before location-view-models.js.
    Failure without it: location-view-models.js throws at load.

17. location-view-models.js, location-ui-state.js, icons.js before
    location-ui-list.js.
    Failure without them: location-ui-list.js throws at load.

18. location-commands.js before modals-location-helper.js.
    Failure without it: modals-location-helper.js throws at load
    ("LocationCommands missing").

19. modals-location-helper.js before modals-location.js and
    modals-moves.js.
    Failure without it: both modal files throw at load
    ("window.LocationModals.escapeHtml/toast/close/runCommand
    missing").

20. location-commands.js before LocationCommands.persist is called
    by any modal's runCommand.
    Failure without it: this is a runtime call, not a load-time
    check. The location-bootstrap.js cross-domain verification also
    checks LocationCommands.persist's existence at init time.

21. location-bootstrap.js loads LAST in the location script group.
    Failure without it: the bootstrap's verification pass runs
    against an incomplete surface and throws. Under the documented
    load order, every module is present by the time the bootstrap
    loads.

22. location-queries.js loads AFTER location-commands.js in the HTML
    order (the commands module does not require queries at load).
    This is the documented HTML ordering. Do not reorder to
    commands-before-queries; the reverse is what the
    location-hierarchy.js header documents.

    Actually — re-reading: the location-hierarchy header documents
    the order as `state → hierarchy → commands → queries`. That is
    the HTML order. location-commands.js does not require
    LocationQueries at load. location-hierarchy.js resolves
    LocationQueries at call time. So the canonical order is
    state → hierarchy → commands → queries. The HTML order in this
    document matches.

23. No dependencies flow FROM core INTO the location subsystem. The
    location domain depends on core (and character and household and
    culture), but no core module depends on location files. js/core/
    state.js requires LocationUIState (which is a location file), but
    that dependency is state.js → location-ui-state.js, not the
    reverse; the location subsystem does not require state.js.


================================================================================
PART 6 — KNOWN HAZARDS
================================================================================

 1. initializeStorage() must run BEFORE location-state.js. Not just
    storage.js — the function call. location-state.js loads fine
    with storage.js present but masterData absent; the failure
    surfaces on the first hydrateFromMasterData, which the bootstrap
    calls. If your bootstrap loads the location files but forgets
    the initializeStorage() call, LocationBootstrap.init() throws
    "masterData.data.places is not available."

 2. deepClone is a HARD dependency of location-state.js. The prior
    fallback was one-level shallow for nested objects, which
    allowed a caller to corrupt canonical data through a public
    read. Do not reintroduce a fallback. See CLONE STRATEGY in the
    module header.

 3. The current-location resolver is overloaded.
    window.getCurrentLocationId returns a string only when world.js
    is loaded. In a reduced environment it returns whatever
    CharacterQueries.getCurrentLocationId returns (also a string),
    or a function from character-queries.js that takes a character
    id — the two functions have different signatures. The location
    subsystem resolves this by calling _resolveCurrentLocationId,
    which prefers World.getCurrentLocationId(character) and falls
    back to CharacterQueries.getCurrentLocationId(character.id). Do
    not call window.getCurrentLocationId directly from location
    code; go through _resolveCurrentLocationId.

 4. Cross-tab reload. location-state.js listens for
    masterDataUpdated and re-hydrates. storage.js invalidates the
    accessor cache before dispatching, and location-state.js also
    invalidates at hydration. Redundant but harmless, and defense
    in depth. A reload that corrupts canonical data is logged and
    the prior indexes are preserved (last-known-good). See MASTER
    DATA RELOAD in the location-state header.

 5. Death handler registration. location-commands.js registers
    LocationCommands.handleCharacterDeath via
    window.registerDeathHandler at load. Under the documented load
    order, character-lifecycle.js loads before location-commands.js
    and the registration succeeds. If character-lifecycle.js is
    missing (reduced environment), the registration block is skipped
    with a debug log, and the caller must wire the death hook
    manually. Do not add a load-time dependency on
    character-lifecycle.js from location-commands.js; the
    registration path is deliberately best-effort.

 6. Household cleanup on place delete. HouseholdCommands.
    clearLocationReferences is a CALL-TIME optional dependency.
    Under a full application load, it is present and the delete
    clears household.locationId. In a location-only harness, it is
    absent and the result reports status: 'unavailable'. Do not
    add a load-time dependency; the location subsystem must work
    without the household domain.

 7. Culture is a call-time optional dependency. createPlace and
    updatePlaceCulture refuse with a structured failure when
    CultureQueries is missing; resolveCultureLabel returns null.
    Do not fabricate a culture label from a culture id.

 8. Icon names. location-ui-list.js reads window.Icons[name]
    directly and throws on unknown names. The prior getIcon fallback
    (Icons.CIRCLE) masked a real bug: CHEVRON_DOWN and
    CHEVRON_RIGHT did not exist and every toggle rendered as a
    circle. Do not re-introduce getIcon in the toggle renderer; the
    correct names are TRIANGLE_DOWN (expanded) and ARROW_RIGHT
    (collapsed).

 9. getPlaceChildren(placeId, recursive) semantic. In
    LocationQueries, recursive=true returns all descendants (no
    self). In LocationHierarchy's getDescendantsAtPriority, it
    walks LocationQueries.getPlaceChildren with recursive=true and
    filters by type priority. Do not confuse the two; the
    hierarchy module's "descendants at priority" does not include
    the source place.

10. Place or type id derivation. new place ids use
    window.generateId('place'). new type ids use
    window.generateId('loctype'). new leader assignment ids use
    window.generateId('lead'). Do not fabricate ids in application
    code.

11. Leader assignment isActive semantics. The location queries
    module's getCurrentLeader treats isActive === true as active;
    it ALSO treats isActive === false with endYear === null/
    undefined as active (backward compatibility with records
    created before isActive was introduced). The
    LocationCommands.handleCharacterDeath path sets isActive = false
    AND endYear = <year> together, so the fallback does not affect
    it. If you write leader assignments from your own code, set
    isActive AND endYear together; do not rely on the fallback.

12. The location domain does not own residence lifecycle.
    deletePlace does NOT delete residence records. ResidenceSystem
    owns residences; place deletion leaves residences in place.
    Callers who want residence cleanup on place delete must
    orchestrate it themselves.

13. The location domain does not own character moves. Moves are
    character-owned (character.moves array). LocationCommands.
    recordMove and bulkRecordMoves write through
    CharacterCommands.updateCharacterFields; LocationQueries.
    getMoveHistory reads through CharacterQueries.getMoveHistory.
    Do not mutate character.moves directly from location code.

14. ui-state.js (core) vs location-ui-state.js. The core ui-state
    is a generic per-panel UI store, not a location module. The
    location domain uses its own location-ui-state.js with a
    dedicated localStorage key. js/core/state.js reads
    location-ui-state.js; the location subsystem does not read
    core ui-state.js.

15. state.js (core) does not own LocationState. The core state
    facade's LocationState-like names (selectedPlaceId,
    currentPlaceId, collapsedNodes, setSelectedPlace,
    hasSelectedPlace, reset) are aliases to LocationUIState, not to
    LocationState or LocationCommands. Do not reach for
    window.selectedPlaceId expecting a domain record; you will get
    a UI selection id (or a view of the expansion map).
