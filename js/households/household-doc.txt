================================================================================
PART 1 — LAYER STACK AND FILE CLASSIFICATION
================================================================================

The household subsystem sits above the character, industry, place,
relationship, storage, and time domains. It orchestrates them; it does
not own them.

  CONSTANTS (leaf)
    js/households/household-constants.js

  RULES (pure policy; depends on constants)
    js/households/household-rules.js

  VIEW MODELS (presentation defaults; no domain state)
    js/households/household-view-models.js

  ORCHESTRATION (shared result/dispatch/finish helpers)
    js/households/household-orchestration.js

  STATE (canonical in-memory store for households/positions/assignments)
    js/households/household-state.js

  QUERIES (semantic reads; defensive snapshots)
    js/households/household-queries.js

  COMMANDS (single write boundary for household data)
    js/households/household-commands.js

  ECONOMY (pure calcs + patch-then-commit mutations)
    js/households/household-economy.js

  ASSIGNMENT (cross-operation orchestration: newborn, marriage,
              inheritance, cadet, merge, split, auto-succession)
    js/households/household-assignment.js

  SERVANT (service-relationship orchestration)
    js/households/household-servant.js

  RESIDENCE (residence domain: canonical storage, units, occupancy,
             rental, staff, rehabilitation, demolition)

        no persist (caller's orchestration owns the batch).

        _residenceSystemAvailable / _industryCommandsAvailable. See the
        module header for the historical bug this fixes.
      - ACCOUNT OF ACCESSOR CACHE INVALIDATION: prior to this revision,
        the household domain never invalidated the accessor cache, so
        industry-queries._resolveOwnerName could return a stale
        household name after a rename. _commit now invalidates at every
        mutation boundary.

PART 3 — THE HOUSEHOLD ↔ INDUSTRY CONTRACT
================================================================================

The two domains meet at exactly TWO facts, both of which the household
domain owns structurally and the industry domain owns canonically.

FACT 1: HOUSEHOLD REVERSE INDEX → ENTERPRISES
---------------------------------------------

  household.enterprises[]   — canonical facts live in Industry
                              (enterprise.ownerType / ownerId)
  enterprise.ownerType / ownerId  — canonical, written ONLY by
                                    IndustryCommands

  STRUCTURAL OWNERSHIP:
    Household domain: household.enterprises[] is a REVERSE INDEX into
                      the canonical enterprise ownership.
    Industry domain:  enterprise.ownerType / ownerId is the CANONICAL
                      relationship.

  WRITE RULES:
    Only HouseholdCommands writes household.enterprises[]. Specifically:
      setHouseholdEnterprises
      addEnterpriseToHousehold
      removeEnterpriseFromHousehold
    These are called by IndustryCommands on every path that changes
    ownership or existence:
      createEnterprise        -> addEnterpriseToHousehold
      updateEnterprise        -> _reconcileHouseholdOwnership
                                 (remove from prior + add to next)
      deleteEnterprise        -> removeEnterpriseFromHousehold
      demolishEnterprise      -> removeEnterpriseFromHousehold
      rebuildEnterprise       -> addEnterpriseToHousehold (if the
                                 demolition record had a household
                                 owner)
    Household domain code NEVER writes enterprise.ownerType / ownerId.
    Industry domain code NEVER writes household.enterprises[] directly;
    it calls HouseholdCommands.

  THE HANDSHAKE:
    1. Industry commits enterprise.ownerType / ownerId on its side.
    2. Industry calls HouseholdCommands.addEnterpriseToHousehold (or
       remove) to sync the reverse index.
    3. If the industry-side mutation succeeds but the household-side
       sync fails, IndustryCommands ROLLS BACK the industry mutation
       (createEnterprise) or surfaces a structured failure
       (updateEnterprise via _reconcileHouseholdOwnership).
    4. HouseholdCommands does NOT write enterprise.ownerType / ownerId
       directly.

  THE RECONCILIATION PATH (updateEnterprise, C2):
    On an enterprise owner change, IndustryCommands calls
    _reconcileHouseholdOwnership(current, nextOwnerType, nextOwnerId,
    year), which:
      1. If wasHouseholdOwned: removes from the PRIOR household.
      2. If isHouseholdOwned: adds to the NEXT household.
      3. On failure: rolls back the industry owner fields to their
         prior values, then attempts to roll back the household-side
         removal (best-effort).
    Idempotency: if the previous and next (ownerType, ownerId) are
    identical, this is a no-op.

  INTEGRITY DIAGNOSTICS:

    industry-state.js::validateIntegrity
      walks masterData.data.households -> enterprises[]. For each
      household's enterprises[] entry, requires:
        (a) non-empty string id
        (b) resolves to an existing enterprise
        (c) enterprise.ownerType === 'household'
        (d) enterprise.ownerId === household.id
      This catches: malformed entries, dangling ids, cross-owner
      entries, and entries whose enterprise has moved to another
      household.

    household-state.js::_diagnostics.getIntegrityReport
      performs the SYMMETRIC check, but reads
      masterData.data.enterprises and masterData.data.households
      DIRECTLY, without depending on IndustryState. It works when the
      industry domain is not loaded (a household-only page or a
      reduced test harness). Reports:
        householdsWithOrphanEnterpriseRef
        enterprisesOrphanedFromHousehold
        enterpriseReverseIndexAvailable

      The two checks are INTENTIONALLY REDUNDANT. Each domain's
      bootstrap reports on the collection it owns. Neither waits for
      the other.

  BOOTSTRAP VERIFICATION:

    household-bootstrap.js's _verifyCrossDomain includes
    IndustryCommands.updateEnterprise and
    IndustryQueries.getEnterpriseSummary as OPTIONAL module checks. If
    present, the full surface must be present (missing method is a
    hard throw). If absent entirely, the dependency is recorded as
    false in Household.dependencies.industryCommandsPresent /
    industryQueriesPresent, and downstream code (economy's
    calculateEnterpriseNet, queries' getHouseholdEnterprises) fails or
    returns 0 per its own contract.

FACT 2: HOUSEHOLD WEALTH → ANNUAL PROCESSING TRANSFER
-----------------------------------------------------

  household.wealth           — canonical household fact
  IndustryCommands.applyAnnualProcessing
                             — writes household.wealth via
                               HouseholdCommands.updateHousehold

  STRUCTURAL OWNERSHIP:
    Household domain: household.wealth is a canonical household fact.
    Industry domain:  the annual processing transfer computes the
                      amount and calls HouseholdCommands.

  WRITE RULES:
    Only HouseholdCommands.updateHousehold writes household.wealth.
    Industry NEVER reaches into a household record directly; it passes
    the new wealth value through HouseholdCommands.updateHousehold.

  WHEN IT HAPPENS:
    IndustryProcessor.processAnnualEnterprise calls
    IndustryCommands.applyAnnualProcessing with
    householdId / householdTransfer / householdReason when the
    enterprise.ownerType === 'household'. applyAnnualProcessing calls
    _applyHouseholdTransfer, which:
      1. Reads the current household.wealth via getHouseholdById.
      2. Computes newWealth = currentWealth + amount.
      3. Calls HouseholdCommands.updateHousehold(householdId,
         { wealth: newWealth }).
    If the household write fails, the enterprise is untouched.

  WHAT INDUSTRY DOES NOT WRITE:
    household.notes          — prior revisions wrote this on transfer;
                               removed (M5) because it clobbered
                               concurrent household note edits based
                               on a stale read.
    household.name / locationId / locationName / status / members /
    departments / residence fields.

  PERSISTENCE:
    _applyHouseholdTransfer does NOT call HouseholdCommands.persist()
    or IndustryCommands.persist(). The caller's orchestration
    (IndustryProcessor.processAnnualEnterprise with default
    shouldPersist=true) calls IndustryCommands.persist() once at the
    end.

CROSS-DOMAIN VISIBILITY SUMMARY
-------------------------------

  From the INDUSTRY domain's perspective, these HOUSEHOLD methods must
  be present:

    HouseholdCommands.addEnterpriseToHousehold
    HouseholdCommands.removeEnterpriseFromHousehold
    HouseholdCommands.updateHousehold
    window.getHouseholdById

  Verified HARD at industry-bootstrap.init() time. Missing -> throw.

  From the HOUSEHOLD domain's perspective, these INDUSTRY methods are
  used:

                                             getHouseholdEnterpriseValue,
                                             getHouseholdDetails)

  All three are OPTIONAL. The household domain returns 0 or [] when
  the household has no enterprises. It throws when the household HAS
  enterprises and the industry query surface is missing. See the

  From the HOUSEHOLD domain's perspective, the following INDUSTRY
  writes are visible (via the reverse index):

    household.enterprises[]                 — one direction
    household.wealth                        — no, industry writes it
                                              via HouseholdCommands, and
                                              the reverse index does
                                              not track it.

  From the INDUSTRY domain's perspective, the following HOUSEHOLD
  facts are visible (via reverse index or accessors):

    household.name                          — read via
                                              getHouseholdById
    household.enterprises[]                 — one direction
    household.wealth                        — read via getHouseholdById
    household.id                            — for
                                              enterprise.ownerId

WHAT THE HOUSEHOLD DOMAIN DOES NOT WRITE TO INDUSTRY
----------------------------------------------------

  household-commands.js never touches enterprise.ownerType or
  enterprise.ownerId. It writes household.enterprises[] only. The
  canonical enterprise ownership is IndustryCommands' job.

  Even the reverse-index write is CALLED by the industry domain (via
  HouseholdCommands.addEnterpriseToHousehold). Household code never
  spontaneously decides to change an enterprise's owner.

WHAT THE INDUSTRY DOMAIN DOES NOT WRITE TO HOUSEHOLD
----------------------------------------------------

  industry-commands.js never touches household.notes, household.name,
  household.locationId, household.locationName, household.status,
  household.members, household.departments, or any residence field.

  It writes household.wealth (via HouseholdCommands.updateHousehold)
  and household.enterprises[] (via
  HouseholdCommands.addEnterpriseToHousehold /
  removeEnterpriseFromHousehold). Both are documented in the
  industry-commands.js header and the industry-bootstrap.js header.

PART 4 — DIAGNOSTICS AND INTEGRITY REPORTS
================================================================================

Three independent diagnostics report on the household domain's data
integrity. They are intentionally redundant — each domain's bootstrap
reports on the collection it owns.

HOUSEHOLD-STATE DIAGNOSTICS
---------------------------

  HouseholdState._diagnostics.getIntegrityReport() returns:

    ok: boolean
    duplicates: { households, positions, assignments }
    duplicateHouseholdHeads: [{id, name, headCount}]
    householdsWithMissingResidence: [{householdId, householdName,
                                       residenceId}]
    residencesWithOrphanHouseholdOccupancy: [{residenceId,
                                              residenceName,
                                              unitNumber,
                                              householdId}]
    residenceReverseIndexAvailable: boolean

    householdsWithOrphanEnterpriseRef: [{householdId, householdName,
                                         enterpriseId, index, reason,
                                         actualOwnerId?}]
    enterprisesOrphanedFromHousehold: [{enterpriseId, enterpriseName,
                                        ownerId}]
    enterpriseReverseIndexAvailable: boolean

    counts: { households, positions, assignments }

  The residence reverse-index check runs when ResidenceSystem is
  present OR when masterData.data.residences is an array. The
  enterprise reverse-index check runs when masterData.data.enterprises
  and masterData.data.households are both arrays. Neither requires the
  other domain's namespace.

  `ok` is true only if every list is empty AND both reverse-index
  checks ran. A caller that needs to distinguish "no issues" from "no
  issues I could check" must inspect the two `available` flags.

RESIDENCE DIAGNOSTICS
---------------------

  ResidenceSystem._diagnostics.getIntegrityReport() returns:

    ok: boolean
    duplicates: [{index, id, reason}]
    count: number

  It detects duplicate residence ids only. Reverse-index failures are
  reported via damageHistory entries on individual residences (see
  §2.11 REVERSE-INDEX FAILURE POLICY) rather than through this report.

INDUSTRY DIAGNOSTICS
--------------------

  IndustryState.validateIntegrity() returns:

    valid: boolean
    errors: string[]
    checksSkipped: string[]

  It walks households -> enterprises[] (one direction) and reports
  broken enterprise references. It requires getCharacterById,
  getPlaceById, and getHouseholdById for full reference checking;
  absent accessors cause the corresponding checks to be skipped and
  reported in checksSkipped.

BOOTSTRAP SUMMARY
-----------------

  HouseholdBootstrap.init() runs HouseholdState._diagnostics and logs
  integrity warnings. It also returns an `integritySummary` with the
  two residence-side counts and residenceReverseIndexAvailable. It does
  NOT run the enterprise reverse-index check directly; that lives on
  HouseholdState._diagnostics and on IndustryState.validateIntegrity.

  A complete audit run:
    1. HouseholdBootstrap.init()  -> residence-side drift
    2. HouseholdState._diagnostics.getIntegrityReport()  -> both sides
    3. IndustryBootstrap.init()   -> industry-side integrity via
                                     IndustryState.validateIntegrity

  The three are independent. A household-only page runs only (1) and
  (2) and still detects enterprise reverse-index drift via (2)'s
  direct read of masterData.data.enterprises.

33.  THE HOUSEHOLD ↔ INDUSTRY HANDSHAKE:
       - IndustryCommands.addEnterpriseToHousehold and
         removeEnterpriseFromHousehold MUST exist before any
         household-side enterprise reverse-index write is attempted
         from industry. Failure without them surfaces as a hard
         throw at industry-bootstrap.init() time.

         HouseholdCommands.addEnterpriseToHousehold /
         removeEnterpriseFromHousehold / setHouseholdEnterprises.
         Industry NEVER writes the array directly.
       - enterprise.ownerType / ownerId is written ONLY via
         IndustryCommands.updateEnterprise. Household NEVER writes
         those fields.
       - household.wealth is written ONLY via
         HouseholdCommands.updateHousehold. Industry calls that
         method; it does not reach into the record.

34.  THE ACCESSOR CACHE CONTRACT:
       Every mutation boundary that changes a canonical record
       cached by accessors.js MUST call
       window.invalidateAccessorCaches(). For the household domain:
         household-commands.js::_commit does this
         residence-system.js::_commit does this
       Failure without it: getHouseholdById / getPlaceById return
       stale data. For the specific case of industry-queries
       resolving a household owner name, the stale name persisted
       after a household rename. This was fixed in the current
       revision by adding the call to _commit.
       household-state.js does NOT invalidate the cache (it does not
       cache; no household accessor exists). If a future revision
       adds a household accessor to accessors.js, household-state.js
       MUST gain the call in its _sync path.

35.  THE STATE.HOUSEHOLDSTATE COLLISION GUARD:
       js/core/household-state.js (the historical UI shim) MUST be
       deleted, not loaded alongside js/households/household-state.js.
       The collision guard throws if both are loaded. The facade
       compatibility surface (selectedHouseholdId,
       setSelectedHousehold, hasSelectedHousehold, reset) is provided
       by js/households/household-state.js directly.

36.  THE HOUSEHOLDSTATE._INTERNAL CONTRACT:
       The following methods must be present when
       household-commands.js, household-queries.js, or
       household-bootstrap.js loads:
         getHouseholdRecord, getAllHouseholdRecords,
         replaceHouseholds
         getPositionRecord, getAllPositionRecords,
         replaceHouseholdPositions
         getAssignmentRecord, getAllAssignmentRecords,
         replaceHouseholdAssignments
       Failure without any: the consuming module throws at load.

37.  THE RESIDENCE↔HOUSEHOLD HANDSHAKE (PRECEDES THE INDUSTRY
     HANDSHAKE IN PRACTICE):
       ResidenceSystem.assignHouseholdToUnit calls
       HouseholdCommands.associateWithResidence.
       ResidenceSystem.markUnitVacant / markResidenceVacant /
       demolishResidence / deleteResidence (force path) call
       HouseholdCommands.disassociateFromResidence.
       HouseholdCommands.deleteHousehold calls
       ResidenceSystem.markUnitVacant / markResidenceVacant.
       BOTH directions are guarded by call-time presence checks
       (_residenceSystemAvailable / _householdCommandsAvailable).
       A loop is impossible because the reverse-index updates do
       NOT trigger reverse-direction writes.

38.  THE PERSISTENCE BOUNDARY:
       One persist() call per batch. No file may call
       saveMasterData except:
         household-commands.js::persist
         residence-system.js::persist
         industry-commands.js::persist         (industry's own)
         industry-type-commands.js::persist    (industry's own)
       No file may call another domain's persist() after its own
       batch. The residence commands leave household state dirty; one
       ResidenceSystem.persist() flushes BOTH. Calling
       HouseholdCommands.persist() after a residence operation
       produces a redundant second save with nothing new to write.


================================================================================
PART 8 — KNOWN HAZARDS
================================================================================

  1.  HOUSEHOLD-DOC.TXT AND THE CURRENT CODE DIVERGE ON ONE FACT:
      household-doc.txt §1 Ownership Contract claims
      "household.enterprises[] is the only household-owned field
      industry mutates." That is FALSE: industry also writes
      household.wealth via HouseholdCommands.updateHousehold during
      annual processing. The code and the industry-bootstrap.js header
      are authoritative. household-doc.txt should be updated to reflect
      the two-fact contract (enterprises[] reverse index + wealth).

  2.  GETCURRENTYEARSAFE IS THE DEPRECATED ALIAS.
      The household subsystem still uses getCurrentYearSafe in:
        household-orchestration.js (via _resolveNowYear, with fallback
                                    to getCurrentYear)
        household-economy.js (via _getCurrentYearSafe)
        modals-helper.js (via currentYear)
        household-bootstrap.js (verification)
      time.js marks the alias as @deprecated and plans to remove it.
      When it is removed:
        - household-orchestration.js silently falls back to
          getCurrentYear (the fallback is built in).
        - household-economy.js throws at load (no fallback in place).
        - modals-helper.js throws at load (no fallback in place).
        - household-bootstrap.js throws at init (the global is
          required).
      Fixing the last three requires:
        - household-economy.js: rename _getCurrentYearSafe's
          binding to prefer getCurrentYear, fall back to
          getCurrentYearSafe.
        - modals-helper.js: same fallback in currentYear.
        - household-bootstrap.js: replace the required-global check
          with "getCurrentYearSafe OR getCurrentYear".

  3.  INDUSTRYSTATE IS NOT A DEPENDENCY OF HOUSEHOLD-STATE DIAGNOSTICS.
      household-state.js::_checkEnterpriseReverseIndex reads
      masterData.data.enterprises directly, not via IndustryState.
      This is intentional: the diagnostics must work on a
      household-only page. But it means the household diagnostics
      cannot validate enterprise-side integrity (e.g. enterprise
      referencing a deleted household in masterData.data.households).
      For that check, use IndustryState.validateIntegrity (which
      requires the industry domain to be loaded). The two checks are
      complementary.

  4.  RESIDENCE SYSTEM HAS NO DEPENDENCY ON HOUSEHOLD COMMANDS AT LOAD.
      Both files guard the OTHER direction at call time via
      presence helpers. This means residence-system.js can load
      without household-commands.js and vice versa. The bootstrap
      then verifies both are present at init. A caller that loads
      residence-system.js WITHOUT household-commands.js will find
      that assignHouseholdToUnit returns
      HOUSEHOLD_COMMANDS_UNAVAILABLE. A caller that loads
      household-commands.js WITHOUT residence-system.js will find
      that deleteHousehold returns
      RESIDENCE_SYSTEM_UNAVAILABLE when the household has a
      residenceId. This is by design; neither file is a hard
      dependency of the other at load.

  5.  THE RETRY IDEMPOTENCY PATTERN IS SPECIFIC TO MODALS-HOUSEHOLD.JS.
      Only the create and edit household modals carry a
      mutation-succeeded flag. modals-household-snapshot.js's
      delete-name-period keeps the modal open on persist failure, but
      does NOT carry a retry flag. A retry of delete-name-period
      re-runs deleteNamePeriod on a NEW period (whatever lands at
      the same index after the first splice). This is a separate
      known issue — see the modals-household.js header.

  6.  DELETE HOUSEHOLD USES CONFIRMDIALOG AND CANNOT KEEP ITSELF
      OPEN.
      modals-household.js's openDeleteHouseholdModal uses
      confirmDialog. If the confirm click's command succeeds but the
      persist fails, the modal is already closed and cannot be
      reopened by the same onConfirm. The mutation is in memory; the
      persist failure is toasted. This is documented as a known
      limitation of the confirm-dialog shape.

  7.  CADET BRANCH ROLLBACK:
      createCadetBranch explicitly removes the head from the parent,
      then transfers the remaining members. If the head-removal fails,
      the new household is rolled back (deleteHousehold(
      removeFromCharacters: true)). If the ROLLBACK fails (e.g. the
      new household was already written to masterData and its
      deletion fails), the result carries
      {newHouseholdId: null, parentHouseholdId} and the head is
      duplicated. The rollback error is logged via console.error.

  8.  SPLIT HOUSEHOLD CARRIES THE SAME ROLLBACK HAZARD AS CADET
      BRANCH.
      splitHousehold applies the same head-removal pattern. The
      rollback path is the same.

  9.  ENTERPRISE TRANSFER IN MERGE / SPLIT / CADET IS
      PARTIAL-TOLERANT.
      mergeHouseholds, splitHousehold, and createCadetBranch report
      enterpriseFailed: true, partial: true when the enterprise side
      of the transfer fails. They do NOT roll back the household-side
      changes (member transfers are legitimate and standalone). This
      is documented in household-assignment.js's header.

 10.  HOUSEHOLD BUDGET DEFAULT UNIT COUNT:
      residence-system.js::createResidence computes a default
      unitCount from the residence type's capacity:
        Math.min(10, Math.max(1, Math.floor(type.capacity / 3)))
      This value comes from THRESHOLDS.DEFAULT_UNIT_COUNT_DIVISOR
      (divided by 3) and MAX_DEFAULT_UNIT_COUNT (min 10). The inline
      math here hard-codes 3 and 10 rather than reading the constants.
      A future change to those thresholds would not take effect unless
      the inline math is also updated. This is a known duplication; the
      canonical home is HouseholdConstants.THRESHOLDS.

 11.  MODALS-HELPER.JS'S currentYear PREFERS THE DEPRECATED ALIAS.
      If time.js eventually deletes getCurrentYearSafe, this helper
      returns null. See HAZARD 2 for the migration.

 12.  REVERSE-INDEX FAILURE POLICY IS HARD-BUT-NOT-ROLLED-BACK.
      When residence commands disassociate a household from a unit
      and the reverse-index update fails, the canonical unit
      occupancy is STILL cleared. The household's residenceId may
      remain stale. The failure is recorded in damageHistory and
      surfaced as reverseIndexFailed: true on the result. The
      corresponding integrity diagnostic (household-state's
      householdsWithMissingResidence) reports the drift. There is no
      automatic repair; a repair tool must walk the damageHistory
      entries.

 13.  HOUSEHOLD REFERENCES CLEANUP IS IDEMPOTENT BUT NOT
      TRANSACTIONAL.
      removeCharacterReferences and clearLocationReferences emit ONE
      commit for the whole sweep. If a later household's mutation
      throws mid-sweep, the earlier mutations are already in memory.
      The results reflect that (removedCount / clearedCount reflect
      the mutations that actually happened). Callers must check the
      result, not assume all-or-nothing.

 14.  THE HOUSEHOLD ↔ RESIDENCE REVERSE-INDEX CROSS-CHECK IS
      ONE-DIRECTIONAL AT EACH SIDE.
      household-state.js walks households -> enterprises and
      households -> residences (via residenceId). residence-system.js
      does NOT walk residences -> households (unit occupancy is
      canonical, and the walk is done by household-state's
      residencesWithOrphanHouseholdOccupancy check). The household-side
      check catches: dangling household.residenceId, and orphan unit
      occupancy. The combined checks cover both directions. Do not
      remove one without adding a symmetric check elsewhere.

 15.  HOUSEHOLD.STATE AND HOUSEHOLDCOMMANDS BOTH HAVE _COMMIT-NAME
      PRIMITIVES.
      household-commands.js::_commit marks dirty, invalidates
      accessor cache, and dispatches events. household-state.js's
      mutation primitives (replaceHouseholds etc.) markDirty but do
      NOT dispatch events. The calling command's _commit is the
      dispatch boundary. This is the contract; do not add dispatch
      to household-state's primitives.

 16.  THE HOUSEHOLD UI LIST USES LOCALSTORAGE FOR PREFERENCES.
      Key 'household_list_state_v6'. Preferences are validated
      against VALID_STATUS_FILTERS on read. A malformed status filter
      falls back to 'all'. If localStorage throws (quota,
      private-browsing mode), the preferences silently become
      in-memory only. There is no isPersistent() reporting for this
      component; callers that need to know can check whether
      localStorage is writable independently.

 17.  MODALS-RESIDENCE-SNAPSHOT.JS IS A DEPRECATED STUB.
      It defines NO functions. It verifies modals-household-snapshot.js
      loaded. Loading it AFTER that file produces a console.warn in
      every build. The script tag should be removed from index.html.
      Until it is, the warning is the intended behavior.

 18.  MODALS-ASSIGN-STAFF.JS, MODALS-RESIDENCE-HISTORY.JS, AND
      MODALS-RESIDENCE-VACANCY.JS ARE COMPATIBILITY SHIMS.
      Each verifies its canonical owner loaded first, then does
      nothing but expose a diagnostic namespace. They should be
      deleted from index.html once external callers are audited.

 19.  THE HOUSEHOLD STAFF MODAL HAS AN ADD-ROLE-IF-MISSING CHECKBOX.
      The residence staff modal DOES NOT. This is by design:
      HouseholdCommands.assignCharacterToPosition supports
      addRoleIfMissing, but ResidenceSystem.assignCharacterToStaffPosition
      does not. Do not add the checkbox to the residence staff modal
      without first adding the option to the residence command.

 20.  BULK ASSIGN ALWAYS PASSES addRoleIfMissing: true.
      modals-household-staff.js's bulk-assign path passes
      addRoleIfMissing: true to bulkAssign unconditionally. Per-entry
      failures surface in result.data.failed with code
      ROLE_ADD_FAILED. If a future revision changes bulkAssign's
      default, this call site must be updated.

 21.  setHead IS SINGLE-COMMIT BUT addMember IS NOT.
      setHead creates the member record inline (via _addMemberRecord,
      no commit) when the character is not a member, then commits
      once. addMember commits once per call. Callers that use
      setHead on a non-member get the single-commit behavior; callers
      that pre-add via addMember then call setHead get TWO commits.
      Prefer setHead's single-commit path when you know the
      character needs to become head AND become a member.

 22.  updateHousehold'S EMPTY-UPDATES CASE IS A VALID TOUCH.
      updateHousehold({}) commits (marks dirty, invalidates accessor
      cache, publishes 'householdUpdated') but changes no fields. The
      intended use is signaling out-of-band mutations. Do not
      "optimize" this into a no-op; callers depend on the event.

 23.  THE ACCESSOR CACHE CONTRACT IS NOT UNIFORM ACROSS FILES.
      household-commands.js::_commit and residence-system.js::_commit
      invalidate the accessor cache. household-state.js does NOT
      (there is no household accessor). If a future revision adds
      getHouseholdById to accessors.js, household-state.js's
      _replace* primitives MUST gain the call. See the contract in
      §2.5.

 24.  HOUSEHOLD-ECONOMY'S getHouseholdResources READS
      HouseholdState._internal DIRECTLY.
      household-economy.js's getHouseholdResources calls
      HouseholdState._internal.getHouseholdRecord to read the raw
      resources object, rather than going through
      HouseholdQueries. The queries projection does not include a
      resources snapshot (by design — the resources catalog is owned
      by HouseholdConstants). This coupling is intentional but should
      be noted: if household-queries is ever changed to include a
      resources accessor, household-economy should prefer that.

 25.  INDUSTRY STATE AND HOUSEHOLD REVERSE-INDEX CROSS-CHECKS
      DUPLICATE WORK IN PRODUCTION.
      Both industry-state.validateIntegrity and household-state.
      _diagnostics.getIntegrityReport perform the household ->
      enterprises cross-check. Running both doubles the work. There is
      no harm beyond performance; both are read-only. A future
      consolidation could make one a consumer of the other, but the
      current design (each domain reports on what it owns) is
      defensible.

 26.  MODAL FILES DO NOT COORDINATE PERSIST WITH THE BOOTSTRAP.
      Each modal's onConfirm calls HouseholdModals.persistOrFail or
      persistResidenceOrFail. The bootstrap does NOT track per-modal
      persist outcomes. A persist failure is toasted and stays open
      for retry; a subsequent success adds a second event to the
      event stream. This matches the modal-per-operation contract but
      means a user who repeatedly clicks Save after persist failures
      generates N events for what should be one logical operation. The
      retry-idempotency flag on modals-household.js create/edit
      prevents this for those two modals; other modals do not have
      the guard.

 27.  HOUSEHOLD.ASSIGNMENT IS NOT ATOMIC ACROSS HOUSEHOLDS.
      processHouseholdInheritanceOnDeath iterates households and
      treats each as its own orchestration (each persists once). A
      failure on household 2 does not roll back household 1. The
      result reports partial: true and lists the processed array. The
      caller must inspect per-household results.

 28.  HOUSEHOLD.SERVANT'S TRANSFER IS NOT ATOMIC.
      transferServantToHousehold creates the new service FIRST, then
      terminates the old. If termination fails, the new service is
      best-effort rolled back. A rollback failure leaves the servant
      in BOTH services' active lists (both have status: 'ongoing' but
      the old one is stale). This is a documented hazard; the fix
      would require a cross-domain transaction framework, which is out
      of scope for the household subsystem.

 29.  MODALS-RESIDENCE-RENTAL.JS'S _persistOrFail DOES NOT DELEGATE TO
      HouseholdModals.persistResidenceOrFail.
      The residence-rental modal defines its OWN local
      _persistOrFail. It should use HouseholdModals.
      persistResidenceOrFail (as modals-residence.js,
      modals-residence-owner.js, and modals-residence-staff.js do).
      The behavior is currently identical, but this is a duplication
      that must be removed. See the modals-residence-rental.js header
      (this file has not yet been updated to the shared helper).

 30.  modals-residence-rental.js HAD TWO IIFEs IN A SINGLE FILE.
      The on-disk version had a syntax error (two stacked IIFEs under
      a shared header, second header commented out). The supplied file
      is a single IIFE with all function definitions consolidated.
      Confirm the on-disk copy was replaced with this version before
      deploying.

 31.  MODALS-RESIDENCE-OWNER.JS'S setResidenceOwner PATH DOES NOT
      VERIFY THE OWNER TYPE.
      openTransferOwnershipModal and openSetResidenceOwnerModal call
      ResidenceSystem.setResidenceOwner(residenceId, ownerType,
      ownerId, ...). The command itself validates the owner type
      (household or character). The modals do NOT pre-check; they rely
      on the command's structured failure. This is intentional
      layering but means the user can enter an invalid state and see
      the failure after clicking Save.

 32.  RENTAL STATUS IS DERIVED, NOT WRITTEN DIRECTLY.
      setResidenceRenter sets rentalStatus = RENTED.
      endResidenceRental sets rentalStatus = VACANT.
      setResidenceOwner sets rentalStatus = VACANT only when there is
      no current renter. A future owner change with an active renter
      leaves rentalStatus = RENTED. This is correct (the residence is
      still rented) but means rentalStatus is NOT a simple
      `ownerId != null && renterId != null` predicate. Do not derive
      it yourself; read the field.

 33.  RESIDENCE-SYSTEM'S demoted _pushHistory / _pushTimeline
      COEXIST WITH SUPERSEDED CONTRACTS.
      _pushTimeline always accepted an explicit year. _pushHistory
      now does (this revision). The year parameter is optional; when
      omitted it falls back to getCurrentYear(). A multi-year
      simulation driver must pass the explicit year, or every entry
      in the batch will be tagged with wall-clock now. This matches
      the processAnnualEconomy contract documented in
      household-economy.js.

 34.  THE HOUSEHOLD SUBSYSTEM'S BOOTSTRAP DOES NOT DIAGNOSE
      ENTERPRISE DRIFT DIRECTLY.
      household-bootstrap.js does not run the enterprise reverse-index
      check. That check lives on HouseholdState._diagnostics (which
      bootstrap does not automatically call) and on
      IndustryState.validateIntegrity (which requires the industry
      domain to load and its bootstrap to run). A caller that wants
      a complete integrity audit must run:
        (1) HouseholdBootstrap.init()
        (2) HouseholdState._diagnostics.getIntegrityReport()
        (3) IndustryBootstrap.init()
      A household-only page runs (1) and (2) and still gets
      enterprise drift detection via (2)'s direct read of
      masterData.data.enterprises.

 35.  REMOVE-CHARACTER-REFERENCES AND CLEAR-LOCATION-REFERENCES
      RETURN COUNTS UNDER result.data, NOT result.
      This is the _ok convention used by the rest of
      household-commands.js. location-commands.js and
      character-deletion-commands.js must read
      result.data.clearedCount (or .removedCount), NOT
      result.clearedCount. Prior revisions returned counts at the
      top level, and deletePlace's cleanup report silently reported
      clearedCount: 0 for every successful sweep. Do not reintroduce
      the top-level shape.

 36.  HOUSEHOLD-DOC.TXT IS NARRATIVE, NOT AUTHORITATIVE.
      The supplied household-doc.txt v6.1 describes the intended
      contract. The supplied code is authoritative where they
      diverge. Divergences:
        - The v6.1 doc says "household.enterprises[] is the only
          household-owned field industry mutates." That is stale
          (wealth is also written). The code and the
          industry-bootstrap.js header are correct.
        - The v6.1 doc lists "modals-assign-staff.js,
          modals-residence-history.js, modals-residence-snapshot.js,
          modals-residence-vacancy.js" as DELETED. They are present
          as shims or deprecated stubs. Confirm they are removed
          from index.html; the shims throw only when their canonical
          owner is missing, which is not the failure mode they were
          meant to prevent.

 37.  THE HOUSEHOLD SUBSYSTEM'S MODALS-TESTED-VIA-BOOTSTRAP PATH IS
      INCOMPLETE.
      household-bootstrap.js verifies HouseholdModals with
      _checkOptionalModule (only if present). It does NOT verify the
      individual modals-*.js globals (openCreateHouseholdModal etc.).
      A missing modal file produces a runtime missing-function error
      when a user clicks the corresponding button, not a load-time
      error. This is intentional layering (the modals layer is not
      part of the domain's verified surface) but means modal-level
      regressions are caught later. Adding a per-modal presence check
      is a future improvement.

 38.  modals-residence.js AND modals-household.js BOTH EXPORT
      openAssignResidenceModal. There is one function; both files
      work with the same namespace when loaded together. No collision.

 39.  modals-residence-rental.js ALSO EXPORTS
      openSetResidenceOwnerModal.
      This OVERLAPS modals-residence-owner.js's owner modal surface.
      modals-residence-owner.js exports openResidenceOwnerDetailsModal,
      openManageOwnedPropertiesModal, openTransferOwnershipModal,
      openOwnerStatsModal — different functions. There is no
      collision. openSetResidenceOwnerModal is defined ONLY in
      modals-residence-rental.js.

 40.  THE HOUSEHOLD LIST COMPONENT DOES NOT RESUBSCRIBE ON REMOUNT.
      mountHouseholdList stores a single unsubscribe handle. Calling
      mount twice replaces the previous handle (unmounting implicitly
      the previous subscription). If a caller mounts a second time
      without unmounting first, the first handle is orphaned. Do not
      assume multiple simultaneous mounts on different containers.
