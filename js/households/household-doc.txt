# HOUSEHOLD & RESIDENCE SYSTEM - ARCHITECTURE DOCUMENTATION

Version: 6.1 (post-consolidation)
Supersedes: v6.0 (post-consolidation), v5.0 (post-refactor), v4.0

================================================================================
SYSTEM OVERVIEW
================================================================================

The Household & Residence System manages household structures, family
units, staff, departments, residence ownership and occupancy, rental
contracts, and integration with enterprises, character, family,
relationship, and industry domains.

The v5.0 refactor established clear ownership boundaries, removed
global processing mutexes, eliminated fabricated domain defaults, and
routed all mutations through explicit command layers.

The v6.0 revision consolidated three latent bugs the v5.0 refactor
left behind:

  1. Constant and rule duplication. The economy and servant modules
     carried private copies of the economic catalogs and quality
     thresholds. Those copies were removed; every household module now
     reads from household-constants.js (catalogs) and household-rules.js
     (pure policy).

  2. Reverse-index corruption. household.residenceId and
     residence.units[].householdId are two views of the same fact. When
     a mutation on one side fails to update the other, the divergence
     survived indefinitely with no signal. Reverse-index failures are
     now hard failures (reverseIndexFailed:true on the result, plus a
     damageHistory entry on the residence), and household-state.js
     diagnostics cross-check both sides.

  3. Multi-year simulation clock drift. HouseholdEconomy.processAnnualEconomy
     and CharacterLifecycle.advanceMortality both used wall-clock "now"
     for year-tagged accounting, so a 5-year advance produced 5 ledger
     entries all tagged with the same year. Both now accept an explicit
     year and propagate it through every calculation.

This v6.1 revision closes three latent bugs the v6.0 consolidation
left behind:

  4. Residence inline catalog duplication. residence-system.js still
     carried inline copies of RESIDENCE_TYPES, RESIDENCE_STATUS,
     RENTAL_STATUS, RESIDENCE_CONDITIONS, CONDITION_MULTIPLIER, and the
     history-cap thresholds, even though the same values lived in
     household-constants.js. Those inline copies were removed;
     HouseholdConstants is now a HARD load-time dependency of
     residence-system.js, and every residence catalog read goes through
     it. A divergence between the two copies (e.g. increasing
     ESTATE.capacity in constants.js while residence-system.js still
     used the old value) is now structurally impossible.

  5. Storage schema household collections. household-bootstrap.js's
     canonical verification requires masterData.data.households,
     masterData.data.householdPositions, and
     masterData.data.householdAssignments to all be arrays at load
     time. Prior revisions of storage-schema.js declared only
     `households`. Every fresh install and every save that predated
     the household subdomain therefore threw at household bootstrap
     with "householdPositions must be an array". Both auxiliary
     collections are now declared in the factory and in the
     normalization pass. The fix is additive and defaults safely for
     old saves.

  6. household-commands.js load-time optional dependency flags.
     `_residenceSystemPresent` and `_industryCommandsPresent` were
     frozen at load. The documented HTML load order places
     residence-system.js AFTER household-commands.js, so the flag
     froze to false. Every deleteHousehold call that touched a
     residence returned RESIDENCE_SYSTEM_UNAVAILABLE — even though
     ResidenceSystem was loaded by the time the command ran. The flags
     are now call-time helpers (_residenceSystemAvailable,
     _industryCommandsAvailable) that resolve the optional dependency
     at command time. Load-order changes in either direction no longer
     affect behaviour.

KEY DESIGN PRINCIPLES
================================================================================

1. SINGLE RESPONSIBILITY PER LAYER

   Each layer owns exactly one kind of operation:

     Constants    → canonical catalogs, thresholds, multipliers
     Rules        → pure policy and calculation (no I/O, no state)
     View Models  → presentation defaults, form helpers, color helpers
     Orchestration→ shared result/dispatch/finish helpers for
                    multi-command coordinators
     State        → canonical storage, indexes, cache, subscriptions
     Queries      → semantic reads returning defensive snapshots
     Commands     → canonical mutations, transaction boundary, persistence
     Assignment   → cross-operation orchestration (newborn, spouse,
                    inheritance, cadet, merge, split)
     Servant      → service-relationship orchestration
     Economy      → wealth / debt / resource accounting, rent, trade
     Residence    → residence CRUD, units, occupancy, rental, staff
     Bootstrap    → load-time verification + hydration + diagnostics
     UI           → rendering, input collection, presentation, toasts

2. NO DUPLICATED CATALOGS OR RULES

   Before v6.0, ECONOMIC_TIERS / INCOME_SOURCES / EXPENSE_CATEGORIES /
   ECONOMIC_EVENTS / SERVICE_TYPES / SERVICE_QUALITY /
   SERVICE_QUALITY_ORDER existed in three places:
     - household-constants.js (canonical)
     - household-economy.js and household-servant.js (private copies)
     - household-rules.js (inline fallbacks)

   After v6.0 there is exactly one copy of each economic/service
   catalog, in household-constants.js. household-rules.js consumes
   it; household-economy.js and household-servant.js import it.

   Before v6.1, the residence catalogs (RESIDENCE_TYPES /
   RESIDENCE_STATUS / RENTAL_STATUS / RESIDENCE_CONDITIONS /
   CONDITION_MULTIPLIER) and the history-cap thresholds were
   duplicated between household-constants.js and residence-system.js.
   After v6.1, residence-system.js reads them from HouseholdConstants;
   the inline copies are gone.

   The rule: every catalog has exactly one canonical home. Domain
   modules that need a catalog either consume HouseholdConstants
   directly or a domain-specific Rules module that consumes
   HouseholdConstants. No module carries a private copy.

3. NO GLOBAL PROCESSING MUTEXES

   The pre-refactor system used `_processingX` boolean flags across
   modules. These broke legitimate composition: a command that
   internally called another command would find itself locked out.

   All such guards have been removed. Commands compose freely.

4. NO FABRICATED DOMAIN DEFAULTS

   Missing infrastructure is never converted into valid-looking domain
   data. No magic 1250 year. No silent empty array in place of a
   missing collection. No fabricated {mother: null, father: null} in
   place of a missing parent.

   Required dependencies fail loudly. Empty results are only returned
   when the domain fact is genuinely empty.

5. NO LIVE RECORD LEAKS

   Public queries return defensive snapshots, not live canonical
   objects. Callers cannot mutate domain state without going through
   commands.

6. ONE PERSISTENCE BOUNDARY PER LOGICAL OPERATION

   Each command performs exactly one commit. Helper functions that
   touch the canonical record do NOT persist; the top-level command
   does, once.

   Orchestrators (assignment, servant) end with a single _finish call
   that dispatches the event and persists the household system.
   Servant additionally persists the relationship system, since
   service-relationship writes live there.

7. STRUCTURED COMMAND RESULTS

   Every command returns:
     { success: true, data: ... }
   or:
     { success: false, code: 'SOME_CODE', reason: 'human message',
       partial: true (when partial mutation occurred),
       ...extra fields }

   No more boolean `success` returns mixed with object returns.

8. REVERSE-INDEX DISCIPLINE

   The household↔residence relationship is two views of one fact:

     household.residenceId          (household-owned reverse index)
     household.residenceUnitNumber  (household-owned reverse index)
     residence.units[].householdId  (canonical occupancy)

   ResidenceSystem is the single authority that mutates unit occupancy.
   It calls HouseholdCommands.associateWithResidence /
   disassociateFromResidence to keep the reverse index in step.

   When the reverse-index update fails:
     - the residence mutation still succeeds (canonical occupancy is
       what it is),
     - the result carries reverseIndexFailed:true and the specific
       failures list,
     - a reverse_index_failure entry is appended to the residence's
       damageHistory (persistent audit trail).

   household-state.js's _diagnostics.getIntegrityReport() cross-checks
   both directions:
     - householdsWithMissingResidence: household.residenceId points
       at a residence that no longer exists
     - residencesWithOrphanHouseholdOccupancy: residence unit still
       names a householdId that no longer exists
     - residenceReverseIndexAvailable: false if the check couldn't run
       (ResidenceSystem not loaded and canonical residences not yet
       populated)

9. CALL-TIME OPTIONAL DEPENDENCIES

   Optional cross-domain dependencies (ResidenceSystem, IndustryCommands,
   RelationshipCommands) are resolved at CALL time, not load time.
   A load-time presence flag freezes to whatever the state was when
   household-commands.js parsed. Under the documented HTML load order,
   that is BEFORE ResidenceSystem loads, so the flag freezes to false
   and every residence-touching command fails even though the module
   is loaded by the time the command runs.

   Call-time resolution (via _residenceSystemAvailable() and friends)
   makes the flag's answer depend on the state at command time, which
   is the only semantic that makes sense for an optional dependency.

household-orchestration.js
──────────────────────────
PURPOSE:
  Shared helpers for multi-command orchestrators (assignment,
  servant). Not a domain module; owns no state, no policy, no catalogs.

PROVIDES:
  • Result builders: ok(data), fail(code, reason, extra)
  • Year resolution: resolveYear(value) → number|null
  • Event dispatch: dispatch(eventName, payload) — never throws
  • Batch close: finish(eventName, payload) — dispatches then
    persists the household system once
  • Small validators: hasId, isPlainObject, isFiniteNumber

CONTRACT:
  • finish dispatches BEFORE persist. Subscribers observe the
    post-mutation in-memory state; a subscriber that triggers further
    writes gets those included in the same save.
  • finish does NOT persist the relationship system. Servant wraps
    finish with its own _finish that adds the relationship persist.

ADD-ROLE-IF-MISSING CONTRACT (Prompt 33):

  assignCharacterToPosition and bulkAssign accept
  options.addRoleIfMissing. When true and the position requires a role
  the character lacks, the profession is added via
  CharacterCommands.addProfession before assignment. If the
  profession cannot be added, the assignment is REFUSED with code
  ROLE_ADD_FAILED (the caller asked for the role to be added; silently
  skipping would produce an assignment whose precondition was not met).

  When addRoleIfMissing is false/absent, the assignment proceeds. The
  result carries roleWarning when a required role is missing but the
  caller opted out of auto-adding.

CROSS-DOMAIN CLEANUP CONTRACT:

  removeCharacterReferences(characterId) and
  clearLocationReferences(locationId) are cross-domain sweep hooks
  dispatched by character-deletion-commands.js and
  location-commands.js respectively. Both:

    • Return { success: true, data: { ... } } with counts and the
      affected-records list nested under `data`, matching the _ok
      convention used elsewhere in this module.
    • Emit exactly ONE commit for the whole sweep (event
      'householdReferencesRemoved' or 'householdsLocationCleared'),
      not one per affected household.
    • Do NOT persist. The calling orchestration owns the batch
      persistence boundary.
    • Are idempotent. Re-running against an already-cleaned target
      returns success with count: 0 and does not commit.

  The `data` nesting matters: location-commands.js reads
  result.data.clearedCount when it reports household reconciliation
  status. Prior revisions of this module returned the count at the
  top level, so deletePlace's cleanup report silently reported
  clearedCount: 0 for every cascade. The nesting is now explicit at
  both ends of the contract.

household-economy.js
────────────────────
OWNER OF:
  • Pure economic calculations (delegating to HouseholdRules for the
    thresholds; reading HouseholdConstants for the catalogs)
  • Wealth/debt/resource mutation via HouseholdCommands.updateHousehold
    with real patch objects
  • Annual economy processing
  • Trade
  • Bankruptcy

PERSIST CONTRACT:
  • _applyMutation is the ONLY place this module mutates a household.
    It runs a pure projection function (mutator) to build a patch,
    applies the patch via HouseholdCommands.updateHousehold, then
    persists via HouseholdCommands.persist.
  • One _applyMutation = one commit + one persist.
  • The prior version mutated the live record directly and used
    updateHousehold(id, {}) as a "touch" hack. That is gone.

CLOCK CONTRACT:
  • Every calculation accepts options.year. When omitted, the fallback
    is getCurrentYearSafe().
  • processAnnualEconomy(householdId, { year }) applies annual income
    and expenses against the specified year.
  • This is required so a multi-year simulation driver can call
    processAnnualEconomy(householdId, { year: y }) for each simulated
    year without every entry collapsing onto wall-clock now.

RANDOMNESS:
  • No Math.random anywhere. Event deltas come from
    HouseholdConstants.getEconomicEventDelta(eventId, randomFn).
  • randomFn is options.random (caller-supplied) or window.random
    (from randomness.js). Missing both throws — silent fallback to
    Math.random would break seeded reproducibility.

PURE CALCULATIONS:

  getHouseholdResources

CROSS-DOMAIN INTEGRATION
================================================================================

Household ↔ Character:
  • character.household / character.householdId  — reverse index
  • character.householdHistory[]                 — full history
  • household.members[]                          — canonical membership
  • Updates flow through HouseholdCommands.addMember/removeMember

Household ↔ Residence (CRITICAL):
  • CANONICAL: unit.householdId
  • Household reverse index maintained by HouseholdCommands
  • ResidenceSystem.assignHouseholdToUnit() updates both sides
  • markResidenceVacant() disassociates every affected household
  • Reverse-index failures are hard (reverseIndexFailed) and
    persistent (damageHistory)
  • HouseholdState._diagnostics cross-checks both directions

Household ↔ Industry (Enterprise ownership):
  • CANONICAL: enterprise.ownerId / enterprise.ownerType
  • Household maintains enterprises[] as a REVERSE INDEX
  • Updates flow through IndustryCommands.updateEnterprise()
  • HouseholdCommands does NOT own enterprise ownership
  • HouseholdAssignment hard-fails enterprise transfer if
    IndustryCommands is unavailable AND the household has enterprises

Household ↔ Economy (Government salaries, taxes):
  • Government salary → HouseholdEconomy.receiveSalary()
  • Salaries stored in economy.salaryIncome + salaryIncomeHistory
  • Wealth updated via HouseholdCommands.updateHousehold
  • Taxes flow through HouseholdEconomy.updateHouseholdWealth()

Household ↔ Servant (Master-servant relationships):
  • Canonical relationship owned by Relationship system
  • Household membership owned by HouseholdCommands
  • HouseholdServant orchestrates between them
  • Persists BOTH domains; result reports both save outcomes

Household ↔ Family (Parentage, kinship):
  • Parentage canonical: FamilyState.parentChildEdges
  • Household ↔ Family interaction is READ-ONLY in the household
    domain (queries via FamilyQueries)

Residence ↔ Rental (Rent income/expenses):
  • residence.ownerId/renterId/rentAmount         — canonical contract
  • residence.rentalHistory/rentPayments          — canonical history
  • HouseholdEconomy.calculateRentIncome/Expenses reads these
  • No duplicate rent tracking in household records

COMMAND RESULT CONTRACT
================================================================================

Every command returns one of:

  { success: true,  data: <any> }
  { success: false, code: 'SOME_CODE', reason: 'human-readable message' }

Some commands add:
  partial: true      when some but not all sub-operations succeeded
  reverseIndexFailed: true    when a reverse-index update failed
  roleWarning: {...}          when a required role was missing but the
                              caller opted out of auto-adding
  industryAvailable: false    when industry transfer couldn't run
  householdPersisted / relationshipPersisted    on orchestrator
                                                 cross-domain results

Common codes:
  INVALID_INPUT, INVALID_NAME, INVALID_YEAR, INVALID_TYPE, INVALID_WAGE,
  NOT_FOUND, ALREADY_MEMBER, NOT_MEMBER, CHARACTER_NOT_FOUND,
  HOUSEHOLD_NOT_FOUND, POSITION_NOT_FOUND, ASSIGNMENT_NOT_FOUND,
  RESIDENCE_NOT_FOUND, DUPLICATE_NAME, ALREADY_ASSIGNED, ALREADY_ENDED,
  INVALID_YEAR_RANGE, OCCUPIED_UNITS, NO_VACANT_UNIT, NO_OWNER, NO_RENTER,
  INSUFFICIENT_WEALTH, INSUFFICIENT_FOOD, INSUFFICIENT_GOODS,
  DEMOLISHED, CANNOT_DELETE_LAST, SAME_NAME, SAME_CONDITION,
  INDUSTRY_COMMANDS_UNAVAILABLE, ROLE_ADD_FAILED,
  RELATIONSHIP_PERSIST_FAILED, PERSIST_FAILED, SAVE_FAILED

CROSS-DOMAIN CLEANUP RESULT SHAPE:

  Commands that emit a cross-domain sweep (removeCharacterReferences,
  clearLocationReferences, and any future sweep hook) nest their
  counts and affected-records list under `data`:

    {
      success: true,
      data: {
        clearedCount: number,
        households: Array<{ householdId, householdName, ... }>,
        // or
        removedCount: number,
        households: Array<{ householdId, householdName, ... }>
      }
    }

  This matches the _ok convention used by the rest of the module.
  Callers that need the count read `result.data.clearedCount` (not
  `result.clearedCount`). Prior revisions returned the count at the
  top level; location-commands.js's deletePlace cleanup report
  silently reported 0 for every successful sweep as a result.

Bulk operations:
  { success: true, data: { succeeded: [...], failed: [...],
                           warnings: [...] } }
  with explicit per-item failure reasons.

STORAGE SCHEMA (cross-reference)
================================================================================

The household domain's canonical collections live in masterData.data:

  households              array   (household records)
  householdPositions      array   (staff position records)
  householdAssignments    array   (staff assignment records)

All three are declared in storage-schema.js's factory
(createDefaultMasterDataOverride) and in the normalization pass
(normalizeMasterData's arrayKeys list). Prior to v6.1, only
`households` was declared. See STORAGE SCHEMA in storage-schema.js
and the character-doc.txt §4.3 for the full envelope shape.

Per-record sub-fields (enterprises, eventLog, nameHistory, units,
history, timeline, etc.) are normalized by the respective state
modules at hydrate time (household-state.js::_ensureHouseholdShape,
residence-system.js::_ensureResidenceShape), not by storage-schema.js.
This is consistent with how the character domain handles embedded
domain containers.

KEY BUGS FIXED (v5.0 → v6.1)
================================================================================

1. Triple economic catalog
   ECONOMIC_TIERS / INCOME_SOURCES / EXPENSE_CATEGORIES /
   ECONOMIC_EVENTS existed in household-constants.js,
   household-economy.js, and household-rules.js. Now: one copy in
   household-constants.js.

2. SERVICE_TYPES window binding collision
   household-servant.js unconditionally overwrote window.SERVICE_TYPES
   with a mutable copy of its own catalog, silently disabling the
   frozen guarantee. Now: guarded aliases.

3. Math.random in economy and constants
   ECONOMIC_EVENTS.*.delta() used Math.random(). Now: the catalog
   carries minDelta/maxDelta; getEconomicEventDelta(eventId, randomFn)
   takes a caller-supplied RNG.

4. Double-commit in _applyMutation
   household-economy.js called updateHousehold(id, {}) as a "touch"
   commit AND then published a domain-specific event. Now: it builds
   a real patch and calls updateHousehold(householdId, patch) once.

5. Multi-year simulation clock drift
   CharacterLifecycle.advanceMortality iterated currentYear + offset
   but never advanced masterData.currentYear, so a second call replayed
   the same years. HouseholdEconomy.processAnnualEconomy used
   getCurrentYearSafe() internally, so every year's ledger landed on
   the wall-clock year. Both now accept explicit years.

6. Silent reverse-index corruption
   Reverse-index failures were reported as reverseIndexWarning but
   universally ignored. Now: hard reverseIndexFailed field,
   damageHistory audit entry, and household-state diagnostics that
   surface drift through householdsWithMissingResidence and
   residencesWithOrphanHouseholdOccupancy.

7. Cadet branch head dangling membership
   HouseholdAssignment.createCadetBranch added the head to the new
   household via createHousehold(headId), then skipped the head in
   the transfer loop, leaving the head as a member of BOTH the parent
   and the new household. Now: the head is explicitly removed from
   the parent before transferring the rest.

8. setHead double-commit
   household-commands.js setHead called addMember for non-member
   characters, producing two commits (one for the add, one for the
   head change) and two different events. Now: single commit, event
   householdHeadSet, addedInline flag in the result.

9. Service relationship persistence gap
   household-servant.js persisted only the household system; service-
   relationship writes were left in the relationship domain's memory.
   Now: _finish persists both, reports both save outcomes.

10. Dead parentage reads in query-helpers.js
    getCharacterParents / getCharacterChildren / getCharacterHasChildren
    read char.motherId / char.fatherId — dead fields. Every call
    returned null/false on any post-refactor dataset. Now: delegated to
    FamilyQueries.

11. Dead relationship reads in selector-base.js
    isBloodRelativeBasic / isSpouseBasic read char.motherId /
    char.fatherId / char.relationships. Every call returned false.
    Now: delegated to FamilyQueries.isBloodRelated and
    getRelationshipBetween.

12. FamilyAccessors references in modals-household-selector.js
    The picker resolved "current household" and "relatives in this
    household" via the deleted FamilyAccessors module. Now: reads
    HouseholdQueries and FamilyQueries directly.

13. Magic-depth caps in location hierarchy walkers
    locationDropdown.js and query-helpers.js capped hierarchy walk
    at 20 iterations, contradicting world.js's Set-based cycle
    detection. Now: both use Set-based cycle detection.

14. getLocationCountry / getLocationDistrict used priority
    Both read locationType.priority (legacy schema) instead of
    locationType.locationScope (current schema). Now: prefer scope,
    fall back to priority only when scope is undefined (legacy).

15. AGE_GROUPS_MAP phantom in query-helpers.js
    getAgeGroupLabel read window.AGE_GROUPS_MAP, which doesn't exist
    in the current tree. Every call fell through to the raw band-key
    string. Now: walks LIFE_STAGES for a matching group when the map
    is absent.

16. Residence inline catalog duplication (v6.1)
    residence-system.js carried inline copies of RESIDENCE_TYPES,
    RESIDENCE_STATUS, RENTAL_STATUS, RESIDENCE_CONDITIONS,
    CONDITION_MULTIPLIER, and the history-cap thresholds. The copies
    were byte-identical to household-constants.js at every revision
    they existed, but the divergence risk was real: a policy change
    in constants.js would silently not take effect in
    residence-system.js, so a consumer reading the constants catalog
    and a consumer reading ResidenceSystem's copies would see different
    values. Now: household-constants.js is a HARD load-time dependency
    of residence-system.js, every catalog read goes through it, and
    the inline copies are gone.

17. Storage schema household collections (v6.1)
    storage-schema.js declared `households` but not
    `householdPositions` or `householdAssignments`. household-bootstrap.js
    requires all three to be arrays. Every fresh install and every
    save that predated the household subdomain failed bootstrap with
    "householdPositions must be an array". Now: all three declared in
    the factory and in the normalization pass.

18. Load-time optional dependency flags (v6.1)
    household-commands.js froze _residenceSystemPresent and
    _industryCommandsPresent at load time. Under the documented HTML
    order, residence-system.js loads AFTER household-commands.js, so
    the flag froze to false. Every deleteHousehold call that touched a
    residence returned RESIDENCE_SYSTEM_UNAVAILABLE. Now: both are
    call-time helpers (_residenceSystemAvailable,
    _industryCommandsAvailable). See KEY DESIGN PRINCIPLES #9.

19. Cross-domain cleanup result shape divergence (v6.1)
    location-commands.js::_cleanupHouseholdsAtPlaces read
    result.clearedCount from HouseholdCommands.clearLocationReferences.
    But clearLocationReferences returns { success: true, data:
    { clearedCount, households } } — the count is nested under `data`,
    not at the top level. So every successful household cleanup
    reported clearedCount: 0 in the deletePlace result. Now: the
    nesting is documented at both ends of the contract. See COMMAND
    RESULT CONTRACT.

REMAINING ARCHITECTURAL DEBT
================================================================================

1. ResidenceSystem is still a single large file
   It has not been split into ResidenceState / ResidenceQueries /
   ResidenceCommands / ResidenceRules. That split is deferred until
   either the file exceeds ~1500 lines or a second consumer forces it.

2. household-view-models.js uses inline defaults for some catalogs
   getResidenceConditionOptions and getResidenceTypeOptions fall back
   to inline defaults when HouseholdConstants isn't loaded. The values
   match the current catalog exactly. This is intentional so the file
   can be tested in isolation; the fallbacks will be removed once the
   constants are guaranteed to load.

3. HouseholdRules does not model economic policy beyond what
   HouseholdEconomy delegates. Complex policy (bracket rates, tier
   progression over time, tax structures) is still inline in
   HouseholdEconomy. Extraction is deferred until a second consumer
   appears.

4. Cross-domain atomicity in HouseholdAssignment and HouseholdServant
   is not transactional. Failure in one subsystem can leave partial
   state. Both modules report partial:true and their results carry
   enough information for a caller to resume or report the failure.
   A proper transaction framework is out of scope.

5. The modals-*.js files still share some inline HTML helpers.
   _buildOwnerDetailsContent, _buildSnapshotContent, etc. could be
   extracted to a shared HTML-builder module. Currently they live
   where they're used, which is a reasonable trade-off (the HTML is
   tightly coupled to each modal's data shape).

6. ResidenceSystem's _householdCommandsPresent and
   _householdQueriesPresent flags are still load-time.
   ResidenceSystem loads AFTER household-commands.js and
   household-queries.js in the documented order, so the flags freeze
   to true and no command fails. But the same fragility exists here as
   in household-commands.js: a load-order change in either direction
   would freeze the flags incorrectly. Converting them to call-time
   helpers (matching the v6.1 fix in household-commands.js) is a
   mechanical pass with no behavioural change today.

7. History array caps (MAX_TIMELINE_ENTRIES, MAX_HISTORY_ENTRIES,
   MAX_RENTAL_HISTORY, MAX_RENT_PAYMENTS, MAX_TRANSACTION_HISTORY,
   MAX_RESOURCE_HISTORY, MAX_SALARY_HISTORY, MAX_TUITION_HISTORY,
   MAX_SCHOOL_PROFIT_HISTORY, MAX_EVENT_LOG) are now sourced from
   household-constants.js THRESHOLDS in both household-economy.js and
   residence-system.js. The prior duplication is closed. Item #7 from
   v6.0 is retired.
