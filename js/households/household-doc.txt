# HOUSEHOLD & RESIDENCE SYSTEM - ARCHITECTURE DOCUMENTATION
#
# Version: 5.0 (post-refactor)
# Replaces: household-doc.txt v4.0

================================================================================
SYSTEM OVERVIEW
================================================================================

The Household & Residence System manages household structures, family units,
staff, departments, residence ownership and occupancy, rental contracts, and
integration with enterprises, government, education, and character systems.

The system underwent a comprehensive architectural refactor to establish clear
ownership boundaries, remove global processing mutexes, eliminate fabricated
domain defaults, and route all mutations through explicit command layers.

================================================================================
KEY DESIGN PRINCIPLES
================================================================================

1. SINGLE RESPONSIBILITY PER LAYER

   Each layer owns exactly one kind of operation:

     State        → canonical storage, indexes, cache, subscriptions
     Queries      → semantic reads returning defensive snapshots
     Rules        → pure policy/calculation (no persistence, no notification)
     Commands     → canonical mutations, transaction boundary, persistence
     UI           → rendering, input collection, presentation, toasts

2. NO GLOBAL PROCESSING MUTEXES

   The previous system used `_processingX` boolean flags across modules.
   These broke legitimate composition: a command that internally called
   another command would find itself locked out.

   Example of the OLD bug:

     processHouseholdInheritanceOnDeath()
       → transferHouseholdToHeir()
         → sees _processingAssignment === true
         → returns { success: false, reason: 'Already processing' }

   All such guards have been removed. Commands compose freely.

3. NO FABRICATED DOMAIN DEFAULTS

   Missing infrastructure is never converted into valid-looking domain data.
   The old system did:

     _getCurrentYear() → 1250
     _getCharacters() → []
     _getParents() → { mother: null, father: null }

   These were removed. Required dependencies fail loudly. Empty results are
   only returned when the domain fact is genuinely empty.

4. NO LIVE RECORD LEAKS

   Public queries return defensive snapshots, not live canonical objects.
   Callers cannot mutate domain state without going through commands.

5. ONE PERSISTENCE BOUNDARY PER LOGICAL OPERATION

   Each command performs exactly one commit. Helper functions that touch the
   canonical record do NOT persist; the top-level command does, once.

6. STRUCTURED COMMAND RESULTS

   Every command returns:
     { success: true, data: ... }
   or:
     { success: false, code: 'SOME_CODE', reason: 'human message' }

   No more boolean `success` returns mixed with object returns.

================================================================================
CROSS-DOMAIN INTEGRATION
================================================================================

Household ↔ Character:
  • character.household / character.householdId  — reverse index
  • character.householdHistory[]                 — full history
  • household.members[]                          — canonical membership
  • Updates flow through HouseholdCommands.addMember/removeMember

Household ↔ Residence (CRITICAL):
  • CANONICAL: unit.householdId
  • Household reverse index maintained by HouseholdCommands
  • ResidenceSystem.assignHouseholdToUnit() updates both sides
  • markResidenceVacant() updates ALL affected households (multi-unit fix)
  • No competing residence.householdId canonical field

Household ↔ Industry (Enterprise ownership):
  • CANONICAL: enterprise.ownerId / enterprise.ownerType
  • Household maintains enterprises[] as a REVERSE INDEX
  • Updates flow through IndustryCommands.updateEnterprise()
  • HouseholdCommands does NOT own enterprise ownership

Household ↔ Economy (Government salaries, taxes):
  • Government salary → HouseholdEconomy.receiveSalary()
  • Salaries stored in economy.salaryIncome + salaryIncomeHistory
  • Wealth updated via HouseholdCommands.updateHousehold()
  • Taxes flow through HouseholdEconomy.updateHouseholdWealth()

Household ↔ Servant (Master-servant relationships):
  • Canonical relationship owned by Relationship system
  • Household membership owned by HouseholdCommands
  • HouseholdServant orchestrates between them

Residence ↔ Rental (Rent income/expenses):
  • residence.ownerId/renterId/rentAmount         — canonical contract
  • residence.rentalHistory/rentPayments          — canonical history
  • HouseholdEconomy.calculateRentIncome/Expenses reads these
  • No duplicate rent tracking in household records

================================================================================
COMMAND RESULT CONTRACT
================================================================================

Every command returns one of:

  { success: true,  data: <any> }
  { success: false, code: 'SOME_CODE', reason: 'human-readable message' }

Common codes:
  INVALID_INPUT, INVALID_NAME, INVALID_YEAR, INVALID_TYPE, INVALID_WAGE,
  NOT_FOUND, ALREADY_MEMBER, NOT_MEMBER, CHARACTER_NOT_FOUND,
  HOUSEHOLD_NOT_FOUND, POSITION_NOT_FOUND, ASSIGNMENT_NOT_FOUND,
  RESIDENCE_NOT_FOUND, DUPLICATE_NAME, ALREADY_ASSIGNED, ALREADY_ENDED,
  INVALID_YEAR_RANGE, OCCUPIED_UNITS, NO_VACANT_UNIT, NO_OWNER, NO_RENTER,
  INSUFFICIENT_WEALTH, INSUFFICIENT_FOOD, INSUFFICIENT_GOODS,
  DEMOLISHED, CANNOT_DELETE_LAST, SAME_NAME, SAME_CONDITION

Bulk operations:
  { success: true, data: { succeeded: [...], failed: [...] } }
  with explicit per-item failure reasons.

KEY BUGS FIXED
================================================================================

1. Inheritance composition bug
   processHouseholdInheritanceOnDeath() → transferHouseholdToHeir() no longer
   fails with "Already processing".

2. Auto-succession bug
   autoAssignHouseholdHead() → getHouseholdHeirs() no longer returns empty
   because of its own processing guard.

3. Enterprise stats bug
   getHouseholdEnterpriseStats() → getHouseholdEnterpriseSummaries() now
   returns actual data instead of [].

4. Annual economy bug
   computeNetAnnualChange() now returns the real value; processAnnualEconomy()
   no longer silently processes a zero net change.

5. Bankruptcy self-block
   handleBankruptcy() → isBankrupt() now works; bankruptcy can process.

6. Servant transfer bug
   transferServantToHousehold() → terminateService() now completes.

7. Residence demolition composition bug
   demolishResidence() → demolishUnit() now works.

8. Multi-unit vacancy bug
   markResidenceVacant() now disassociates EVERY affected household, not just
   residence.householdId.

9. Stale residence.householdId
   Removed. Occupancy is now unit-level canonical; residence-level occupant is
   derived.

10. markUnitVacant stale household bug
    Fixed by removing residence-level occupant field.

11. assignHouseholdToVacantResidence with no unit
    Now returns NO_VACANT_UNIT failure instead of success.

12. Inheritance historical age bug
    getHouseholdHeirs() now uses the operation year, not the current year.

13. Snapshot read mutates canonical data
    Fixed: name-period projection lives in HouseholdQueries; UI no longer
    decorates nameHistory records in place.

14. Ownership transfer mutates history from UI
    Fixed: setResidenceOwner() owns the entire transaction.

15. Staff position edit directly mutates canonical data
    Fixed: routes through ResidenceSystem.updateStaffPosition().

16. Silent failure swallowing
    Removed. Errors surface as structured command results.

17. 1250 fallback
    Removed everywhere. Required time dependency fails loudly.

18. Emoji icon policy violations
    Removed. All icons via _getIcon() or plain text.

19. Live record leaks
    Fixed. Queries return defensive snapshots.

20. Modal guard deadlocks
    Removed _processing*Modal guards.

REMAINING ARCHITECTURAL DEBT
================================================================================

1. ResidenceSystem is a single large file
   It is not yet split into ResidenceState / ResidenceQueries /
   ResidenceCommands / ResidenceRules. This is deliberate: the internal
   structure is command/query separated by section, and no second consumer
   has forced the split. If it grows past ~1500 lines or a second consumer
   appears, split then.

2. DEFAULT_SKILL_LEVEL is a UI-presented constant
   Currently defined in modals-household-staff.js and
   modals-residence-staff.js. Should move to HouseholdRules /
   ResidenceRules when a second consumer needs it.

3. HouseholdRules module does not exist yet
   Succession policy, merge/split validation, cadet branch rules, and
   recommendation thresholds are currently implicit in the queries and
   commands. Should be extracted when a second consumer appears.

   so callers can decide. A proper transaction framework would be needed
   for full atomicity.

5. modals-residence-snapshot.js still loaded
   Deprecation stub. Delete from index.html.

6. Shims still loaded
   modals-assign-staff.js, modals-residence-vacancy.js,
   modals-residence-history.js are verification shims. Delete from
   index.html once callers migrate.

## SYSTEM OVERVIEW

The Household & Residence System manages all household structures, family units, staff, departments, residence management, and rental/ownership relationships. It provides a complete API for household CRUD operations, member management, household economy, staff positions, servant relationships, residence management including units, vacancy, history, and full rental/ownership tracking with rent income/expense integration.

**Key Design Principles:**
- **Single Source of Truth**: `household-state.js` holds all household data; `residence-system.js` holds all residence data
- **Command-Query Separation**: Commands (writes) vs Queries (reads) separated
- **Separation of Concerns**: State, commands, queries, economy, UI all separate
- **Recursion Guards**: All public functions protected from infinite loops
- **Role Integration**: Positions can require roles (generic professions)
- **Name Period Management**: Full household and residence name history with period tracking
- **Deceased Members**: Remain in household (don't stop being part of the family)
- **History Preservation**: All previous households always stay in history
- **Residence Integration**: Households can be assigned to residences and units
- **Rental System**: Full ownership/renter tracking with adjustable annual rent
- **Rent Income/Expenses**: Rent flows to owner's household wealth; deducted from renter's household wealth
- **Government Integration**: Government salaries flow into household economy; taxes collected
- **Enterprise Integration**: Households can own and manage enterprises
