================================================================================
PART 1 — FILE INVENTORY AND LAYERS
================================================================================

The industry subsystem sits ABOVE the character, household, place,
storage, and time domains. It orchestrates them; it does not own them.

  CONSTANTS (leaf)
    js/core/industry/industry-constants.js

  DEFAULTS (pure data, leaf)
    js/core/industry/industry-type-defaults.js

  ECONOMICS (pure calculations, leaf)
    js/core/industry/industry-economics.js

  RULES (pure policy; reads constants + economics at call time)
    js/core/industry/industry-rules.js

  STATE (in-memory canonical catalogue; depends on storage + constants)
    js/core/industry/industry-state.js

  TYPE INIT (seed defaults into masterData)
    js/core/industry/industry-type-init.js

  TYPE COMMANDS (write boundary for the type registry)
    js/core/industry/industry-type-commands.js

  TYPES (read-only facade over the type registry)
    js/core/industry/industry-types.js

  MIGRATION (pre-hydration canonicalisation)
    js/core/industry/industry-migration.js

  COMMANDS (the single enterprise write boundary)
    js/core/industry/industry-commands.js

  QUERIES (semantic reads over state + cross-domain accessors)
    js/core/industry/industry-queries.js

  PROCESSOR (annual processing orchestration)
    js/core/industry/industry-processor.js

  VIEW MODELS (presentation preparation)
    js/core/industry/industry-view-models.js

  UI LIST (DOM renderers over view models)
    js/core/industry/industry-ui-list.js

  MODALS (input gathering + command invocation)
    js/core/industry/modals-industry.js

  BOOTSTRAP (verification + migration + seeding + hydration + diagnostics)
    js/core/industry/industry-bootstrap.js

Layer ordering (dependency direction):

  constants, defaults, economics
      |
      v
  rules
      |
      v
  state  ->  migration, type-init, types
      |
      v
  type-commands
      |
      v
  commands
      |
      v
  queries
      |
      v
  processor, view-models
      |
      v
  ui-list, modals
      |
      v
  bootstrap

bootstrap loads LAST among industry files and verifies every layer
above it. modals-industry.js depends on the command / query /
view-model / processor namespaces directly (not on bootstrap), so the
documented HTML load order places modals-industry.js BEFORE
industry-bootstrap.js.

2.1 CONSTANTS — industry-constants.js
--------------------------------------------------------------------------------

  js/core/industry/industry-constants.js
    Owns: window.IndustryConstants.

    Exports (frozen):
      Economic thresholds: DEBT_INTEREST_RATE, BANKRUPTCY_THRESHOLD,
        REBUILD_WEALTH_FRACTION, REBUILD_WEALTH_MINIMUM.
      Status vocabulary: STATUS, PROCESSABLE_STATUSES,
        WORKER_BLOCKED_STATUSES, FINANCIALS_FROZEN_STATUSES.
      Ownership vocabulary: OWNERSHIP_TYPE, VALID_OWNERSHIP_TYPES,
        OWNER_TYPE, VALID_OWNER_TYPES, PLACE_OWNER_TYPES,
        HOUSEHOLD_OWNER_TYPES.
      Derived-field classification: DERIVED_FIELDS, DERIVED_FIELDS_MAP.
      Canonical shape: CANONICAL_ENTERPRISE_FIELDS,
        CANONICAL_ENTERPRISE_FIELDS_MAP.
      Domain-owned field map: DOMAIN_OWNED_ENTERPRISE_FIELDS.
      Type resolution: UNKNOWN_TYPE_CATEGORY.
      Migration error vocabulary: MIGRATION_ERROR.
      Processing caps: MAX_HISTORY_ENTRIES, ABSOLUTE_MAX_WORKERS.
      Event names: EVENT.
      Result shape literals: RESULT_SHAPE.

    Load-time dependencies: NONE. Attaches its export to window only.
    Call-time dependencies: NONE.

    Consumed by:
      [load] industry-rules.js             (call-time via
                                            _requireConstants)
      [load] industry-state.js             (HARD)
      [load] industry-type-init.js         (HARD)
      [load] industry-migration.js         (HARD)
      [load] industry-commands.js          (HARD)
      [load] industry-bootstrap.js         (indirect, via every
                                            module above)

    Contracts:
      - Everything is frozen. Mutation is a bug.
      - String values are the canonical stored values. Do not alias.
      - Arrays are frozen. Iteration is fine; mutation is not.
      - Maps that need O(1) lookup are frozen objects with boolean
        `true` values.
      - CANONICAL_ENTERPRISE_FIELDS_MAP is the allowlist used by
        validateEnterprise to reject unknown fields (except tombstone
        fields, permitted only when status === 'demolished').
      - DOMAIN_OWNED_ENTERPRISE_FIELDS is currently empty. It exists
        so that when a cross-domain field is added, the rejection path
        is already wired up and consistent with household-commands.js.
      - UNKNOWN_TYPE_CATEGORY is a RESOLUTION fallback used by
        queries and integrity diagnostics, NOT a stored value.
      - Semantics for typeId null vs missing are distinguished by
        queries: both resolve to null metadata; the difference is
        visible only in the integrity diagnostic.

      - resolveYearsToProcess(enterprise, currentYear)
      - calculateAnnualTransition(enterprise, currentYear, options)
      - DEBT_INTEREST_RATE (exported constant, mirrors the value in

    Load-time dependencies: NONE.
    Call-time dependencies: NONE.

    Consumed by:
      [load] industry-rules.js             (call-time via

2.4 RULES — industry-rules.js
--------------------------------------------------------------------------------

  js/core/industry/industry-rules.js
    Owns: window.IndustryRules.
      - applyEnterpriseDefaults(raw, typeDefaults)
      - applyEnterpriseTypeDefaults(raw)
      - validateEnterprise, validateEnterprisePatch
      - validateCreateInput, validateUpdateInput
      - validateEnterpriseType, validateEnterpriseTypePatch
      - validateAnnualTransitionResult
      - canApplyOwnershipChange

    Load-time dependencies: NONE. Both window.IndustryConstants and
      window.IndustryEconomics are read at CALL time via
      _requireConstants / _requireEconomics.

    Call-time dependencies:
      window.IndustryConstants     — throws if missing.
      window.IndustryEconomics     — throws if missing.
      window.isValidYear           — optional, used by
                                     _isValidYearOrMissing; falls
                                     back to a finite-integer check
                                     when absent.

    Consumed by:
      [load] industry-migration.js         (HARD)
      [load] industry-type-commands.js     (HARD)
      [load] industry-commands.js          (HARD)
      [load] industry-bootstrap.js         (indirect, via every
                                            module above)

    Contracts:
      - Pure policy. No state. No persistence. No events. No
        randomness.
      - Every validator returns { valid: boolean, errors: string[] }.
      - applyEnterpriseDefaults preserves every field on the input
        (including unknown fields) so validation can reject them with
        a clear reason.
      - applyEnterpriseDefaults does NOT assign id, createdAt, or
        updatedAt — the command layer does.
      - applyEnterpriseDefaults does NOT fabricate financial defaults
        — "income: 0" and "income: undefined" mean different things
        to the annual processor.
      - applyEnterpriseDefaults is idempotent.
      - validateEnterprise rejects derived fields, domain-owned
        fields, and unknown fields not in
        CANONICAL_ENTERPRISE_FIELDS_MAP (except tombstone fields when
        status === 'demolished').
      - validateEnterprise does NOT check cross-record references.
        Those belong to IndustryState.validateIntegrity.
      - validateAnnualTransitionResult is a SHAPE / COHERENCE check,
        not a re-computation. It verifies totalProfit ===
        netProfit * yearsProcessed and that the transition reported
        ok === true.
      - canApplyOwnershipChange rejects a flip to 'public' unless
        ownerType is 'settlement' or 'state'.
      - When window.isValidYear is absent, _isValidYearOrMissing
        falls back to a finite-integer check. The caller's load order
        guarantees time.js.

2.5 STATE — industry-state.js
--------------------------------------------------------------------------------

  js/core/industry/industry-state.js
    Owns: window.IndustryState.
      - In-memory canonical enterprises[] and enterpriseTypes[].
      - Derived indexes: byId, byOwner, byLocation, byStatus, byType,
        byOwnershipType, typesById, typesByCategory.
      - Subscription notification.
      - Hydration and diagnostics.
      - All _-prefixed mutation primitives used by IndustryCommands,
        IndustryTypeCommands, and IndustryBootstrap.

    Load-time dependencies:
      window.IndustryConstants    — HARD.
      window.masterData           — HARD at hydrate time, not load
                                    time.
      window.markDataDirty        — HARD at first mutation, not load
                                    time.

    Call-time dependencies (optional, used by validateIntegrity only):
      window.getCharacterById     — if present, character reference
                                    checks run.
      window.getPlaceById         — if present, place reference checks
                                    run.
      window.getHouseholdById     — if present, household reference
                                    checks run.
      window.masterData.data
        .households               — read directly (not via accessor)
                                    for the household reverse-index
                                    cross-check.

      Absent accessors cause the corresponding checks to be skipped;
      their names appear in checksSkipped.

    Consumed by:
      [load] industry-type-commands.js     (HARD)
      [load] industry-types.js             (HARD)
      [load] industry-commands.js          (HARD)
      [load] industry-queries.js           (HARD)
      [load] industry-bootstrap.js         (indirect)

    Contracts:
      - Public reads return CLONES. Container array and object fields
        on each record are copied.
      - Authorised mutation code calls _getEnterpriseCanonical(id) /
        _getEnterpriseTypeCanonical(id) for a live reference.
        Reserved for commands and bootstrap.
      - Duplicate ids fail hydration loudly.
      - Unknown fields on a record are preserved (forward
        compatibility).
      - Every mutation writes the in-memory arrays back into
        masterData.data.enterprises / .enterpriseTypes, then calls
        markDataDirty(). Storage decides when to flush.
      - _syncToMasterData does NOT invalidate the accessor cache —
        the accessors do not cache enterprises or enterprise types.
        IF A FUTURE REVISION ADDS AN ACCESSOR FOR ENTERPRISES OR
        ENTERPRISE TYPES, _syncToMasterData MUST GAIN AN
        invalidateAccessorCaches() CALL, with the same try/catch
        pattern used by household-commands.js. Do not add it now.
      - validateIntegrity() returns { valid, errors, checksSkipped }.
        valid: true means "no integrity issues were detected by the
        checks that could run" — NOT "all checks ran and passed". A
        caller that needs to distinguish the two must inspect
        checksSkipped.
      - validateIntegrity() cross-checks the household reverse
        index. For every household in masterData.data.households,
        each enterprises[] entry must:
        (a) be a non-empty string id;
        (b) resolve to an existing enterprise in this catalogue;
        (c) have that enterprise's ownerType === 'household' and
            ownerId === household.id.
      - The reverse-index check is ONE-DIRECTIONAL (households ->
        enterprises). The reverse direction (enterprise.ownerId ->
        household.enterprises[]) is covered by the enterprise-side
        ownerType household + ownerId check.
      - Rehydration is driven by the masterDataUpdated listener.
      - _markDirty calls markDataDirty() but never saveMasterData().

2.9 MIGRATION — industry-migration.js
--------------------------------------------------------------------------------

  js/core/industry/industry-migration.js
    Owns: window.IndustryMigration.
      - migrateEnterprisesToCanonicalShape() derives ownershipType
        from legacy isPublic, strips derived fields, validates each
        record, reports per-record failures.

    Load-time dependencies:
      window.IndustryConstants    — HARD.
      window.IndustryRules        — HARD.
      window.saveMasterData       — HARD (storage.js).
      window.markDataDirty        — HARD (storage.js).

    Call-time dependencies:
      window.masterData           — throws if absent.
      window.IndustryState
        .hydrateFromMasterData    — optional; if present and
                                    changed > 0, migration
                                    re-hydrates state before
                                    saving.

    Consumed by:
      [load] industry-bootstrap.js         (HARD)

    Contracts:
      - Idempotent. On a clean save: { ok: true, migrated: N,
        changed: 0, errors: [] } with zero side effects.
      - masterData.data.enterprises must be an array or absent. The
        three cases are:
          absent (undefined / null)   -> coerced to [] and written
                                         back to masterData.
                                         Legitimate "fresh install"
                                         case.
          array                       -> returned as-is.
          present-but-non-array       -> REFUSED. Returns
                                         { ok: false, migrated: 0,
                                           changed: 0, errors:
                                           [{ index: -1, ... }] }
                                         WITHOUT touching masterData,
                                         WITHOUT saving, and WITHOUT
                                         calling saveMasterData.
                                         Nothing is coerced to []
                                         and nothing is discarded.
      - Rationale (verbatim from the module header): prior revisions
        coerced any non-array value to []. The bootstrap path was
        already safe (it verifies canonical shape and throws before
        migration runs), but a direct caller of
        migrateEnterprisesToCanonicalShape() would silently lose a
        corrupted enterprises array. The refusal closes that hazard
        at the migration boundary, not at the bootstrap boundary.
      - A record with a missing typeId is a MIGRATION ERROR, not an
        invitation to invent 'other'.
      - Failed records are LEFT IN PLACE (not deleted); they remain
        in the canonical array so the bootstrap integrity diagnostic
        and any future repair tool can see them.
      - ok is true when every record migrated cleanly and the
        collection shape was valid; ok is false when the collection
        shape was invalid, at least one record failed validation, or
        the post-migration save failed.
      - Side effects: markDataDirty() and saveMasterData() are called
        only when changed > 0.
      - If IndustryState is loaded and changed > 0,
        hydrateFromMasterData() is invoked BEFORE saveMasterData so
        already-hydrated state reflects the migrated records.
      - Does NOT publish events or notify subscribers.

2.10 COMMANDS — industry-commands.js
--------------------------------------------------------------------------------

  js/core/industry/industry-commands.js
    Owns: window.IndustryCommands.
      - persist()  (the only saveMasterData call site in the
                    enterprise domain)
      - createEnterprise, updateEnterprise, deleteEnterprise
      - addWorkerToEnterprise, removeWorkerFromEnterprise,
        setWorkerWage
      - updateEnterpriseWealth, updateEnterpriseDebt
      - applyAnnualProcessing
      - createPublicEnterprise, convertEnterpriseToPublic
      - demolishEnterprise, rebuildEnterprise

    Load-time dependencies:
      window.IndustryState        — HARD.
      window.IndustryRules        — HARD.
      window.IndustryConstants    — HARD.
      window.generateId           — HARD (ids.js).
      window.saveMasterData       — HARD (storage.js).
      window.getCurrentYear       — HARD (time.js).
      window.getCharacterById     — HARD (accessors.js).
      window.getPlaceById         — HARD (accessors.js).

    Call-time dependencies:
      window.HouseholdCommands.addEnterpriseToHousehold         [household]
      window.HouseholdCommands.removeEnterpriseFromHousehold    [household]
      window.HouseholdCommands.updateHousehold                  [household]
      window.getHouseholdById                                   [accessors]
      All four are verified by _requireHouseholdCommands at call
      time, not load time. IndustryCommands' createEnterprise,
      updateEnterprise, deleteEnterprise, demolishEnterprise,
      rebuildEnterprise, and _applyHouseholdTransfer all touch
      households when ownerType === 'household'. The bootstrap
      verifies HouseholdCommands as a HARD cross-domain
      prerequisite; see §2.16.

    Consumed by:
      [load] industry-processor.js         (HARD)
      [load] modals-industry.js            (HARD)
      [load] industry-bootstrap.js         (indirect)

    Contracts:
      - Every command returns { success: true, ... } or
        { success: false, reason }.
      - Commands do NOT save. Every command mutates in-memory state
        and returns. The caller calls IndustryCommands.persist() once
        per batch, after every command in the batch has succeeded.
      - Commands compose freely. There is no _processingCommand
        guard.
      - createEnterprise: validates input via
        RULES.validateCreateInput, resolves type defaults via
        IndustryState, applies RULES.applyEnterpriseDefaults,
        stamps id / timestamps, validates, calls
        IndustryState._addEnterprise, then registers with the
        household (if applicable). On household registration
        failure, the enterprise is rolled back via
        IndustryState._removeEnterprise (wrapped in try/catch so
        a rollback failure does not mask the original error).
      - updateEnterprise: validates the update shape, enforces the
        field allowlist (_ALLOWED_UPDATE_FIELDS), enforces the
        frozen-status financial guard, then updates the industry
        record. If ownership changes, _reconcileHouseholdOwnership
        runs and, on failure, rolls back the industry record's
        owner fields and returns a structured failure.
      - workerList and workerWages are NOT in the update allowlist.
        Callers must use addWorkerToEnterprise /
        removeWorkerFromEnterprise / setWorkerWage.
      - wealth and debt are rejected while status is in
        FINANCIALS_FROZEN_STATUSES, and the single-call combination
        { status: 'demolished', wealth } / { status: 'demolished',
        debt } is rejected. Callers use updateEnterpriseWealth /
        updateEnterpriseDebt.
      - deleteEnterprise unregisters from the household first
        (when applicable), then removes the enterprise. On
        unregistration failure, returns the failure without
        deleting.
      - applyAnnualProcessing applies the household transfer FIRST
        (when applicable), then updates the enterprise. On
        household-transfer failure, the enterprise is untouched.
      - _applyHouseholdTransfer writes only `wealth`, not `notes`.
        Prior revisions wrote notes based on a potentially stale
        read, overwriting concurrent household note edits. The
        reason goes into the industry event payload and the
        household eventLog entry written by
        HouseholdCommands.updateHousehold.
      - _reconcileHouseholdOwnership on owner change:
        (1) if the enterprise was previously household-owned,
            remove it from the previous household;
        (2) if the enterprise is now household-owned, add it to
            the new household.
        On any failure in (1) or (2), the industry record is
        restored to its prior owner shape. If (2) fails after (1)
        succeeded, the source-side removal is rolled back
        (best-effort). The caller sees a structured failure and
        nothing is committed.
      - persist(): calls window.saveMasterData(); returns
        { success: true } on success, { success: false, reason } on
        failure or throw.

    CROSS-DOMAIN WRITE CONTRACT (from the module header):

      household.enterprises[]  — reverse index
        addEnterpriseToHousehold / removeEnterpriseFromHousehold.
        Called from createEnterprise, deleteEnterprise,
        rebuildEnterprise, demolishEnterprise, and updateEnterprise
        (on owner change, via the C2 reconciliation path). Both the
        source and target household are updated so the reverse index
        stays in sync with the canonical enterprise.ownerType /
        ownerId.

      household.wealth  — annual processing transfer
        HouseholdCommands.updateHousehold({ wealth }).
        Called from applyAnnualProcessing when the enterprise is
        household-owned. Wealth is the only household field this
        path writes; notes / name / location / status / members are
        left untouched.

      Industry does NOT write:
        household.notes          (prior revisions wrote this on
                                  transfer; removed because it
                                  clobbered concurrent household
                                  note edits based on a stale read)
        household.name / locationId / locationName / status /
        members / departments / residence fields.
        Any character-record field.
        Any place-record field.

    REVERSE-INDEX RECONCILIATION (updateEnterprise path):

      updateEnterprise now reconciles the household reverse index
      when ownerType / ownerId change. Prior revisions changed the
      enterprise record's owner fields but left household A's
      enterprises[] still listing the enterprise and household B's
      enterprises[] missing it, producing a silent reverse-index
      desync on both sides.

      _reconcileHouseholdOwnership runs AFTER
      IS._updateEnterprise succeeds and BEFORE _commit. It rolls
      back the industry record (and, for the target side, the source
      removal) on any cross-domain failure.

      Idempotency: if the previous and next (ownerType, ownerId) are
      identical, _reconcileHouseholdOwnership is a no-op.

        throws for a domain error. Programming errors (missing
        dependency, invalid argument type where the caller is
        expected to have validated) throw at load or at call,

2.16 BOOTSTRAP — industry-bootstrap.js
--------------------------------------------------------------------------------

  js/core/industry/industry-bootstrap.js
    Owns: window.IndustryBootstrap.
      - init()
      - reinit()

    Load-time dependencies: NONE (the module parses regardless).
      The REQUIRED_MODULES list is checked at call time by init().

    init() REQUIRED modules (verified at call time, throws on any
    missing):
      IndustryConstants, IndustryRules, IndustryEconomics,
      IndustryState, IndustryTypeDefaults, IndustryTypeInit,
      IndustryTypeCommands, IndustryTypes, IndustryMigration,
      IndustryCommands, IndustryQueries, IndustryProcessor,
      IndustryViewModels.

    init() REQUIRED globals:
      generateId, markDataDirty, saveMasterData, getCurrentYear,
      getCharacterById, getPlaceById, getHouseholdById.

    init() REQUIRED cross-domain (HouseholdCommands methods):
      addEnterpriseToHousehold, removeEnterpriseFromHousehold,
      updateHousehold.
      HouseholdCommands itself is verified at the namespace level
      first.

    Canonical shape verification:
      masterData.data.enterprises must be an array or absent.
      masterData.data.enterpriseTypes must be an array or absent.
      A present-but-non-array value is a HARD FAILURE at init (throws
      before migration can run). See VERIFICATION-BEFORE-MIGRATION
      ORDERING below.

    VERIFICATION-BEFORE-MIGRATION ORDERING:

      init() runs _runVerification() (which includes
      _verifyCanonicalShape) and then _throwOnFatal() BEFORE
      migration runs. This ordering is the reason
      industry-migration.js's internal coercion of a non-array
      masterData.data.enterprises to [] cannot discard corrupted
      data at bootstrap time:

        - If masterData.data.enterprises is non-array,
          _verifyCanonicalShape reports it, _throwOnFatal throws,
          and migration never runs.
        - If migration runs, masterData.data.enterprises is
          guaranteed to be an array (or undefined, which migration's
          _requireEnterprisesArray coerces to [] — the legitimate
          "fresh install" case).

      The coercion in industry-migration.js::_requireEnterprisesArray
      is therefore a LEGITIMATE default for the "absent" case, but
      would be a silent-data-loss hazard for the
      "present-but-non-array" case if migration were called directly
      (bypassing the bootstrap).

    INITIALISATION CONTRACT:

      init() is idempotent. Calling it twice returns
      { success: true, alreadyInitialized: true, lastResult } on the
      second call. The auto-init at the bottom of the file runs if
      masterData is already present at load time. If the loader has
      not run yet, the loader calls init() explicitly.

      init() steps:
        1. Verification (throws on any missing).
        2. Migration (idempotent; persists its own changes when it
           makes any).
        3. Type seeding (idempotent; persists when it seeds).
        4. Hydration (IndustryState.hydrateFromMasterData).
        5. Integrity diagnostics (warn only, do not throw).
        6. Expose window.Industry as a frozen namespace.

      ORDERING GUARANTEE:
        Step 1 runs _verifyCanonicalShape() and _throwOnFatal()
        BEFORE step 2. A non-array masterData.data.enterprises (or
        enterpriseTypes) is rejected before migration can reach it.

    _lastResult.integrity.checksSkipped carries through from
      IndustryState.validateIntegrity(). Existing callers that read
      .integrity.valid and .integrity.errorCount are unchanged; the
      new field is additive.

    reinit() forces re-verification, re-migration, and re-hydration.
      Intended for test fixtures and repair flows where the caller
      knows masterData has been replaced out-of-band. Normal
      production flow does not need this — IndustryState listens for
      masterDataUpdated and re-hydrates on its own.

    ICON POLICY: No emojis. No icons.

    This file does NOT:
      - mutate enterprise or type records directly
      - persist (migration persists its own changes; type seeding
        persists its own changes; nothing else here writes)
      - toast or render

    Consumed by: the application bootstrap, which either relies on
      the auto-init or calls init() explicitly after storage.js runs.

    Exposes: window.Industry (frozen) with:
      Constants, Rules, Economics,
      State, Types, TypeInit, TypeCommands,
      Commands, Queries, Processor,
      Migration, ViewModels.

================================================================================
PART 7 — KNOWN HAZARDS
================================================================================

  1.  industry-doc.txt is partially out of date.

      §1 Ownership Contract states that
      "household.enterprises[] is the only household-owned field
      industry mutates, and it is done via HouseholdCommands".

      That is false in two ways:

        (a) industry also writes household.wealth via
            HouseholdCommands.updateHousehold during annual
            processing household transfer;

        (b) prior revisions of industry-commands.js also wrote
            household.notes on that path, removed because it
            clobbered concurrent household note edits based on a
            stale read of the household record.

      The industry-bootstrap.js header documents the corrected
      contract in its CROSS-DOMAIN CONTRACT section. Use the
      bootstrap header as authoritative; the industry-doc.txt §1
      paragraph is stale. Update the doc before citing it as
      authoritative.

  2.  RESULT SHAPE DIVERGENCE across types and enterprises.

      IndustryCommands returns { success, reason?, ... }.
      IndustryTypeCommands returns { success, reason?, ... }.
      IndustryProcessor returns structured results per entry point
      (see §2.12).
      IndustryMigration returns { ok, migrated, changed, errors }.

      These are not uniform. IndustryMigration uses `ok`, not
      `success`, matching the household-migration convention. Do
      not unify without auditing every caller.

  3.  HOUSEHOLD REVERSE INDEX CROSS-CHECK IS ONE-DIRECTIONAL.

      industry-state.js::validateIntegrity walks
      masterData.data.households -> enterprises[]. It does not walk
      enterprises -> household.enterprises[]. The reverse direction
      is covered by the enterprise-side ownerType household + ownerId
      check combined with the household-side check just described.
      A desync where the enterprise points at the correct household
      but the household does not list the enterprise IS caught
      (household-side check); a desync where the household lists the
      enterprise but the enterprise points at a DIFFERENT household
      is caught (household-side check (c)); a desync where the
      household does not list the enterprise and the enterprise
      points at a DIFFERENT household is only caught by the
      enterprise-side check (which does not look at
      household.enterprises[]). That case is rare and is a
      pre-existing desync class, not one produced by any current
      write path.

  4.  MIGRATION IS NOT A REPAIR TOOL.

      industry-migration.js migrates. It does not repair broken
      typeId references (a record whose typeId points at a missing
      type is a MIGRATION ERROR, not an invitation to invent
      'other'). The bootstrap integrity diagnostic reports the
      broken reference; a repair tool must fix it.

  5.  TYPE SEEDING AND MIGRATION RACE.

      init() calls IndustryTypeInit.ensureEnterpriseTypesInitialized()
      after migration. If migration changed the enterprises array,
      hydration runs inside migration (before type seeding). Type
      seeding then populates masterData.data.enterpriseTypes.
      Because migration re-hydrates before type seeding, the
      initial hydration sees the enterprise records but not the
      freshly-seeded type records. The bootstrap then calls
      hydrateFromMasterData again (step 4) with the post-seeding
      type array. This is intentional and idempotent, but a future
      revision that removes the second hydrateFromMasterData call
      would leave the state missing the seeded types until the next
      masterDataUpdated event.

  6.  NO CROSS-DOMAIN ATOMICITY FOR OWNERSHIP.

      updateEnterprise reconciles the household reverse index on
      owner change. On reconciliation failure, it rolls back the
      industry record. There is no transaction spanning the
      household and industry domains; the rollback is the only
      consistency mechanism.

  7.  MUTATION PRIMITIVES ARE INTERNAL.

      IndustryState exposes _addEnterprise, _updateEnterprise,
      _removeEnterprise, _addEnterpriseType, _updateEnterpriseType,
      _removeEnterpriseType, and the _get*Canonical accessors.
      These are reserved for IndustryCommands,
      IndustryTypeCommands, and IndustryBootstrap. Calling them
      from queries, UI, or cross-domain consumers bypasses
      validation, event publication, and cross-domain
      reconciliation.

  8.  AUTO-INIT AT LOAD TIME.

      industry-bootstrap.js runs init() at load if
      masterData.data exists. The try/catch wraps auto-init so a
      broken dependency surfaces as a console error rather than an
      uncaught exception at load time. The loader's explicit init()
      call will still throw on failure. Do not rely on auto-init
      in production — call init() explicitly after storage.js has
      run and after initializeStorage() has completed.

  9.  PRESENT-BUT-NON-ARRAY enterpriseTypes IS COERCED.

      industry-type-init.js replaces a present-but-non-array
      masterData.data.enterpriseTypes with the defaults.
      industry-migration.js REFUSES to coerce a present-but-non-array
      masterData.data.enterprises. The asymmetry is documented
      in the industry-migration.js header but not in
      industry-type-init.js. A corruption of enterpriseTypes is
      therefore silently overwritten with defaults at bootstrap,
      whereas the same corruption of enterprises is a hard failure.
      The rationale (defaults are pre-validated data; nothing is
      discarded that was not already unusable) is defensible but is
      an inconsistency a future maintainer should be aware of.

  10. INDUSTRY-ECONOMICS DUPLICATES DEBT_INTEREST_RATE.

      industry-constants.js::DEBT_INTEREST_RATE is the canonical
      constant. industry-economics.js independently declares
      var DEBT_INTEREST_RATE = 0.05 at module scope and exports it.
      The two are equal today; a change to one without the other
      would silently desynchronise them. The household subsystem's
      v6.0 consolidation removed a similar duplication; the same
      pattern is still present here.

  11. INDUSTRY-ECONOMICS DUPLICATES BANKRUPTCY_THRESHOLD.

      industry-constants.js::BANKRUPTCY_THRESHOLD = -100 is
      canonical. _calculateLinear accepts a bankruptcyThreshold
      option, and the fallback is the literal -100. Same hazard as
      §10.

  12. IDEMPOTENCY OF BUILT-IN TYPE IDS.

      IndustryTypeDefaults.get() returns records with fixed ids
      (e.g. 'hut_workshop'). If the enterpriseTypes collection is
      seeded, edited, deleted, and reseeded, the fixed ids survive
      across reseeds. If a future revision adds ID generation for
      built-in types, all default ids must remain stable to preserve
      enterprise typeId references.

  13. PROCESSOR VS. SINGLE-ENTERPRISE PERSISTENCE.

      processAnnualEnterprise(id) persists once at the end of a
      successful run. processAnnualEnterprise(id, { persist: false })
      does not. processAllEnterprises persists once at the end of
      the batch. A batch caller that invokes processAnnualEnterprise
      without the persist:false option will produce one save per
      enterprise. The processor's default is persist:true; the
      batch caller must pass persist:false explicitly.

  14. HOUSEHOLD TRANSFER REASON IS EVENT-ONLY.

      _applyHouseholdTransfer passes the reason to
      HouseholdCommands.updateHousehold, which writes it to the
      household eventLog entry. The household.notes field is NOT
      touched (removed in M5). Any future maintainer who wants the
      reason visible outside the event log must update both
      industry-commands.js and this documentation.

  15. MODALS-INDUSTRY PERSISTENCE ON FAILURE.

      Every onConfirm handler that mutates calls persist() once
      after success. If persist fails, the modal shows an error and
      stays open. The in-memory state is already mutated; the user
      can retry from a command, but the modal cannot roll back.
      This matches the processor's persistence model and the
      household subsystem's v6.0 fix pattern.

  16. MODALS-INDUSTRY DOM SCOPING.

      Every DOM lookup is scoped to the modal's own root element.
      A null handle produces a null return; a caller that then
      dereferences null sees a clear TypeError instead of a silent
      wrong-modal mutation. Do not reintroduce document.getElementById
      in this file.

  17. INDUSTRY-QUERIES IS A READ FACADE, NOT A DOMAIN BOUNDARY.

      getEnterpriseWorkers, getEnterpriseSummary, and
      getOwnerEnterprisesSummary all read through IndustryState and
      cross-domain accessors. They return cloned data. A caller
      that wants to mutate must use IndustryCommands. Reads never
      persist.

  18. VIEW MODELS DO NOT FABRICATE DOMAIN DEFAULTS.

      buildCard, buildDetails, and buildWorkerManagement present a
      missing value as the ABSENT glyph (\u2014), never as a
      fabricated domain value (no "0" for a missing wealth, no
      "Unknown" for a missing status). This is the same principle
      the household subsystem applies in
      household-view-models.js.

  19. VIEW MODELS AND QUERIES BOTH RESOLVE OWNER NAMES.

      IndustryQueries._resolveOwnerName and
      IndustryViewModels._stringOrAbsent both participate in owner
      display. The query layer resolves the raw owner name;
      the view-model layer formats it (presentation-safe) and
      substitutes ABSENT for an empty string. Do not move owner
      resolution into the view-model layer; that would couple
      presentation to accessors.

  20. UI LIST RENDERER DOES NOT ESCAPE THE CONTAINER ID.

      renderEnterpriseList calls _resolveContainer(containerId). A
      string containerId is passed to document.getElementById. An
      Element container is used directly. There is no HTML injection
      path through the container id; the ids are developer-supplied.

  21. NO ICON POLICY VIOLATIONS.

      No industry module emits emojis or inline SVG. modals-industry.js
      uses no icons in confirm/cancel buttons. industry-ui-list.js
      emits no icons. If a future revision needs an icon, it must go
      through window.Icons via the modals-core _getIcon contract, not
      an inline SVG or an emoji.

  22. ANNUAL PROCESSING IS DETERMINISTIC TODAY.

      No industry file uses randomness.js, Math.random, or
      window.Random. Every annual transition is computed from the
      enterprise record and the current year. A future revision
      that introduces economic randomness (e.g. random events) must
      introduce a caller-supplied roll source, matching the
      household subsystem's v6.0 fix, not Math.random.

  23. UNKNOWN FIELDS ON ENTERPRISE RECORDS.

      validateEnterprise rejects unknown fields. Every stored
      enterprise must have exactly the fields in
      CANONICAL_ENTERPRISE_FIELDS, plus tombstone fields when
      demolished. A future cross-domain field must be added to
      CANONICAL_ENTERPRISE_FIELDS (and, if it is domain-owned,
      DOMAIN_OWNED_ENTERPRISE_FIELDS) before any record carrying it
      can pass validation.

  24. HISTORY CAPS ARE ENFORCED AT VALIDATE, NOT AT APPEND.

      validateEnterprise checks history.length <= MAX_HISTORY_ENTRIES.
      The command layer appends history entries WITHOUT enforcing
      the cap. A record whose history exceeds the cap is rejected at
      validate time, not at append time. The cleanup path (dropping
      older entries) is not implemented in this batch. A future
      revision that adds a history cleanup should drop the OLDEST
      entries first, never the newest.

  25. ABSOLUTE_MAX_WORKERS IS NOT ENFORCED AT APPEND.

      addWorkerToEnterprise checks against enterprise.maxWorkers.
      validateEnterprise additionally checks maxWorkers against
      IndustryConstants.ABSOLUTE_MAX_WORKERS. A record whose
      maxWorkers is set above ABSOLUTE_MAX_WORKERS is rejected at
      validate time; the command layer's allowlist accepts the
      value and relies on the validation pass to reject it.

  26. MODALS-INDUSTRY CLOSE / REOPEN ROUTING.

      Details -> Edit, Details -> Manage Workers, and Manage
      Enterprise Types -> Edit / Create Type transitions route
      through _closeThen, matching modals-helper.js::closeThen.
      There is one tick of teardown between closing the current
      modal and opening the next. A future revision that opens the
      next modal synchronously will produce a double-stack of modal
      roots.

  27. TYPE DELETION REQUIRES REASSIGNMENT.

      deleteEnterpriseType refuses if any enterprise references the
      type. The caller must reassign enterprises first. There is no
      bulk-reassign command in this batch. A future UI should offer
      a reassignment flow before offering the delete.

  28. BOOTSTRAP VERIFIES A SPECIFIC HOUSEHOLD SURFACE.

      The verification covers addEnterpriseToHousehold,
      removeEnterpriseFromHousehold, and updateHousehold. A future
      household-commands revision that renames, merges, or removes
      any of these three methods will break industry bootstrap at
      init time. Coordinate the rename across both subsystems.

  29. INDUSTRY DOES NOT USE household-queries.js OR
      household-economy.js.

      Household reads go through getHouseholdById (accessors.js).
      Household economy integration (salary, tuition, government
      funding) is not wired into industry in this batch.
      Settlement-owned enterprise treasury routing is not
      implemented.

  30. ANNUAL PROCESSING SKIPS 'inactive', 'closed', 'bankrupt',
      AND 'demolished' ENTERPRISES.

      Only status === 'active' enterprises process.
      IndustryProcessor's _isEligibleForProcessing is the sole gate.
      A caller that wants to process a bankrupt enterprise must
      change status to 'active' first.

  31. HOUSEHOLD OWNER ID IS STRING-ONLY.

      enterprise.ownerId is validated as a non-empty string when
      ownerType is character / household / settlement / state.
      Non-string ids are coerced to null by the state normaliser
      and fail validation. This matches the accessors.js contract
      ("only string IDs are indexed").
