================================================================================
PART 1 — FILE INVENTORY AND LAYERS
================================================================================

The name subsystem follows a layered chain distinct from the
catalogue subsystems (rank/culture/role). It has:

  QUERIES (read-only; composes accessors + randomness + world)
    js/modules/names/name-queries.js

  RULES (pure policy; rule vocabulary, validation, application)
    js/modules/names/name-rules.js

  STATE (cache + UI state + subscriptions)
    js/modules/names/name-state.js

  COMMANDS (writes; only saveMasterData call site)
    js/modules/names/name-commands.js

  SHIM (deprecated compatibility wrapper; aliases onto canonical
        modules; persists after command wrappers)
    js/modules/names/name-system.js

  MODALS (DOM + commands; batch persist per successful action)
    js/modules/names/modals-name.js

Note the layer ordering is DIFFERENT from the catalogue subsystems:
name-rules.js depends on name-queries.js (not the reverse), and
name-state.js depends on name-rules.js (for RULE_TYPES). This is
documented in name-docs.txt §3.

2.2 RULES — name-rules.js
--------------------------------------------------------------------------------

  js/modules/names/name-rules.js
    Owns: window.NameRules
      ({ RULE_TYPES, MARRIAGE_RULES, VALID_ANCESTOR_TYPES,
         validateRules, generateSurnameFromRules,
         determineNewbornSurname, calculateMarriageSurnames,
         getBaseFirstName, getRulePreset, getRulePresetNames,
         describeRule }).
    Load-time dependencies (HARD — throw at load if missing):
      window.NameQueries                  [name] via
                                          name-queries.js
    Load-time method checks (throw at load if missing):
      NameQueries.getAncestorNames
      NameQueries.getRandomSurname
      NameQueries.getCountrySurnameRules
      NameQueries.getCharacterCountryId
    Call-time dependencies: NONE beyond the load guards (every
      dependency is reached through NameQueries).
    Consumed by:
      [load] name-state.js                (HARD —
                                           RULE_TYPES for the
                                           generationMode UI
                                           validation)
      [load] name-commands.js             (HARD)
      [load] name-system.js               (HARD)
    Notes:
      - This module is the ONLY owner of rule application. It is not
        a "catalogue" rules module; it produces surnames.
      - TRANSITIVE DEPENDENCY ON world.js: this module reads country
        facts through NameQueries, which delegates to world.js. The
        world dependency is not visible in this file's import list
        because NameQueries owns it. The edge to watch on load-order
        reshuffles is name-queries → world.
      - Rule types: RANDOM, FAMILY, PATRONYMIC, CHAIN.
      - CHAIN model (from the header): `order` is the COMPLETE,
        ORDERED list of absolute ancestor slots. `order.length` is
        the depth. There is NO separate `depth` field. Duplicate
        slots are rejected at validation.
      - PATRONYMIC GENDER: a gendered patronymic rule requires a
        resolvable child gender. If child gender is 'unknown' or
        'other', _applyPatronymicRule returns null. NO silent
        male-form default.
      - NEWBORN POLICY (from the header): determineNewbornSurname
        walks:
          1. Mother's country rules
          2. Father's country rules
          3. Random surname from explicit countryId pool
          4. Father's surname
          5. Mother's surname
          6. null
        A rule PRESENT but INVALID throws. A rule present and valid
        but unable to produce a result falls through.
      - MARRIAGE POLICY (from the header): calculateMarriageSurnames
        returns null for an unknown rule (does NOT silently
        default). Gender-checked rules ('wife_takes_husband',
        'husband_takes_wife') return the ORIGINALS when the pair's
        genders do not match the rule's expectation. They do NOT
        silently invert.
      - PRESETS: RULE_PRESETS is deep-frozen at load. getRulePreset
        returns a deep CLONE. The freeze prevents this module from
        mutating presets; the clone prevents callers from mutating
        them.
      - getBaseFirstName strips exactly ONE trailing token after
        "the" and ONE after "of". Not a general-purpose parser.
      - generateSurnameFromRules THROWS on an invalid rules object
        (validation failure) rather than returning null. A caller
        that wants to test in advance should call validateRules.

    Notes:
      - This module does NOT own persisted data. It holds two
        caches (surnameHistoryCache, nameListCache) and one UI
        state object (_uiState). No canonical records. No derived

      - NAMESPACE OWNERSHIP: primary export is window.NamesState

      - ACCESSOR MUTABILITY CONTRACT (from the header):
          getMutableSurnameHistory    → LIVE reference.

                                        mutate.
          getMutableNameList          → LIVE reference.
                                        NameCommands mutates
                                        through it. UI must NOT
                                        mutate.
          getUiState                  → FROZEN shallow snapshot.

          - Nested objects are not supported.

        writable via setUiState — they belong to the compat surface

        deleted, the double-save concern (canonical persist +
        wrapper persist) goes away.
      - REMOVED FUNCTIONS (from the header): getMarriageSurnameRule,
        _getAncestorNamesForChain, _getConnectorValue,
        _splitSurname, _getSurnamePart, getAncestorChain. Each
        throws a clear error. None returns a fabricated value.
      - Some legacy signatures take character OBJECTS while the
        canonical signatures take character IDs. The wrapper
        adapts the object → ID conversion. Do not "simplify" by
        passing IDs to the wrapper — the wrapper would throw on
        the non-string check.
      - getBirthSurname and getCurrentSurname preserve the OLD
        empty-string contract for missing history. The canonical
        functions return null. The wrapper translates null → ''.
      - getSurnameHistory takes a character OBJECT and returns
        NameQueries.getSurnameHistory(character.id).

      - PERSISTENCE: every successful command path in the surname

        via _persistOrReport. A failed persist is a toast
        (_renderError), not a thrown error and not a rollback.

        module does NOT touch accessors directly.

        are required. An unknown icon name throws.
      - CANONICAL STRINGS in innerHTML are escaped via
        window.escapeHtml.

        value delegates to window.formatYear (which handles year 0,
        BC years, non-finite, non-integer, non-number).
      - _renderError AUTO-CLEAR after 5 seconds (documented
        deferral). Calling again while an error is visible removes
        the previous and starts a fresh timer.
      - MODAL BODY CONTRACT: _refreshSurnameModalContent requires
        a `.modal-body` element inside the root modal. If the
        modals-core.js modal shell uses a different class name or
        structure, the refresh throws. Confirm before deploying.
      - Uses onOpen (compatibility alias of onMount) — both are
        accepted by modals-core.js. No setTimeout-based binding.
      - No document.getElementById. Handlers are attached to the
        modal root and scoped via data-action. (Note: _readSurname-
        History-related code uses modalRoot.querySelector; the
        generator binds on the root element it receives.)

        marriage_surname, surname_reverted,
        surname_history_cleared. Not for every name-list
        mutation.

PART 6 — LOAD-ORDER INVARIANTS
================================================================================

Each invariant names the failure mode it prevents.

 1.  accessors.js, randomness.js, and world.js before
     name-queries.js.
     Failure without them: name-queries.js throws at load
     ("missing required dependencies: getNameLists,
     getCharacterById, pickRandom, getCharacterCountryId,
     getCountryIdForPlace").

 2.  name-queries.js before name-rules.js.
     Failure without it: name-rules.js throws at load
     ("name-queries.js must load first" / "missing required
     dependencies: NameQueries.getAncestorNames" etc.).

 3.  name-rules.js before name-state.js.
     Failure without it: name-state.js throws at load
     ("missing required dependencies: NameRules").

 4.  name-state.js before name-commands.js.
     Failure without it: name-commands.js throws at load
     ("missing required dependencies: NamesState").

 5.  name-commands.js before name-system.js and modals-name.js.
     Failure without them: name-system.js throws at load
     ("missing required dependencies: NameCommands"); modals-name.js
     throws at load.

 6.  NameCommands.persist must exist at name-system.js and
     modals-name.js load time.
     Failure without it: each throws at load.

 7.  CharacterCommands.updateCharacter must exist at
     name-commands.js load time.
     Failure without it: name-commands.js throws at load
     ("missing required dependencies:
     CharacterCommands.updateCharacter").

 8.  js/core/formatting.js before modals-name.js.
     Failure without it: modals-name.js throws at load
     ("missing required dependencies: escapeHtml, formatYear").

 9.  js/core/icons.js before modals-name.js.
     Failure without it: modals-name.js throws at load
     ("missing required dependencies: Icons").

 10. js/core/modals-core.js before modals-name.js.
     Failure without it: modals-name.js throws at load
     ("missing required dependencies: openModal, confirmDialog").

 11. js/core/world.js before modals-name.js.
     Failure without it: modals-name.js throws at load
     ("missing required dependencies: getCountryPlaces").

 12. js/core/world.js before name-queries.js.
     Failure without it: name-queries.js throws at load
     ("missing required dependencies: getCharacterCountryId,
     getCountryIdForPlace").

 13. initializeStorage() before NamesState's first cache read.
     Failure without it: no load-time throw (accessors.js loads
     fine), but the first getCharacterById / getNameLists call
     fails because masterData is undefined. Under the documented
     full-app order this holds.

 14. NamesState.clearAllCaches() (or its alias
     hydrateFromMasterData()) must be called after masterData
     reload or import.
     Failure without it: NameState caches retain stale records
     after a cross-tab reload or import. There is no
     auto-wiring because the loaded dependency set does not
     include a masterData-reload event for this module.

 15. js/character/family-queries.js before name-queries.js if
     ancestor-based rule types must resolve correctly.
     Failure without it: no load-time throw (FamilyQueries is
     OPTIONAL); ancestor lookups return null. This is the
     documented "no usable data" outcome, not a fabrication.


================================================================================
PART 7 — KNOWN HAZARDS
================================================================================

 1.  name-docs.txt is out of sync with the code in one place.
     Its §2 uses paths consistent with the tree. Its §3 load
     order is consistent. Its §7 persistence section, §9 caching
     section, and §14 verification checklist are consistent with
     the current code. Its §0 preamble explicitly says "New file.
     Replaces name-docs.txt (which should be deleted)."
     The narrative doc is accurate for the post-refactor state,
     but the name-docs.txt in the tree may be an older revision.
     This document plus the code are the source of truth; verify
     name-docs.txt has been replaced by name-doc.md before citing
     it as authoritative.

 2.  name-queries.js does NOT capture window.getRandomNameFromCountry
     before the shim aliases it.
     This is DIFFERENT from role-queries.js, which captures
     window.getRoles at load time before role-system.js aliases
     it. name-queries.js uses window.getNameLists and
     window.pickRandom directly, which the shim does NOT alias
     (it aliases getRandomNameFromCountry and
     getRandomSurnameFromCountry, which are NEW names, not
     re-aliases of internal functions). Therefore load order
     between name-queries.js and name-system.js is not
     stack-overflow-sensitive. The only ordering concern is that
     name-queries.js must be loaded before the shim can call it.

 3.  js/core/names.js and js/modules/names/name-system.js
     potential collision.
     js/core/names.js is the CORE names module (provide
     window.getRandomNameFromCountry, window.getRandomSurnameFromCountry,
     etc. at the CORE level per stillwaters-docs.txt §2.11).
     js/modules/names/name-system.js is the NAME SUBSYSTEM
     compatibility shim that aliases window.getRandomNameFromCountry
     = NameQueries.getRandomName, etc.
     If both files load, the LATER one wins the alias. This is a
     [UNVERIFIED] hazard — the tree's js/core/names.js may or may
     not exist as a supplied file, but the docs say it does.
     Confirm the load order and the alias winner before
     deploying. If js/core/names.js loads AFTER name-system.js,
     the shim's aliases are overwritten by the core module. If
     js/core/names.js loads BEFORE name-system.js, the shim wins.
     Neither is documented as wrong, but the shim's aliases route
     through NameQueries (which honours the RNG contract), while
     the core module may not. Verify the winner.

 4.  NameState caching lifecycle requires manual
     clearAllCaches() after masterData reload.
     Unlike CultureState / ReligionState / RoleState, NameState
     has no auto-wiring for cross-tab reload (there is no
     'masterDataUpdated' listener). The caller MUST invoke
     NamesState.clearAllCaches() (or hydrateFromMasterData()) on
     masterData reload or import. This matches name-docs.txt §9
     which says: "The caller is responsible for invoking it;
     there is no auto-wiring, because the loaded dependency set
     does not include a masterData-reload event."

 5.  name-queries.js ancestor resolution depends on
     FamilyQueries.getParentsByRole.
     FamilyQueries is an OPTIONAL dependency; missing -> ancestor
     lookups return null (documented outcome). This means
     ancestor-based rule types (CHAIN, PATRONYMIC) produce no
     surname in a family-less environment. Under the documented
     full-app order this holds (family-queries.js is loaded
     before name-queries.js). But in a name-only test harness, do
     not expect ancestor resolution to work.

 6.  name-commands.js requires an explicit year in
     _validateSurnameChange.
     Missing year is REJECTED. Year 0 is accepted. There is NO
     1250 fallback. This is the correct contract for this
     module. character-commands.js::recordCharacterSurnameChange
     is a SUPERSET that accepts a missing year and defaults to
     getCurrentYear — but name-commands.js does NOT delegate to
     it, because doing so would silently approve a surname
     change this module's contract says must be rejected.

 7.  DUPLICATION between name-commands.js::recordSurnameChange
     and character-commands.js::recordCharacterSurnameChange.
     Both write the SAME fields (surname, surnameSource,
     surnameRules, surnameHistory). The current implementations
     differ in three ways:
       1. Year requirement — character accepts missing and
          defaults to getCurrentYear; name-commands requires an
          explicit year.
       2. Read mechanism — character uses
          getLiveCharacterForMutation; name-commands uses
          getCharacterById (projection).
       3. Options shape — character accepts a previousSurname
          override; name-commands does so but via a different path.
     Consolidation is a future refactor once surname-command
     semantics settle. Do not "simplify" by having name-commands
     delegate to character-commands; that would introduce a
     validation divergence.

 8.  name-system.js legacy command wrappers call persist() after
     every successful command.
     This preserves the OLD "saves immediately" contract. When
     the wrapper is deleted, the double-save concern (canonical
     persist + wrapper persist) goes away. Callers that go
     through the wrapper AND also call persist() themselves will
     see two saveMasterData calls per command — not a bug, but a
     performance concern. Do not add persistence to the wrapper
     for non-command exports; only the four command wrappers
     persist.

 9.  name-system.js removed functions throw.
     getMarriageSurnameRule, _getAncestorNamesForChain,
     _getConnectorValue, _splitSurname, _getSurnamePart,
     getAncestorChain each throw a clear error. They do NOT
     return fabricated values. Do not "restore" them; migrate
     callers to the canonical modules.

 10. modals-name.js requires a `.modal-body` element for in-place
     refresh.
     _refreshSurnameModalContent does
     root.querySelector('.modal-body'). If the
     modals-core.js modal shell uses a different class name or
     structure, the refresh throws. Confirm the class name
     before deploying; align at one end if needed (per
     name-docs.txt §15 open question 9).

 11. modals-name.js does NOT use _showToast.
     Error display goes through _renderError, which is a DOM
     element with a 5-second auto-clear. There is no showToast
     dependency. Do not add one; the name modals use a different
     error-surfacing strategy from the catalogue modals (which
     use _showToast).

 12. modals-name.js name generator modal does NOT persist.
     Selecting a name is a caller concern. The modal reads
     NameQueries.getRandomName and delivers the chosen string via
     onSelect. It does not write to any character or name list.
     Do not add persistence to the generator modal.

 13. modals-name.js surname modal persists after every successful
     command path.
     _persistOrReport calls NameCommands.persist(); a failed
     persist is _renderError (not a throw, not a rollback). This
     matches name-docs.txt §7. A persistent storage failure looks
     like a toast + a successful-looking UI refresh. This is a
     documented deferral (see name-docs.txt §15 open question 11).

 14. Persistence divergence across domains.
       - SettlementCommandCommit throws on persist failure.
       - GovernmentCommands.persist returns { success: false }
         but does not throw (does not read getLastSaveError).
       - ReligionCommands.persist returns { success, reason? }
         and DOES read getLastSaveError.
       - RankCommands.persist returns { success, reason? } and
         DOES read getLastSaveError.
       - RoleCommands.persist returns { success, reason? } and
         DOES read getLastSaveError (typeof-guarded).
       - CultureCommands.persist returns { success, reason? }
         but does NOT read getLastSaveError.
       - NameCommands.persist returns { success, reason? } and
         DOES read getLastSaveError (typeof-guarded).
     Do not unify without updating every caller's
     error-handling.

 15. getCurrentYearSafe is NOT used by name-commands.js.
     Only getCurrentYear. This is the canonical accessor
     post-Phase-0. name-docs.txt §2's infrastructure table
     mentions getCurrentYearSafe but the current name-commands.js
     implementation does not reference it (see REFACTOR HISTORY
     in name-commands.js: "getCurrentYearSafe references
     replaced with getCurrentYear. The deprecated alias remains
     exported by time.js for one revision but this module no
     longer depends on it."). name-docs.txt's verification
     checklist explicitly checks for getCurrentYearSafe
     references — if the current implementation has none, that
     checklist item is vacuously satisfied.

 16. _renderError auto-clears after 5 seconds.
     This is documented as a deliberate deferral. A dismissable
     error would need a CSS class and a click handler; out of
     scope. Do not assume errors persist.

 17. modals-name.js's setUiState validation rejects explicit
     undefined.
     Omitting a key leaves it unchanged; passing explicit
     `undefined` is a programming error and throws. This
     prevents a caller from accidentally clearing a field.
     Null is permitted only for selectedCountryId and
     selectedGender.

 18. NamesState.getMutableSurnameHistory /
     NamesState.getMutableNameList return LIVE references.
     These are for NameCommands (which mutate through them) and
     NameQueries (which clones the result). UI must NOT mutate
     the returned object. Public read-only access goes through
     NameQueries, which returns a clone.

 19. NamesState.getUiState returns a FROZEN snapshot.
     Attempting to mutate the returned object does not affect
     _uiState (freeze throws in strict mode; no-ops in sloppy
     mode). Use setUiState to change UI state.

 20. hydrateFromMasterData is an ALIAS for clearAllCaches.
     It does NOT rebuild derived indexes — there are none. It
     clears caches. This is different from the reference-pattern
     hydrateFromMasterData in CultureState / ReligionState /
     RoleState / RankState, which DO rebuild derived indexes.
     The alias exists so bootstrap code can use the
     reference-pattern name without pretending NameState has a
     hydrate operation.
