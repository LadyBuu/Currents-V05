# Name System — Architecture Documentation

A reference document for the name/character-naming subsystem.

---

## 1. Purpose

The name system answers four questions:

1. **What is this character's name and surname?** (canonical data, on the character record)
2. **How are names generated for a new character?** (rules over cultural data)
3. **Where does a name come from?** (cultural pools keyed by country)
4. **What has this character's surname been historically?** (surname history)

It does **not** answer: who is married to whom, who lives where, what a character looks like, or what the UI should display. Those belong to their own domains.

## 3. Dependency direction

```
                  ┌──────────────────┐
                  │  modals-name     │  presentation
                  └────────┬─────────┘
                           │
                  ┌────────▼─────────┐
                  │  name-system     │  legacy compatibility
                  └────────┬─────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
 ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
 │name-commands│   │name-queries │   │ name-rules  │
 └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
        │                 │                 │
        │                 ▼                 │
        │          ┌─────────────┐          │
        │          │  NameState  │          │
        │          │ (cache hint)│          │
        │          └──────┬──────┘          │
        │                 │                 │
        │                 ▼                 ▼
        │          ┌─────────────┐   ┌──────────────┐
        │          │ accessors   │   │ randomness   │
        │          └──────┬──────┘   └──────────────┘
        │                 │
        └────────────────►│
                          ▼
                  ┌────────────────┐
                  │   masterData   │
                  └────────────────┘
```

Rules of the graph:

- **Nothing depends upward.** `name-queries.js` never calls `name-rules.js`. `name-rules.js` never calls `name-commands.js`. Commands do not call modals.
- **Load order**: `name-queries.js` → `name-rules.js` → `name-state.js` → `name-commands.js` → `modals-name.js` / `name-system.js`.
- **`NameState` is optional to Queries.** Queries reads through it as a cache hint if present, but falls through to the character record if not. The character record is canonical in both cases.
- **`NameState` requires `NameRules`** for the rule-type vocabulary used to validate the `generationMode` UI field. This is the one cross-module dependency that isn't strictly "state depends only on accessors."
- **`name-system.js` and `modals-name.js` are the only files that reference legacy globals.** `modals-name.js` does not — it uses only canonical modules. `name-system.js` is the entire legacy compatibility surface.

## 5. Data shapes

### 5.1 Character (name-relevant fields)

```js
{
    id: 'char_...',
    name: 'Alice',
    surname: 'Ashvale',
    surnameSource: 'country' | 'cultural' | 'inherited' | 'custom' | 'none',
    surnameRules: { ... } | null,
    surnameHistory: {
        birthSurname: 'Ashvale',
        entries: [
            {
                surname: 'Blackwood',
                year: 1250,
                reason: 'marriage' | 'custom' | 'inheritance' | 'birth' | ...,
                previousSurname: 'Ashvale',
                previousSurnameSource: 'country' | 'custom' | ... | null,
                previousSurnameRules: { ... } | null,
                spouseId: 'char_...' | null,
                notes: '',
                timestamp: 1700000000000
            }
        ],
        lastUpdated: 1250
    },
    fatherId: 'char_...' | null,
    motherId: 'char_...' | null,
    birthYear: 1230,
    isDeceased: false,
    birthplaceId: 'place_...' | null,
    currentLocationId: 'place_...' | null,
    moves: [{ locationId: 'place_...', year: 1240 }, ...]
}
```

### 5.2 Name list (per place/country)

Stored in `masterData.data.nameLists[placeId]`:

```js
{
    male: ['William', 'John', ...],
    female: ['Mary', 'Elizabeth', ...],
    surnames: ['Ashvale', 'Blackwood', ...],
    rules: {
        type: 'random' | 'family' | 'patronymic' | 'chain',
        family?: { ... },
        patronymic?: { ... },
        chain?: { ... }
    } | null
}
```

### 5.3 Rule object

```js
// RANDOM — pick a random surname from the culture
{ type: 'random' }

// FAMILY — combine parent surnames
{
    type: 'family',
    family: {
        source: 'father' | 'mother' | 'both',
        order: 'father_first' | 'mother_first',   // default 'father_first'
        count: 1 | 2 | ...,                        // default 1
        position: 'first' | 'last',                // default 'first'
        connector: 'space' | 'hyphen' | 'custom' | 'none',  // default 'space'
        customConnector: '-'                       // required non-empty if connector='custom'
    }
}

// PATRONYMIC — derive from a parent's given name
{
    type: 'patronymic',
    patronymic: {
        source: 'father' | 'mother',
        malePrefix: '', maleSuffix: 'son',
        femalePrefix: '', femaleSuffix: 'dottir',
        usePrefix: false, useSuffix: true
    }
}

// CHAIN — walk up the ancestor graph by absolute slots
{
    type: 'chain',
    chain: {
        order: ['father', 'paternal_grandfather', 'paternal_great_grandfather'],
        source: 'firstname' | 'surname',
        connector: 'space' | 'hyphen' | 'none' | 'custom',
        customConnector: '-'                       // required non-empty if connector='custom'
    }
}
```

### 5.4 Ancestor slots

`getAncestorData(character, slot)` and `getAncestorNames(character, order, source)` support these slots, all resolved against the starting character:

```
father
mother
paternal_grandfather
paternal_grandmother
maternal_grandfather
maternal_grandmother
paternal_great_grandfather
maternal_great_grandfather
```

There is no `depth` parameter. `order.length` is the depth. Duplicate slots in `order` are rejected at rule validation.

### 5.5 Rule presets

Available via `NameRules.getRulePreset(name)`:

| Name | Type | Meaning |
|------|------|---------|
| `patrilineal` | family | Father's surname only |
| `dual_family` | family | Father + mother, space-separated |
| `hyphenated` | family | Father + mother, hyphenated |
| `patronymic_son_dottir` | patronymic | Icelandic-style |
| `patronymic_ovich_ovna` | patronymic | Slavic-style |
| `chain_two_generation` | chain | Father → paternal grandfather |
| `chain_three_generation` | chain | Father → paternal grandfather → paternal great-grandfather |

Presets are deeply frozen. `getRulePreset` returns a clone.

### 5.6 Marriage rules

Available in `NameRules.MARRIAGE_RULES`:

```
wife_takes_husband
husband_takes_wife
hyphenate
keep
```

`applyMarriageSurnames` requires an explicit rule. There is no default.

### 5.7 Command results

Every command returns:

```js
{ success: true, ...payload }
{ success: false, reason: 'human-readable message' }
```

Never `null` on failure. Never a toast.

## 6. The three main flows

### 6.1 Character creation with a surname rule

Called from `character-commands.js` during `createCharacter`:

```
1. Character data is submitted with fatherId, motherId, birthplaceId.
2. CharacterCommands resolves:
   - countryId = world.getCharacterCountryId(motherId) or (fatherId) or birthplace
   - rules     = NameQueries.getCountrySurnameRules(countryId)
3. If rules exist:
   - surname = NameRules.generateSurnameFromRules(mother, father, childGender, rules)
   - surnameSource = 'country_rules'
   - surnameRules = rules
   Else:
   - surname = '' (no fallback)
   - surnameSource = 'none'
4. CharacterCommands calls NameCommands.recordSurnameChange(
       newCharacterId, surname, birthYear, 'birth', { previousSurname: '' }
   ) — the initial entry is the birth surname.
5. The character is persisted once by CharacterCommands.
```

### 6.2 Newborn surname determination

Called when a character is born into an existing family:

```
1. NameRules.determineNewbornSurname(mother, father, countryId) is called.
2. Cascade:
   a. Mother's country rules (if resolvable and valid)
   b. Father's country rules (if resolvable and valid)
   c. Random surname from `countryId` pool
   d. Father's surname
   e. Mother's surname
   f. → null (no surname)
3. A rule PRESENT but INVALID throws.
   A rule present and valid but unable to produce a result falls through.
4. The result is:
   { surname, surnameSource, surnameRules, countryId }
5. The caller (character-commands or lifecycle) passes `surname` into
   the new character's `createCharacter` call.
```

The cascade is a named policy. It lives in one place: `_tryParentCountryRules` and the sequence in `determineNewbornSurname`.

### 6.3 Manual surname change

Called from the surname modal or any other UI:

```
1. UI calls NameCommands.recordSurnameChange(
       characterId, newSurname, year, reason, options
   ).
2. Command validates the year (rejects missing; accepts year 0).
3. Command validates the character is not deceased.
4. Command ensures surnameHistory exists, appends the change entry
   (recording previousSurname, previousSurnameSource,
   previousSurnameRules), updates character.surname, and updates
   character.surnameSource / surnameRules.
5. Command emits characterChanged with action 'surnameChange'.
6. NameState subscribes; invalidates its surname-history cache for
   that character.
7. Any UI subscribed to NameState re-renders.
```

### 6.4 Revert

```
1. UI calls NameCommands.revertLastSurnameChange(characterId).
2. Command pops the last entry from surnameHistory.entries.
3. Command restores character.surname from the entry's previousSurname
   (or birthSurname).
4. Command restores character.surnameSource and character.surnameRules
   from the entry's recorded previous values.
5. Command persists, invalidates, emits 'surnameRevert'.
```

### 6.5 Marriage surname application

```
1. UI calls NameCommands.applyMarriageSurnames(personId, spouseId, rule, year, notes).
2. Command resolves both characters.
3. Command calls NameRules.calculateMarriageSurnames(person, spouse, rule).
   Returns null for an unknown rule.
4. If neither side needs a change, returns success without mutating.
5. Command validates both changes before applying either.
6. Command applies both changes in memory (via the private primitive
   _recordSurnameChange, not via the public command).
7. If the second application fails, the first is rolled back.
8. Command persists once, invalidates both characters, emits ONE
   characterChanged event with both IDs.
```

The whole marriage operation is atomic from the caller's perspective: either both surnamed change or neither does.

## 7. Randomness

**The name system consumes the canonical RNG stream.** No `Math.random()` anywhere in the name modules.

Functions that consume RNG:

| Function | Uses |
|----------|------|
| `NameQueries.getRandomName(countryId, gender)` | `pickRandom` |
| `NameQueries.getRandomSurname(countryId)` | `pickRandom` |
| `NameRules._applyRandomRule` (via `NameQueries.getRandomSurname`) | indirect |
| `NameRules.determineNewbornSurname` (priority 3 only) | indirect |

**Random results are never cached.** There is no `country + gender → name` cache. That would turn a random query into a stable lookup.

**Reproducibility contract:** given the same RNG seed and the same call sequence, name generation is deterministic. This is what the simulation layer relies on.

**Callers who want stability** (e.g., "show me one name and don't change it when the user looks away") must store the result themselves. `modals-name.js` does this via a local `state.generatedName`.

**`NameRules` does not depend on `randomness.js` directly.** It calls `NameQueries.getRandomSurname`, which owns the RNG contract. This keeps the RNG implementation behind a single module boundary.

## 8. Caching

`NameState` maintains exactly two caches:

| Cache | Key | Value | Invalidation |
|-------|-----|-------|--------------|
| `_surnameHistoryCache` | `characterId` | surname history object (live reference) | `invalidateSurnameHistory(id)`; event `characterChanged` with action `surnameChange` / `surnameRevert` / `surnameHistoryCleared` / `birthSurname` |
| `_nameListCache` | `countryId` | name list object (live reference) | `invalidateNameList(countryId)`; event `nameListChanged` |

Caches are cleared entirely by `NameState.clearAllCaches()` on masterData reload or import. The caller is responsible for invoking it; there is no auto-wiring, because the loaded dependency set does not include a masterData-reload event.

**Accessor mutability contract:**

- `NameState.getMutableSurnameHistory(id)` — returns the **live** reference. Intended for `NameQueries` as a cache hint and for `NameCommands` to mutate through. UI must not use this.
- `NameState.getMutableNameList(countryId)` — returns the **live** reference. Intended for `NameCommands` add/remove operations.
- `NameState.getUiState()` — returns a **frozen shallow snapshot**.
- `NameState.getSurnameHistory(id)` — **does not exist**; that name belongs to `NameQueries`, which returns a deep clone.
- `NameState.getNameList(countryId)` — **does not exist**; that name belongs to `NameQueries`, which returns a deep clone.

The `getMutable*` prefix makes the mutability contract enforceable at the call site rather than aspirational.

**Nothing else is cached.** Not random results. Not ancestor data. Not country resolution.

**Cache misses return `null`**, not `undefined`, and not a synthesized empty object.

## 9. Events

The name system participates in two events. Both use `CustomEvent` on `window`.

| Event | Emitted by | Detail | Consumed by |
|-------|-----------|--------|-------------|
| `characterChanged` | `name-commands.js` (also `character-commands.js`, `family-commands.js`) | `{ action: string, characterIds: string[] }` | `NameState`, `CharacterState`, accessor cache |
| `nameListChanged` | `name-commands.js` | `{ countryId: string, name: string }` | `NameState` |

`NameState` re-emits its own internal events to its own subscribers (`cachesCleared`, `surnameHistoryInvalidated`, `nameListInvalidated`, `uiStateChanged`). These are private callbacks, not DOM events.

For compound operations, `NameCommands` emits ONE `characterChanged` event covering all affected character IDs. `applyMarriageSurnames` does not emit one event per participant.

## 10. What lives where — the anti-confusion table

| Not here | Here |
|----------|------|
| Country hierarchy walking → `world.js` | `getCountryPlaces`, `getCharacterCountryId`, `getCountryIdForPlace` |
| Random selection implementation → `randomness.js` | `getRandomName`, `getRandomSurname` (delegate) |
| Persistence, storage → `storage.js` | Commands call `saveMasterData` |
| Schema repair → `storage-schema.js` | NameState does not create missing entries |
| UI notifications → caller / modals | Commands return `{ success, reason }` |
| Icons → `icons.js` | Domain modules never see icon markup |
| Presentation strings → `formatting.js` / modals | Queries return data, not labels |
| Time fallbacks → `time.js` | No `1250` anywhere; missing year throws |
| Character validation → `validation.js` | Commands check only what they need to mutate |
| Marriage/relationship policy → relationship domain, eventually | Currently in `name-rules.js` for want of a better home |
| Base-first-name extraction → `formatting.js`, eventually | Currently in `name-rules.js` because it's a name rule |

## 12. Extending the system

### 12.1 Adding a new rule type

1. Add the type to `RULE_TYPES` in `name-rules.js`.
2. Add a validator branch in `validateRules`.
3. Add a dispatch branch in `generateSurnameFromRules`.
4. Add a description branch in `describeRule`.
5. Add a preset if useful.
6. Add the type to `NameState`'s generation-mode vocabulary — this happens automatically because `_getValidGenerationModes` reads from `NameRules.RULE_TYPES`.

Do not add a new public global. Do not add a second implementation in `NameQueries`.

### 12.2 Adding a new preset

1. Add the definition to `RULE_PRESETS` in `name-rules.js`.
2. Ensure every field validates. Run `validateRules` on it in a test.
3. Name it after what it does, not where it comes from.

### 12.3 Adding a name list field

1. Extend the shape in `storage-schema.js` if a default is needed.
2. Update `NameQueries.getNameList` if consumers need typed access.
3. Update `NameCommands.addNameToList` / `removeNameFromList` if the field is user-editable.
4. Nothing else changes.

### 12.4 Adding a country field to name resolution

1. Extend `world.js`, not the name modules. Country semantics belong to the world domain.
2. If the field is exposed through `NameQueries`, add a facade. If not, name-domain consumers call `World` directly.

### 12.5 Adding a new ancestor slot

1. Add the slot name to `VALID_ANCESTOR_TYPES` in `name-rules.js`.
2. Add the slot to `_isValidAncestorSlot` and `_resolveAncestor` in `name-queries.js`.
3. `getAncestorData` and `getAncestorNames` handle it automatically.
4. Update the ancestor slot list in this document.

### 12.6 Adding a new command

1. Implement in `name-commands.js`.
2. Return `{ success, reason, ... }`. Never `null`.
3. Take an ID, not an object.
4. Call `window.saveMasterData()`, invalidate the relevant cache, and emit exactly one domain event.
5. Do not call another public command. Compose via private primitives, or accept that the operation is not atomic across commands.
6. Do not call `_showToast`. Commands return structured results.

## 14. Open questions

These are not blockers but are worth resolving as the codebase grows.

1. **Canonical character-mutation owner.** `name-commands.js` writes character surname fields directly through `_applySurnameToCharacter`. When a general character-state mutation module exists, that helper becomes a delegation and nothing else changes. Until then, the write point is centralized but not externally owned.

2. **Marriage surname policy ownership.** Currently in `name-rules.js` as `calculateMarriageSurnames`. If marriage rules become per-country or per-religion, the policy could migrate to a dedicated module. The name system would keep the mechanics.

3. **Cross-country name rules.** `determineNewbornSurname` prefers the mother's country rules, then the father's. If the world has interfaith or international marriages, this is a policy decision that may need a more explicit resolution — "whose culture wins for the child?" — with an explicit answer.

4. **Surname inheritance beyond great-grandparents.** The FAMILY rule uses parent surnames directly. The CHAIN rule walks up to great-grandparent slots. If the world needs deeper dynastic chains, `VALID_ANCESTOR_TYPES` needs to grow, and the naming grammar needs to decide whether "great-great-grandfather" is a distinct slot or a repeated relative step.

5. **Name list mutation UI.** `addNameToList` and `removeNameFromList` are commands, but no modal uses them yet. When you build a "manage country name lists" UI, it will be the third name modal.

6. **Rule editing UI.** Similarly, no UI lets a user edit a country's surname rules. When you build one, it should use `NameRules.validateRules` for inline validation and a new `NameCommands.setCountrySurnameRules` command for persistence (the command does not exist yet).

7. **Base first-name extraction grammar.** `NameRules.getBaseFirstName` strips one token after `"the"` and one after `"of"`. Multi-token epithets (`John of Saint Orleans`) are not fully handled. If the naming grammar grows, this function needs to grow with it, and it will deserve its own test suite.

8. **`name-system.js` removal timeline.** The legacy wrapper is meant to be deleted. Grep for each deprecated global (and its aliases and definitions, not just call sites); when the count reaches zero, delete the corresponding wrapper. When the count for the whole file reaches zero, delete the file.

9. **`modals-core.js` modal-body contract.** `modals-name.js` requires a `.modal-body` element inside the modal root for in-place content refresh. If `modals-core.js` uses a different class name or structure, the refresh throws. Worth confirming and, if needed, aligning the class name at one end.

10. **`NameState` dependency on `NameRules`.** State reads `NameRules.RULE_TYPES` to validate the `generationMode` UI field. This makes State no longer a leaf in the dependency graph. If the load order is ever reshuffled, this is the edge that will break first. An alternative is a shared `NameConstants` module that both consume, but that adds a module for five strings. Current choice: accept the dependency, keep the load order documented.
