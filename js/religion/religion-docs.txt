## 1. Ownership Contract

The religion subsystem is split into twelve modules, each with a single
layer of responsibility. The rule is the same as the rank/role/relationship/
education reference set: **every module owns exactly one thing, and
everything else is out of scope.**

| Module | Owns | Does NOT own |
|---|---|---|
| `ReligionConstants` | Frozen vocabulary (traits, inheritance rules, worship types, conversion reasons, default templates) | Display names, validation, state |
| `ReligionFormat` | Display names for every religion enum (trait, inheritance rule, worship type, conversion reason, law type/category/domain/severity) | Colors, icons, CSS classes |
| `ReligionValidation` | Structural validation (enum membership, required fields, type checks, year integer-ness) | Domain rules (eligibility), orchestration, mutation |
| `ReligionState` | Derived indexes, mutation primitives, subscriptions | Canonical data ownership, persistence, query semantics, mutation policy |
| `ReligionQueries` | Semantic reads, analytics, cross-domain composition | Mutation, rendering, presentation defaults |
| `ReligionRules` | Pure policy ("can X happen?"), inheritance algorithm | Validation, orchestration, mutation, persistence |
| `ReligionCommands` | Write boundary, validation orchestration, rule orchestration, transaction commit, `persist()` | Canonical data ownership, cross-domain side effects, presentation |
| `ReligionLaws` | Law queries, crime-mapping queries, law statistics | Law mutation (moved to Commands in Phase 7) |
| `ReligionInheritance` | Thin adapter: fetch facts → call Rules → call Commands for assignment; provenance observer | The inheritance algorithm, the assignment mutation, display names |
| `ReligionViewModels` | Presentation-ready projections (row shapes, detail models, sorting) | DOM, event handlers, queries, canonical reads |
| `ReligionRender` | DOM rendering for lists, cards, tables; delegated event binding; per-container refresh scheduling | Domain logic, field resolution, icon policy for chrome icons |
| `ReligionUIState` | UI-only state (selected religion, filters, view mode, expanded cards) | Canonical data, queries, commands |
| `ReligionBootstrap` | Load-time verification, index hydration, `window.Religion` namespace | Mutation, persistence, UI wiring |
| `modals-religion.js` | Modal forms for religion CRUD + leadership + gods + laws + places | Validation, defaults, field resolution, mutation |

### The cross-cutting rules

**Commands own mutation.** Nothing outside `ReligionCommands` may call
`ReligionState._addReligion`, `_updateReligion`, or `_removeReligion`. If
another subsystem needs to write religion data, it must go through a command.

**Commands own persistence.** `ReligionCommands.persist()` is the only
call site for `window.saveMasterData` in the religion subsystem. Nothing
else saves. The modal (or the caller) calls `persist()` once per
successful command batch.

**Queries own reads.** Every read goes through `ReligionQueries`. No
module reads `masterData.data.religions` directly except `ReligionState`
(for indexing) and `ReligionQueries` (for enumeration). `ReligionLaws`
reads via `ReligionQueries` for law enumeration; `ReligionViewModels` and
`ReligionRender` never read canonical data at all.

**Rules and validation are pure.** `ReligionRules` and
`ReligionValidation` have no side effects, no persistence, no randomness.
Given the same facts and candidate, they return the same verdict.

**Live records are for commands only.** `ReligionState._getReligionCanonical(id)`,
`_getGodCanonical(id)`, and `_getLawCanonical(id)` return live objects.
Only `ReligionCommands` may call them. Everything else uses
`ReligionQueries.getReligion(id)`, which returns a clone.

**One exception to the clone rule: character records.** `ReligionQueries.getFollowers*`
returns live character records. Character records are owned by the
character domain; cloning them here would create a false impression that
mutation was safe. Callers who want a snapshot must deep-clone themselves.

**No fallbacks.** Missing dependencies throw at load time (bootstrap) or
at call time (individual module `_require*` helpers). No module silently
substitutes a default for a missing capability.

## 2. Load Order

Every HTML file that loads religion modules must include them in this
order. Load order is verified by `ReligionBootstrap.init()` at page load;
a broken order throws before anything tries to use the religion subsystem.
