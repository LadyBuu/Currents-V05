## 1. Ownership Contract

The religion subsystem is split into twelve modules, each with a single
layer of responsibility. The rule is the same as the rank/role/relationship/
education reference set: **every module owns exactly one thing, and
everything else is out of scope.**

| Module | Owns | Does NOT own |
|---|---|---|
| `ReligionConstants` | Frozen vocabulary (traits, inheritance rules, worship types, conversion reasons, default templates) | Display names, validation, state |
| `ReligionFormat` | Display names for every religion enum (trait, inheritance rule, worship type, conversion reason, law type/category/domain/severity) | Colors, icons, CSS classes |
| `ReligionValidation` | Structural validation (enum membership, required fields, type checks, year integer-ness) | Domain rules (eligibility), orchestration, mutation |
| `ReligionState` | Derived indexes, mutation primitives, subscriptions | Canonical data ownership, persistence, query semantics, mutation policy |
| `ReligionQueries` | Semantic reads, analytics, cross-domain composition | Mutation, rendering, presentation defaults |
| `ReligionRules` | Pure policy ("can X happen?"), inheritance algorithm | Validation, orchestration, mutation, persistence |
| `ReligionCommands` | Write boundary, validation orchestration, rule orchestration, transaction commit, `persist()` | Canonical data ownership, cross-domain side effects, presentation |
| `ReligionLaws` | Law queries, crime-mapping queries, law statistics | Law mutation (moved to Commands in Phase 7) |
| `ReligionInheritance` | Thin adapter: fetch facts → call Rules → call Commands for assignment; provenance observer | The inheritance algorithm, the assignment mutation, display names |
| `ReligionViewModels` | Presentation-ready projections (row shapes, detail models, sorting) | DOM, event handlers, queries, canonical reads |
| `ReligionRender` | DOM rendering for lists, cards, tables; delegated event binding; per-container refresh scheduling | Domain logic, field resolution, icon policy for chrome icons |
| `ReligionUIState` | UI-only state (selected religion, filters, view mode, expanded cards) | Canonical data, queries, commands |
| `ReligionBootstrap` | Load-time verification, index hydration, `window.Religion` namespace | Mutation, persistence, UI wiring |
| `modals-religion.js` | Modal forms for religion CRUD + leadership + gods + laws + places | Validation, defaults, field resolution, mutation |

### The cross-cutting rules

**Commands own mutation.** Nothing outside `ReligionCommands` may call
`ReligionState._addReligion`, `_updateReligion`, or `_removeReligion`. If
another subsystem needs to write religion data, it must go through a command.

**Commands own persistence.** `ReligionCommands.persist()` is the only
call site for `window.saveMasterData` in the religion subsystem. Nothing
else saves. The modal (or the caller) calls `persist()` once per
successful command batch.

**Queries own reads.** Every read goes through `ReligionQueries`. No
module reads `masterData.data.religions` directly except `ReligionState`
(for indexing) and `ReligionQueries` (for enumeration). `ReligionLaws`
reads via `ReligionQueries` for law enumeration; `ReligionViewModels` and
`ReligionRender` never read canonical data at all.

**Rules and validation are pure.** `ReligionRules` and
`ReligionValidation` have no side effects, no persistence, no randomness.
Given the same facts and candidate, they return the same verdict.

**Live records are for commands only.** `ReligionState._getReligionCanonical(id)`,
`_getGodCanonical(id)`, and `_getLawCanonical(id)` return live objects.
Only `ReligionCommands` may call them. Everything else uses
`ReligionQueries.getReligion(id)`, which returns a clone.

**One exception to the clone rule: character records.** `ReligionQueries.getFollowers*`
returns live character records. Character records are owned by the
character domain; cloning them here would create a false impression that
mutation was safe. Callers who want a snapshot must deep-clone themselves.

**No fallbacks.** Missing dependencies throw at load time (bootstrap) or
at call time (individual module `_require*` helpers). No module silently
substitutes a default for a missing capability.

### Core-compatibility rules (v3.0)

The religion subsystem relies on the canonical core helpers. The following
patterns are prohibited. Each was present in the pre-v3.0 code and was
removed by the compatibility pass.

**Time:**

    PROHIBITED:  window.getCurrentYearSafe()
    CANONICAL:   window.getCurrentYear()

Files affected by the v3.0 pass:
    religion-bootstrap.js   (REQUIRED_GLOBALS verification)
    religion-queries.js     (_getCurrentYear helper)
    religion-commands.js    (_getCurrentYear helper)
    modals-religion.js      (_getCurrentYear helper)

**UI helpers:**

    PROHIBITED:  window._escapeHtml(), window._showToast(), window._getIcon()
    CANONICAL:   window.escapeHtml(), window.showToast(), window.getIcon()

Files affected:
    religion-render.js      (helper fallback removed)
    modals-religion.js      (helper guards + inline calls)

**Modal infrastructure:**

`js/core/modals-core.js` exposes `window.openModal`, `window.closeTopModal`,
and reads the option keys `titleHtml` / `contentHtml`. It calls
`onMount(root)` after DOM insertion and `onConfirm(root)` on confirm.
`window.openModal` returns `{ element, close }`.

    PROHIBITED:  passing `title:` or `content:` to openModal
    PROHIBITED:  reading `result.content` from openModal
    PROHIBITED:  using `onOpen:` as the mount hook
    PROHIBITED:  inspecting `document.querySelector('.modal-body')`
                 to find the modal's own content
    CANONICAL:   titleHtml:, contentHtml:, onMount:, onConfirm:
    CANONICAL:   result.element
    CANONICAL:   onMount(root) — root is the modal element

The keys `title` and `content` are silently ignored by the core. A modal
that passes those renders with the default title ("Modal") and an empty

pass.

Files affected:
    modals-religion.js      (all 11 modal call sites)

**File location:**

    PROHIBITED:  js/core/religion/<file>
    CANONICAL:   js/religion/<file>

Every religion module's `LOCATION:` header previously named
`js/core/religion/…` while the file was actually at `js/religion/…`.

## 2. Load Order

Every HTML file that loads religion modules must include them in this
order. Load order is verified by `ReligionBootstrap.init()` at page load;
a broken order throws before anything tries to use the religion subsystem.

```html
<!-- Core -->
<script src="js/core/storage.js"></script>
<script src="js/core/ids.js"></script>
<script src="js/core/time.js"></script>
<script src="js/core/formatting.js"></script>
<script src="js/core/accessors.js"></script>
<script src="js/core/collections.js"></script>
<script src="js/core/icons.js"></script>
<script src="js/core/modals-core.js"></script>
<script src="js/core/ui.js"></script>

<!-- Cross-domain (religion reads from these) -->
<script src="js/character/character-state.js"></script>
<script src="js/character/character-queries.js"></script>
<script src="js/location/location-state.js"></script>
<script src="js/location/location-queries.js"></script>
<script src="js/location/location-bootstrap.js"></script>

<!-- Modals for character selection -->
<script src="js/selectors/modals-char-selector.js"></script>
<script src="js/selectors/locationDropdown.js"></script>

<!-- Crime constants (law vocabulary shared with religion) -->
<script src="js/crime/crime-constants.js"></script>

<!-- Religion domain -->
<script src="js/religion/religion-constants.js"></script>
<script src="js/religion/religion-format.js"></script>
<script src="js/religion/religion-validation.js"></script>
<script src="js/religion/religion-state.js"></script>
<script src="js/religion/religion-queries.js"></script>
<script src="js/religion/religion-rules.js"></script>
<script src="js/religion/religion-commands.js"></script>
<script src="js/religion/religion-laws.js"></script>
<script src="js/religion/religion-inheritance.js"></script>
<script src="js/religion/religion-view-models.js"></script>
<script src="js/religion/religion-render.js"></script>
<script src="js/religion/religion-ui-state.js"></script>
<script src="js/religion/modals-religion.js"></script>
<script src="js/religion/religion-bootstrap.js"></script>
```

Critical constraints:

1. `religion-constants.js` must load before every other religion module.
   `ReligionFormat`, `ReligionValidation`, `ReligionRules`, and
   `modals-religion.js` all read it at load.

2. `religion-state.js` must load before `religion-queries.js`,
   `religion-commands.js`, `religion-laws.js`, `religion-inheritance.js`,
   and `religion-bootstrap.js`. All of those call State methods at load
   or on first use.

3. `religion-queries.js` must load before `religion-rules.js`,
   `religion-laws.js`, `religion-inheritance.js`, and
   `religion-bootstrap.js`. Rules read Queries. Laws reads Queries.
   Inheritance reads Rules + Queries + Commands.

4. `religion-commands.js` must load before `religion-inheritance.js`,
   `religion-laws.js` (indirectly — `ReligionLaws` is queried by
   `ReligionCommands` but not the reverse; still required by
   `religion-bootstrap.js`), and `modals-religion.js`.

5. `religion-rules.js` must load before `religion-commands.js` and
   `religion-inheritance.js`.

6. `religion-format.js` must load before `religion-queries.js`,
   `religion-view-models.js`, and `modals-religion.js`.

7. `modals-religion.js` must load after `modals-core.js`, `ui.js`,
   `formatting.js`, `icons.js`, `modals-char-select.js`, and
   `locationDropdown.js`. It verifies all of these at load.

8. `religion-bootstrap.js` must load LAST. It verifies every other
   religion module, every cross-domain method, and hydrates
   ReligionState.

If you see `Cannot read property 'X' of undefined` at load, check the
order above against the actual HTML script tags.

**Note on `ReligionModals`:** the bootstrap treats `ReligionModals` as an
optional module. Not every page needs the modals bundle. When
`modals-religion.js` is not loaded, the domain is fully functional and
only the modal entry points are absent. The bootstrap warns but does not
throw.

## 3. File-by-File API Reference

### 3.1 `religion-constants.js`

Pure data. No dependencies, no side effects.

Exports `window.ReligionConstants`:

    RELIGIOUS_TRAITS        { MONOTHEISTIC, POLYTHEISTIC, SYNCRETIC,
                              EVANGELICAL, ANIMIST }
    RELIGIOUS_TRAIT_NAMES   { 'monotheistic': 'Monotheistic', ... }
    INHERITANCE_RULES       { MOTHER, FATHER, BOTH, DOMINANT, NONE }
    INHERITANCE_RULE_NAMES  { 'mother': "Mother's Religion", ... }
    WORSHIP_TYPES           { TEMPLE, CHURCH, SHRINE, MOSQUE, SYNAGOGUE,
                              MONASTERY, GROVE }
    WORSHIP_TYPE_NAMES      { 'temple': 'Temple', ... }
    CONVERSION_REASONS      { MARRIAGE, PERSONAL, FORCED, POLITICAL,
                              FAMILY, OTHER }
    CONVERSION_REASON_NAMES { 'marriage': 'Marriage', ... }
    DEFAULT_RELIGION        (template)
    DEFAULT_GOD             (template)
    DEFAULT_PLACE_OF_WORSHIP (template)

### 3.2 `religion-format.js`

Pure functions. Dependency: `ReligionConstants`.

Exports `window.ReligionFormat`:

    getReligiousTraitName(id)     → string
    getWorshipTypeName(id)        → string
    getInheritanceRuleName(id)    → string
    getConversionReasonName(id)   → string
    getLawTypeName(id)            → string
    getLawCategoryName(id)        → string
    getLawDomainName(id)          → string
    getLawSeverityName(id)        → string

All lookups return the id unchanged for unknown values. Empty input
returns empty string. None of these functions invent labels for
unrecognized ids.

### 3.3 `religion-validation.js`

Pure functions. Dependency: `ReligionConstants`.

Exports `window.ReligionValidation`:

    validateReligionCreate(data)  → { valid, errors }
    validateReligionUpdate(data)  → { valid, errors }
    validateLawInput(data, opts)  → { valid, errors }
    validateYear(value, opts)     → { valid, errors }
    validateNonEmptyString(value, name) → { valid, errors }

`validateLawInput` reads `window.LAW_TYPES`, `window.LAW_CATEGORIES`,
`window.LAW_DOMAINS`, `window.LAW_SEVERITY`, and `window.CRIME_TYPES` from
globals. This is a documented deferral — those enums live in the crime
domain and will move to a shared vocabulary module in a future phase.

### 3.4 `religion-state.js`

Indexes over canonical data. Dependency: `window.getCharacters`.

Exports `window.ReligionState`:

    rebuildIndexes()              → deprecated alias
    refreshFromMasterData()       → deprecated alias

    getByTrait(trait)             → clones[]
    getByLocation(locationId)     → clones[]
    getByLeader(characterId)      → clone | null
    getFollowersByReligion(id)    → live character records[]
    getGodById(id)                → clone | null
    getLawById(id)                → clone | null
    getPlaceOfWorshipById(placeId) → clone | null

Deprecated:
    getIndexes()                  → live Map wrappers (avoid)

Canonical reads (commands only):
    _getReligionCanonical(id)     → live record | null
    _getGodCanonical(id)          → live record | null
    _getLawCanonical(id)          → live record | null

Mutation primitives (commands only):
    _addReligion(religion)
    _updateReligion(id, religion)
    _removeReligion(id)

    subscribe(callback)           → unsubscribe
    publish(eventName, data)
    notify(event)                 → deprecated alias

`hydrateFromMasterData` throws on duplicate ids and on malformed canonical
data (non-array `masterData.data.religions`). It returns `false` silently
when the canonical store is absent (which is a legitimate pre-load state,
not an error).

### 3.6 `religion-rules.js`

Pure policy. Dependencies: `ReligionQueries`, `ReligionConstants`,
`getCharacterById`.

Exports `window.ReligionRules`:

Conversion:
    canConvert(charId, targetId, options)  → { allowed, reason }
    canAssignReligion(charId, religionId, options) → { allowed, reason }
    canRemoveReligion(charId)              → { allowed, reason }

Leadership:
    canSetLeader(religionId, charId, options) → { allowed, reason }
    canEndLeaderTerm(religionId, charId, endYear) → { allowed, reason }

Lifecycle:
    canDeprecate(religionId)      → { allowed, reason }
    canReactivate(religionId)     → { allowed, reason }
    canDelete(religionId)         → { allowed, reason }

Inheritance (pure engine — no reads):
    resolveInheritance(facts)     → { religionId, source, rule }

Inheritance (convenience — reads, then delegates):
    resolveInheritanceForChild(childId, motherId, fatherId, locId)
                                  → { religionId, source, rule }

The pure engine takes `{ motherReligion, fatherReligion, dominantReligion }`
and returns a verdict. It does not read anything. This is what unit tests
use. The convenience wrapper fetches the facts and delegates.

### 3.7 `religion-commands.js`

Write boundary. Dependencies: `ReligionState`, `ReligionQueries`,
`ReligionValidation`, `ReligionRules`, `getCharacterById`, `getPlaceById`,
`generateId`, `getCurrentYear`, `saveMasterData`.

Exports `window.ReligionCommands`:

Religion CRUD:
    createReligion(data)          → { success, data?, reason? }
    updateReligion(id, updates)   → { success, data?, reason? }
    deleteReligion(id)            → { success, data?, reason? }
    deprecateReligion(id, year)   → { success, data?, reason? }
    reactivateReligion(id)        → { success, data?, reason? }

Leadership:
    setReligionLeader(religionId, charId, options)
    endReligionLeaderTerm(religionId, charId, endYear, reason)

Gods:
    addGod(religionId, godData)
    updateGod(godId, updates)
    removeGod(religionId, godId)

Laws (absorbed from religion-laws.js in Phase 7):
    addLaw(religionId, lawData)
    updateLaw(lawId, updates)
    removeLaw(religionId, lawId)

Locations:
    addReligionLocation(religionId, locationId)
    removeReligionLocation(religionId, locationId)

Character assignment:
    assignReligionToCharacter(charId, religionId, options)
    removeReligionFromCharacter(charId)
    convertCharacter(charId, newReligionId, options)

Places of worship:
    createPlaceOfWorship(data)
    updatePlaceOfWorship(placeId, updates)   (partial)
    deletePlaceOfWorship(placeId)
    calculateTitheIncome(placeId)            (partial)
    collectTithes(placeId, year)             (partial)

Persistence:
    persist()                     → { success, reason? }

Every command returns a structured result. Success results have
`success: true`. Failure results have `success: false` and a `reason`.
Commands never display UI, never show toasts, never save directly (except
`persist()`, which is the save boundary).

`updateReligion` enforces a field allowlist. `isDeprecated` and
`deprecatedYear` are not in the allowlist — they go through
`deprecateReligion` / `reactivateReligion`. Passing them produces a
"Field X is not updatable via updateReligion" failure.

### 3.9 `religion-inheritance.js`

Thin adapter + observer. Dependencies: `ReligionRules`,
`ReligionQueries`, `ReligionCommands`, `getCharacterById`.

Exports `window.ReligionInheritance`:

    getInheritedReligion(childId, motherId, fatherId, locId)
                                  → { religionId, source, rule }

    inheritReligionForChild(childId, motherId, fatherId, locId, options)
                                  → { success, inherited, religion, source,
                                      rule, data, reason }

    getInheritanceSource(motherId, fatherId, religionId)
                                  → 'mother' | 'father' | 'both' |
                                    'location' | null

`getInheritedReligion` resolves. `inheritReligionForChild` resolves and
assigns. `getInheritanceSource` is a post-hoc observer — it reads the
current state of the parents and reports where the child's religion
probably came from. It's not the rule engine.

## 5. Known Deferrals

Three deferrals, all tracked in the code:

### 5.1 Inline styles remain

`modals-religion.js` uses inline `style` attributes on every form
element. A layout rewrite is a design task, not a compatibility fix, and
is deferred.

### 5.2 `setTimeout(100)` between close and open

`openReligionDetailsModal` closes the modal, then uses
`setTimeout(fn, 100)` before opening the next one. The stated reason is
to avoid a z-index/transition race. This is a real fragility: if the
user double-clicks a button, two modals open 100ms apart. Deferred as a
navigation-architecture concern.

### 5.3 Places of worship are not canonically stored

ADR Decision 2 resolves where place-of-worship records live. Until that
decision lands, `ReligionCommands.createPlaceOfWorship` builds the full
record, stores the id on `religion.placesOfWorship`, and returns the
record to the caller. Subsequent reads cannot retrieve the full record
from the id — they get an id or a stub `{ id, religionId, religionName }`.

Functions marked "partial" in §3.13 are the ones affected by this
deferral.

### 5.4 Law enum vocabulary lives on window globals

`religion-validation.js` `validateLawInput` and `modals-religion.js`
`openAddLawModal` read `window.LAW_TYPES`, `window.LAW_CATEGORIES`,
`window.LAW_DOMAINS`, `window.LAW_SEVERITY`, and `window.CRIME_TYPES`
from globals owned by the crime domain. When those enums move to a
shared vocabulary module, this module should read from there instead.

## 6. Anti-Patterns

Do NOT:

- Call `saveMasterData` outside `ReligionCommands.persist()`.
- Call `ReligionState._addReligion` / `_updateReligion` / `_removeReligion`
  outside `ReligionCommands`.
- Mutate a record returned by `ReligionState.getById` — it is a clone.
  Mutate through commands.
- Mutate a record returned by `ReligionQueries.getReligion` — it is a
  clone. Mutate through commands.
- Read `masterData.data.religions` directly. Use
  `ReligionQueries` for reads and `ReligionState` for indexing.
- Read `window.getCurrentYearSafe`. The canonical accessor is
  `window.getCurrentYear`.
- Call `window._escapeHtml`, `window._showToast`, or `window._getIcon`.
  The canonical names are `window.escapeHtml`, `window.showToast`,
  `window.getIcon`.
- Pass `title:` or `content:` to `window.openModal`. The accepted keys
  are `titleHtml:` and `contentHtml:`.
- Use `onOpen:` as the mount hook. The correct key is `onMount:`.
- Inspect `document.querySelector('.modal-body')` to find the modal's
  own content. Use the `root` element passed to `onMount` / `onConfirm`.
- Add a dependency on `window.ModalsCore`. That namespace does not exist.
- Add a dependency on `ReligionQueries.getPlacesOfWorshipByReligion`
  returning full place records until ADR Decision 2 resolves.
- Fabricate default labels in domain code. `ReligionFormat` resolves
  display labels; `ReligionViewModels` fabricates fallbacks where
  presentation demands them.
- Call `ReligionState.publish` from a query. Publish is a command
  concern.

### Anti-patterns fixed by the v3.0 pass

These patterns existed in the codebase and were removed:

- Every religion module's `LOCATION:` header said `js/core/religion/…`
  when the file was at `js/religion/…`.
- Four files called `window.getCurrentYearSafe` (deprecated alias).
- `religion-render.js` had a three-tier `escapeHtml` fallback chain that
  silently recovered from missing `formatting.js`.
- `modals-religion.js` had three-tier fallbacks for `_escapeHtml`,
  `_showToast`, and `_getIcon`.
- All 11 `openModal` calls in `modals-religion.js` passed `title:` and
  `content:` (silently ignored, resulting in empty modals).
- Two modals in `modals-religion.js` used `onOpen:` and inspected
  `document.querySelector('.modal-body')` instead of the scoped `root`
  element.
