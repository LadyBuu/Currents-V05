# SETTLEMENT SYSTEM — ARCHITECTURE AND REFERENCE

Version 5.2
Status: current
Scope: settlement domain and its direct integrations
Purpose: reference for the settlement system as it is implemented
Supersedes: settlement-docs.txt v5.1

This document describes the settlement system after the architectural
refactor defined by the Settlement Architecture Contracts, and after the
v5.2 year-transition hardening pass. It documents the modules that
actually exist, their responsibilities, and the contracts they honor.
Where legacy files have been replaced, the replacement is named.

The six frozen domain decisions described in the contracts are:

  1. rankId is canonical settlement state. Population determines
     eligibility, not current rank.
  2. wealth and totalDebt are independent canonical balances. Debt is
     not derived from negative wealth.
  3. Enterprises are owned by Industry. Settlement does not maintain
     authoritative enterprise-membership arrays.
  4. Places of worship are owned by Religion. Settlement owns only its
     own derived religious interpretation (dominant religion,
     religious unity).
  5. budget allocation and actual spending are distinct concepts.
  6. prosperity is derived. If a persistent baseline is required, it is
     named baseProsperity and treated as an input, not as the final
     value.

The contracts remain authoritative for the refactor and for any future
change. This document describes the resulting system.

# 1. ARCHITECTURE

Dependency direction:

    Definitions
        ↓
    Rules
        ↓
    Queries
        ↓
    Commands
        ↓
    Canonical Data
        ↓
    State Indexes
        ↓
    Persistence

Presentation path:

    Canonical Data
        ↓
    Queries
        ↓
    ViewModels
        ↓
    UI
        ↓
    DOM

Layer responsibilities:

    Definitions   declare what the world allows
    Rules         decide what is valid
    Queries       read the current world
    Commands      change the world in transactions
    Canonical     masterData.data.settlementData
    State         derived indexes and subscriptions
    ViewModels    shape query results for rendering
    UI            DOM and events

No layer may silently substitute a missing dependency with a fabricated
value. Required dependencies are explicit; if one is unavailable, the
call fails.

# 3. CANONICAL SETTLEMENT RECORD

Canonical settlement data lives at:

    masterData.data.settlementData[locationId]

The object keyed by locationId is the authoritative settlement record.

**Schema declaration.**
The `settlementData` object is declared in `storage-schema.js`:
it is created by `createDefaultMasterDataOverride()` and normalized by
`normalizeMasterData()` (missing → `{}`, malformed → `{}` + warning).
Prior revisions relied on `SettlementCommandCommit._getCanonicalStore()`
to lazily create the object on first commit; that path still works but
is no longer the load-bearing creation mechanism. Every fresh install
and every old save now gets the object up front, matching the shape
`SettlementCommandCommit` expects.

**Default record shape.**
The default record is constructed by
`SettlementFactory.getDefaultSettlement`. Every canonical field is
present, even when its value is null, 0, false, or an empty array.
This removes the ambiguity of "field missing" versus "field has a
legitimate zero/empty value".

Fields, classified per the contracts:

Canonical (persistent authoritative state):
    locationId
    rankId
    specializationRoleId
    featureIds
    wealth
    totalDebt
    taxRate
    tradeTariff
    industryTaxRate
    educationBudget
    governmentSalaryBudget
    infrastructureBudget
    militaryBudget
    educationSpending
    infrastructureSpending
    militarySpending
    budgetAllocationYear
    governmentType
    governmentStyle
    governmentTypeId
    justiceSeverity
    useReligiousLawsAsCivil
    hasWatch
    watchSize
    watchFounded
    civilLaws
    demolitionHistory

Historical markers:
    foundedYear
    lastUpgraded

Derived (not stored; calculated by queries):
    prosperity
    employment
    crimeRate
    religiousUnity
    dominantReligion
    eligibleRank
    debtRatio
    financialEfficiency

Foreign entities (owned elsewhere, referenced only through queries):
    enterprises (Industry)
    places of worship (Religion)
    characters (Character / Education)

**Data access contract (live vs. copy).**
Canonical reads expose different reference semantics depending on the
call site's trust level. `SettlementQueries` documents three tiers:

    LIVE RECORD (getSettlementData)
        The exact object stored in masterData. Every command reads
        through this method to build a candidate, clones it, mutates
        the clone, and calls SettlementCommandCommit.commit. Because
        commit REPLACES the record with the candidate, the live
        reference a command reads is never mutated in place.
        Non-command callers must not mutate it.

    SHALLOW COPY (getAllSettlements)
        [{ locationId, data }, ...] where each data is a fresh object
        whose scalars are copied by value and whose nested arrays /
        objects are shared with the canonical record. The annual
        processor and the ViewModels both build their own candidates
        before committing; the shallow copy is exactly the boundary
        those callers need without a per-settlement deep clone.

    PRIMITIVE / CLONE (all other reads)
        getFeatureIds returns a defensive slice. Scalar reads return
        the raw primitive. getBudgetAllocation constructs a fresh
        object. getCurrentRank delegates to SettlementRankQueries.

The rule: mutate nothing. Live and shallow-copy reads are
optimizations for trusted callers, not licenses to write. If a
mutation is needed, go through a command.

# 4. MISSING-VALUE SEMANTICS

    undefined   not supplied / unknown
    null        explicitly absent
    0           legitimate numeric zero
    false       legitimate boolean false
    ""          legitimate empty string where permitted
    []          legitimate empty collection

The following patterns are prohibited for domain values:

    value || 0
    value || 50
    value || 1250
    value || []
    value || {}

Missing required dependencies are not the same as empty results:

    missing PopulationQueries ≠ population of zero
    missing PlaceQueries      ≠ no place
    missing Time              ≠ year 1250
    missing ReligionQueries   ≠ no religion
    missing IndustryQueries   ≠ no enterprises

Required dependencies must fail explicitly.

**Derived-value semantics.**
The v5.2 hardening pass eliminated three places where a derived value
was fabricated or silently zeroed:

  - **Religious unity.** Prior revisions returned 50 when the
    settlement had zero population or the religion breakdown was
    unavailable. Both are now null, and the two states are
    distinguished via `getReligiousUnityStatus`, which returns
    `{ unity, reason }` with reason in `{ 'available',
    'no_population', 'no_breakdown', 'settlement_not_found' }`. The
    fabricated 50 flowed into `SettlementProsperityQueries.
    modifiers.religiousUnity` as a neutral reading that looked
    correct but was meaningless.

  - **Dominant religion.** Prior revisions returned null for both
    "no religions" and "unaffiliated majority." Both are now
    distinguished via `getDominantReligionStatus`, with reason in
    `{ 'available', 'no_population', 'no_breakdown',
    'unaffiliated_majority', 'no_religions', 'settlement_not_found' }`.

  - **Government leader modifier.** Prior revisions read
    `leader.character.traits` from `LocationQueries.getCurrentLeader`,
    which returns an ASSIGNMENT projection without a `character`
    field. The trait read was always undefined, so the modifier was
    silently 0 for every settlement. `SettlementProsperityQueries`
    now resolves the character via
    `CharacterQueries.getCharacterById(leader.characterId)` and reads
    traits from that projection.

**Character enumeration.**
Three settlement query modules computed settlement-level facts over
the settlement's character population:

  - settlement-education-queries.js (literacy rate, education levels)
  - settlement-prosperity-queries.js (role diversity, master
    concentration, average skill)
  - (settlement-employment-queries.js and settlement-economy-queries.js
    read through IndustryQueries and getLocationPopulationCount, and
    were never affected.)

Prior revisions called `CharacterQueries.getCharactersInLocations`,
which filters on `character.currentLocationId === locationId`. That
missed characters placed only via move records (their
`currentLocationId` is null but their latest move points into the
settlement) and included characters whose raw field pointed into the
settlement but whose latest move pointed elsewhere. The under/over-
count silently propagated into literacy rate, prosperity modifiers,
and everything that composed them.

The current revision enumerates via
`CharacterQueries.getAllCharacters()` and filters through
`LocationQueries.getCurrentLocationId`, matching the pattern
established in `location-view-models.js::buildBulkMoveModel`. A
character placed only by a move record now counts; a character whose
latest move points outside the settlement does not.

**Education level derivation.**
`SettlementEducationQueries.getLiteracyStats` previously called
`CharacterQueries.getEducationLevelId`, which is not present on the
character-queries.js surface in the current build. The query now
derives the level locally from `character.isLiterate` and
`character.subjectProgress`. The returned ids match the education-
definitions ids, so the derivation is drop-in compatible with a
future canonical accessor if one is introduced.

# 5. STATE CONTRACT

SettlementState is a state / index layer.

It owns:
    - derived indexes over canonical settlement data
    - a subscription mechanism
    - a publish() function called by commands after commit

It does not own:
    - canonical data
    - definitions
    - rules
    - queries
    - UI state
    - persistence

Reads are provided by SettlementQueries, not by State. State's role is
to expose index lookups (getLocationIdsByRank, etc.) and to rebuild
indexes after commit.

Public API:
    rebuildIndexes()
    getLocationIdsByRank(rankId)
    getLocationIdsByGovernment(governmentType)
    getLocationIdsBySpecialization(specializationRoleId)
    getLocationIdsByFeature(featureId)
    subscribe(callback) → unsubscribe
    publish(event)

There is no initialize(), no refreshFromMasterData(), no
invalidateCache(). Indexes are rebuilt lazily on first access and
explicitly after every commit.

# 6. COMMAND TRANSACTION CONTRACT

Every command follows the same transaction shape:

    1. read canonical state
    2. resolve required foreign-domain inputs
    3. build a candidate settlement object
    4. validate the requested operation (via rules)
    5. apply domain consequences
    6. commit candidate       (SettlementCommandCommit.commit)
    7. return structured result

The commit helper owns steps 7 through 10 of the full contract:

    write candidate to canonical store
    → rebuild State indexes
    → persist once (saveMasterData)
    → publish once (SettlementState.publish)

Commands must not:
    - display UI
    - log events via a UI-facing logger
    - show toasts
    - clamp or coerce inputs
    - fabricate missing values
    - use recursion guards
    - write to canonical data except through SettlementCommandCommit

Multi-field operations are single transactions. A command that changes
two canonical fields changes both in one candidate and one commit.
There is no window in which a partial commit is observable.

Examples of commands:
    SettlementFeatureCommands.buildFeature
    SettlementFiscalCommands.updateFiscalPolicy
    SettlementGovernmentCommands.setGovernmentType
    SettlementDebtCommands.repayDebt
    SettlementRankCommands.upgradeSettlementRank

**Persistence failure.**
`SettlementCommandCommit._saveMasterData` inspects the boolean return
of `saveMasterData()` per Pattern A in `storage.js`'s
DOMAIN PERSIST CONTRACT. On `false`, it reads `getLastSaveError()` and
throws an `Error` carrying the underlying reason. The published event
is NOT dispatched after a failed persist; subscribers must not be told
the world changed when it was not durably written.

Commands do not catch the throw. A caller that wants structured failure
handling wraps its command call in its own try/catch and converts the
exception into a `{ success: false, code: 'SAVE_FAILED', ... }` result.
The annual processor is one such caller (see §26).

# 7. QUERY CONTRACT

Queries are observational. They:
    - read canonical data through the query module that owns it
    - compose other queries
    - may return derived calculations (prosperity, crime, employment)
    - do not mutate anything
    - do not persist
    - do not create records
    - do not display UI
    - do not use recursion guards
    - do not fabricate missing values

Missing versus empty:
    - settlement missing          → return null
    - settlement exists, no items → return [] or 0
    - dependency missing          → throw (required)

Query results must not mutate canonical data. See §3 for the live /
shallow-copy / clone reference contract.

Two-tier status queries:
    Some derived facts are exposed as both a value query and a status
    query. The value query returns `T | null`; the status query
    returns `{ value: T | null, reason: string }`. Callers that only
    need the value use the value query; callers that want to render
    honest copy for the unavailable states use the status query.
    Current pairs:
        getReligiousUnity        / getReligiousUnityStatus
        getDominantReligion      / getDominantReligionStatus

---

# 8. RULES CONTRACT

Rules are pure functions. They:
    - do not mutate canonical state
    - do not persist
    - do not display UI
    - do not log
    - do not depend on DOM state
    - do not clamp or coerce
    - do not fabricate missing values

Rules return structured results, not bare booleans and not human strings.

Example result shape:

    {
        valid: false,
        reason: {
            code: 'OUT_OF_RANGE',
            field: 'Tax Rate',
            actual: 75,
            min: 0,
            max: 50
        }
    }

Rules that evaluate a complex operation return a structured evaluation
with a list of reasons, so a UI can present all problems at once.

---

# 9. DEFINITIONS CONTRACT

Definitions describe what the world allows. They are frozen, pure data.
They have no dependencies and do not read state.

Each definitions module owns exactly one conceptual catalog:

    settlement-rank-definitions.js        RANKS
    settlement-feature-definitions.js     FEATURES, FEATURE_CATEGORIES
    settlement-government-definitions.js  GOVERNMENT_TYPES, JUSTICE_SEVERITIES
    settlement-law-definitions.js         LAW_TYPES, LAW_DOMAINS, LAW_SEVERITIES
    settlement-fiscal-definitions.js      TAX_RATE, TRADE_TARIFF, INDUSTRY_TAX_RATE
    settlement-finance-definitions.js     DEBT_INTEREST_RATE, EFFICIENCY_BANDS,
                                          DEBT_RATIO_BANDS
    settlement-prosperity-definitions.js  BASE_PROSPERITY, PROSPERITY_BANDS
    settlement-education-definitions.js   EDUCATION_LEVELS

No UI module maintains its own copy of these catalogs. No command
invents them. No State owns them.

Definition fields are always explicit. A rank with no modifier declares
the neutral value (1.0 for multipliers, 0 for addends). A feature with
no trade bonus declares tradeBonus: 1.0. Missing fields are not used to
imply defaults.

**Definition-shape guards.**
View models that consume a definition (e.g.
`SettlementViewModels.buildDebtView` reading
`DEBT_INTEREST_RATE.annualFraction`, or
`buildEfficiencyView` iterating `EFFICIENCY_BANDS`) return null for the
affected field when the definition is missing or malformed. The
alternative — `Math.floor(undefined)` producing `NaN` — silently
poisoned the downstream calculation. The settlement-docs §4 rule
("missing is not the same as zero") applies to definitions as well as
to canonical data.

# 10. VIEWMODEL AND UI CONTRACT

ViewModels translate query results into presentation-ready structures.
They:
    - compose multiple queries
    - resolve display labels from definitions
    - format numbers for presentation
    - may mark values as unavailable (null fields, or an explicit
      availability marker)
    - may expose reason codes alongside nullable values (e.g.
      `dominantReligionReason`) so a consumer can distinguish "no
      population" from "no religions" from "unaffiliated majority"

They do not:
    - invent domain values
    - mutate canonical state
    - persist
    - create records

UI modules own:
    - DOM construction
    - event wiring
    - modal lifecycle
    - CSS class selection

UI modules do not:
    - create settlement records because a tab opened
    - call State private methods
    - contain domain definitions
    - contain domain validation
    - fabricate missing domain values
    - mutate canonical state directly
    - render a raw null/undefined value as the string "null" or
      "undefined" (see NUMERIC RENDERING below)

Opening a tab is observational. Rendering does not change the world.

**Numeric rendering.**
Every numeric field that reaches the DOM is formatted through a helper
that returns a presentation placeholder (typically an em-dash inside a
`value-unknown` span) for null / undefined / non-finite values. The
prior revision of `modals-settlement-core.js` concatenated three feature
maintenance and cost values as raw strings, so a feature with a null
maintenance rendered "maintenance null". The current revision routes
every numeric through `_fmtNumber`.

**Reason-code rendering.**
Nullable derived fields rendered by a modal (e.g. `religiousUnity`,
`dominantReligion`) read both the value and the reason code, and render
honest text for each reason:

    'available'               → the value
    'no_population'           → 'No population'
    'no_breakdown'            → 'Unavailable'
    'unaffiliated_majority'   → 'Unaffiliated majority'
    'no_religions'            → 'No religions'
    'settlement_not_found'    → 'Unknown'

A settlement with zero population and a settlement with an unaffiliated
majority render differently. Prior revisions collapsed all unavailable
cases into a generic 'Unknown'.

**Modal infrastructure.**

    Settlement UI modules call the CORE modal shell directly:

        window.openModal(options)     -> { element, close }
        window.closeTopModal()
        window.showToast(message, type)
        window.confirmDialog(message, title, onConfirm)

    These are the functions exported by js/core/modals-core.js and
    js/core/ui.js. There is no window.ModalsCore namespace, and no
    settlement module may introduce one.

    The option keys accepted by openModal are:

        titleHtml   : trusted HTML string for the modal title
        contentHtml : trusted HTML string for the modal body

    The option keys `title` and `content` are NOT read by the core
    modal shell. Settlement modals must use titleHtml / contentHtml.
    A modal that passes title / content will render with the default
    title ("Modal") and an empty body.

    The container to attach event delegation to is result.element, not
    result.content and not a bare HTMLElement. A modal that reads the
    wrong field will silently fail to wire its buttons.

# 11. RANK CONTRACT

rankId is canonical. Population determines eligibility, not current rank.

Rank definitions live in SettlementRankDefinitions.

Eligibility is calculated by SettlementRankRules.getRankFromPopulation.

Upgrade evaluation is SettlementRankRules.evaluateUpgrade, which takes
{ currentRankId, population, prosperity } and returns a structured
result with reasons.

Current rank is changed by:
    SettlementRankCommands.upgradeSettlementRank   (rule-enforced)
    SettlementRankCommands.setSettlementRank       (explicit, for
                                                    migrations and
                                                    exceptions)

lastUpgraded records the world year of the last successful rank change.

---

# 12. DEBT CONTRACT

wealth and totalDebt are independent canonical balances. Debt is not
derived from negative wealth. Negative wealth is permitted.

Debt is always >= 0.

Interest rate is owned by SettlementFinanceDefinitions.DEBT_INTEREST_RATE.
The interest calculation is centralized in SettlementDebtCommands.applyInterest.

Commands that change both balances in one logical operation change both
in one candidate:

    SettlementDebtCommands.borrow       : totalDebt += amount, wealth += amount
    SettlementDebtCommands.repayDebt    : totalDebt -= amount, wealth -= amount
    SettlementDebtCommands.applyInterest: totalDebt += interest, wealth -= interest
    SettlementDebtCommands.adjustDebt   : totalDebt += delta, wealth unchanged

There is no code path in which a partial repayment can occur.

---

# 13. ENTERPRISE OWNERSHIP CONTRACT

Enterprises are owned by the Industry domain. An enterprise's location
and ownership are represented on the enterprise record itself:

    enterprise.locationId
    enterprise.ownerType
    enterprise.ownerId

Settlement does not maintain authoritative stateEnterpriseIds or
publicEnterpriseIds arrays.

Settlement queries that need enterprise data compose Industry queries.
SettlementEconomyQueries.calculateStateEnterpriseIncome, for example,
asks IndustryQueries.getLocationEnterprisesSummary and filters by
ownership.

Enterprise ownership changes go through Industry commands. Settlement
does not own enterprise mutation.

SettlementUIList and settlement modals do not attempt to add or remove
enterprises. They display what Industry reports.

---

# 14. PLACE OF WORSHIP CONTRACT

Worship-place entities are owned by the Religion domain. Religion owns:
    - the worship-place record (id, name, type, religion, active state)
    - the worship-place's locationId linkage

Settlement does not duplicate the worship-place entity. There is no
canonical settlement.placesOfWorship array under the new architecture.

Settlement queries that need worship-place data ask Religion. The
religion query module in Settlement (SettlementReligionQueries)
composes these reads.

dominantReligionId and religiousUnity are derived, not canonical. They
are calculated by SettlementReligionQueries from the Religion domain's
breakdown:

    getDominantReligion(locationId)
    getReligiousUnity(locationId)

Both are exposed alongside status queries that carry a reason code:

    getDominantReligionStatus(locationId) → { religion, religionId, reason }
    getReligiousUnityStatus(locationId)   → { unity, reason }

See §4 (MISSING-VALUE SEMANTICS) for the reason vocabulary.

If a settlement-authored override is ever introduced (for example an
official religion distinct from the mathematically dominant one), it is
a distinct canonical field with its own commands and queries. It is not
handled here until the contract is amended.

# 15. FISCAL CONTRACT

Budget allocation and actual spending are distinct concepts.

    educationBudget        : allocation for the budget period
    educationSpending      : actual outflow
    governmentSalaryBudget : allocation
    governmentSalaryExpense: actual outflow (used by the economy queries)
    infrastructureBudget   : allocation
    infrastructureSpending : actual outflow
    militaryBudget         : allocation
    militarySpending       : actual outflow

SettlementEconomyQueries reads actual spending fields when computing
expenses. Allocation is a policy decision; spending is what was paid.

Fiscal commands:
    SettlementFiscalCommands.setTaxRate
    SettlementFiscalCommands.setTradeTariff
    SettlementFiscalCommands.setIndustryTaxRate
    SettlementFiscalCommands.updateFiscalPolicy       (combined)
    SettlementFiscalCommands.setBudgetAllocation      (partial)

Fiscal limits are declared in SettlementFiscalDefinitions. Validation is
performed by SettlementFiscalRules. Out-of-range values are rejected;
they are not clamped.

# 16. PROSPERITY CONTRACT

Prosperity is derived. It is not an independently authored canonical
field.

The calculation is in SettlementProsperityQueries.getProsperity. It
consumes canonical and derived inputs:

    rank, features, specialization, tax rate, crime rate, literacy,
    employment, debt, government leader traits and tenure, role
    diversity, master concentration, average skill, religious unity,
    places of worship, dominant religion, public enterprise profit

The result shape:

    {
        value: number,
        base: number,
        band: { id, name, color },
        modifiers: { ... }
    }

modifiers contains the delta contributed by each factor. The sum of the
modifiers plus base, clamped to [0, 100], equals value.

The calculation is deterministic. Same inputs produce the same output.
Randomness is not part of a query. If annual variation is added later,
it is applied by SettlementAnnualProcessor as an explicit step.

Persisted values named prosperity on old settlement records are ignored
by the new architecture.

**Character input.**
Role-density, master-concentration, underserved-roles, and average-
skill modifiers are computed over every living character whose
RESOLVED current location is in the settlement. "Resolved current
location" is the semantic notion (explicit field, then latest move,
then birthplace), not the raw `currentLocationId` field. See §4
(Character enumeration).

**Leader input.**
The government-leader modifier composes the leader's traits and
tenure. Traits are read from the character projection resolved via
`CharacterQueries.getCharacterById(leader.characterId)`. Tenure is
`getCurrentYear() - leader.startYear`. The prior revision read
`leader.character.traits` from an assignment projection that never
carried a `character` field; the modifier was silently 0 for every
settlement. Fixed in v5.2. See §4 (MISSING-VALUE SEMANTICS).

# 17. HISTORICAL DATA CONTRACT

Historical records describe events that happened. They are distinct
from current state and from projections.

The settlement record contains:

    demolitionHistory   : append-only log of feature demolitions
    annualHistory       : append-only log of annual processing entries

World years are stored under explicit names:

    foundedYear
    lastUpgraded
    budgetAllocationYear
    demolishedYear
    year

Technical timestamps are separate:

    recordedAt          : Date.now() at the moment a record is created

A world year is never stored under a field whose semantics imply a
technical timestamp, and vice versa.

Financial reports presented as "current" are current. The financial
report modal explicitly labels its view as a current snapshot. No
fabricated historical data is produced by calculating current numbers
five times and labeling them with different years.

**Financial report year.**
`SettlementViewModels.buildFinancialReportView(locationId, options)`
accepts an optional `options.year`. When supplied and valid, the report
describes that year and `isHistorical` is computed as
`reportYear !== getCurrentYear()`. When omitted, the report describes
the current year and `isHistorical` is false. The result carries
`reportYear`, `isHistorical`, and `currentYear` so callers don't have
to infer the year from the surrounding context.

Prior revisions hardcoded `isHistorical: false` and read the clock
directly. A caller rendering a past year's report would have shown a
"current" label over historical numbers. Fixed in v5.2.

# 18. TIME CONTRACT

World time is supplied by the Time domain:

    window.getCurrentYear()

This is the canonical current-year accessor. The deprecated
window.getCurrentYearSafe alias exists for migration only and must NOT
be used by settlement modules. A settlement module that calls
window.getCurrentYearSafe is a bug, even if the alias is currently
present.

No settlement module invents a current year. The pattern

    return 1250;

as a missing-time fallback does not exist anywhere in the settlement
system.

The pattern

    year || getCurrentYear()

does not exist either, because year 0 is a legitimate value.

A required time dependency that is unavailable is an application
failure. It is not converted into a fabricated year.

**Query layer year reads.**
SettlementQueries does not read the clock directly. The two facts that
depend on the clock are:

  - `settlement.budgetAllocationYear` (a stored canonical field; read
    verbatim by `getBudgetAllocation`; the caller compares it against
    `getCurrentYear` as needed)

  - the upgrade eligibility computation (delegated to
    SettlementRankQueries.getUpgradeStatus, which composes prosperity
    via SettlementProsperityQueries.getProsperityValue, and thus
    indirectly reads the clock)

When the year transition lands, the only query-layer file in this
module's transitive dependency graph that needs an explicit year is
SettlementProsperityQueries.getProsperity (via the leader tenure
bonus). If that query gains an options.year parameter,
SettlementQueries.getCurrentRank and getUpgradeStatus get it for free
because they delegate. SettlementQueries itself does not need a year
parameter, because every fact it exposes is either year-agnostic
(wealth, taxRate, featureIds) or a stored year (budgetAllocationYear)
that the caller interprets against its own clock.

**Year transition integration.**
The annual processor (see §26) accepts an explicit `options.year`.
`CharacterLifecycle.advanceMortality` (see the character domain's
CLOCK CONTRACT) invokes the annual processor once per simulated year
with the same year the character mortality loop uses. The loop is the
clock; settlement annual processing and character mortality see the
same simulated year.

The caller that invoked `advanceMortality` still owns the clock
advance:

    var result = CharacterLifecycle.advanceMortality(5, { startYear: 1250 });
    // ...
    window.masterData.data.currentYear = result.finalYear;
    window.markDataDirty();

No settlement module touches `masterData.data.currentYear`.

# 19. ERROR CONTRACT

Silent failure is prohibited.

The patterns

    catch (error) { return []; }
    catch (error) { return null; }
    catch (error) { return false; }

are not used to hide dependency or runtime failures in domain code.

An error is either:
    - rethrown,
    - converted into a structured domain/application error,
    - handled explicitly as a documented best-effort operation.

Subscriber exceptions in SettlementState.publish and
SettlementUIState.subscribe are logged with console.error and do not
silently disappear. Other subscribers still receive the event.

**Persistence failures.**
`saveMasterData()` returns a boolean and does not throw on write
failure. The boolean must be inspected. `SettlementCommandCommit.
_saveMasterData` inspects it and throws an `Error` on false, reading
`getLastSaveError()` for the underlying reason. The published event is
NOT dispatched after a failed persist.

# 20. RECURSION GUARD POLICY

Global processing guards are not used in queries, rules, calculations,
commands, or renderers.

The following do not exist anywhere in the settlement system:

    _processing
    _processingQuery
    _processingEconomy
    _processingProsperity
    _processingRanks
    _processingFeatures
    _processingCommand
    _rendering

Composition is legal. A query may call another query. A rule may call
another rule. A renderer may call another renderer.

If a genuine cycle exists, the dependency graph must be fixed, not
masked by a boolean flag.

# 26. ANNUAL PROCESSING

SettlementAnnualProcessor owns the annual simulation step for a
settlement. It:
    - applies debt interest
    - records the annual summary in the settlement's history
    - publishes settlementAnnualProcessed

Annual processing is the only place where temporal effects are applied.
It is not called from queries. It is not called from commands triggered
by user interaction.

Each settlement is processed as its own transaction. A failure on one
settlement does not prevent others from being processed.

**Explicit year.**
Both entry points accept an explicit `options.year`:

    processSettlementAnnual(locationId, options)
        options.year    the world year to process. Defaults to
                        window.getCurrentYear().

    processAllSettlementsAnnual(options)
        options.year    the world year to process. Defaults to
                        window.getCurrentYear(). Forwarded to every
                        per-settlement call.

When `options.year` is supplied and invalid, the call throws. The
processor does not silently fall back to the current year for an
invalid explicit year; that is a caller bug.

**Per-settlement failure isolation.**
`processSettlementAnnual` throws on failure (settlement-not-found,
invalid interest rate, or commit failure — including the persistence
throw added in v5.2). A single-settlement caller wants to know if that
settlement could not be processed.

`processAllSettlementsAnnual` catches per-settlement failures and
records them in `result.failures[]`, then CONTINUES to the next
settlement. The result shape is:

    {
        success: boolean,
        year: number,
        processed: number,
        failed: number,
        results: Array<Object>,
        failures: Array<{ locationId, code, message }>
    }

`success` is true only when no settlement failed. This matches the
per-character death failure isolation in
`CharacterLifecycle.advanceMortality` (`result.skipped`).

**Character-lifecycle integration.**
`CharacterLifecycle.advanceMortality(yearsAdvanced, options)` runs the
annual processor once per simulated year, after the character
mortality pass for that year, using the SAME year:

    window.SettlementAnnualProcessor.processAllSettlementsAnnual({
        year: year
    })

Settlement failures are collected into `result.settlementFailures`
(logged with console.warn) and do not abort the character loop. The
step is optional (skipped when the processor is absent or when
`options.skipSettlements === true`) and area-guarded (a thrown
exception from the processor becomes a single failure entry covering
all settlements, not an aborted loop).

See §18 (TIME CONTRACT, Year transition integration) for the caller-
owns-the-clock contract that this integration preserves.

# 27. COMPLETION STANDARD

The settlement refactor is complete when:

    - SettlementState contains no canonical mutation commands.
    - SettlementState contains no domain definitions.
    - Queries are read-only.
    - Rules are pure.
    - Commands own transaction boundaries.
    - Commands persist once per logical mutation.
    - State indexes rebuild from canonical data.
    - UI cannot create settlement data merely by rendering.
    - No domain module contains UI operations.
    - No required dependency is silently optional.
    - No missing value is silently converted into a domain fact.
    - No calculation depends on a recursion guard.
    - No canonical relationship has competing owners.
    - No derived value is treated as independently authored state.
    - Historical reports use historical data, or are labeled as current.
    - Allocation and spending are semantically distinct.
    - Debt and wealth are independently represented.
    - Prosperity is deterministic outside explicit annual simulation.
    - All domain definitions have one authoritative owner.
    - Documentation matches the architecture actually implemented.

Additional mechanical requirements introduced in v5.1:

    - No settlement module calls window.getCurrentYearSafe. The
      canonical accessor is window.getCurrentYear.
    - No settlement module invents a current year. The fallback
      pattern `return 1250;` does not exist.
    - No settlement UI module references window.ModalsCore. The core
      modal shell is accessed through window.openModal,
      window.closeTopModal, window.showToast, window.confirmDialog.
    - No settlement modal call site passes `title:` or `content:` to
      window.openModal. The accepted keys are titleHtml and contentHtml.
    - No settlement modal call site reads `result.content` from
      window.openModal. The modal element is `result.element`.
    - No HTML file references a deleted settlement script. The file
      inventory in §2 is authoritative.
    - No `trash/` directory exists under `js/` or `js/settlement/`.

Additional mechanical requirements introduced in v5.2:

    - `settlementData` is declared in storage-schema.js's factory and
      normalization. No settlement module relies on lazy creation of
      the object.
    - SettlementCommandCommit inspects the boolean return of
      saveMasterData() and throws on false, using
      getLastSaveError() to surface the underlying reason. The
      published event is NOT dispatched after a failed persist.
    - SettlementAnnualProcessor.processSettlementAnnual and
      processAllSettlementsAnnual accept an explicit options.year and
      throw when it is invalid. The processor does not silently
      fall back to the current year for an invalid explicit year.
    - processAllSettlementsAnnual catches per-settlement failures and
      records them in result.failures, continuing to the next
      settlement. CharacterLifecycle.advanceMortality invokes
      processAllSettlementsAnnual once per simulated year and collects
      its failures into result.settlementFailures without aborting the
      character loop.
    - SettlementEducationQueries and SettlementProsperityQueries
      enumerate characters via CharacterQueries.getAllCharacters()
      plus LocationQueries.getCurrentLocationId, not via
      CharacterQueries.getCharactersInLocations (the raw-field
      filter). Characters placed only by move records are counted.
    - SettlementProsperityQueries resolves the leader's traits via
      CharacterQueries.getCharacterById(leader.characterId), not by
      reading leader.character (which is never populated by
      LocationQueries.getCurrentLeader).
    - SettlementReligionQueries returns null (never a fabricated 50)
      for religious unity when the settlement has zero counted
      population or the breakdown is unavailable. Both states are
      distinguished via getReligiousUnityStatus. getDominantReligion
      distinguishes "no religions" from "unaffiliated majority" via
      getDominantReligionStatus.
    - SettlementQueries.getAllSettlements returns shallow copies of
      canonical records; getFeatureIds returns a defensive slice. The
      live canonical accessor is getSettlementData, documented as
      such. See §3 (Data access contract).
    - SettlementViewModels.buildFinancialReportView accepts an
      optional options.year and computes isHistorical from
      reportYear !== getCurrentYear(). SettlementViewModels.
      buildSettlementSummary exposes religiousUnityReason and
      dominantReligionReason alongside the nullable values.
      Definition reads that feed view models (DEBT_INTEREST_RATE,
      EFFICIENCY_BANDS, DEBT_RATIO_BANDS) return null for the
      affected field when the definition is missing or malformed,
      instead of producing NaN.
    - Settlement modals render honest copy for every reason code.
      Nullable numeric fields route through _fmtNumber, which renders
      a presentation placeholder instead of the string "null" or
      "undefined". openBudgetModal guards against sub-object
      nullability that would throw a TypeError on property access.

# 28. AMENDMENT RULE

This document and the Settlement Architecture Contracts describe the
current architecture. If implementation reveals a genuine domain
contradiction, the contract is amended explicitly before the code is
changed to accommodate it.

The correct sequence is:

    discover contradiction
        ↓
    resolve domain meaning
        ↓
    amend contract
        ↓
    update affected modules

The incorrect sequence is:

    code gets awkward
        ↓
    add another fallback
        ↓
    add another State helper
        ↓
    add another global flag
        ↓
    pretend nothing happened

The settlement system has had enough of those.

| Version | Date       | Notes                                                                                                    |
|---------|------------|----------------------------------------------------------------------------------------------------------|
| 5.0     | 2026-10-16 | Post-refactor baseline. Hydrate-from-masterData. Clone returns. Command-commit helper. Definitions split. |
| 5.1     | 2026-10-27 | Modal infrastructure fix. getCurrentYearSafe removal. Legacy file inventory reconciliation.              |
| 5.2     | 2026-10-28 | Year-transition hardening. Persistence truth. Character-enumeration fixes. Reason codes.                 |

v5.2 changes:

  **Persistence truth.**
    - SettlementCommandCommit inspects the boolean return of
      saveMasterData() and throws on false, using getLastSaveError().
      The prior revision called saveMasterData() and ignored the
      result, reintroducing the Pattern C bug documented in
      storage.js's DOMAIN PERSIST CONTRACT. Every settlement command
      silently reported success on every failed save; the annual
      processor's per-settlement history records were lost on quota
      failure with no signal.

  **Schema declaration.**
    - settlementData is now declared in storage-schema.js's factory
      and normalization pass. Every fresh install and every old save
      gets the object up front, matching the shape
      SettlementCommandCommit expects. Prior revisions relied on lazy
      creation on first commit.

  **Annual processor year contract.**
    - processSettlementAnnual and processAllSettlementsAnnual accept
      an explicit options.year. When supplied and valid, that year
      drives the history record. When supplied and invalid, the call
      throws. When omitted, the current year is used. Prior revisions
      read the clock directly inside the processor, which meant an
      N-year advance produced N history entries tagged with the same
      wall-clock year.

  **Per-settlement failure isolation.**
    - processAllSettlementsAnnual catches per-settlement failures and
      records them in result.failures, continuing to the next
      settlement. The prior revision threw and aborted the entire
      batch on the first failure. With the new throw-on-persist
      contract, that would have been catastrophic for a
      multi-settlement advance.

  **Character-lifecycle integration.**
    - CharacterLifecycle.advanceMortality now runs the settlement
      annual processor once per simulated year, after the character
      mortality pass for that year, using the same year. Settlement
      failures are collected into result.settlementFailures and
      logged, but do not abort the character loop. The step is
      optional (skipped when the processor is absent or when
      options.skipSettlements === true) and area-guarded (a thrown
      exception from the processor becomes a single failure entry
      covering all settlements).

  **Character enumeration.**
    - SettlementEducationQueries and SettlementProsperityQueries
      enumerate characters via CharacterQueries.getAllCharacters()
      plus LocationQueries.getCurrentLocationId, not via
      CharacterQueries.getCharactersInLocations (the raw-field
      filter). Characters placed only by move records were not
      counted before; the under-count silently shifted literacy
      rate, role diversity, master concentration, and average skill.
      The under-count propagated into prosperity modifiers.

  **Leader traits.**
    - SettlementProsperityQueries resolves the leader's traits via
      CharacterQueries.getCharacterById(leader.characterId). The
      prior revision read leader.character.traits from an assignment
      projection that never carried a `character` field. The
      government-leader modifier was silently 0 for every settlement.

  **Religion reason codes.**
    - SettlementReligionQueries returns null (never a fabricated 50)
      for religious unity when the settlement has zero counted
      population or the breakdown is unavailable. Both states are
      distinguished via getReligiousUnityStatus.
      getDominantReligion distinguishes "no religions" from
      "unaffiliated majority" via getDominantReligionStatus. The
      fabricated 50 flowed into SettlementProsperityQueries.
      modifiers.religiousUnity as a neutral reading that looked
      correct but was meaningless.

  **Data access contract.**
    - SettlementQueries.getAllSettlements returns shallow copies of
      canonical records. getFeatureIds returns a defensive slice. The
      live canonical accessor is getSettlementData, documented as
      such. See §3 (Data access contract).

  **View model hardening.**
    - SettlementViewModels.buildFinancialReportView accepts an
      optional options.year and computes isHistorical from
      reportYear !== getCurrentYear(). buildSettlementSummary exposes
      religiousUnityReason and dominantReligionReason alongside the
      nullable values. Definition reads that feed view models return
      null for the affected field when the definition is missing or
      malformed, instead of producing NaN.

  **Modal reason rendering.**
    - Settlement modals render honest copy for every religion reason
      code. openSettlementDetailsModal distinguishes "No population"
      from "Unavailable" from "Unaffiliated majority" from "No
      religions". openManageFeaturesModal routes feature maintenance
      and cost through _fmtNumber. openBudgetModal guards against
      sub-object nullability.
