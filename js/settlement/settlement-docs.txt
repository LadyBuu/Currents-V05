PART 2 — DEPENDENCIES
================================================================================

Terminology:
  REQUIRED (load-time)  — a module-level guard throws if the
                          dependency is missing when this file loads.
  REQUIRED (call-time)  — a function throws or refuses if the
                          dependency is missing at call time; the
                          module loads without it.
  OPTIONAL              — the module checks and falls back when absent.

Cross-domain references (which are not settlement files) are labeled
with their subsystem:
  [core]      js/core/...
  [character] js/character/...
  [location]  js/location/...
  [selectors] js/selectors/...
  [industry]  js/industry/...       (not provided; see notes)
  [religion]  js/religion/...       (not provided; see notes)
  [household] js/households/...     (not provided; see notes)
  [roles]     js/roles/...          (not provided; see notes)

2.1 DEFINITIONS
--------------------------------------------------------------------------------

All eight definition modules share the same dependency shape: none.
Each is a pure `Object.freeze` literal install of a `window.X` global.
Load order among them is unimportant.

  js/settlement/settlement-fiscal-definitions.js
    Exports window.SettlementFiscalDefinitions
      ({ TAX_RATE, TRADE_TARIFF, INDUSTRY_TAX_RATE }).
    Consumed by:
      [load] settlement-fiscal-rules.js
      [load] settlement-fiscal-commands.js (indirectly via rules —
                                            not a hard guard)
      [call] modals-settlement-economy.js (via
             SettlementFiscalDefinitions.TAX_RATE etc.)
      [call] settlement-view-models.js (via the fiscal limit reads in
             modals)

             justice-severity name lookups)
      [call] modals-settlement-economy.js (JUSTICE_SEVERITIES for the

  js/settlement/settlement-rank-definitions.js

      [load] settlement-rank-rules.js

  js/settlement/settlement-law-definitions.js

  Notes:

      EDUCATION_LEVEL_THRESHOLDS object on the definitions module.
      When it is absent, the query falls back to its own
      DEFAULT_EDUCATION_LEVEL_THRESHOLDS. The current
      settlement-education-definitions.js does NOT declare
      EDUCATION_LEVEL_THRESHOLDS; the query's fallback is therefore the
      active path. Adding the object to the definitions would change
      the mapping without changing any query code, matching the
      "single source of truth" policy.

--------------------------------------------------------------------------------
2.3 STATE / COMMIT INFRASTRUCTURE
--------------------------------------------------------------------------------

  js/settlement/settlement-state.js
    Owns window.SettlementState.
    Requires at load: nothing (the module is a Map factory +
    subscriber list + index rebuilder; it does not import any
    module).
    Reads at call:
      window.masterData.data.settlementData (via _getCanonicalStore).
    Consumed by:
      [load] settlement-command-commit.js
             (via _getState().rebuildIndexes / .publish)
    Notes:
      - SettlementState has NO initialize(), refreshFromMasterData(),
        or invalidateCache(). Load order matters only insofar as it
        must precede settlement-command-commit.js.
      - Load BEFORE any command (commands publish through it).

  js/settlement/settlement-command-commit.js
    Owns window.SettlementCommandCommit ({ commit }).
    Requires at load: nothing (all dependencies are call-time lookups).
    Reads at call:
      window.SettlementState (rebuildIndexes, publish),
      window.masterData.data.settlementData (write target),
      window.saveMasterData,
      window.getLastSaveError.
    Consumed by:
      [load] every settlement command file (each command wraps its
             candidate with _getCommit().commit).
      The load-time dependency is not a hard guard (no
      `if (!window.SettlementCommandCommit) throw`), but a command
      that loads without it throws on first commit.
    Notes:
      - _saveMasterData inspects the boolean return and throws on
        false per Pattern A in storage.js's DOMAIN PERSIST CONTRACT.
      - CANDIDATE-WRITE ORDERING: candidate is written to in-memory
        canonical store BEFORE persist. On persist throw, in-memory
        and storage diverge until the caller reloads, retries, or
        re-commits. See settlement-docs.txt §6 and the module header.

2.4 QUERIES
--------------------------------------------------------------------------------

All settlement query modules are read-only. They do not mutate
canonical data, do not persist, and do not read the clock directly
(except settlement-prosperity-queries.js via the leader tenure bonus
and settlement-view-models.js explicitly).

  js/settlement/settlement-queries.js
    Owns window.SettlementQueries.
    Requires at load: nothing.
    Reads at call:
      window.masterData.data.settlementData (via _getCanonicalStore),
      window.SettlementRankQueries (via getCurrentRank —
        SettlementRankQueries is a CALL-TIME dependency for the
        getCurrentRank composed query).
    Consumed by:
      [call] EVERY other settlement query, command, factory, and
             view model that needs canonical settlement data.
    Notes:
      - The LIVE record is returned by getSettlementData. Commands
        read through it and clone before mutating.
      - getAllSettlements returns SHALLOW COPIES (scalars by value;
        nested arrays by reference). See the SETTLEMENT DATA ACCESS
        CONTRACT in the module header.
      - getFeatureIds returns a defensive slice.

  js/settlement/settlement-rank-queries.js
    Owns window.SettlementRankQueries.
    Requires at load: nothing.
    Reads at call:
      window.SettlementRankRules,
      window.SettlementQueries,
      window.SettlementProsperityQueries,
      window.getLocationPopulationCount.
    Consumed by:
      [call] settlement-queries.js (getCurrentRank),
      [call] settlement-rank-commands.js,
      [call] settlement-prosperity-queries.js (via
             SettlementRankRules — not SettlementRankQueries),
      [call] settlement-view-models.js (buildRankView),
      [call] modals-settlement-core.js (openUpgradeSettlementModal).
    Notes:
      - getUpgradeStatus reads prosperity via
        SettlementProsperityQueries.getProsperityValue. The
        settlement.prosperity field is NOT consulted. See the module
        header's design notes.
      - getUpgradeStatus returns a structured result with
        availability flags and reasons. A caller that only needs a
        boolean should read upgradeStatus.eligible after confirming
        upgradeStatus.available is true.

  js/settlement/settlement-feature-queries.js
    Owns window.SettlementFeatureQueries.
    Requires at load: window.SettlementFeatureDefinitions.
    Reads at call: window.SettlementQueries.
    Consumed by:
      [call] settlement-feature-commands.js,
      [call] settlement-feature-rules.js? No — rules read definitions
             directly.
      [call] settlement-education-queries.js (getSettlementFeatures),
      [call] settlement-economy-queries.js (getSettlementFeatureEffects),
      [call] settlement-prosperity-queries.js,
      [call] settlement-view-models.js,
      [call] modals-settlement-core.js.

  js/settlement/settlement-law-queries.js
    Owns window.SettlementLawQueries.
    Requires at load: nothing.
    Reads at call: window.SettlementQueries.
    Consumed by:
      [call] settlement-law-commands.js (findDuplicateName),
      [call] settlement-view-models.js,
      [call] modals-settlement-core.js (not directly —
             buildSettlementSummary covers it).
      [call] religion / crime cross-domain consumers ([NOT PROVIDED]
             — those domains read SettlementLawQueries on their side).

  js/settlement/settlement-education-queries.js
    Owns window.SettlementEducationQueries.
    Requires at load:
      window.SettlementQueries,
      window.SettlementFeatureQueries,
      window.SettlementEducationDefinitions,
      window.LocationQueries,
      window.CharacterQueries.
    Reads at call:
      window.SettlementQueries (settlement record),
      window.SettlementFeatureQueries (getSettlementFeatures),
      window.LocationQueries (getAllSubLocationIds,
        getCurrentLocationId),
      window.CharacterQueries (getAllCharacters),
      window.EducationQueries (OPTIONAL — getSchoolCapacity when
        available).
    Consumed by:
      [call] settlement-prosperity-queries.js (getLiteracyStats),
      [call] settlement-view-models.js,
      [call] modals-settlement-roles.js.
    Notes:
      - Character enumeration is via getAllCharacters + LocationQueries
        .getCurrentLocationId, NOT getCharactersInLocations. See the
        CHARACTER ENUMERATION section of the module header.
      - _deriveEducationLevelId maps character subjectProgress entries
        (via entry.level) through the threshold policy. The 0 case
        maps to 'literate', not 'basic', because isLiterate === true
        already establishes literate status.

  js/settlement/settlement-religion-queries.js
    Owns window.SettlementReligionQueries.
    Requires at load: nothing.
    Reads at call:
      window.SettlementQueries,
      window.LocationQueries,
      window.ReligionQueries,
      window.CharacterQueries (declared but not directly used in
        supplied code — the enumeration is not yet needed by the

    Consumed by:
      [call] settlement-crime-queries.js (getReligiousUnity,

      [call] settlement-prosperity-queries.js (getReligiousUnity,

      window.SettlementQueries,
      window.SettlementFeatureQueries,
      window.SettlementFeatureDefinitions,
      window.SettlementEmploymentQueries,
      window.SettlementFinanceDefinitions,

2.5 COMMANDS
--------------------------------------------------------------------------------

All settlement commands have the same load-time shape: no hard
guards. Each command file is a `window.SettlementXCommands` install
whose methods are call-time lookups into SettlementQueries,
SettlementCommandCommit, and (for validation) the corresponding
rules module.

  js/settlement/settlement-feature-commands.js
    Owns window.SettlementFeatureCommands
      ({ buildFeature, removeFeature, demolishFeature }).
    Reads at call:
      window.SettlementQueries,
      window.SettlementFeatureQueries,
      window.SettlementFeatureRules,
      window.SettlementCommandCommit,
      window.getCurrentYear (demolishFeature only).
    Consumed by:
      [call] modals-settlement-core.js (feature build/remove/demolish).
    Time dependency:
      window.getCurrentYear is REQUIRED at call time for
      demolishFeature. There is no fallback.

  js/settlement/settlement-fiscal-commands.js
    Owns window.SettlementFiscalCommands
      ({ setTaxRate, setTradeTariff, setIndustryTaxRate,
         updateFiscalPolicy, setBudgetAllocation }).
    Reads at call:
      window.SettlementQueries,
      window.SettlementFiscalRules,
      window.SettlementCommandCommit,
      window.getCurrentYear (setBudgetAllocation only).
    Consumed by:
      [call] modals-settlement-economy.js
             (openTaxRateModal calls updateFiscalPolicy).

  js/settlement/settlement-government-commands.js
    Owns window.SettlementGovernmentCommands
      ({ setGovernmentType, setUseReligiousLawsAsCivil,
         setJusticeSeverity, setWatch }).
    Reads at call:
      window.SettlementQueries,
      window.SettlementGovernmentRules,
      window.SettlementCommandCommit,
      window.getCurrentYear (setWatch — records watchFounded).
    Consumed by:
      [call] modals-settlement-economy.js (openJusticeModal calls
             setJusticeSeverity and setWatch),
      [call] [NOT PROVIDED] religion bootstrap — the religion
             domain reads SettlementGovernmentCommands in its
             bootstrap per settlement-docs.txt §14.
    Notes:
      - setGovernmentType applies consequence patches from
        SettlementGovernmentRules.evaluateGovernmentChange
        (theocracy implies useReligiousLawsAsCivil = true).

  js/settlement/settlement-law-commands.js
    Owns window.SettlementLawCommands
      ({ addCivilLaw, updateCivilLaw, removeCivilLaw }).
    Reads at call:
      window.SettlementQueries,
      window.SettlementLawQueries,
      window.SettlementLawRules,
      window.SettlementCommandCommit,
      window.getCurrentYear (via _currentYear).
    Consumed by:
      [call] modals-settlement-* (law-editing modals; not in
             this batch — settle-law UI lives in tabs /
             modals-settlement-* but not the three provided).
    Notes:
      - _generateLawId uses 'civillaw_' + Date.now() + '_' + random.
        That is a session-scoped unique id; it does not go through
        ids.js. The trade-off is documented implicitly by the
        function being local: civil laws are not first-class
        entities (they live inside the settlement record), so
        ids.js generateId is not required.

  js/settlement/settlement-wealth-commands.js
    Owns window.SettlementWealthCommands
      ({ adjustWealth }).
    Reads at call:
      window.SettlementQueries,
      window.SettlementCommandCommit.
    Consumed by:
      [call] any caller that needs to adjust wealth without
             touching debt. Not currently consumed by any
             settlement modal in this batch.

  js/settlement/settlement-debt-commands.js
    Owns window.SettlementDebtCommands
      ({ borrow, repayDebt, adjustDebt, applyInterest }).
    Reads at call:
      window.SettlementQueries,
      window.SettlementCommandCommit,
      window.SettlementFinanceDefinitions
        (DEBT_INTEREST_RATE.annualFraction — applyInterest only).
    Consumed by:
      [call] modals-settlement-economy.js (openRepayDebtModal,
             openBorrowModal),
      [call] settlement-annual-processor.js (via
             processSettlementAnnual — does NOT call applyInterest;
             it does the interest math inline. See Notes below).
    Notes:
      - processSettlementAnnual does NOT call
        SettlementDebtCommands.applyInterest. It applies interest
        inline using SettlementFinanceDefinitions.DEBT_INTEREST_RATE
        and commits via SettlementCommandCommit. This duplicates the
        interest math. settlement-docs.txt §12 states interest
        calculation is centralized in applyInterest. The
        annual-processor code diverges from that policy — it
        produces the same number but is not the single-source-of-
        truth path. Do not change processSettlementAnnual to call
        applyInterest without also removing the inline math; doing
        either alone would double-count interest. Fix as a follow-up
        in the annual processor, not in the debt commands.

  js/settlement/settlement-rank-commands.js
    Owns window.SettlementRankCommands

================================================================================
PART 6 — LOAD-ORDER INVARIANTS
================================================================================

Each invariant names the failure mode it prevents.

 1. Every definitions module before its corresponding rules
    module.
    Failure without it: rules call window.SettlementXDefinitions.Y
    at call time and throw TypeError on first validation.

 2. Every rules module before the corresponding commands module.
    Failure without it: commands call _getXRules().validateX at call
    time and throw TypeError on first command invocation.

 3. settlement-state.js before settlement-command-commit.js.
    Failure without it: SettlementCommandCommit calls
    SettlementState.rebuildIndexes and SettlementState.publish at
    commit time and throws TypeError on first commit.

 4. settlement-command-commit.js before any command module.
    Failure without it: each command calls
    SettlementCommandCommit.commit at call time and throws
    TypeError on first command invocation.

 5. Every settlement X queries module before its corresponding
    X commands module (when the command reads through the query).
    Failure without it: command throws TypeError on first
    invocation. In practice, every command module reads
    SettlementQueries; load SettlementQueries before every
    command.

 6. SettlementQueries before SettlementViewModels.
    Failure without it: every view model calls
    SettlementQueries.getSettlementData at call time.

 7. The specific query modules that a view model composes
    (feature, economy, prosperity, crime, employment, law,
    religion, rank) before SettlementViewModels.
    Failure without it: view model throws TypeError on the
    composed read.

 8. LocationQueries before the settlement query modules that read
    it (education, religion, employment, economy, prosperity).
    Failure without it: those queries call
    LocationQueries.getAllSubLocationIds / getCurrentLocationId /
    getCurrentLeader at call time and throw TypeError.

 9. CharacterQueries before settlement-education-queries and
    settlement-prosperity-queries.
    Failure without it: those queries call
    CharacterQueries.getAllCharacters / getCharacterById at call
    time and throw TypeError.

10. CharacterCommands before settlement-prosperity-queries.
    Failure without it: the prosperity query calls
    CharacterCommands.getProfessions per character at call time and
    throws TypeError on first invocation.

11. core/time.js before every command module and before the
    factory, the annual processor, and the view models.
    Failure without it: the modules call window.getCurrentYear at
    call time and throw TypeError.

12. core/storage.js before initializeStorage().
    Failure without it: initializeStorage is not a function and
    the call throws.

13. initializeStorage() before character-state.js and
    location-state.js (and therefore before the settlement
    subsystem's cross-domain reads).
    Failure without it: the state modules throw at load with
    "masterData missing".

14. core/modals-core.js and core/ui.js before every
    modals-settlement-*.js file.
    Failure without it: the modal helpers call window.openModal /
    window.showToast / window.confirmDialog /
    window.closeTopModal at call time and throw TypeError on
    first modal open.

15. js/religion/religion-queries.js before
    settlement-religion-queries.js's first call.
    Failure without it: settlement religion queries call
    ReligionQueries.getPlacesOfWorshipByLocation /
    getReligion / getReligiousBreakdownForLocations at call time.
    This is a CALL-TIME dependency; the module loads fine.

16. js/industry/industry-queries.js before
    settlement-economy-queries.js /
    settlement-employment-queries.js /
    settlement-prosperity-queries.js's first call.
    Failure without it: each throws TypeError on first invocation
    of a function that needs industry data.

17. js/roles/role-queries.js before
    settlement-specialization-commands.js and
    modals-settlement-core.js and modals-settlement-roles.js.
    Failure without it: each throws TypeError on first invocation.

18. character-lifecycle.js AFTER
    settlement-annual-processor.js.
    Failure without it: advanceMortality's
    SettlementAnnualProcessor.processAllSettlementsAnnual step is
    skipped (the settlement processor is a call-time optional
    dependency of character-lifecycle). The character loop still
    runs, but no settlement annual processing happens.

19. SettlementState.publish is ONLY called by commands (through
    SettlementCommandCommit). Do not publish from queries, view
    models, or UI.
    Failure without it: subscribers receive events for state
    that did not change, and the "one publish per logical
    mutation" contract (settlement-docs.txt §14) is broken.

20. Do not call SettlementAnnualProcessor.processSettlementAnnual
    OR processAllSettlementsAnnual from inside a settlement
    command.
    Failure without it: the annual processor's commit calls back
    into a command path that is already holding a canonical
    record read; recursive commit and rebuildIndexes is fine at
    the state level but the caller's canonical record reference
    is now stale, and the caller's subsequent code operates on
    the pre-annual-processor record. Annual processing is
    orchestrated by the caller (character-lifecycle); it is not
    composed by commands.


================================================================================
PART 7 — KNOWN HAZARDS
================================================================================

 1. window.PlaceQueries is referenced by name in the settlement
    subsystem (settlement-factory.js, settlement-view-models.js,
    all three modals). No supplied file installs window.PlaceQueries.
    [UNVERIFIED]: confirm the accessor exists in your build before
    relying on settlement UI. The natural provider is world.js
    (which exports getPlaceById); if PlaceQueries is a separate
    facade, ensure it loads before settlement-factory.js.

 2. Interest math duplication.
    processSettlementAnnual computes interest inline.
    SettlementDebtCommands.applyInterest also computes interest.
    Both read DEBT_INTEREST_RATE.annualFraction; both produce the
    same number. The two paths are not chained. Changing one without
    the other silently changes which settlements accumulate interest
    differently depending on which path runs.
    Fix as a follow-up: have processSettlementAnnual call
    applyInterest (which commits on its own), or remove the
    duplication by making applyInterest's math the shared helper.
    settlement-docs.txt §12 says interest calculation is centralized
    in applyInterest; the annual processor code diverges from that
    policy. Do not "fix" by adding a fallback; the fix is to
    consolidate.

 3. LEADER TRAITS and character projection.
    settlement-prosperity-queries.js resolves the leader's traits
    via CharacterQueries.getCharacterById(leader.characterId). The
    leader ASSIGNMENT projection from
    LocationQueries.getCurrentLeader does NOT carry a character
    field. Do not "simplify" by reading leader.character.traits;
    that field never exists. See LEADER TRAITS in the module
    header.

 4. PROFESSIONS and character projection.
    settlement-prosperity-queries.js reads professions via
    CharacterCommands.getProfessions. The character projection no
    longer includes professions (character-state.js
    _DOMAIN_OWNED_FIELDS). Do not "simplify" by reading
    character.professions off the projection; that field is
    undefined. See PROFESSION INPUT in the module header.

 5. CHARACTER ENUMERATION.
    settlement-education-queries.js and
    settlement-prosperity-queries.js enumerate via
    CharacterQueries.getAllCharacters + LocationQueries
    .getCurrentLocationId, NOT CharacterQueries
    .getCharactersInLocations. The latter uses the raw
    currentLocationId field, misses move-placed characters, and
    over-counts characters whose latest move has left the
    settlement. Do not revert.

 6. RELIGION BREAKDOWN SHAPE.
    settlement-religion-queries.js calls
    ReligionQueries.getReligiousBreakdownForLocations(locationIds)
    and expects { byReligion, unaffiliated, total }. It does NOT
    call ReligionQueries.getReligiousBreakdown(locationId) (the
    singular variant), whose shape differs. Do not "simplify" by
    using the singular call; the settlement subtree aggregation is
    a different contract.

 7. RELIGIOUS UNITY nulls.
    SettlementReligionQueries.getReligiousUnity returns null for
    'no_population' and 'no_breakdown'. The prior revision
    fabricated 50. The settlement-docs.txt §4 MISSING-VALUE
    SEMANTICS rule prohibits fabricated values. If a caller needs
    a value, use getReligiousUnityStatus and read the reason.
    Do not add a fallback.

 8. DOMINANT RELIGION nulls.
    Same as (7) for getDominantReligion. 'unaffiliated_majority'
    and 'no_religions' both return null but mean different
    things. Use getDominantReligionStatus.

 9. baseProsperity coupling.
    settlement-factory.js initializes baseProsperity: 50. That
    value MUST equal
    SettlementProsperityDefinitions.BASE_PROSPERITY. If you
    change one, change the other in the same commit. There is
    no code-level enforcement (an import would reintroduce the
    crime ↔ prosperity cycle that the stored field exists to
    break).

10. candidate-write ordering.
    On persist failure, SettlementCommandCommit leaves the
    candidate in the in-memory canonical store but does not
    notify subscribers. The caller is responsible for one of:
    reload, retry persist, or re-commit the previous candidate.
    A caller that catches the throw and moves on without doing
    one of those leaves the tab with in-memory state ahead of
    storage until the next successful save. See
    settlement-command-commit.js CANDIDATE-WRITE ORDERING.

11. Modals are UI-only.
    The settlement modals (settlement-core, settlement-economy,
    settlement-roles) call commands on user action. They do not
    commit on modal open. Opening a settlement details modal does
    not create a settlement record (settlement-docs.txt §16).
    If the modal renders "No settlement", the settlement does not
    exist and the user cannot create one from this modal.

12. UI state persistence.
    SettlementUIState is session state, not masterData state. A
    reload resets the selection, tab, filters, and expanded
    sections. That is intended.

13. Tab initialization.
    settlement-tabs.js::init() is idempotent but must run AFTER
    SettlementUIState is loaded and AFTER the tab renderers are
    registered. The module attempts an automatic init on
    DOMContentLoaded plus a setTimeout(0) tick; if a renderer
    registers later, call SettlementTabs.requestRender() to force
    a re-render. There is no polling and no setTimeout in the
    tab renderer itself.

14. Modals escape HTML inline.
    Each of the three settlement modals defines its own
    _escapeHtml helper. The helper duplicates
    formatting.js::escapeHtml exactly. Switching to
    window.escapeHtml would be a zero-behavior change; it has
    not been done here. Do not introduce a third variant; if you
    change one, change all.

15. settlement-queries.js::getCurrentRank call-time dependency.
    SettlementQueries.getCurrentRank delegates to
    SettlementRankQueries.getCurrentRank. The settlement queries
    module loads fine without SettlementRankQueries, but any call
    to getCurrentRank throws TypeError. Load
    settlement-rank-queries.js before settlement-queries.js if
    anything will call getCurrentRank during the settlement
    bootstrap.

16. settlement-prosperity-queries.js reads getCurrentYear for the
    leader tenure bonus.
    This is the one query module in the settlement subsystem that
    reads the clock directly. If the year-transition path lands,
    it will need an options.year parameter (or the tenure
    calculation needs to accept an explicit "as of" year). Do not
    add other direct clock reads to query modules without an
    explicit year parameter; settlement-docs.txt §18 requires the
    caller to own the clock.

17. SettlementTabs and DOM.
    settlement-tabs.js wires its click handler on document and
    applies classes on tab activation. It does not fight CSS over
    presentation; inline styles are not used. If the DOM has no
    tab buttons, init() finds nothing and returns; do not
    silently render an empty tab pane.

18. RoleQueries / IndustryQueries / ReligionQueries are not in
    this batch.
    [UNVERIFIED]: the settlement code's expectations are
    documented in the returns it reads. Confirm the actual
    modules exist and export the specific functions named above
    before relying on settlement features that call them
    (economy income, employment, religion breakdown, leader
    traits, specialization picker).
