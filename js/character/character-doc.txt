================================================================================
PART 1 — CORE FILE DEPENDENCIES
================================================================================

This section answers, for each character-subsystem file, WHICH core files
it needs and WHY. Read it top-to-bottom as the answer to "what does the
character module depend on".

Terminology:
  REQUIRED (load-time) — a module-level guard throws if the dependency
    is missing when this file loads.
  REQUIRED (call-time) — a function or method throws/refuses if the
    dependency is missing when the function is invoked.
  OPTIONAL — the module checks for the dependency and falls back
    (usually by skipping the feature) when it is absent.

--------------------------------------------------------------------------------
1.1 CORE FILES THE CHARACTER SUBSYSTEM DEPENDS ON
--------------------------------------------------------------------------------

  js/core/time.js
    Provides: TIME_CONSTANTS (DEFAULT_YEAR, MIN_YEAR, MAX_YEAR),
              getCurrentYear, isValidYear, calculateAge.
    Used for: year defaults, year validation, age computation, birth
              year defaults when `options.currentYear` is omitted.

  js/core/ids.js
    Provides: generateId (all prefixes).
    Used for: character id, edge id, pregnancy id, surrogacy id,
              adoption id, conversion event id.

  js/core/randomness.js
    Provides: random, randomInt, randomBoolean, pickRandom,
              pickRandomMultiple, pickWeighted, shuffleArray.
    Used for: every random draw in the character subsystem. Math.random
              is forbidden; the module guards on window.random.

  js/core/storage.js
    Provides: masterData (initialized reference), markDataDirty.
    Used for: canonical collection read, dirty marker after mutation.

  js/core/accessors.js
    Provides: getCharacters, invalidateAccessorCaches, getPlaces,
              getPlaceById, getLocationTypeById, getNameLists, getRoles,
              getPlaceScope, getLocationTypeScope, getCharacterById
              (via accessors, the shim, or the projection override —
              whichever wins the documented load-order race).
    Used for: initial character load, cache invalidation after writes,
              generator access to places and roles, names.js access
              inside generator.

  js/core/formatting.js
    Provides: escapeHtml.
    Used for: all UI modal string interpolation (modals-character,
              modals-children-*, modals-death, character-ui-list).

  js/core/icons.js
    Provides: Icons.
    Used for: all modal SVG icon injection.

  js/core/modals-core.js
    Provides: openModal, closeTopModal, confirmDialog.
    Used for: every modal in modals-character, modals-children-*,
              modals-death.

  js/core/validation.js
    Provides: validateImportData (indirect — via storage.js on import).
    Used for: import path only. The character subsystem does not call
              validation.js directly.

  js/core/world.js
    Provides: getPlaceScope, getLocationTypeScope (used by
              character-generator for country resolution).
    Used for: character-generator only.

  js/core/names.js
    Provides: getRandomNameFromCountry, getRandomSurnameFromCountry.
    Used for: character-generator only.

  js/core/constants/character-traits.js
    Provides: CHARACTER_TRAIT_VALUES.
    Used for: HARD load-time guard in character-factory.js and
              character-generator.js; the trait write path in
              character-commands.js refuses without it.

  js/core/state.js
    Not a direct dependency of the character subsystem. state.js
    depends on CharacterState, not the other way around. Do not add a
    dependency in this direction.

  js/core/collections.js
    Not used directly by the character subsystem. Nothing in the
    supplied character files imports from collections.js.

  js/core/exportUtils.js
    Not used directly by the character subsystem. CSV/JSON export is a
    separate concern.

  js/core/responsive.js
  js/core/ui/collapsible.js
  js/core/tab-manager.js
  js/core/ui.js
  js/core/ui-state.js
    Not used directly by the character subsystem. modals-core.js
    internally may depend on formatting.js and icons.js, which are
    already on the list.

  js/core/maintenance.js
    Not used directly. maintenance.js depends on integrity.js, which
    depends on accessors.js, not on the character subsystem.

  js/core/integrity.js
    Not used directly by the character subsystem. It audits reference
    integrity of characters, but the character subsystem never calls
    into it. It reads via accessors.js.

  js/core/constants/age-constants.js
    Indirect dependency: character-lifecycle.js's getLifeStage /
    getAgeGroup read window.LIFE_STAGES / window.AGE_GROUPS at call
    time. If the constants are missing, those helpers return null
    rather than fabricating. Character-lifecycle does not throw for a
    missing age-constants.js at load time. Under the documented core
    load order, age-constants.js is present.

  js/core/constants/character-constants.js
    Indirect dependency via character-factory.js: the factory's
    VALID_GENDERS / VALID_ATTRACTIONS constants are locally declared
    (they do not read GENDER_VALUES / ATTRACTION_VALUES from the
    constants file). validation.js optionally reads the constants
    files. The factory therefore does not require
    character-constants.js at load. Under the documented core load
    order, character-constants.js loads first anyway.

  js/core/constants/character-traits.js
    (Already listed above. Listed here again for visibility because it
    is the one constants file that is a HARD load-time dependency of
    the character subsystem.)

  js/core/constants/relationship-constants.js
  js/core/constants/location-constants.js
  js/core/constants/constants.js
    Not direct dependencies of the character subsystem. relationship-
    constants.js is used by validation.js; the character subsystem
    itself does not read RELATIONSHIP_STATUS or LOCATION_LEVELS.

================================================================================
PART 2 — LOAD ORDER
================================================================================

The order below is derived from:
  (a) module-level guard blocks (which throw if a dependency is not
      loaded),
  (b) call-time window.X lookups in code,
  (c) the character-system.js REQUIRED list (which throws if any
      canonical character module is absent),
  (d) character-creation-commands.js's own guard against
      buildCharacter / validateBuiltCharacter / getCurrentYear,
  (e) character-lifecycle.js's guard against markDeceased,
  (f) children-commands.js's guard against many character modules,
  (g) the documented core load order (see stillwaters-docs.txt),
  (h) the character-doc.txt §3 bootstrap contract.

Reading note:
  The character subsystem sits above the core layer and below the
  application bootstrap. Groups C0 and C1 below are the core
  prerequisites; groups A1..A9 are the character subsystem's own load
  order; group A10 is the shim; group A11 is the bootstrap call.

GROUP A11 — APPLICATION BOOTSTRAP
--------------------------------------------------------------------------------

Between GROUP C0 and GROUP A2, the application must call:

    window.initializeStorage();

This is the same call described in stillwaters-docs.txt §Group 10.
It initializes window.masterData and starts cross-tab sync. Every
character-subsystem file in Groups A2 and later that touches
masterData (character-state.js, family-state.js, children-state.js)
requires it at load time.

After character-system.js (Group A10), the application is free to call
any character-subsystem init routines. The supplied character files do
not declare an explicit "init()" — they self-install on load. Any
application-level bootstrap (dashboard wiring, tab-manager init,
toolbar binding) runs after Group A10.

================================================================================
PART 5 — KNOWN HAZARDS
================================================================================

  1. initializeStorage() must run BEFORE character-state.js,
     family-state.js, children-state.js. Not just storage.js — the
     function call itself. This is the single most common load-order
     mistake, because storage.js loads fine and its exported functions
     are all present; the failure is that window.masterData is still
     undefined when the state modules parse. See character-doc.txt
     §3.1 for the canonical wording.

  2. window.getCharacterById race. accessors.js exports the
     live-entity version. character-queries.js ALSO defines a
     getCharacterById, but does NOT install it on window — the
     character-system.js shim does, at load time. Under the
     documented load order the shim wins the runtime race, so
     window.getCharacterById returns a PROJECTION. The
     character-ui-list.js onSelect callback therefore receives a
     projection. Do not attempt to mutate the callback's argument;
     use CharacterCommands or
     CharacterState.getLiveCharacterForMutation.

  3. Character-commands trait dependency. character-traits.js is a
     HARD load-time dependency of character-factory.js and
     character-generator.js, but character-commands.js is a SOFT
     dependency: the module loads, and trait WRITE operations refuse
     with a clear reason if CHARACTER_TRAIT_VALUES is not present.
     This asymmetry is documented in character-commands.js's TRAITS
     header section. If your bootstrap loads the factory and the
     generator but skips character-traits.js, those two throw; if it
     skips the trait vocabulary but loads only character-commands.js,
     trait writes fail. Under the documented load order, the
     vocabulary is present at all times.

  4. character-system.js is a one-way alias shim. It does not define
     any module behavior; every alias points at a canonical
     character-subsystem function. Do not add new behavior to the
     shim; add it to the canonical module and alias it.

  5. Cross-domain cleanup hooks. character-lifecycle.js and
     character-deletion-commands.js both install
     window.registerDeathHandler and window.registerDeleteHandler.
     These registries are the load-order-independent path for
     domains that load AFTER the character subsystem
     (location-commands.js and relationship-integrations.js are the
     two named in the headers). Do not add new dependencies on those
     domains from inside the character subsystem; use the
     registration hooks.

  6. Maternal death is routed through CharacterLifecycle.killCharacter,
     not through CharacterCommands.markDeceased. children-commands.js
     REFUSES the maternal-death outcome if CharacterLifecycle is
     missing rather than leaving a half-dispatch. Do not "fix" this
     by calling markDeceased directly; that would produce a dead
     mother with stale family edges and stale rank assignments.

  7. children-commands.js writes to masterData.data directly
     (pregnancyRecords, surrogacyArrangements, adoptionRecords) and
     calls markDataDirty. This is documented; do not
     "helpfully" reroute those writes through storage.js's own save
     functions. They go through markDataDirty for the same reason
     every other domain does.

  8. FamilyAccessors does not exist in the current tree. The shim's
     family aliases route to FamilyQueries and FamilyCommands
     directly. Any caller that reaches for FamilyAccessors gets
     undefined and must be fixed.

  9. RelationshipIntegrations (plural) — this is the load-order-safe
     path for relationship cleanup. The named dispatch table in
     character-lifecycle.js and character-deletion-commands.js
     references it, but under the documented load order it loads
     AFTER the character subsystem, so the named dispatch is a
     no-op. The registration hooks are what actually reach it.

 10. modals-death.js's childbed-fever routing has a per-call guard
     (`routingInProgress`). A second "Confirm Death" click while the
     father selector is open is a no-op. Do not remove this guard on
     the assumption that the modal stack handles double-clicks; the
     stack handles them, but the routing sequence would open a second
     father selector.

 11. Settlement data does NOT need accessor cache invalidation.
     masterData.data.settlementData is not indexed by accessors.js.
     Settlement commands may write through markDataDirty and read via
     SettlementQueries; character-state.js's invalidateAccessorCaches
     is what keeps getCharacterById fresh, and that is what the
     character subsystem calls on every write.

 12. character-statistics.js::getLiteracyStatistics requires a
     literacy predicate as an argument; it throws without one. The
     education domain owns literacy and routes through
     CharacterCommands.isLiterate. Do not add a fallback inside
     character-statistics.js that returns 0; zero is a legitimate
     result and a fabricated zero would mask a missing education
     domain.
