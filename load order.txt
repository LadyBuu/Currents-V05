Notation:

  file.js
      a script load.
  call()
      a function invocation (not a script load).
  <- AFTER: file.js            (HARD)
      mandatory load-time dependency: this file's guard throws if
      file.js is not already loaded.
  <- after: file.js            (call-time)
      strong recommendation: the file loads without it, but a
      function throws or degrades when it is missing. Order to
      avoid first-use failures.
  <- after: file.js            (soft)
      optional dependency with a documented fallback. Ordering is
      optional but recommended.
  OPTIONAL block
      may be skipped if the corresponding features are not used.
  [UNVERIFIED]
      referenced but not in the supplied batch; confirm exports.
  [NOT PROVIDED]
      referenced by a header or REQUIRED list but not in the
      supplied files.

Reading rule: never reorder two lines within a block unless the
block says "order within this block is unimportant". Every
"<- AFTER: (HARD)" note is mandatory. Every "<- after: (call-time)"
is a strong recommendation for a functioning page.

BLOCK 18 — CULTURE SUBSYSTEM
==============================================================================

This block is placed AFTER the religion block because
culture-queries.js, culture-view-models.js, and culture-modals.js
read window.ReligionQueries at load time. It is placed AFTER the
location block (BLOCK 26) indirectly — see the noted ordering in
the notes below for why PlaceQueries must resolve.

The actual sequence requirement is:

  - window.PlaceQueries must exist BEFORE culture-queries.js,
    culture-view-models.js, and culture-modals.js load.
    [UNVERIFIED]: provider not in supplied batch.
  - window.ReligionQueries must exist BEFORE those same files
    load. Provided by religion-queries.js (BLOCK 17).
  - window.CharacterQueries must exist BEFORE
    culture-queries.js and culture-view-models.js load.
    Provided by character-queries.js (BLOCK 11).
  - window.LocationQueries must exist BEFORE the first call to
    CultureQueries.getCultureForCharacter. Provided by
    location-queries.js (BLOCK 26). Culture loads WITHOUT it —
    _resolveCurrentLocationId falls back to
    CharacterQueries.getCurrentLocationId — but resolution is
    degraded.

Because location-queries.js lives in the LOCATION block (which
this document keeps at BLOCK 26, after settlement), the culture
block's LOAD-TIME guards on PlaceQueries and ReligionQueries must
both be satisfiable at BLOCK 18. ReligionQueries is available
(BLOCK 17). PlaceQueries is [UNVERIFIED] — if it is a facade over
location-queries.js and location-queries.js lives at BLOCK 26,
then culture CANNOT load at BLOCK 18. Two resolutions:

  Option A (recommended): the PlaceQueries provider is not
    location-queries.js itself but a facade that loads alongside
    the core accessors (BLOCK 5). Confirm the provider and ensure
    it loads before BLOCK 18.

  Option B (fallback): move the LOCATION block (BLOCK 26) and
    the CULTURE block (BLOCK 18) before the RANK block
    (BLOCK 16), then re-order religion / settlement / government
    after culture. This preserves the same top-level invariants
    (culture→location, culture→religion, culture→character) but
    requires re-auditing rank's cross-domain assertions.

  This document uses Option A: the culture block assumes
  PlaceQueries is available by BLOCK 18 (either from BLOCK 5 or
  from a location-queries.js pre-load if the build requires it).
  If your build ships PlaceQueries inside location-queries.js,
  re-order: LOCATION before CULTURE.

==============================================================================

  1.  getCurrentYear vs getCurrentYearSafe. Culture and Rank use
      getCurrentYear. Government uses getCurrentYearSafe.

  2.  window.PlaceQueries is [UNVERIFIED]. Three consumers:

      ship; getNextRankNumber 3-arg signature; rank-bootstrap
      REQUIRED vs OPTIONAL split; death / delete cascade calls
      RankIssues.handleCharacterDeath / removeAllReferencesTo

  5.  Culture subsystem internal hazards. See BLOCK 18 notes and
      culture-docs PART 7. Top items:
        - window.PlaceQueries provider [UNVERIFIED].
        - window.Culture is created by init(), not at script load.
        - CultureBootstrap auto-init catches throw; window.Culture
          may not exist on failed init.
        - getCultureSummary silently skips dangling references.
        - generateAppearanceForLocation throws when no primary
          culture applies.
        - culture-ui-list.js list rows lack keyboard activation.
        - CultureCommands.persist does not read
          getLastSaveError; the failure reason is generic.
        - culture-modals.js modal callbacks ignore the DOM root
          parameter — reads via document.getElementById. Stacked
          culture modals collide. rank's modals fixed this in
          Phase 8.1; culture has not.
        - CultureBootstrap does not verify lazy dependencies

        - CULTURE_DEFAULT_MYTHOLOGY does not exist;
          culture-commands.js's local _emptyMythology is active.
        - CULTURE_APPEARANCE_CATEGORIES is not read; consumers
          iterate the culture.appearance keys directly.
        - generateAppearanceWithRandomCulture returns
          { culture, appearance }, not the appearance alone.
        - appearance and mythology are WHOLE-OBJECT replacements
          on updateCulture.
        - Cross-domain cascade is absent. cultureDeleted fires but
          does not clear character.cultureId / place.cultureId.
        - window.getCharacterById resolves to the projection
          override in culture code. Do not mutate the returned
          character.

  33. rank-bootstrap.js auto-init. init() runs at load.

  34. No listener registry for death / delete hooks.
      CharacterLifecycle calls RankIssues.handleCharacterDeath
      DIRECTLY. CharacterDeletionCommands calls
      RankIssues.removeAllReferencesTo DIRECTLY.

  35. Culture bootstrap auto-init failure. CultureBootstrap.init()
      catches and logs; window.Culture may not exist. Do not
      assume auto-init guarantees window.Culture.

  36. Culture cross-domain cascade absent. cultureDeleted fires
      but no listener clears references. A future CultureCascade
      must listen and coordinate.

  37. Culture appearance / mythology replacement semantics.
      updateCulture replaces appearance and mythology
      whole-object. Sub-field mutation goes through the dedicated
      helpers.

  38. Culture list rows lack keyboard activation. tabindex="0"
      present, no keydown handler. Click-only.

  39. Culture modal DOM scoping bug. onConfirm callbacks use
      document.getElementById, not root.querySelector. Stacked
      culture modals read the first modal's inputs.

  40. CULTURE_DEFAULT_MYTHOLOGY does not exist.
      _emptyMythology() in culture-commands.js is the active
      default.

  41. CULTURE_APPEARANCE_CATEGORIES is not read. Consumers
      iterate the culture.appearance object keys directly.

  42. generateAppearanceWithRandomCulture returns
      { culture, appearance }, not the appearance alone.

  43. Character generation ordering. character-generator.js
      depends on CultureGeneration.generateAppearance (typeof-
      guarded, call-time). Under the documented order the culture
      block loads AFTER the character block; the FIRST character
      generation must run after CultureBootstrap.init() completes
      and culture-queries.js is available. Any application
      bootstrap that generates characters must respect this.

  44. culture-docs.txt is out of sync with the code. Its own
      §7.1 says it should be replaced by culture-doc.md. Its
      paths in §2 do not match the tree. Do not cite it as
      authoritative; the code and the culture subsystem doc's
      PART 2 catalog are the source of truth.
